# WaterBridge 백엔드 수정·확인 요청

작성일: 2026-08-31 · 요청 화면: 상담사 Web

아래는 로컬 소스와 Web 테스트를 기준으로 확인한 내용입니다. 운영 AWS/RDS에서 동일한 결과를 직접 확인한 보고서는 아닙니다. **1번은 인증 수정 요청, 2번은 완료 처리 정책·API 계약 확인 요청**입니다.

## 1. 로그인 아이디 대소문자 구분 — 수정 요청

상담사 로그인 시 등록된 아이디의 대소문자까지 정확히 일치해야 로그인되도록 수정 부탁드립니다.

```text
[담당 영역 문제 발견]
- 영역: 백엔드 인증
- 관련 파일: backend/apps/accounts/services/p1_auth_service.py:939
- 웹에서 확인된 현상: Web은 입력한 아이디 대소문자를 그대로 전달하지만, 서버의 아이디 조회는 대소문자를 구분하지 않는다.
- 예상 원인: 로그인 조회에 username__iexact=username을 사용한다.
- 필요한 협의: 아이디를 대소문자까지 정확히 비교하도록 로그인 조회와 인증 테스트를 수정하고 기존 계정에 미치는 영향을 확인한다.
- 웹 임시 대응: 자동 대문자화·자동 교정·맞춤법 검사를 끄고 입력 원문을 전송한다. 프론트에서 별도 계정 목록이나 임의 차단 로직을 만들지는 않는다.
```

확인 부탁드리는 항목:

- 등록된 아이디와 대소문자가 정확히 같고 비밀번호가 맞으면 로그인 성공.
- 아이디의 대문자 또는 소문자만 바꾸면 로그인 실패. 해당 변형 아이디로 별도 계정이 없는 조건에서 검증.
- 아이디가 맞아도 비밀번호 대소문자가 다르면 로그인 실패. 기존 `check_password` 검증은 유지.
- 기존 계정, 아이디 중복 검사, DB 문자열 비교 규칙과의 호환성 확인. 공통 인증 서비스를 사용하는 다른 클라이언트에 미치는 영향도 점검.
- 기존 로그인 실패 응답·권한·시도 제한 동작 유지.

## 2. 상담 확정·전화 등록 후 완료 처리 — 정책·계약 확인 요청

사용자 요구는 다음 두 동작 이후 처리 완료된 문의 화면으로 이동하는 것입니다.

- 상담사가 상담 내용을 확정한 경우.
- 상담사가 전화 문의를 등록한 경우.

Web은 성공 후 완료 목록으로 이동하도록 수정했습니다. 다만 **화면 이동과 실제 문의의 완료 상태 전환은 다른 작업**이므로, 서버 상태와 집계를 임의로 변경하지 않았습니다.

### 현재 확인한 차이

| 동작 | API | 현재 코드·Web 테스트 기준 |
| --- | --- | --- |
| 상담 내용 확정 | `POST /api/v1/inquiries/{inquiry_id}/consultation-summary/confirm` | 상담 요약 확정 요청이며 `/finalize`와 다른 동작입니다. 확정 성공만으로 실제 최종 완료를 보장하지 않으며 `CONSULTATION_IN_PROGRESS`가 유지되는 응답을 Web에서 처리합니다. |
| 전화 문의 등록 | `POST /api/v1/consultant/phone-inquiries` | 생성 응답 상태가 `CONSULTATION_REQUIRED`인 흐름입니다. 등록 성공 자체를 실제 최종 완료로 간주하지 않습니다. |

따라서 아직 완료되지 않은 문의는 완료 목록으로 이동하더라도 해당 목록에 표시되지 않을 수 있습니다. 현재 Web은 이때 실제 상태와 미완료 안내, 해당 문의 다시 열기를 제공합니다.

### 회신 부탁드리는 내용

1. 각 동작을 실제 최종 완료로 처리해야 하는지, 아니면 상담사의 작업 종료와 문의의 최종 완료를 구분해야 하는지 확인 부탁드립니다.
2. 실제 완료 상태로 전환해야 한다면 두 흐름 각각의 **목표 `status`, 필수 API 호출 순서, `allowed_actions`, `state_version` 규칙**을 알려 주세요.
3. 고객의 해결 여부 선택, 미해결 신고, 방문 처리, 최종 완료 권한 등 기존 필수 절차와 충돌하지 않는지 확인 부탁드립니다.
4. 실제 완료 전에도 완료 목록에 보여야 한다는 정책이라면, 목록 분류와 집계 기준을 별도로 합의해야 합니다. Web 단독으로 서버 상태나 숫자를 완료로 바꾸지 않겠습니다.

단순히 화면을 맞추기 위한 DB 상태 직접 변경, 기존 문의 초기화, Seed 변경 또는 필수 절차를 건너뛰는 자동 `/finalize` 호출은 요청하지 않습니다. 현재 상태 머신의 오류라고 단정한 것이 아니라, 사용자 요구와 현행 계약의 처리 범위를 확인하려는 요청입니다.

## 3. 프론트 연동 참고

- 상담 기록 입력란은 하나로 통합했습니다. 기존 계약을 유지하기 위해 저장 시 `consultation_note`, `customer_guidance`, `additional_check`, `summary`에 통합한 같은 원문을 전달합니다. 백엔드 필드 삭제나 스키마 변경을 요청하는 것은 아닙니다.
- 저장 성공 응답의 실제 `state_version`을 사용하며, 실패하거나 취소하면 확정·완료 목록 이동을 진행하지 않습니다.
- `allowed_actions`, `/finalize`, 409 충돌 처리, 중복 클릭·멱등키, 성공 후 상태 재조회와 관련된 기존 동작은 유지했습니다.
- 이번 Web 작업에서 Backend·Mobile·DB/RDS·Seed·공용 계약은 변경하지 않았습니다.

## 회신 요약

- 로그인 아이디 대소문자 구분 수정 여부와 검증 결과.
- 상담 확정 후 목표 상태와 필요한 후속 API.
- 전화 문의 등록 후 목표 상태와 필요한 후속 API.
- 각 흐름의 `state_version`·`allowed_actions` 및 기존 고객 확인/방문 절차 유지 여부.
- Web에서 추가로 연결하거나 수정해야 할 사항.
