# Web 잔여 작업 협업 요청 v0.2

> 수정일: 2026-08-24
> 작성자: 한예나 / Web
> 현재 Web 기준 SHA: `bd019a83741081427e201efe7decef5cdc510e6a`
> 상태: Backend의 미배정 상담 기능 main 병합 대기

## 한 줄 요약

Backend 병합 후 Web에 `미배정 상담 목록 → 내가 상담하기 → 기존 상담 처리` 흐름을 연결하고, AI 인계정보·공식 근거·HITL은 이번 작업에서 제외합니다.

## 변경된 Backend 상담 방식

고객이 상담을 요청해도 특정 상담사에게 바로 배정하지 않습니다.

```text
고객 상담 요청
→ 미배정 상담 대기 목록
→ 상담사가 '내가 상담하기' 선택
→ 해당 상담사에게 배정
→ 상담 시작·저장·요약 확정·완료
```

현재 Backend 변경은 PM에게 merge 요청된 상태입니다. Web은 해당 변경이 `main`에 병합된 뒤 최신 `main`을 Pull하고, 실제 공개 API 계약을 확인한 후 작업합니다.

# 1. 지금 진행: 미배정 상담 목록과 상담사 가져오기 기능

## 1-1. Backend·PM에 먼저 요청드리는 내용

main 병합 후 다음 정보를 공유해 주세요.

- 병합 완료 여부와 기준 Commit SHA
- 미배정 상담 목록 조회 API 경로와 응답 DTO
- 상담사가 문의를 가져오는 API 경로와 요청·응답 DTO
- 목록과 상세에서 사용하는 `allowed_actions`, 담당자 정보, `state_version`
- 다음 상황의 HTTP 상태와 오류 코드
  - 다른 상담사가 먼저 가져간 문의
  - 같은 상담사가 버튼을 두 번 누른 경우
  - 오래된 `state_version`으로 요청한 경우
- 기존 상담 시작·저장·요약 확정·완료 API의 변경 여부
- 두 상담사의 동시 가져오기를 확인할 수 있는 합성 Demo 계정 또는 공식 실행 절차
- 신규 합성 Inquiry 생성 방법과 대표 `inquiry_id`

Token·Cookie·Password·DSN·실제 개인정보는 문서나 채팅에 넣지 말아 주세요.

## 1-2. main 병합 후 Web에서 진행할 작업

1. 최신 `main`을 Pull하고 실행 SHA를 기록합니다.
2. 배정되지 않은 상담 요청 목록을 보여줍니다.
3. 목록에 Backend의 `allowed_actions`가 허용한 경우에만 `내가 상담하기` 버튼을 보여줍니다.
4. 상담사가 버튼을 누르면 Backend API로 해당 문의를 가져옵니다.
5. 배정 성공 후 미배정 목록과 문의 상세를 다시 불러옵니다.
6. 배정된 상담사와 현재 가능한 작업을 최신 Backend 응답으로 표시합니다.
7. 이후 기존 상담 흐름을 실행합니다.
   - 상담 시작
   - 상담 내용 저장
   - 상담 요약 확정
   - 상담 완료
   - 새로고침 후 완료 상태 복구
8. 다음 충돌 상황에는 Backend의 실제 오류 응답에 맞는 안내를 보여줍니다.
   - 다른 상담사가 이미 가져간 문의
   - `내가 상담하기`를 두 번 누른 경우
   - 오래된 화면의 `state_version`으로 요청한 경우
9. 오류가 발생한 뒤에도 목록과 상세를 다시 불러와 최신 배정 상태를 보여줍니다.
10. 고정 성공 처리나 임의 배정 상태를 만들지 않습니다.

## 1-3. 정식 제품 테스트 범위

실제 성공 흐름에는 아래 세 제품 코드만 사용합니다.

| 구분 | 정식 제품 코드 | 사용 범위 |
|---|---|---|
| 냉온정수기 | `WPUJAC104DWH` | 실제 신규 합성 Inquiry 및 성공 흐름 |
| 얼음 냉온정수기 | `WPUIAC425SNW` | 실제 신규 합성 Inquiry 및 성공 흐름 |
| 얼음 냉온정수기 | `WPUIAC606SNW` | 실제 신규 합성 Inquiry 및 성공 흐름 |

`WPUJCC104D`는 실제 Product·Subscription·Inquiry Fixture로 만들지 않습니다. 잘못된 제품 코드 또는 별칭 입력을 거절하거나 구분하는 테스트에만 사용합니다.

## 1-4. 새로 확인할 전체 화면 흐름

기존 완료 Inquiry를 재사용하지 않고 새로운 합성 Inquiry로 다음 과정을 확인합니다.

```text
신규 상담 요청 생성
→ 미배정 상담 목록 노출
→ 상담사 A가 '내가 상담하기'
→ 목록·상세 최신화
→ 상담 시작
→ 내용 저장
→ 요약 확정
→ 상담 완료
→ 새로고침 후 상태 복구
```

추가로 상담사 A와 상담사 B를 사용해 다음 항목을 확인합니다.

- 두 상담사가 같은 문의를 가져오려고 할 때 한 명만 성공하는지
- 이미 배정된 문의를 다른 상담사가 다시 가져올 때 알맞은 오류가 보이는지
- 같은 버튼을 빠르게 두 번 눌러도 중복 배정되지 않는지
- 오래된 `state_version` 요청이 거절되고 화면이 최신 상태로 복구되는지

## 1-5. 기존 Playwright 결과 사용 기준

기존 상담 시작 → 저장 → 요약 확정 → 완료 Playwright 결과는 이전 방식의 참고 기록으로만 보관합니다.

해당 결과에는 `미배정 목록 → 내가 상담하기` 과정이 없으므로 새 배정 방식이 통과했다는 증거로 사용하지 않습니다. Backend 변경이 main에 병합된 뒤 새로운 Inquiry와 새로운 실행 결과를 다시 남깁니다.

## 1-6. 이번 작업 완료 기준

- 미배정 상담 목록이 실제 Backend 응답으로 표시됨
- `내가 상담하기` 성공 후 목록과 상세가 최신 상태로 갱신됨
- 기존 상담 시작·저장·요약 확정·완료·새로고침 복구가 새 Inquiry에서 통과함
- 다른 상담사 선점·중복 클릭·오래된 화면 충돌이 알맞은 오류로 표시됨
- 정식 제품 코드 3종의 신규 합성 Inquiry로 확인됨
- `WPUJCC104D`가 실제 성공 Fixture에 포함되지 않음
- Web 작업만 Commit됨
- 화면 전체 흐름 테스트 결과와 해결되지 않은 문제가 정리됨
- Web Test·Lint·TypeCheck·E2E TypeCheck·Production Build 결과가 보고됨

# 2. 나중에 진행: AI 인계정보·공식 근거·HITL 화면

아래 기능은 Backend 공개 규칙과 API 계약이 확정된 뒤 별도 작업으로 진행합니다.

- 상담사용 AI 인계정보 표시
- 상담사용 공식 Evidence 표시
- AI 결과 승인·수정 승인·거절 HITL 화면
- `AI → ESCALATE → Handoff → 상담사 확인` Playwright
- 제품별 Evidence 혼입 방지 화면 검증

이번 미배정 상담 작업에서는 위 기능을 구현하거나 Mock 성공 처리하지 않습니다. 준비가 완료되면 Backend 공개 DTO·OpenAPI·오류 규칙을 전달받아 별도 범위로 작업합니다.

---

## 작업 범위 제한

- 수정 범위는 `web/**`로 제한합니다.
- Backend·Mobile·AI·DB·Migration·Fixture 원본은 수정하지 않습니다.
- Web은 `/api/v1`의 공개 Backend API만 호출합니다.
- Backend 계약이 불명확하면 임의 추측하지 않고 Blocker로 보고합니다.
- 고정 배정값, 로컬 성공 처리, 기존 완료 Inquiry 재사용은 하지 않습니다.
