# Web 문의 삭제·취소 연동 Backend 협업 요청

- 요청자: 한예나 (Web Frontend)
- 수신자: 최지용 (Backend)
- 작성일: 2026-09-01
- 대상 화면: 상담사 Web 문의 상세·상담 처리
- 현재 상태: Web 로컬 작업만 존재하며 커밋·푸시 전

## 한 줄 요약

상담사 화면의 `문의 삭제` 요구사항을 기존 `CANCEL_INQUIRY`로 처리해도 되는지와 사용자 문구·취소 사유·목록 반영 정책을 확인 부탁드립니다.

## 요청 배경

상담사 Web에서 문의를 삭제할 수 있는 기능과 삭제 버튼을 추가해 달라는 요청이 있었습니다. 확인 결과 현재 Backend와 공용 계약에는 문의 레코드를 영구 삭제하는 `DELETE /api/v1/inquiries/{id}`가 없고, 아래 상태 전이형 취소 API만 구현되어 있습니다.

```http
POST /api/v1/inquiries/{inquiry_id}/cancel
```

따라서 Web이 화면에서 문의를 임의로 숨기거나 실제 삭제처럼 처리하면 서버 데이터·집계·감사 이력과 화면이 달라집니다. 현재 Web 로컬 작업은 기존 계약을 따라 `allowed_actions`에 `CANCEL_INQUIRY`가 있을 때만 버튼을 표시하고, 성공 시 문의를 `CANCELLED` 상태로 전환하는 방식으로만 연결해 둔 상태입니다.

## 현재 확인한 계약

### 요청

```json
{
  "state_version": 6,
  "reason_code": "OTHER",
  "reason_detail": "상담사 화면에서 문의 삭제 요청"
}
```

- Bearer 인증과 `Idempotency-Key`가 필요합니다.
- `reason_code` 허용값은 다음과 같습니다.
  - `CUSTOMER_REQUEST`
  - `DUPLICATE_INQUIRY`
  - `ISSUE_RESOLVED`
  - `OTHER`
- 상담사는 현재 자신에게 배정된 문의만 취소할 수 있습니다.
- `allowed_actions`에 `CANCEL_INQUIRY`가 없으면 Web 버튼도 노출하지 않습니다.

### 성공 결과

- 문의 레코드를 삭제하지 않고 상태를 `CANCELLED`로 변경합니다.
- `state_version`이 증가합니다.
- 취소 사유와 처리 이력을 보존합니다.
- `CANCELLED` 문의는 현재 Web의 처리 완료 Bucket과 전체 문의 집계에 포함됩니다.

## Backend 확인·협의 요청

### 1. 제품 요구사항의 의미 확인

아래 중 어떤 정책이 맞는지 확인 부탁드립니다.

1. 상담사의 `문의 삭제` 요구는 기존 `CANCEL_INQUIRY`를 의미한다.
2. 상담사가 문의 레코드를 목록에서도 완전히 제거하는 별도 삭제 기능이 필요하다.

2번이 필요하다면 권한, 감사 이력, 연관 Consultation·Visit·AI 기록, 집계 제외 기준을 포함한 신규 Backend·공용 계약이 먼저 필요합니다. Web에서 단독으로 물리 삭제나 로컬 숨김 처리를 적용하지 않겠습니다.

### 2. 버튼 문구 확인

현재 API 의미와 상태 이력을 기준으로는 `문의 삭제`보다 `문의 취소`가 정확합니다. 상담사 화면 문구를 아래 중 어떤 방식으로 사용할지 결정 부탁드립니다.

- 권장: 버튼 `문의 취소`
- 대안: 버튼 `문의 삭제`, 확인창에서 “취소 상태로 전환되며 처리 이력은 보관됩니다”라고 명시

### 3. 취소 사유 입력 방식 확인

현재 Web 로컬 작업은 별도 사유 입력 UI 없이 아래 값을 자동 전송합니다.

```text
reason_code = OTHER
reason_detail = 상담사 화면에서 문의 삭제 요청
```

운영 감사 이력에 충분한지 확인 부탁드립니다. 상담사가 사유를 직접 선택해야 한다면 기본값, 필수 여부, 표시할 한글 문구와 `reason_detail` 입력 조건을 알려 주세요.

### 4. 취소 후 목록·집계 정책 확인

현재 계약대로라면 취소 성공 후 문의는 다음 위치에서 계속 확인됩니다.

- 전체 문의
- 처리 완료된 문의
- `CANCELLED`가 포함된 상태 집계
- 문의 상세의 처리 이력

취소 문의를 특정 화면에서 제외해야 한다면 목록 API의 공식 필터와 `page_info.total`, `status_counts`, Dashboard 집계 기준을 함께 확정 부탁드립니다.

### 5. 운영 배포 확인

AWS 운영 Backend에서도 상담사 계정으로 아래 항목을 확인 부탁드립니다.

1. 문의 상세·목록의 `allowed_actions`에 조건에 맞는 `CANCEL_INQUIRY`가 포함되는지
2. `POST /api/v1/inquiries/{inquiry_id}/cancel`이 200을 반환하는지
3. 성공 후 `state=CANCELLED`, 증가한 `state_version`, 빈 `allowed_actions`가 반환되는지
4. 오래된 `state_version`에서 최신 상태 Snapshot을 포함한 409가 반환되는지
5. 동일 Idempotency-Key와 동일 본문 재요청이 중복 처리 없이 Replay되는지
6. 활성 Visit이 있는 문의와 담당자가 아닌 문의가 기존 권한·Guard 정책대로 차단되는지

## 현재 Web 로컬 구현 범위

- `CANCEL_INQUIRY`를 Web 상담 Action 타입에 추가
- Backend `allowed_actions` 기반 조건부 버튼 노출
- 위험 동작 색상과 실행 전 확인창 적용
- 현재 `state_version`과 새 Idempotency-Key 전송
- 중복 클릭 방지
- 성공 후 목록·상세·집계 재조회
- 409 발생 시 최신 상태 재조회 안내
- Mock 환경에서 `CANCELLED` 상태 전환 확인

현재 문구는 사용자 요청을 반영해 `문의 삭제`로 표시하지만, 확인창에서 실제로는 취소 상태로 전환되고 이력이 보관된다는 점을 안내하고 있습니다. Backend·PM 협의 결과에 따라 `문의 취소`로 변경할 수 있습니다.

## 회신 부탁드리는 내용

```diff
- 영구 삭제 필요 여부 또는 CANCEL_INQUIRY 사용 확정
- 최종 버튼 문구
- 취소 사유 입력 정책과 권장 reason_code
- 취소 후 목록·집계 노출 기준
- AWS 운영 API·allowed_actions 확인 결과
- Web에서 추가로 반영해야 할 계약 또는 예외 처리
```
