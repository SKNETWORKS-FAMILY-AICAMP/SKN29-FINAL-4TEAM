# 1. 6주차 핵심 목표

6주차에는 새로운 화면을 계속 추가하기보다 지금까지 구현한 상담사 Web을 실제 배포와 시연에 사용할 수 있는 수준으로 마감한다.

이번 주의 최우선 목표는 다음 세 가지다.

1. **기능과 레이아웃을 최종 확정한다.**
2. **배포 가능한 수준까지 디자인과 화면 품질을 완성한다.**
3. **다른 팀원의 작업과 전체 E2E 흐름을 정확히 이해하고 주간발표를 준비한다.**

최종 목표는 단순히 화면이 예쁘게 보이는 것이 아니다. 상담사가 별도의 설명 없이 화면을 이해하고, 필요한 업무를 빠르게 처리하며, 실제 Backend 데이터와 Mock 데이터에서도 동일한 사용 흐름을 경험할 수 있어야 한다.

> **6주차 Web 목표는 “기능이 있는 화면”을 “배포하고 시연할 수 있는 완성된 업무 화면”으로 마감하는 것이다.**

# 2. 6주차 작업 원칙

- 상담사 Web의 기존 기능을 기준으로 화면 범위를 확정한다.
- 운영 관리자 화면은 P1이므로 6주차 기능·레이아웃·디자인 확정 범위에서 제외한다.
- 기능·레이아웃 확정 이후에는 신규 화면이나 대규모 구조 변경을 임의로 추가하지 않는다.
- Mock Mode와 Remote Mode가 다른 제품처럼 보이지 않도록 동일한 레이아웃과 상태 표현을 사용한다.
- 화면은 Backend의 `status`, `risk_level`, `priority`, `allowed_actions`, `state_version`을 기준으로 동작한다.
- 위험도·상태·우선순위·SLA를 프론트에서 임의 계산하거나 실제 데이터처럼 꾸미지 않는다.
- 실제 API가 제공하지 않는 정보는 디자인 편의를 위해 실제 데이터처럼 표시하지 않는다.
- 긴급·주의·성공 등 의미가 있는 상태 색상은 유지하고, 비의미적 장식 색상은 정수기 서비스에 맞는 하늘·파랑·청록 계열로 통일한다.
- Backend·Mobile·AI·DB·공용 계약의 변경이 필요하면 직접 수정하지 않고 담당자에게 정확한 재현 정보와 요청사항을 전달한다.
- 주간발표 준비는 마지막 날에 몰아서 하지 않고 기능 확정과 동시에 화면 근거·수치·설명을 축적한다.

# 3. 필수 업무 1 — 기능 최종 확정

## 3.1 상담사 Web 기능 범위 확정

다음 화면과 기능을 6주차 상담사 Web의 최종 범위로 관리한다.

- 업무 대시보드
- 새 문의 목록
- 처리 중인 문의 목록
- 처리 완료된 문의 목록
- 문의 검색·위험도 탭·상태 필터·페이지네이션
- 문의 상세
- 상담 시작·기록·AI 요약 확인·완료
- 방문 전환이 허용된 문의의 전환 화면
- 전화 문의 등록
- Loading·Empty·Error·Forbidden·Not Found 상태

### 확인 기준

1. 메뉴명과 실제 화면의 기능이 일치한다.
2. 업무 대시보드의 건수와 각 목록의 데이터 기준이 일치한다.
3. 목록에서 선택한 문의가 올바른 상세 화면으로 연결된다.
4. Mock Mode와 Remote Mode에서 같은 메뉴·목록·상세 구조를 사용한다.
5. 사용 가능한 버튼은 `allowed_actions`를 기준으로 표시한다.
6. 상태 변경 성공 후 최신 데이터를 다시 표시한다.
7. 403·404·409·422·5xx 오류를 서로 구분한다.
8. 상담사가 작성 중인 내용은 오류 발생 시 가능한 범위에서 보존한다.
9. 고객명·연락처·식별자는 역할에 맞게 마스킹한다.
10. 문의번호·고객명·제품·대표 증상·상태 등 화면에 필요한 정보가 잘리지 않고 읽힌다.

### 기능 확정 산출물

- 상담사 화면별 기능 목록
- 메뉴·Route·화면 연결표
- 화면별 사용 API와 Mock 데이터 기준
- 미구현·부분 구현·완료 상태표
- 배포 전 제외하거나 숨겨야 하는 기능 목록

---

## 3.2 기능 확정 회의 기준

기능을 확정할 때는 다음 질문에 답할 수 있어야 한다.

- 이 화면의 주 사용자는 누구인가?
- 사용자가 이 화면에 들어온 직후 가장 먼저 해야 하는 일은 무엇인가?
- 반드시 보여야 하는 정보와 숨겨야 하는 정보는 무엇인가?
- 현재 상태에서 사용 가능한 다음 행동은 무엇인가?
- 데이터가 없거나 API가 실패하면 무엇을 보여주는가?
- Mock과 실제 API에서 같은 구조로 검증할 수 있는가?
- 주간발표에서 이 기능의 필요성과 효과를 한 문장으로 설명할 수 있는가?

위 질문에 답하지 못하는 기능은 배포 범위에 억지로 포함하지 않고, 미확정 또는 후속 과제로 분리한다.

# 4. 필수 업무 2 — 레이아웃 최종 확정

## 4.1 레이아웃 Freeze 대상

다음 요소를 화면별로 최종 확정한다.

- Header·Sidebar·본문의 기본 구조
- 상담사 업무 대시보드의 요약 카드·우선 업무 목록·AI 검수 영역
- 문의 목록의 탭·필터·목록 행·페이지네이션
- 문의 상세의 정보 우선순위와 행동 영역
- 전화 문의 등록의 입력 Form·가이드 영역
- Loading·Empty·Error·Forbidden 상태의 공통 배치

## 4.2 레이아웃 검수 기준

1. 1920×1080 발표 화면과 일반 노트북 화면에서 주요 업무가 첫 화면에 보인다.
2. 불필요한 빈 공간이나 의미 없는 배경 영역이 업무 영역보다 크지 않다.
3. 긴 문의 제목·고객명·모델명·오류 문구가 화면을 깨뜨리지 않는다.
4. 목록 제목, 관련 태그, 고객명이 명확히 구분된다.
5. 선택된 메뉴·탭·필터가 한눈에 구분된다.
6. 스크롤 영역과 전체 페이지 스크롤이 충돌하지 않는다.
7. 버튼·입력창·목록 행의 정렬과 간격이 화면마다 일관된다.
8. 상담사가 자주 사용하는 핵심 행동이 긴 스크롤 끝에만 배치되지 않는다.
9. 레이아웃 확정 이후 색상 수정 때문에 크기·간격·정렬이 다시 바뀌지 않는다.

## 4.3 레이아웃 변경 승인 규칙

레이아웃 Freeze 이후 변경은 다음 조건에서만 허용한다.

- 기능을 사용할 수 없는 수준의 배치 오류
- 글자·버튼·입력창이 잘려 업무 수행이 불가능한 경우
- 해상도 변경 시 핵심 영역이 사라지는 경우
- 접근성 또는 권한·오류 안내가 가려지는 경우
- 팀 발표 시 핵심 흐름을 설명할 수 없는 구조적 문제

단순 취향 차이, 새로운 레퍼런스 발견, 장식 효과 추가는 레이아웃 재변경 사유로 보지 않는다.

# 5. 필수 업무 3 — 배포 가능한 디자인 완성

## 5.1 디자인 방향

정수기 서비스의 깨끗함과 신뢰감을 전달하기 위해 전체 화면을 다음 기준으로 통일한다.

- 밝은 하늘색·파란색·청록색 중심의 서비스 색상
- 흰색 또는 옅은 파란색의 정보 카드
- 높은 대비의 남색 본문 글자
- 과하지 않은 그림자와 테두리
- 긴급·주의·성공 상태의 의미 색상 유지
- 장시간 업무에도 읽기 쉬운 글자 크기와 행간
- 장식보다 정보 우선순위가 먼저 보이는 화면

## 5.2 화면 품질 검수

### 공통

- 화면마다 색상·글꼴·버튼·카드 스타일이 달라 보이지 않는다.
- 선택·Hover·Focus·Disabled 상태가 구분된다.
- 색상만으로 상태를 전달하지 않고 문구·아이콘을 함께 사용한다.
- 낮은 대비의 회색 글자나 지나치게 투명한 카드를 사용하지 않는다.
- 개발용 문구·디버그 정보·내부 코드가 배포 화면에 노출되지 않는다.

### 상담사

- 위험 문의와 전화 연결 필요 문의가 즉시 구분된다.
- 문의 제목과 태그, 고객명이 잘리지 않고 읽힌다.
- 선택한 문의와 선택하지 않은 문의의 차이가 명확하다.
- AI 요약 초안·수정본·확정 상태가 혼동되지 않는다.
- 상담 기록 Form의 필수값·오류·저장 상태가 명확하다.

## 5.3 배포 전 Web Gate

최소 다음 검증을 통과해야 디자인 완료로 판단한다.

```bash
cd web
npm run typecheck
npm run lint
npm test
npm run build
```

추가로 다음 브라우저 Smoke를 수행한다.

```text
상담사 로그인
→ 업무 대시보드
→ 새 문의·처리 중·처리 완료 목록
→ 문의 상세
→ 상담 Action
→ 전화 문의 등록
```

### 배포 가능 완료 기준

- Production Build가 성공한다.
- 주요 화면에 치명적인 콘솔 오류가 없다.
- 새로고침과 직접 URL 접근이 동작한다.
- Mock Mode와 Remote Mode의 레이아웃 차이가 없다.
- 환경변수 누락이 Production에서 임의 Mock 전환으로 이어지지 않는다.
- 오류 발생 시 재시도 또는 다음 행동을 사용자가 이해할 수 있다.
- 다른 팀원이 실행 방법과 시연 경로를 재현할 수 있다.

# 6. 필수 업무 4 — 다른 팀원 작업 완전 이해

주간발표에서는 자신의 화면만 설명하는 것이 아니라 고객 문의가 생성되고 AI 처리와 Backend 상태 전이를 거쳐 상담사 Web에서 처리된 뒤 고객에게 결과가 돌아가는 전체 흐름을 설명할 수 있어야 한다.

## 6.1 반드시 이해할 전체 흐름

```text
고객 Mobile 문의 등록
→ Backend 문의·상태 저장
→ AI 증상 분석·안내·근거 생성
→ 고객 상담 요청
→ 상담사 Web 목록·상세 조회
→ 상담 시작·기록·완료 또는 방문 전환
→ 고객 상태·결과 확인
```

## 6.2 협업 영역별 확인 내용

| 협업 영역 | 확인할 내용 | Web 발표 연결점 |
| --- | --- | --- |
| Backend·DB·API | Inquiry 생성·조회·상태 전이, `allowed_actions`, `state_version`, 권한·오류, 전화 문의 등록 | 화면 버튼과 상태가 서버 계약을 따르는 이유 |
| 고객 Mobile | 고객 문의 등록, 추가 답변, AI 안내 확인, 상담 요청, 처리 결과 확인 | Mobile 문의가 상담사 Web에 이어지는 Cross-client 흐름 |
| AI·RAG·Evidence | 증상 분석, 안전 안내, 상담 요약, 공식 근거 공개 범위, 실패 Fallback | 상담사가 AI 결과를 검수하고 근거를 확인하는 방식 |
| 통합 QA·데이터 | 대표 합성 시나리오, 동일 Inquiry 추적, `correlation_id`, 회귀·E2E 기준 | 기능이 실제로 연결되었다는 검증 근거 |
| 기획·정책 | 사용자 역할, 우선순위, 위험도, 상담·방문 전환 정책, 발표 메시지 | 화면 기능의 필요성과 서비스 가치 설명 |

## 6.3 팀원 작업 이해 완료 기준

- 각 영역의 입력·처리·출력 데이터를 설명할 수 있다.
- Web이 어떤 API를 왜 호출하는지 설명할 수 있다.
- AI 결과 중 고객 공개 정보와 내부 정보를 구분할 수 있다.
- Mobile에서 생성된 문의가 Web에 나타나는 과정을 설명할 수 있다.
- 상담 완료 또는 방문 전환 이후 상태가 어디에 반영되는지 설명할 수 있다.
- 오류가 발생했을 때 Web 문제와 Backend·AI·데이터 문제를 구분할 수 있다.
- 각 팀원이 해결한 핵심 문제와 전체 서비스에 미친 영향을 한 문장으로 정리할 수 있다.

이해가 부족한 부분은 추측으로 발표 자료에 넣지 않는다. 담당자에게 질문하고 답변·관련 문서·기준 Commit을 함께 기록한다.

# 7. 필수 업무 5 — 주간발표 준비

## 7.1 발표 핵심 메시지

발표는 화면 개수를 나열하는 방식이 아니라 다음 흐름으로 구성한다.

1. 고객과 상담사의 기존 업무 문제
2. 고객 Mobile·AI·Backend·상담사 Web이 연결되는 해결 구조
3. 상담사가 지금 처리할 업무를 빠르게 판단하는 대시보드
4. 문의 상세와 AI 요약 검수로 반복 확인을 줄이는 방식
5. 전화 문의와 일반 문의가 같은 Workflow로 처리되는 구조
6. 상담 완료 결과가 고객의 후속 확인 흐름과 연결되는 방식
7. 실제 E2E 검증 결과와 남은 한계

## 7.2 Web 시연 순서

```text
1. 상담사 업무 대시보드 진입
2. 전화 연결 필요·새 문의·진행 중·AI 검수 건수 설명
3. 위험 문의 목록 확인
4. 문의 상세 진입
5. 고객 원문·AI 요약·공식 근거 확인
```

# 11. Blocker 처리 규칙

```text
[6주차 Web 최종화 Blocker]
기준 Commit: <SHA>
화면: <상담사/공통 상태>
실행 Mode: <Mock/Remote>
재현 순서: <사용자 행동>
기대 결과: <정상 기능·레이아웃>
실제 결과: <오류·불일치>
관련 API·상태: <Method·Path·status·allowed_actions>
필요 담당자: <이름·영역>
발표 영향: <있음/없음 및 대체 자료>
```

- Web 렌더링·상태·디자인 문제는 한예나가 우선 확인한다.
- Backend·API·DB 문제는 재현 정보와 요청·응답을 정리해 Backend 담당자에게 전달한다.
- AI 요약·공식 근거 문제는 공개 DTO와 화면 결과를 함께 AI 담당자에게 전달한다.
- Mobile 연계 문제는 동일 Inquiry와 상태 흐름을 기준으로 Mobile 담당자와 확인한다.
- 공용 정책·범위 문제는 PM·기획 담당자와 확정한 뒤 화면에 반영한다.
- Blocker 해결 전에는 Mock 성공 화면으로 실제 연동 완료를 대신하지 않는다.
