## 01. 프로젝트 개요

### 선정 배경과 기획 의도

정수기 고객은 상담사와 방문기사에게 같은 증상과 이전 조치를 반복해서 설명하기 쉽다. 담당자가 바뀌면 안전 안내, 상담 내용, 방문 결과가 끊길 수도 있다. WaterBridge는 하나의 문의 ID에 고객 문진, AI 안내, 공식 근거, 상담과 방문 이력을 연결해 이 문제를 줄이는 것을 목표로 한다.

### 프로젝트 내용과 차별점

- 고객, 상담사, 방문기사, 운영 담당자까지 4개 역할을 하나의 흐름으로 연결한다.
- AI 답변만 보여 주지 않고 공식 매뉴얼 근거와 사용 제한 상태를 함께 표시한다.
- 위험하거나 근거가 부족한 문의는 상담 경로로 전환한다.
- `allowed_actions`, `state_version`, 409 충돌 처리를 사용해 임의 상태 변경과 덮어쓰기를 막는다.
- 실제 개인정보 대신 합성 고객·문의 데이터를 사용한다.

### Web 활용 기술과 구조

| 구분 | 사용 내용 |
| --- | --- |
| 화면 | React 19, TypeScript, React Router |
| 개발·Build | Vite 8 |
| 검증 | Vitest, Testing Library, ESLint, TypeScript Build |
| Web 사용자 | 상담사, 운영 담당자 |
| 대표 화면 | 상담 목록, 문의 상세·상담, 방문 전환, 운영 대시보드 |

Web은 Backend REST API만 사용하며 DB나 AI 내부 API에 직접 접근하지 않는 구조를 따른다. 현재 발표 화면의 업무 데이터는 합성 Mock이고, 실제 상담·방문 저장은 Backend 계약 확정 이후 연결한다.

### Web 실행·검증 방법

```powershell
cd web
npm.cmd ci
npm.cmd test -- --run
npm.cmd run lint
npm.cmd run build
npm.cmd run dev
```

브라우저에서 `http://localhost:5173/consultant/inquiries`를 연다. Mock 시연은 `.env.local`에서 `VITE_USE_MOCK_API=true`, `VITE_MOCK_ROLE=CONSULTANT`를 사용한다. 운영 화면은 `VITE_MOCK_ROLE=OPERATOR`로 바꾼 뒤 `http://localhost:5173/admin`을 연다.

### 기대 효과

1. 고객이 같은 내용을 여러 담당자에게 반복 설명하는 일을 줄인다.
2. 상담사와 방문기사가 공식 근거와 이전 조치를 함께 확인할 수 있다.
3. 위험 문의를 먼저 확인하고 안전한 안내를 제공할 수 있다.
4. 운영 담당자가 지연·위험·재문의 현황을 한 화면에서 확인할 수 있다.

## 05. 자체 평가 의견

### 잘한 점

- 화면 수를 늘리는 것보다 목록 → 상세 → 상담 → 방문의 대표 흐름을 연결했다.
- AI 초안, 공식 근거, 상담사 확정 내용을 구분해 안전성과 책임 경계를 드러냈다.
- 테스트 수치를 현재 Source에서 다시 확인하고 다른 팀원이 README로 교차 검증했다.
- 실제 API와 Mock을 발표 문구와 화면에서 구분했다.

### 아쉬운 점

- 상담·방문 Active OpenAPI가 없어 실제 저장까지 완성하지 못했다.
- 운영 대시보드도 실제 집계보다 Mock 화면이 먼저 확장됐다.
- 일부 핵심 CSS가 크고 중복되어 발표 이후 분리가 필요하다.

### Web 자체평가 초안

**8점 / 10점**을 제안한다. 화면 흐름·오류 처리·자동 검증·발표 준비와 3회 리허설은 완료했지만 실제 Backend 저장이 남아 있기 때문이다. 최종 점수는 팀 합의 후 확정한다.

### 추후 개선

1. Backend 계약 승인 뒤 실제 목록·상담·방문 Remote Repository를 연결한다.
2. 실제 API 기준 401·403·404·409·422·5xx·Network 오류를 다시 검증한다.
3. 상담사와 운영 화면의 중복 CSS를 시각 회귀 테스트와 함께 분리한다.
4. 대표 E2E와 발표 3회 반복 결과를 최종 보고서에 추가한다.
