## 1. 완료한 작업

### 1.1 문의 목록·상세 Web Adapter

- Mock과 Remote Repository를 분리한 기존 구조를 유지했다.
- Remote 목록의 검색·상태·위험도·우선순위·기간·정렬·페이지 Query와 `page_info`, `status_counts` 소비 구조를 확인했다.
- Remote 상세의 Nullable 상담·방문 정보와 `section_errors` 처리 구조를 유지했다.
- Remote 상세에서 Backend `allowed_actions`를 기준으로 실제 상담·방문 작업 화면으로 진입할 수 있게 연결했다.
- URL 또는 화면 내부 계산값을 권한 근거로 사용하지 않고, Remote 모드 작업 노출은 Backend `allowed_actions`를 기준으로 제한했다.

### 1.2 상담 시작·기록·요약 확정·완료 Remote API 연결

- 다음 실제 API를 Remote 상담 처리 화면에 연결했다.
  - `POST /api/v1/inquiries/{id}/start-consultation`
  - `PATCH /api/v1/inquiries/{id}/consultation-summary`
  - `POST /api/v1/inquiries/{id}/consultation-summary/confirm`
  - `POST /api/v1/inquiries/{id}/complete-consultation`
- 상담 완료 요청은 서버 계약대로 `state_version`만 전송하도록 DTO를 수정했다.
- 상담 기록 저장 시 공개 계약 필드만 전송하고 문자열 앞뒤 공백을 제거하도록 했다.
- 성공 후 Backend가 반환한 `status`, `state_version`, `allowed_actions`를 화면 상태에 반영하도록 했다.
- 중복 클릭을 차단하고, 네트워크·Timeout·5xx 재시도에는 동일한 `Idempotency-Key`를 재사용하도록 했다.
- `409 STATE-CONFLICT-01` 발생 시 최신 상태·버전을 반영하되 사용자가 작성한 입력값은 지우지 않도록 했다.
- 403·404·409·422·5xx·Network·Timeout을 구분할 수 있도록 상담 작업 오류 타입을 확장했다.
- Remote 상세 화면에서 Mock 응답 시나리오 선택 UI가 노출되지 않도록 별도 Remote 작업 패널을 구성했다.

### 1.3 방문 검토·생성·일정 저장·확정 Remote API 연결

- 다음 실제 API를 Remote 방문 화면에 연결했다.
  - `POST /api/v1/inquiries/{id}/visit-review`
  - `POST /api/v1/inquiries/{id}/visits`
  - `POST /api/v1/inquiries/{id}/visit-not-needed`
  - `PATCH /api/v1/visits/{visitId}/schedule`
  - `POST /api/v1/visits/{visitId}/confirm`
- `visit-not-needed` 요청 DTO와 Repository 메서드를 추가했다.
- 방문 생성 요청에는 기사 ID를 넣지 않고, 생성 응답의 `resource.visit_id`를 확보한 뒤 기사·일정을 저장하도록 순서를 분리했다.
- 방문 날짜는 `YYYY-MM-DD` date-only 형식만 사용하고 `datetime-local` 또는 시각 값을 전송하지 않도록 했다.
- 희망일보다 확정일이 빠른 입력을 Web에서 차단했다.
- 방문 사유·인계 내용·안전 유의사항·점검 우선순위·기사·날짜의 단계별 필수값을 Web에서 확인하도록 했다.
- 성공 후 Backend의 `state_version`, `allowed_actions`, `resource.visit_id`를 반영하고, 실패 시 작성 중인 방문 입력값을 유지하도록 했다.
- Remote 방문 버튼은 Location State가 아니라 Backend `allowed_actions`로만 활성화하도록 했다.

### 1.4 계약·회귀 자동 검증

- 상담 완료 Body가 `state_version`만 갖는지 Repository Test를 수정했다.
- 방문 불필요 Endpoint와 HTTP Method를 Repository Test에 추가했다.
- Remote 상담 요약 저장의 공개 DTO 필드와 현재 `state_version` 전송을 Hook Test로 추가했다.
- Remote `409 STATE-CONFLICT-01`에서 성공으로 오인하지 않고 최신 버전을 반영하는 Test를 추가했다.

## 3. 미완료 작업 완료를 위해 담당자들과 협의할 사항

### 최지용 — Backend·DB

- 상담사 API가 실행되는 공용 Base URL과 적용 Commit을 공유한다.
- Remote Smoke용 상담사 계정과 해당 상담사에게 배정된 Inquiry UUID를 제공한다.
- 상담·방문 Operation별 성공 Fixture와 403·404·409·422 예시를 제공한다.
- `GET /inquiries/{id}`의 `visit` 공개 DTO에서 `visit_id` 위치를 최종 고정한다.
- 방문 생성 응답의 `resource.visit_id`와 상세 조회의 `visit_id`가 동일한지 확인한다.
- 일정 저장에 사용할 합성 기사 UUID 목록 또는 기사 조회 API 계약을 제공한다.
- Web이 전달한 `X-Correlation-ID`로 Backend Log와 DB 상태 변경 이력을 함께 확인한다.
- AI 내부 결과를 Public allowlist DTO로 조립하는 Backend Endpoint와 오류 Wrapper를 확정한다.

### 이동윤 — AI·RAG

- 실제 Scenario별 Guidance·Evidence·Summary·Fallback 결과를 Backend에 전달 가능한 형태로 고정한다.
- 상담사 공개 Evidence 필드의 최종 목록을 최지용과 함께 확인한다.
- `chunk_id`와 공개 Evidence ID 또는 문서·개정·페이지 정보의 Crosswalk 책임 경계를 확정한다.
- 검색 점수, 내부 파일 경로, Prompt, Token, Chain-of-Thought가 Public DTO에 포함되지 않는지 확인한다.
- 같은 대표 Scenario에서 정상·근거 없음·AI 실패 결과를 제공해 Web 표시를 공동 검증한다.

### 김은진 — Data·QA·DevOps

- 실제 인증이 가능한 상담사 계정, 대표 Inquiry·Consultation·Visit Fixture와 초기 `state_version`을 준비한다.
- Web 자동 Test와 동일 Commit을 기준으로 Remote Smoke 및 전체 E2E를 실행한다.
- 로그인→상담 큐→상세→상담 저장·확정→방문 검토·생성→기사·일정→확정 Scenario ID를 고정한다.
- 409 재현용 동시 변경 Fixture와 Idempotency 재전송 검증 조건을 제공한다.
- Test·Build·E2E Report에 Correlation ID와 실패 시 담당자·해제 조건을 기록한다.

### 윤승혁 — PM·기술 통합

- Backend State와 `allowed_actions`가 5주차 상태표와 일치하는지 최종 승인한다.
- 상담 완료 뒤 방문 검토로 이동하는 조건과 `VISIT_NEEDED`·`VISIT_NOT_NEEDED` 분기 기준을 승인한다.
- 기사 목록 API 부재 시 승인된 합성 Fixture 사용 여부와 Release Candidate 허용 범위를 결정한다.
- AI Public Evidence allowlist와 P0 완료 기준을 승인한다.
- 실제 Remote Smoke와 전체 E2E 완료 후 3~8번의 최종 완료 판정을 갱신한다.

### 양정현 — Mobile·방문 데이터 협업

- `synthetic_technician_id`, `preferred_date`, `confirmed_date`의 명칭과 date-only 형식을 Mobile 흐름과 교차 확인한다.
- 방문 생성 단계에는 기사 ID를 넣지 않고 생성 후 기사·일정을 저장하는 순서가 Mobile과 동일한지 확인한다.
- Web·Mobile이 같은 합성 기사 UUID와 대표 Visit Fixture를 사용하도록 김은진·최지용과 Crosswalk를 맞춘다.
