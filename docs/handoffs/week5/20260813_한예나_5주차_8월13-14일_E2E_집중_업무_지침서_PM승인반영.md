# 1. 이번 이틀의 목표

이번 이틀 동안 한예나의 최우선 목표는 **상담사 Web을 실제 Backend에 끝까지 연결하여, 고객이 Mobile에서 넘긴 문의를 상담사가 실제로 조회하고 처리할 수 있는 상태를 만드는 것**이다.

현재 Web은 Remote Repository, 문의 목록·상세, 상담 Action, 오류 처리, `state_version`, `allowed_actions` 소비 구조까지 대부분 구현되어 있다. 남은 핵심은 실제 Backend 브라우저 검증, 실제 AI Guidance 연결, Mobile 상담 요청과 Web 상담 완료를 잇는 Cross-client E2E다.

따라서 새로운 화면을 늘리거나 디자인을 고도화하기보다 다음 흐름을 완성한다.

> **Mobile 실제 AI 안내 → 상담 요청 → 동일 `inquiry_id` Web 조회 → 상담 시작·기록·완료 → Mobile 최종 상태 확인**

# 4. 8월 13일 — 상담사 Web 실제 연결 완료

## 4.1 오전 — Remote Mode 기준선 확인

최신 통합 환경에서 Web이 실제 Backend를 바라보도록 설정하고 빠르게 정상 여부를 확인한다.

작업 시작 전에 다음을 고정한다.

- 통합 기준 SHA와 Web·Backend·AI·Mobile 실제 실행 SHA
- 공용 Backend·DB·AI Base URL과 Health 상태
- CUSTOMER·CONSULTANT 합성 계정
- 대표 구독·제품·Inquiry Fixture와 초기화 방법
- Backend 로그에서 `correlation_id`를 확인하는 방법
- 대표 상태 전이와 예상 `allowed_actions`

Cross-client의 동일 업무 건은 `inquiry_id`로 판별한다. `correlation_id`는 개별 HTTP 요청과 Backend 로그의 일치 여부를 확인하는 추적값으로 사용한다.

최소 확인:

```
상담사 로그인
→ 문의 목록 조회
→ 문의 상세 조회
→ 상담 Action 호출 가능
```

필요한 경우 다음 Gate만 빠르게 실행한다.

```bash
cd web
npm run lint
npm run typecheck
npm run build
```

전체 Test가 오래 걸리면 E2E보다 우선하지 않는다. 기존 표적 Test가 이미 존재하므로 **실제 브라우저 연동을 먼저 닫는다.**

---

## 4.2 Cross-client 선행 Gate — Mobile 실제 Guidance·상담 요청 연결

양정현·최지용·이동윤·김은진과 다음 두 경로가 실제 Runtime을 사용하는지 먼저 확인한다.

```
Mobile 문의 제출
→ Backend가 실제 Baseline AI 호출
→ Guidance 저장·조회
→ Mobile 실제 Guidance 표시
→ 상담 요청 API 호출
→ CONSULTATION_REQUIRED 상태와 inquiry_id 확인
```

### Gate 통과 조건

- Remote Mode에서 Guidance 실패를 Fake·Fixture 성공으로 바꾸지 않는다.
- 상담 요청 버튼이 로컬 알림으로 끝나지 않고 실제 API를 호출한다.
- 상담 요청 성공 후 최신 `status`, `state_version`, `allowed_actions`를 사용한다.
- 생성된 `inquiry_id`를 Web E2E 인계값으로 기록한다.
- AI 실패 시 문의가 유실되거나 화면이 무한 대기하지 않고 명시적 Fallback을 표시한다.

이 Gate가 닫히기를 기다리는 동안 Web 목록·상세·상담 Action Smoke를 병렬 수행한다.

---

## 4.3 상담사 목록·상세 실제 브라우저 Smoke

최지용과 함께 실제 Backend·PostgreSQL을 사용하여 다음 흐름을 검증한다.

```
상담사 로그인
→ 상담 필요 문의 목록
→ 검색·Filter·Pagination
→ 고객 Inquiry 상세
→ 고객 원문·추가 답변 확인
→ 현재 상태·허용 행동 확인
```

### 반드시 확인할 것

- Remote Mode에서 Mock 데이터가 섞이지 않는다.
- Backend 결과 행과 화면이 일치한다.
- 새로고침 후에도 같은 문의가 유지된다.
- `state_version`과 `allowed_actions`를 Web이 임의 계산하지 않는다.
- 상담사에게 허용되지 않은 개인정보·내부 ID를 추가로 노출하지 않는다.
- 403·404가 실제 Backend 응답 기준으로 처리된다.

## 4.4 실제 AI Guidance 표시와 Public Evidence Fallback

Backend가 실제 AI 결과를 저장하고 상담사 상세 DTO로 제공하면 즉시 Web에 연결한다.

```
Backend Inquiry Detail
→ AI Guidance / Summary
→ 상담사 상세 화면 표시
```

### 화면에 보여줄 것

- 고객이 입력한 증상과 추가 답변
- AI가 제공한 고객 안내 또는 처리 결과
- 상담이 필요한 이유 또는 현재 상태
- 상담사가 수행할 수 있는 다음 행동

### Public Evidence 처리

- Public Evidence Web 표시 기능은 이번 P0 완료 조건에 포함하지 않는다.
- Runtime이 제공되지 않으면 EvidenceCard를 가짜 데이터로 생성하지 않는다.
- `공개 근거 미제공 / 상담 검토 필요` 수준의 안전한 빈 상태를 표시한다.
- Runtime이 제공되더라도 Cross-client P0를 지연시키는 화면 고도화는 하지 않는다.
- Backend State 전이에 필요한 Evidence 검증 결과는 Web 공개 Evidence와 분리하여 판단한다.

### 화면에 보여주지 않을 것

- 내부 `chunk_id`
- Vector score
- Prompt
- 서버 내부 경로
- 전체 원문 문서
- AI 내부 Trace

AI 결과의 표현이 완벽하지 않더라도 DTO가 정상이고 상담사가 이해 가능한 수준이면 E2E를 진행한다. **문구 개선 때문에 연결을 늦추지 않는다.**

## 4.5 상담 Start → 완료 흐름 실제 Remote 마감

다음 흐름을 실제 Backend에서 끝까지 실행한다.

```
문의 상세
→ 상담 시작
→ 상담 내용 입력·저장
→ 필요한 경우 요약 확정
→ 상담 완료
→ 최신 Inquiry 재조회
```

이번 P0 E2E에서는 방문으로 넘기지 않고 **상담 완료 경로를 우선 사용**한다.

### 확인 사항

- 버튼은 `allowed_actions`가 있을 때만 노출된다.
- 성공 후 서버가 반환한 최신 상태를 사용한다.
- 409 발생 시 작성 중인 내용을 보존한다.
- 중복 클릭으로 상담 기록이 중복 생성되지 않는다.
- 새로고침 후 상담 결과가 유지된다.

# 7. 최소 오류 검증

Happy Path가 성공한 뒤 다음 정도만 확인한다.

1. **409 Conflict** — 작성 내용을 보존하고 최신 상태·행동으로 화면을 갱신하는가
2. **403/404** — 권한 없는 문의와 존재하지 않는 문의가 정상 처리되는가
3. **AI 결과 없음/실패** — 화면 전체가 깨지지 않고 Fallback 상태를 표시하는가
4. **중복 클릭** — 같은 상담 Action이 반복 제출되지 않는가
5. **Public Evidence Runtime 없음** — 가짜 근거 없이 `공개 근거 미제공 / 상담 검토 필요` 상태가 표시되는가

광범위한 UI 회귀나 모든 Filter 조합 검증은 이번 이틀의 우선순위가 아니다.

# 8. 작업이 조기에 끝났을 경우

Web 독립 작업이 먼저 끝나면 새로운 화면을 만들지 않고 팀 E2E를 지원한다.

1. 김은진과 실제 브라우저 Smoke 수행
2. Mobile에서 만든 Inquiry가 Web에 표시되는지 반복 검증
3. Backend DTO·Web Mapper 불일치 확인
4. `correlation_id` 대조
5. 실제 시연용 상담사 계정·문의 흐름 고정
6. 시연 시 필요한 핵심 화면 상태 확인

특히 상담사 관점에서 **“고객이 무엇을 문의했고, AI가 무엇을 했으며, 지금 내가 무엇을 해야 하는지”**가 한 화면에서 이해 가능한지 확인한다.

대규모 UI 개편은 하지 않는다. 명백히 시연을 방해하는 표시 문제만 최소 수정한다.
