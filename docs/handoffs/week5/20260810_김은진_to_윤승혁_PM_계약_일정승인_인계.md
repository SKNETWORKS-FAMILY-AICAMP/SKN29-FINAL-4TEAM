## 1. 인계 목적

실제 QA에서 확인된 Runtime 범위를 기준으로 상담·방문·Evidence의 개발 순서,
담당자, 목표일과 완료 Gate를 승인해 달라는 요청이다. 문서나 Mock이 아니라
Method·Path·DB 저장·오류·추적 증거를 공식 완료 조건으로 사용해야 한다.

세부 실행 결과는
[Web–Backend 실제 연결 QA 보고서](../../testing/results/week4-web-backend-live-verification-20260810.md)를
기준으로 한다.

## 3. 요청할 결정

### DEC-W5-01 — 구현 순서

다음 기본 순서를 승인하거나 변경안을 회신해 달라.

1. 상담사 목록·상세 Route와 객체 권한
2. 상담 시작·사용자 저장·확정·완료
3. 방문 검토·생성·불필요·일정·확정
4. AI 오류·Evidence Backend 연결
5. Web 실제 Adapter 전환
6. 고객→상담사→기사→고객 전체 E2E

상담·방문 Runtime과 Evidence 계약을 동시에 무리하게 확장하지 말고, 각
단계의 PostgreSQL·권한·멱등·추적 Gate 통과 후 다음 단계로 진행한다.

### DEC-W5-02 — Public Evidence 계약

- 최종 Public DTO 조립 책임은 Backend로 둔다.
- AI는 구조화 근거와 내부 메타데이터를 반환하되 업무 상태를 변경하지 않는다.
- `chunk_id`, 검색 점수, 내부 경로, 원문 전체와 Vector 식별자는 Public에서
  제외한다.
- 문서명·버전·페이지·요약·검증 상태·공식 URL과 안전 필드의 최종
  allowlist를 계약에 확정한다.
- `contracts/api/components/schemas/evidence/**`,
  `contracts/api/paths/evidence.yaml`, Example과 Changelog를 같은 변경으로
  갱신한다.

### DEC-W5-03 — 완료 상태와 일정

- 23개 Action의 현재 Runtime 분류를 최신 구현과 다시 대조한다.
- 상담·방문 Operation별 Backend·Web·QA 담당과 목표일을 지정한다.
- `CONTRACT_ONLY`, `MOCK_UI`, `PARTIAL_RUNTIME`, `VERIFIED_RUNTIME`을 구분한다.
- 담당자 회신과 실제 재검증 날짜를 5주차 WBS에 반영한다.
