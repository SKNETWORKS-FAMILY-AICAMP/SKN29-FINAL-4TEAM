# 한예나 → 양정현 방문 데이터 형식 확인 요청

> 작성일: 2026-08-10  
> 요청자: 한예나(Web)  
> 수신자: 양정현(Mobile)  
> 목적: Web·Mobile·Backend의 방문 날짜, 상태명, 전달 항목 통일

## 1. 확인 요청

5주차 방문 기능 연동 전에 Web과 Mobile에서 사용하는 방문 데이터 형식을 맞추고자 합니다.

아래 항목을 Mobile에서도 같은 이름과 값으로 사용하고 있는지 확인 부탁드립니다. 다른 이름을 사용하고 있다면 알려주시면 Backend 계약을 기준으로 함께 맞추겠습니다.

## 2. 방문 날짜와 기사 정보

| 구분 | 공통 필드명 | 형식 |
|---|---|---|
| 고객 방문 희망일 | `preferred_date` | `YYYY-MM-DD`, 값이 없으면 `null` |
| 방문 확정일 | `confirmed_date` | `YYYY-MM-DD`, 값이 없으면 `null` |
| 담당 기사 ID | `synthetic_technician_id` | UUID |

날짜는 시간 없이 날짜만 사용합니다.

```json
{
  "preferred_date": "2026-08-12",
  "confirmed_date": "2026-08-13",
  "schedule_status": "CONFIRMED",
  "synthetic_technician_id": "UUID"
}
```

## 3. 방문 상태명

| 상태 코드 | 화면 표시명 |
|---|---|
| `ASSIGNING` | 기사 배정 중 |
| `SCHEDULING` | 일정 조율 중 |
| `CONFIRMED` | 방문 확정 |
| `IN_PROGRESS` | 방문 진행 중 |
| `COMPLETED` | 방문 완료 |
| `FOLLOW_UP_REQUIRED` | 재방문 필요 |
| `CANCELLED` | 취소 |

상태는 Mobile이나 Web에서 임의로 계산하지 않고 Backend가 전달한 값을 그대로 사용합니다.

문의 상태와 방문 상태는 서로 다른 값으로 관리합니다.

- 문의 상태 예시: `VISIT_REVIEW_PENDING`, `VISIT_SCHEDULING`, `VISIT_SCHEDULED`
- 방문 상태 예시: `ASSIGNING`, `SCHEDULING`, `CONFIRMED`

## 4. 고객 → 상담사 → 기사 전달 항목

아래 항목을 방문기사 화면에서 받을 수 있어야 하는지 확인 부탁드립니다.

- 문의 ID: `inquiry_id`
- 제품 요약: `product_summary`
- 증상 요약: `symptom_summary`
- 고객 조치 요약: `action_summary`
- 위험도·안전 안내 요약: `risk_summary`
- 우선 점검 항목: `priority_check_items`
- 상담사 최종 확인 내용: `consultant_final`
- 고객 방문 희망일: `preferred_date`
- 방문 확정일: `confirmed_date`
- 방문 일정 상태: `schedule_status`
- 담당 기사 정보: `synthetic_technician_id`

전달 항목은 현재 계약상 최종 확인이 필요한 부분이 있어 최지용(Backend) 담당자와 윤승혁(PM)에게도 함께 확인할 예정입니다.

## 5. 회신 요청

아래 형식으로 간단히 회신 부탁드립니다.

```text
방문 날짜 필드명 일치: 예 / 아니요
날짜 형식 YYYY-MM-DD 사용: 예 / 아니요
방문 상태 코드 일치: 예 / 아니요
담당 기사 ID UUID 사용: 예 / 아니요
전달 항목 누락 여부: 없음 / 있음
Mobile에서 다르게 사용하는 항목: 없음 / 항목명 작성
추가 확인이 필요한 내용: 없음 / 내용 작성
```

## 6. 확인 후 진행

1. Web·Mobile의 필드명과 상태 코드를 공통 계약에 맞춥니다.
2. 최지용 담당자에게 Backend 요청·응답 형식을 최종 확인합니다.
3. 실제 API가 준비되면 Web·Mobile에서 같은 데이터로 연동 결과를 확인합니다.
