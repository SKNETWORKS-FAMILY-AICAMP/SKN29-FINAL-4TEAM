## Web 검토 결과

### 1. Endpoint 계약

다음 두 Endpoint의 Method, Path, 성공 응답 및 오류 응답을 확인했습니다.

- `GET /api/v1/me/subscriptions`
- `GET /api/v1/me/subscriptions/{subscription_id}`

목록 응답의 `items`, `page`, `size`, `total` 구조와 빈 목록의 `200` 처리 방식을 Web에서 소비할 수 있습니다. 알 수 없는 Query와 잘못된 Pagination을 `422`로 구분하는 정책도 수용 가능합니다.

### 2. DTO 계약

목록과 상세 응답에 포함된 다음 필드의 이름, Type, Nullable 규칙을 확인했습니다.

- `subscription_id: uuid`
- `status_code: ACTIVE`
- `management_type_code: SELF_MANAGED | VISIT_CARE`
- `started_on: date`
- `ended_on: date | null` — 상세 응답에만 포함
- `last_care_on: date | null`
- `next_care_on: date | null`
- `product.product_model_id: uuid`
- `product.model_code: WPUJAC104DWH`
- `product.model_name: string`
- `product.generation_code: string | null`
- `product.manufacturer: string`

API DTO는 `snake_case`로 받고, 향후 실제 Web 연동 시 Mapper에서 화면용 View Model로 변환할 수 있습니다.

### 3. 이전 Web 검토 요청사항 반영 확인

이전 `T018-D06` Web 검토에서 요청한 항목이 다음과 같이 반영된 것을 확인했습니다.

1. `last_care_on`은 `COMPLETED` CareRecord의 `performed_on`을 우선 사용하며, `Asia/Seoul` 업무일 기준 최근 날짜를 계산하고 기록이 없으면 `null`로 처리합니다.
2. 로그인 고객 본인의 활성 `WPUJAC104DWH` 모델·`ACTIVE` 구독만 조회합니다.
3. Web에서 제품 지원 범위를 임의로 판단하지 않고 Backend의 확정 필터를 따릅니다.
4. 문의 가능 여부는 T-022 Guard에서 검증합니다.
5. `allowed_actions`는 T-023 State Machine 후속 계약에서 제공합니다.
6. T-018 응답에 문의 가능 여부와 `allowed_actions`가 포함되지 않는 경계를 수용합니다.

### 4. 개인정보 및 비노출 범위

다음 정보가 T-018 응답에 포함되지 않는 것을 확인했으며, Web에서도 별도로 추측하거나 표시하지 않습니다.

- 내부 Database ID
- 계약번호
- Serial 번호
- 설치주소
- 원천 고객·제품 공개 ID
- 고객 개인정보
- 제품 Features

타 고객, 삭제 고객, 비활성 구독 및 비지원 모델의 상세 조회에서 존재 여부를 숨기고 동일한 `404`를 반환하는 정책도 수용 가능합니다.

### 5. 구현 경계

두 Endpoint의 계약 상태는 `CONFIRMED`이지만 Runtime 상태는 `NOT_IMPLEMENTED`입니다.

따라서 현재 단계에서는 다음 작업을 진행하지 않습니다.

- 실제 API 연결
- 기존 Mock 제거
- Remote Adapter 구현
- Customer 구독 화면 및 Route 연결

`consumer_integration_start_allowed=false`를 유지하며, 별도의 Runtime 및 소비 시작 승인이 내려진 이후 실제 Web 연동을 진행하겠습니다.

## 결론

Endpoint, DTO, 개인정보 보호 경계 및 T-022·T-023 책임 분리를 Web에서 소비할 수 있습니다. 추가 변경 요청은 없으며, 실제 Runtime과 소비 시작 Gate가 열릴 때까지 구현 보류 상태를 유지합니다.
