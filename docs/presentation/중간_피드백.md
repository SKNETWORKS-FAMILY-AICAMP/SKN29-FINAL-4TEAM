# WaterBridge 중간발표 피드백 정리본

## 1. 총평

현재 발표는 **고객 문의 접수부터 상담·방문·후속 관리까지 이어지는 전체 흐름과 기술 구조는 잘 드러났으나**, 다음 세 가지가 상대적으로 약하게 전달되었다.

1. **기업이 도입했을 때 얻는 구체적인 효과**
2. **현재 구현된 기능과 향후 구현할 설계의 구분**
3. **모델·기술을 선택한 실험적 근거**

최종 발표에서는 기술 요소를 추가로 나열하기보다, 하나의 문의가 어떻게 처리되고 그 결과 고객·상담사·현장기사·기업의 부담이 어떻게 줄어드는지를 중심으로 설명할 필요가 있다.

---

## 2. 기술 설계 관련 피드백

### 2.1 Rule Engine과 Safety Guard 설명 보강

발표 중 Rule Engine이 어떤 방식으로 동작하는지 명확하지 않아 추가 질문이 나왔다.

현재 구조는 다음과 같이 정리할 수 있다.

* 고객이 입력한 증상에서 위험 가능성을 먼저 확인
* 누수, 전기, 스파크, 탄 냄새, 화상 위험 등의 명시적 규칙을 적용
* 위험한 경우 일반 안내나 자가조치를 생성하지 않고 상담사 연결로 전환
* 현재 Safety Guard는 LLM이 아니라 **규칙 기반 모듈**로 동작

최종 발표에서는 다음처럼 명확히 설명하는 것이 적절하다.

> Safety Guard는 생성형 AI가 아니라 명시적인 안전 규칙을 검사하는 모듈입니다. 위험 증상이 확인되면 RAG 검색이나 자가조치 안내보다 상담 전환을 우선합니다.

단순 키워드 매칭만 사용하는 것처럼 보이지 않도록, 증상 조합과 표현 변형을 어떻게 처리하는지도 보완해야 한다.

---

### 2.2 Output Validator의 역할 구체화

Output Validator가 무엇을 검증하는지 설명이 부족했다.

발표에서 구분해야 할 검증 항목은 다음과 같다.

* 응답 Schema 준수 여부
* 공식 근거 연결 여부
* 확정 진단·과도한 안전 보증·직접 수리 표현 포함 여부
* 위험도와 안내 내용의 모순 여부
* 근거가 없는 상태에서 임의 자가조치가 생성됐는지 여부

검증 실패 시 최대 1회 재생성한다는 설명도 나왔으나, 다음을 명확히 해야 한다.

* 현재 실제로 구현된 검증 범위
* 향후 구현할 Grounding 검증 범위
* 재생성도 실패했을 때의 처리 방식

권장 처리 방식:

> 재생성에도 실패하면 생성문을 고객에게 노출하지 않고, 안전 Template으로 대체하거나 상담 필요 상태로 전환한다.

---

### 2.3 현재 구현과 목표 설계 구분

슬라이드에서는 다중 Agent, GPT 기반 생성, Output Validator가 완성된 구조처럼 보일 수 있다. 그러나 현재 구현 범위와 향후 목표 구조가 섞여 있다는 지적이 있었다.

명확히 구분해야 할 항목은 다음과 같다.

#### 현재 구현·검증 범위

* 증상 구조화
* 규칙 기반 안전 판정
* 공식 문서 검색
* 제품·세대 기반 필터링
* 근거 유무에 따른 상태 반환
* 규칙·Template 기반 안내
* 독립 pgvector 환경 검증

#### 향후 구현 또는 통합 범위

* GPT 기반 최종 자연어 생성
* 독립적인 역할별 Multi-Agent
* 상담 요약 Agent
* 기사 리포트 Agent
* 팀 공용 DB 저장 E2E
* 전체 Mobile·Web·Backend 통합
* 완성형 Output Grounding 검증

최종 발표에서는 각 기능에 `구현 완료`, `통합 중`, `설계안` 상태를 표시하는 것이 필요하다.

## 3. 모델 및 RAG 관련 피드백

### 3.1 bge-m3 선택 근거 부족

평가자는 다음 내용을 질문했다.

* 정수기 관련 전문 용어를 충분히 처리할 수 있는가
* 파인튜닝이 필요한 것은 아닌가
* 다른 임베딩 모델과 비교했는가
* 왜 bge-m3를 선택했는가

현재는 데이터가 충분하지 않아 파인튜닝하지 않고 사전학습 모델을 적용한 상태다. 이 판단 자체는 문제가 없지만, **후보 모델과의 비교가 없기 때문에 최적 모델이라고 주장할 수는 없다.**

발표 답변은 다음처럼 제한하는 것이 적절하다.

> bge-m3가 가장 우수하다는 비교 결과는 아직 없습니다. 한국어를 포함한 다국어 임베딩 지원, 로컬 실행, 고정된 1024차원 출력과 pgvector 연계 가능성을 기준으로 MVP 기준 모델로 선택했습니다.

최종 발표 전 가능하면 다음 비교를 수행하는 것이 좋다.

* Recall@1·3·5
* MRR 또는 nDCG
* 검색 지연시간
* 메모리 사용량
* 모델 적재시간
* Hard Negative 오검색률

---

### 3.2 생성 모델의 성능·비용 비교 필요

GPT-5.4 mini를 선택한 이유도 기능 설명만으로는 충분하지 않다는 의견이 있었다.

비교해야 할 항목:

* JSON Schema 출력 성공률
* 증상 구조화 정확도
* 근거 외 내용 생성 여부
* 안전 표현 준수율
* 평균 응답시간
* 문의 1건당 예상 비용
* 한국어 문장 품질

아직 실제 LLM 호출이 연결되지 않았다면 다음처럼 표현해야 한다.

> GPT-5.4 mini는 적용 후보 모델이며, 실제 문의 데이터 기준 성능과 비용 비교는 아직 완료되지 않았습니다.

---

### 3.3 제품별 문서 분리와 확장 구조 설명

현재 MVP는 정수기 모델 1종만 지원한다. 평가자는 여러 제품이 존재할 때 다른 제품의 문서가 잘못 검색되는 문제를 질문했다.

최종 발표에서는 현재 범위를 명확히 밝혀야 한다.

> 현재 MVP는 정수기 모델 1종, D세대 공식 매뉴얼을 대상으로 검증했습니다.

향후 확장 시 다음 조건을 검색 전후로 검증해야 한다.

* 제품 모델 코드
* 제품 세대
* 문서 버전
* 문서 적용 기간
* 공식 검증 상태
* 문서 Hash
* 고객 안내 사용 허용 여부

신규 모델 확장 절차도 제시할 필요가 있다.

```text
신규 제품 등록
→ 공식 문서 수집
→ 제품·세대 검수
→ 청킹 및 임베딩
→ 검색 평가
→ 승인 후 서비스 적용
```

## 4. 서비스 가치와 기대효과 관련 피드백

### 4.1 기업 관점의 기대효과가 가장 부족함

평가자들이 공통적으로 지적한 핵심이다.

현재 발표는 기술 구성과 사용자 흐름은 보여주지만, 기업 입장에서는 다음 질문에 대한 답이 부족하다.

* 상담 시간이 얼마나 줄어드는가
* 상담사 1명이 처리할 수 있는 문의가 늘어나는가
* 고객 자가 해결률이 얼마나 되는가
* 현장기사 재방문이 줄어드는가
* 운영비와 출장비를 얼마나 줄일 수 있는가

현업 데이터가 없으므로 임의의 절감률을 제시해서는 안 된다. 대신 **검증할 KPI와 산정 방법**을 명시해야 한다.

#### 고객 KPI

* 동일 증상 반복 설명 횟수
* 다음 행동 확인까지 걸린 시간
* 자가점검 완료율
* 상담 전환율

#### 상담사 KPI

* 공식 문서 탐색 시간
* 재질문 횟수
* 문의당 평균 처리시간
* AI 요약 채택률·수정률

#### 현장기사 KPI

* 방문 전 리포트 완성도
* 현장 재확인 항목 수
* 최초 방문 해결률
* 재방문율

#### 기업 KPI

* 상담사 1인당 처리 건수
* 문의당 처리비용
* 자가 해결률
* 불필요한 방문 건수
* 평균 해결 소요시간

---

### 4.2 고객 셀프서비스 흐름 강조

기업 비용 절감 측면에서 고객이 상담 전에 스스로 해결할 수 있는 흐름이 중요하다는 의견이 나왔다.

발표에서 다음 흐름을 더 강하게 보여줄 필요가 있다.

```text
증상 접수
→ 위험 여부 확인
→ 안전한 경우 공식 근거 기반 점검 안내
→ 고객 수행 결과 입력
→ 해결되면 종료
→ 미해결이면 상담 연결
```

핵심 메시지:

> 모든 문의를 즉시 상담으로 보내는 것이 아니라, 안전하게 해결 가능한 일부 문의를 고객 셀프서비스로 처리해 상담 대기시간과 운영비용을 줄인다.

단, 위험하거나 공식 근거가 없는 경우에는 자가조치를 제공하지 않아야 한다.

---

### 4.3 현장기사 가치 구체화

현장기사 기능이 발표에서 잠깐 등장하고 끝나, 기사 관점의 장점이 충분히 보이지 않았다.

기사에게 전달할 정보는 다음처럼 구체화할 수 있다.

* 제품·구독 정보
* 증상과 발생 조건
* 고객이 수행한 자가점검 결과
* 상담 내용
* 위험도
* 관련 공식 문서
* 우선 점검 항목
* 예상 점검 후보
* 필요한 장비·부품 후보
* 주의사항

표현상 주의할 점:

> AI가 수리 방법을 확정하는 것이 아니라, 공식 문서에 근거한 우선 점검 후보를 제공하고 최종 판단은 현장기사가 담당한다.

또한 고객용 Mobile, 상담사용 Web, 운영자 Dashboard뿐 아니라 **현장기사용 Mobile·Tablet 화면**도 명확히 구분해야 한다.

## 5. 사업성과 차별성 관련 피드백

### 5.1 경쟁 서비스 벤치마킹 보강

ChatGPT나 범용 CRM과 비교하는 것보다 실제 유사 사업자와 비교하는 것이 적절하다는 의견이다.

검토 대상:

* SK매직·SK인텔릭스
* 코웨이
* 삼성전자
* LG전자
* 기타 렌탈·방문 A/S 서비스

다만 경쟁사의 내부 상담 시스템은 확인할 수 없으므로, 다음 표현은 피해야 한다.

* “경쟁사에는 상담–방문 연계 기능이 없다.”
* “기존 기업은 모두 제품 관리만 한다.”

보다 안전한 차별화 문장:

> Water Bridge는 제품 제어 앱의 대체재가 아니라, 모델·세대가 검증된 공식 문서를 기반으로 고객 문의, 상담, 방문과 후속 결과를 하나의 업무 맥락으로 연결하는 A/S 지원 계층입니다.

---

### 5.2 기업과 고객의 이점을 별도로 제시

최종 발표에서는 다음 두 질문에 직접 답해야 한다.

#### 고객에게 좋은 점

* 설명서와 FAQ를 직접 찾지 않아도 됨
* 같은 증상을 반복 설명하지 않아도 됨
* 위험한 상황에서 즉시 적절한 경로로 안내받음
* 안전한 경우 상담 전에 자가점검 가능

#### 기업에게 좋은 점

* 반복 상담과 문서 탐색 감소
* 불필요한 상담·방문 감소 가능
* 상담과 방문 간 정보 누락 감소
* 재방문 가능성 감소
* 문의·상담·방문 결과를 데이터로 축적 가능

## 6. 발표 방식 관련 피드백

### 6.1 대표 시나리오 1건 추가

기술 용어 중심의 설명보다 실제 문의 한 건을 처음부터 끝까지 보여달라는 의견이 있었다.

예시:

> “정수기에서 탄 냄새가 나고 물이 미지근해요.”

```text
1. 고객 증상 입력
2. 증상 구조화
3. Safety Guard에서 위험 가능성 감지
4. 일반 자가조치 차단
5. 상담 전환
6. 상담 내용과 공식 근거 요약
7. 현장기사에게 사전 리포트 전달
8. 방문 결과 저장
9. 최종 해결 여부 확인
```

이 시나리오 하나로 RAG, Safety Guard, 상태 전이, 상담 요약, 기사 리포트의 관계를 설명할 수 있다.

---

### 6.2 화면별 사용자 명확화

발표 화면의 사용자가 혼동됐다는 의견이 있었다.

슬라이드와 시연에 다음 라벨을 명확히 표시해야 한다.

* 고객용 Mobile
* 상담사용 Web
* 운영 관리자 Dashboard
* 현장기사용 Mobile·Tablet

미구현 화면은 `설계 완료`, `구현 예정`으로 표시해야 한다.

---

### 6.3 어색한 AI 번역체 제거

영어 기술 용어를 억지로 한글화하거나, AI가 생성한 듯한 추상적인 문장이 있다는 지적이다.

수정 원칙:

* 실무에서 영어로 사용하는 용어는 무리하게 번역하지 않음
* 발표자가 설명하기 어려운 조어는 제거
* 추상 명사보다 실제 동작으로 표현
* 영어와 한국어 혼용 형식을 통일

예시:

| 기존 표현          | 수정 권장                  |
| -------------- | ---------------------- |
| 역할성 책임 분리      | 요청 처리와 상태 저장 책임 분리     |
| fail-closed    | 검증 실패 시 요청을 허용하지 않는 방식 |
| artifact drift | 기준 산출물과 재생성 결과의 불일치    |
| 멱등성            | 문맥에 맞는 일반적인 실무 용어로 교체  |

---

## 7. 보안·운영 관련 피드백

### 7.1 외부 API와 로컬 모델 비교

기업은 내부 문서와 고객 정보가 외부 API로 전송되는 것을 부담스러워할 수 있다.

비교 관점:

| 방식         | 장점                        | 한계                 |
| ---------- | ------------------------- | ------------------ |
| 외부 LLM API | 빠른 개발, 높은 성능, 운영 편의       | 비용, 외부 전송, 네트워크 의존 |
| 로컬 모델      | 데이터 통제, 폐쇄망 대응            | GPU·운영비, 성능 검증 필요  |
| Hybrid     | 민감정보 내부 처리, 제한된 생성만 외부 사용 | 구조 복잡도 증가          |

권장 설명:

> MVP에서는 개발 속도와 구조 검증을 우선하되, 실제 기업 도입 시에는 보안 요구와 개인정보 등급에 따라 외부 API, 로컬 모델 또는 Hybrid 구성을 선택할 수 있도록 AI Runtime을 분리합니다.

---

### 7.2 Migration 제외 범위 설명

Migration 과정에서 일부 테이블이 제외됐다는 내용이 있었으나 이유가 설명되지 않았다는 지적이다.

최종 발표 전에 다음을 통일해야 한다.

* 전체 계약 테이블 수
* 현재 Migration 적용 테이블 수
* MVP 활성·검증 테이블 수
* 제외된 테이블과 이유
* 향후 포함 일정
* 전체 흐름에 미치는 영향

예시:

```text
전체 계약 Schema: 32개
MVP 활성·검증 대상: 12개
후속 통합 대상: 20개
```

단, 실제 코드와 자료의 숫자가 정확히 일치하는지 먼저 검증해야 한다.

# 최종 발표 수정 우선순위

## 반드시 수정

1. 기업·고객·상담사·기사별 기대효과와 KPI 제시
2. 현재 구현과 향후 설계의 명확한 구분
3. Rule Engine과 Output Validator 동작 설명
4. 실제 고객 문의 시나리오 1건 추가
5. 모델 1종·공식 문서 1종이라는 MVP 범위 명시
6. 임베딩·생성 모델 선택 근거와 비교 계획 제시
7. 고객·상담사·운영자·기사 화면 구분
8. 경쟁사·유사 서비스 벤치마킹 보강
9. 외부 API와 로컬 모델 적용안 비교
10. 어색한 번역체와 숫자 불일치 수정
11. Migration 제외 범위와 이유 설명

## 가능하면 보완

* 자가 해결 흐름을 별도 강조
* 기사 사전 리포트 내용 구체화
* 모델 성능·비용 비교 실험
* 실제 또는 비식별 VOC 기반 평가
* 상담·방문 업무의 정량 KPI 측정 계획
* 개인정보 마스킹·보관 정책 설명

## 최종 한 문장

> 현재 발표는 기술 구조와 기본 업무 흐름은 충분히 보여줬지만, 기업이 얻는 경제적 효과, 실제 구현 범위, 모델 선택 근거와 역할별 사용자 가치가 약하므로 이를 대표 시나리오와 검증 가능한 KPI 중심으로 보완해야 한다.
