## 1. 총평

중간 발표에서는 고객 문의에서 상담·방문·후속 관리로 이어지는 구조는 전달됐지만, 기업 도입 효과, 현재 구현과 목표 설계의 구분, 모델 선택 근거가 부족했다. 피드백을 이유로 기능 범위를 즉시 확대하지 않고 5주차 구현·검증 업무와 최종 발표 개선 업무로 분리한다.

## 3. 5주차 신규 범위와 기존 결함 분리

### 5주차 제품 구현 범위

- 단일 RAG 기준선과 선택형 책임 분리 비교
- 위험·사용 안내 분류와 근거 없음 Guard
- 제품·세대 Filter 기반 검색과 `EvidenceCardDTO` 조립
- Timeout·Retry·안전 Template·상담 전환 Fallback
- 증상 구조화·추가 질문의 Backend·소비자 연결

### 4주차에서 이관된 선행 결함

- Backend Python 3.13.13 Gate 미복구
- AI 현재 Test와 팀 DB pgvector 미재현
- Mobile SDK Platform Provider 차단
- Backend↔AI 실제 HTTP·Schema·DB 저장 E2E 부재
- 상담·방문 Operation Runtime 부재
- 외부 GitHub Issue와 담당자 회신 미확인

### 최종 발표 개선 항목

- 역할별 KPI와 산정 방법
- 실제 문의 대표 시나리오와 화면 사용자 Label
- 임베딩·생성 모델 비교 결과 또는 비교 전 상태
- 경쟁 서비스 벤치마킹, 외부·로컬·Hybrid 적용안
- 계약·Migration·활성 Table 범위와 제외 이유

## 4. 범위 통제 결정

1. 심사 질문만으로 신규 Agent·Dashboard·제품 모델을 추가하지 않는다.
2. 환경·계약·최소 수직 연결 Gate를 신규 Agent 구현보다 먼저 처리한다.
3. 비교 실험 결과가 없으면 `최적`, `학습 완료`, `전체 E2E 완료`로 표현하지 않는다.
4. KPI 실측값이 없으면 목표·산식·수집 계획만 제시한다.
5. 발표 준비 단계에서 수행하지 않은 리허설·사전 승인은 사후에 소급 작성하지 않는다.

## 5. 판정

발표 피드백은 8개 범주로 분류했고, 5주차 제품 구현·4주차 잔여 결함·최종 발표 개선으로 나눴다. 세부 순서와 완료 증거는 `week5-priority-backlog.md`에서 관리한다.
