## 1. 당시 검토 배경

2026-07-25 기준 ERD 구조는 준비됐지만 다음 여섯 항목의 물리 선택값이
확정되지 않았다.

1. 기본키와 외부 식별자 정책
2. `usage_guidance_status` 물리 필드명
3. 사용 안내 코드 집합
4. 방문 희망일·확정일·일정 상태 저장 방식
5. `FOLLOW_UP_REQUIRED` 포함 여부
6. 계약 YAML·Django Enum·Seed 동기화 방식

이 단계의 `PENDING`은 당시 제안 상태를 뜻하며 현재 구현의 미결
상태가 아니다.

## 2. 제안과 최종 결과

| 결정 주제 | 당시 검토안 | 최종 반영 |
| --- | --- | --- |
| 기본키 정책 | 도메인 문자열 ID 단일 발급 우선 검토 | ADR 0010에서 내부 BigInt PK·외부 UUID·업무 코드 3계층으로 대체 |
| 사용 안내 필드 | `usage_guidance_status`를 canonical 필드로 사용 | 반영됨, `usage_guidance_code`는 반입 별칭 |
| 사용 안내 코드 | `NORMAL`을 canonical 값으로 검토 | 반영됨, `USE_ALLOWED`는 `NORMAL` 반입 별칭 |
| 방문 일정 저장 | 희망일·확정일·상태를 분리 | 반영됨 |
| 방문 상태 | `FOLLOW_UP_REQUIRED` 포함 여부 검토 | 포함한 7개 코드로 반영 |
| Enum·Seed | 계약 YAML·Django Enum·멱등 Upsert 비교 | 해당 방식으로 반영 |

기본키 정책은 최초 제안을 그대로 채택하지 않고 실제 Auth 호환성과
공통 개발 규칙을 대조한 뒤 후속 ADR로 교정했다. 이 변경 경로가 이
보관본을 유지하는 이유다.

- 당시 제안서의 `--require-wbs-complete` 실패 예상은 여섯 선택값이
  미확정이던 시점의 설명이다.
- 현재 검증은 활성 T-005 README와 Physical Contract v1.3에 적힌

  additive Migration으로 기록한다.
