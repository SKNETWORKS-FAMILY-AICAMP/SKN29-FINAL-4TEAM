## 1. 결론

현재 T-022 Slice A 변경은 계약, Runtime, 테스트, 설명 문서의 네 묶음으로
논리 분류할 수 있다. 다만 현재 Diff를 경로만 골라 계약 PR과 Runtime PR로
바로 나누면 중간 Commit의 전체 테스트가 깨질 수 있으므로 아직 Stage하거나
Commit하지 않는다.

특히 다음 두 테스트가 계약과 Runtime을 동시에 본다.

- `test_openapi_runtime_coverage.py`는 OpenAPI Operation의 정확한 개수와
  Django Route·View 존재를 함께 검증한다.
- `test_runtime_examples_contract.py`는 JSON 예시 목록과 실제 Runtime
  Serializer를 함께 검증한다.

따라서 계약 선병합을 지키려면 계약 PR의 중간 상태에서 `submitSymptom`을
`OPENAPI_ONLY`로 판정하는 테스트 변경을 먼저 만들고, Runtime PR에서 다시
Route·View·Serializer 검증으로 전환해야 한다. 이 중간 상태를 만들지 않으면
윤승혁(PM)의 기록된 예외 승인 아래 계약과 Runtime을 한 PR로 검토해야 한다.

## 3. 안전한 게시 후보 구성

사용자가 게시를 승인한 뒤에도 다음 순서를 지킨다.

1. 계약 후보는 OpenAPI·Schema·예시와 계약 전용 테스트로 구성한다.
2. 계약 후보의 중간 상태에서는 `submitSymptom` Runtime을 아직 존재한다고
   검사하지 않도록 교차 계층 테스트를 별도 조정한다.
3. 계약 후보 전체 테스트가 통과하고 PM이 병합한 뒤 Runtime·Serializer·
   Repository·Service와 Runtime 테스트를 별도 후보로 만든다.
4. 설명·인계 문서는 실제 병합된 SHA와 재현 결과를 기준으로 마지막에
   게시한다.
5. 중간 테스트 조정 없이 한 PR로 처리하려면 계약 선병합 원칙의 예외 사유와
   윤승혁(PM)의 승인을 PR에 기록한다.

현재는 위 결정을 받지 않았으므로 `git add`, Commit, Push, PR을 수행하지
않는다.

| 경계 | 자동 증거 | 현재 판정 |
