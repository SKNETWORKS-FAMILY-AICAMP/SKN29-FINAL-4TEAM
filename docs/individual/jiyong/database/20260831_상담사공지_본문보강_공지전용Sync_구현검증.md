# 상담사 공지 본문 보강·공지 전용 Sync 구현 검증

## 1. 목적

상담사 Web의 공지 목록과 상세 화면에서 동일한 한 줄 본문만 표시되던
문제를 보완한다. 공지 상세에는 실제 업무에 필요한 처리 순서와
주의사항을 제공하되, 목록은 첫 문단만 간결하게 표시한다.

전체 Dashboard Seed를 다시 실행하지 않고 공지 6건만 안전하게
Plan·Dry-run·Apply·Replay할 수 있는 Backend 명령도 함께 제공한다.

## 2. 변경 범위

### Backend·DB

- `SYN-WEB-DASH-NOTICE-001~006` 본문을 3개 이상 문단으로 보강
- 대상: `operations_dashboard_notice` 테이블의 합성 공지 6건
- 공지 전용 명령 `sync_consultant_notices` 추가
- 적용 대상 DB명과 Host가 명시적으로 일치할 때만 `--apply` 허용
- 고객·문의·상담·직원·AI 데이터는 조회하거나 수정하지 않음

### Web

- 공지 목록: 본문의 첫 문단만 표시하고 최대 2줄로 제한
- 공지 상세: Backend가 전달한 전체 본문과 줄바꿈을 그대로 표시
- 검색: 기존처럼 전체 본문을 검색 대상으로 유지
- Mock 공지: Backend 합성 공지와 같은 본문으로 정합화

## 3. 공지 구성 원칙

각 본문은 다음 범위에서 작성했다.

1. 공지 목적과 적용 상황
2. 상담사 또는 임직원이 확인할 순서
3. 금지사항과 개인정보 보호 주의
4. 기존 담당 부서로의 문의 또는 공유 기준

실제 점검 시각, 설문 URL, 검진 기관, 개인 연락처처럼 확정되지 않은
운영값은 임의로 만들지 않았다. HTML을 저장하지 않고 일반 텍스트와
줄바꿈만 사용한다.

## 4. 공지 전용 명령

저장소 Root에서 Backend 폴더로 이동한 뒤 실행한다.

```powershell
Push-Location .\backend

# 읽기 전용 변경 계획
.\.venv\Scripts\python.exe manage.py sync_consultant_notices

# 실제 쓰기와 검증을 수행하지만 마지막에 전체 롤백
.\.venv\Scripts\python.exe manage.py sync_consultant_notices --dry-run

# 실제 적용: 현재 연결 대상과 정확히 같은 DB명·Host를 명시해야 함
.\.venv\Scripts\python.exe manage.py sync_consultant_notices `
  --apply `
  --expected-database <현재_DB명> `
  --expected-host <현재_DB_Host>

Pop-Location
```

`--apply` 전에는 반드시 Plan과 Dry-run 결과에서 다음을 확인한다.

- `target_count=6`
- 대상 코드가 `SYN-WEB-DASH-NOTICE-001~006`인지 확인
- 공지 외 데이터에 대한 생성·수정 작업이 없는지 확인
- 적용 후 동일 명령 Replay에서 `updated_count=0`인지 확인

기존 `seed_consultant_dashboard`는 공지 외에 고객·문의·직원 데이터를
함께 준비하므로 공지만 갱신할 목적으로 RDS에서 실행하면 안 된다.

## 5. 로컬 PostgreSQL 실행 결과

검증 대상은 로컬 `127.0.0.1:5432/waterbridge`이며 RDS에는 접근하지
않았다.

| 단계 | 결과 |
| --- | --- |
| Plan | 6건 `UPDATED` 예정 |
| Dry-run | 6건 `UPDATED` 후 전체 롤백 |
| Dry-run 후 재계획 | 동일 Before Hash 유지 |
| Apply | 기존 공지 6건만 `UPDATED` |
| Replay | 6건 모두 `UNCHANGED`, `updated_count=0` |
| API | 로그인·Dashboard·공지 상세 HTTP 200 |
| 상세 확인 | 공지 6건, 첫 공지 265자·7줄·처리 단계 포함 |

적용 후 공지 Snapshot SHA-256은 다음과 같다.

```text

```

## 7. RDS 적용 경계

현재 판정은 `LOCAL_VERIFIED / RDS_NOT_APPLIED`이다.

RDS 적용은 김은진 담당자가 최신 main과 배포 대상 SHA를 고정한 뒤
다음 순서로 진행한다.

1. Backup 또는 복구 가능한 Snapshot 확인
2. `sync_consultant_notices` Plan 실행
3. Dry-run 실행 및 6건 범위 확인
4. 승인된 DB명·Host를 명시해 Apply
5. 동일 명령 Replay에서 6건 `UNCHANGED` 확인
6. 공지 목록·상세 API 200과 화면 표시 확인

비밀번호, Token, RDS Endpoint 등 보호값은 문서나 일반 채팅에 기록하지
않는다. Raw SQL 직접 수정과 전체 Dashboard Seed 실행은 금지한다.

## 8. 최종 판정

```text
local_postgresql=PASS
notice_scope=6_ONLY
dry_run_rollback=PASS
apply_replay=PASS
backend_api=PASS
web_rendering=PASS
rds_apply=HOLD_UNTIL_DEVOPS
```
