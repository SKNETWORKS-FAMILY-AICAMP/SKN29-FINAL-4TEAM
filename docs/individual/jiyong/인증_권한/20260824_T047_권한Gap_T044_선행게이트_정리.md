## 1. 결론

T-047은 기존 Customer·Consultant API의 역할·소유권 검사가 상당 부분
구현됐지만, 방문기사 객체 권한과 T-044 사후관리 Runtime이 없어 완료할 수
없다. 이번 단계에서는 Production 코드를 추측 구현하지 않고 Gap Matrix와
선행조건만 고정한다.

## 2. 현재 권한 Matrix

| 영역 | 현재 역할 경계 | 객체 경계 | 판정 |
|---|---|---|---|
| 고객 구독·케어 | 활성 CUSTOMER | 본인 소유 구독 | 구현·테스트 존재 |
| 고객 문의·문진·안내 | 활성 CUSTOMER | 본인 Inquiry, 타 고객 404 | 구현·테스트 존재 |

## 3. T-047 잔여 Gap

현재 구현 범위의 역할·소유권·상담·방문·운영자 표적 검증은
`102 passed / 3 PostgreSQL-only skipped`다. 이는 아래 잔여 Runtime까지
완료됐다는 뜻은 아니다.

1. 기사에게 배정된 Visit만 목록·상세 조회
2. 미배정 Visit의 기사 접근 차단
3. 다른 기사에게 배정된 Visit의 존재 은닉 404
4. Start·Complete의 `state_version` 409와 동일 요청 Replay
5. 역할 전체 Matrix의 실제 HTTP 인수 검증
6. 방문 완료 뒤 케어 이력·다음 일정 연계 검증

위 1~4는 Mobile 화면만으로 대신할 수 없고 Backend Runtime이 필요하다.

## 4. T-044 선행조건

WBS상 T-044는 T-019와 T-043 이후 작업이다.

- T-019: 케어 이력 Runtime
- T-043: 방문기사 실제 처리 흐름·인계 결과
- T-044: 방문 결과를 케어 이력에 반영하고 다음 일정을 갱신

현재 `visit_completion_service.py`는 구현 본문이 없는 상태다. 따라서 지금
T-044를 완료 처리하거나 임의 결과코드·일정 계산을 넣으면 안 된다.

## 5. T-044 구현 착수 입력

다음 항목이 실제 실행 증거로 도착한 뒤 구현한다.

1. 동일 `visit_id`와 배정 `technician_id`
2. 방문 시작·완료 요청의 `state_version`
3. 승인된 방문 결과 코드와 공개 필드
4. 동일 요청 Replay 기대값
5. 완료 후 생성할 CareRecord Type과 Data Source
6. 다음 Care Schedule 계산에 사용할 승인 Rule

## 6. 안전한 후속 순서

1. Mobile 담당자가 T-043 결과와 실제 Payload를 인계
2. 최지용이 T-044 Service·Transaction·Idempotency를 구현
3. 기사 객체 권한 Route와 Test를 추가
4. PostgreSQL에서 동시 완료·Replay·Rollback 검증
5. 김은진이 타 기사 접근·409·중복·일정 갱신을 독립 QA
6. T-047과 T-044를 각각 판정한 뒤 통합 E2E 진행

이번 문서는 `web/**`, `mobile/**`, `ai/**`, `data/**`, Workflow와 기존
Migration을 수정하지 않는 준비 문서다.
