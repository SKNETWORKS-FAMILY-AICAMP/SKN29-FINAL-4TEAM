# 데이터베이스 Schema·Migration 구현 가이드

> 관련 업무: 데이터 설계·물리 구현
> 책임: 최지용 — Backend·Database

## 1. Source of Truth

DB 구조는 다음 순서로 판단한다.

1. 승인된 데이터 계약과 ADR
2. Django Model
3. Django Migration
4. PostgreSQL 실제 Schema
5. Validator·Readiness Audit

문서의 과거 테이블 수나 작업률로 현재 구현을 판정하지 않는다.

## 2. 구현 원칙

- 업무 식별자는 `public_id` UUID를 사용하고 내부 PK를 공개하지 않는다.
- FK·Unique·Check·Index는 Model과 Migration에 함께 반영한다.
- 공통코드는 Registry와 DB 제약의 허용값을 일치시킨다.
- 상태 이력·감사·멱등 원장은 Runtime Transaction과 함께 저장한다.
- 확장 테이블은 미사용이어도 승인된 계약에서 임의 삭제하지 않는다.
- Data Migration은 Forward·Reverse·Replay 가능성을 검토한다.

## 3. 변경 순서

1. 요구사항·계약·소비자 영향 확인
2. Model 최소 변경
3. 새 Migration 생성
4. SQL·제약·인덱스 검토
5. 빈 PostgreSQL Forward 적용
6. 데이터 보존·Backfill 확인
7. Reverse 또는 명시적 비가역 판정
8. drift·표적·전체 회귀

```powershell
Set-Location .\backend
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py migrate --plan
.\.venv\Scripts\python.exe manage.py migrate --noinput
.\.venv\Scripts\python.exe manage.py check
```

## 4. Migration 불변성

이미 적용된 Migration 파일을 수정하지 않는다. 과거 Migration의 오류는 새
교정 Migration으로 해결한다. 적용 이력과 파일 Hash가 다르면 다음 순서로
중단한다.

1. 대상 DB와 적용 Migration 확인
2. 코드·DB 백업 가능 여부 확인
3. 임의 `fake`·행 삭제 금지
4. 새 Migration 또는 승인된 복구 절차 작성
5. 빈 DB와 기존 데이터 DB에서 각각 재현

## 5. Runtime 지원 테이블

계약 테이블 외에 Lock·원장·감사 같은 지원 테이블이 필요하면 Readiness
Auditor의 허용 목록과 테스트도 함께 갱신한다. Model만 추가하거나 Auditor를
우회하지 않는다.

## 6. 필수 검증

| 검증 | 성공 조건 |
| --- | --- |
| Schema Validator | Table·Column·FK·Code 불일치 0 |
| Readiness Audit | blocker 0 |
| Fresh Apply | 빈 PostgreSQL 적용 성공 |
| Existing Apply | 기존 데이터 보존 |
| Reverse/Reapply | 지원 범위에서 성공 |
| Drift | `No changes detected` |
| Concurrency | PostgreSQL 실제 Row Lock 검증 |
| Secret·PII | Schema·로그·Fixture 노출 없음 |

## 7. 금지사항

- 공유 DB에서 승인 없는 Migration·Rollback·Seed 실행
- 기존 Migration 내용 수정
- SQLite 결과만으로 PostgreSQL 제약 PASS 선언
- FK 오류를 제약 삭제만으로 해결
- 운영 데이터나 개인 식별정보를 Fixture로 사용

## 8. 완료 판정

Model·Migration·Registry가 일치하고 빈 DB·기존 DB·Rollback 경계·전체 회귀가
확인되면 작성자 구현 완료다. 독립 QA와 PM 판정은 별도다.
