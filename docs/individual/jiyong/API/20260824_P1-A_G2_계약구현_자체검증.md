## 1. 목적

윤승혁(PM)의 조건부 정책 결정과 양정현(Mobile)의 Android 계약 검토를
기계 판독 가능한 OpenAPI 검토 계약으로 반영하고, 기존 계약과 P1-A Candidate
검증을 깨뜨리지 않았는지 확인한다.

## 2. 반영한 정책

- OTP 유효시간 300초
- OTP 재전송 대기 60초
- OTP 최대 실패 5회 후 Challenge 폐기
- 비밀번호 12~64자, 영문·숫자 필수, 특수문자 선택
- 이용약관·개인정보 수집 이용 필수, 마케팅 선택
- 계약·계정 존재 여부 외부 비노출
- P1-A 범위를 합성 고객 ID/PW·OTP·계정연결·로그인·복구로 제한

## 3. 계약 구현 내용

다음 9개 Operation을 `IN_REVIEW / NOT_IMPLEMENTED`로 추가했다.

1. 계약 확인 Challenge 생성
2. 계약 확인 OTP 검증
3. 회원가입
4. ID/PW 로그인
5. 아이디 찾기 Challenge 생성
6. 아이디 찾기 OTP 검증
7. 비밀번호 재설정 Challenge 생성
8. 비밀번호 재설정 OTP 검증
9. 비밀번호 재설정 확정

세 OTP 검증 주소는 모두 다음 규칙을 사용한다.

```text
.../challenges/{challenge_id}/verify
```

회원가입과 로그인 성공 응답은 기존 `LoginResponse`를 재사용한다.

## 4. 비노출 오류 경계

Challenge 생성은 계약 후보 존재 여부와 관계없이 다음 결과를 사용한다.

```text
HTTP 202
challenge_id
expires_in=300
resend_after=60
일반 안내 문구
```

전체·마스킹 이메일, 계약·계정 존재 여부는 반환하지 않는다. Challenge 생성
Operation에는 계약 후보 없음 `404`가 없다.

OTP·Ticket 실패는 `AUTH_VERIFICATION_FAILED`, ID/PW 로그인 실패는
`AUTH_LOGIN_FAILED`로 일반화했다. 사용 불가능한 ID와 가입 충돌도 다른
계정의 실제 존재 이유를 노출하지 않는다.

## 5. Mobile 연동 보강

- `claim_ticket`, `reset_ticket`은 JWT와 분리해 요청 Body에 넣는다.
- Ticket·OTP·Password는 로그·감사 이벤트·영구 저장 대상이 아니다.
- `422`는 안전한 `details.fields`를 사용한다.
- `429`는 `Retry-After`와 `details.retry_after_seconds`를 사용한다.
- 기존 Mobile `SessionResponse`와 Backend `LoginResponse` 필드가 일치한다.
