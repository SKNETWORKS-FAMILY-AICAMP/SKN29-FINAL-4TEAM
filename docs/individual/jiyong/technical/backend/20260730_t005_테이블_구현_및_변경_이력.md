## 3. 구현 순서와 공통 규칙

모든 Wave는 다음 순서를 반복했다.

1. 활성 Physical Contract·Decision Register·테이블 사전·코드 계약을
   대조한다.
2. 부모 FK와 Migration leaf를 확인한다.
3. Model·Runtime export·번호 Migration을 같은 변경 단위로 만든다.
4. `makemigrations --check --dry-run`으로 drift 0을 확인한다.
5. SQLite 집중 테스트와 전체 Migration을 실행한다.
6. 격리 PostgreSQL에서 Catalog·유효/위반 쓰기·rollback·reapply를
   검증한다.
7. Seed·Importer·Data QA 영향이 있으면 즉시 재생성하고 해시를
   확인한다.
8. 해당 Wave 회귀가 통과한 뒤 다음 자식 Wave로 이동한다.

공통 식별자는 내부 자동 증가 bigint PK, 공개 UUID, 별도 업무 식별자의
3계층을 유지했다. FK·UNIQUE·CHECK·Index는 설명에만 두지 않고
Migration DDL에 포함했다. 승인되지 않은 상태·위험·검토 코드는 open
문자열과 최소 비공백 제약만 적용하고 후보 literal을 임의 고정하지
않았다.

## 4. 주요 연쇄 오류와 보존한 결정

### 4.1 Seed 충돌과 적용 순서

Wave 1A·1B 체크포인트에서 다음 연쇄 오류를 확인했다.

- 문진 Seed의 구독 참조가 실제 bigint FK가 아닌 과거 문자열을 사용했다.
- Demo CustomerProfile을 고객번호로만 찾으면 같은 User의 Profile
  UNIQUE가 충돌했다.
- Data Crosswalk는 Model·Importer 변경 뒤 승인 소스 해시를 다시
  생성해야 했다.

수정 원칙은 FK를 실제 부모 식별자로 해석하고, Profile을 고유 User로
Upsert하며, 소스 해시는 공식 도구로 승인 파일만 갱신하는 것이다.
최종 5종 Seed 2회에서 두 번째 실행의 신규 생성은 0이었고, Importer
Replay는 355 unchanged·12 projected였다.

### 4.2 문진·문의 복합 FK

QuestionnaireSession과 Inquiry는 각각 Subscription을 참조하므로 단일
Inquiry FK만으로 동일 구독을 보장할 수 없다.

```text
support_inquiry
  UNIQUE (id, subscription_id)
        ▲
        │ PostgreSQL composite FK
support_questionnaire_session
  (inquiry_id, subscription_id)
```

PostgreSQL은 `fk_questionnaire_inquiry_subscription`으로 raw write까지
차단한다. SQLite와 Model은 보조 검증을 사용한다. 역Migration은 자식
복합 FK를 먼저 제거한 뒤 부모 후보키를 제거한다.

### 4.3 상태 이력과 Migration 불변성

`workflow.0004`는 UUID Bridge backfill, 테이블명 정렬, 정확히 한 대상,
대상별 version UNIQUE와 4개 trace Index까지 담당한다. 이미 적용한
`0004`에 후속 CHECK 이름과 일반 Index를 덧붙인 것은 결함이었다.

`0004`를 실제 적용 상태로 복원하고 이름·일반 조회 Index 변경을
`workflow.0005`로 분리했다. clean PostgreSQL과 기존 History 125건·
AuditEvent 125건 DB에서 forward·rollback·reapply 후 행 Hash와 FK
연결이 보존됐다. 상세 사고 근거는
[Migration 불변성 사고 및 복구 보고서](t005_마이그레이션_불변성_사고_및_복구_보고서.md)에
유지한다.

### 4.4 pgvector 1024차원

`knowledge_chunk_embedding`은 `BAAI/bge-m3` 원본 출력과 맞춘
1024차원 `vector`를 사용한다. 임베딩이 다른 본문 버전을 참조하지
않도록 `(chunk_id, content_sha256)` 복합 FK를 사용한다.

- Migration이 `vector` 확장과 테이블을 재현 가능하게 생성한다.
- MVP 검색은 HNSW·IVFFlat 없이 Exact Search를 사용한다.
- SQLite는 구조적 fallback을 사용하고 PostgreSQL 전용 Catalog·거리
  검색은 별도 테스트한다.
- apply → rollback → reapply에서 확장·테이블·복합 FK가 일관되게
  복원돼야 한다.

### 4.5 EvidenceLink 다중 문맥 무결성

EvidenceLink는 Guidance·Consultation·HandoffReport 중 정확히 하나를
대상으로 삼는다. 대상별 청크·역할 중복과 표시 순서 중복을 각각 부분
UNIQUE로 막는다.

RetrievalHit를 연결할 때 hit·run·chunk·AI Run 문맥을 함께 검증한다.
PostgreSQL은 복합 FK, SQLite는 Trigger, Model은 `clean()` 선검증을
사용한다. `clean()`은 raw SQL·`QuerySet.update()`에 자동 적용되지
않으므로 Importer와 Service도 명시적으로 검증해야 한다.

## 5. 의도적으로 보류한 계약

| 범위 | 보류 이유 | 후속 조건 |
| --- | --- | --- |
| 위험도 소문자↔대문자 | 코드 계약과 DB CHECK 충돌 | 계약 담당자 값·소비자 영향 승인 |
| Guidance review·evidence sufficiency | 상태집합·전이 미승인 | YAML·Service 권한·기존 데이터 정규화 |
| Handoff 상태·payload | 사전 인계 원천과 확인 규칙 없음 | PM·AI·Importer 계약 |
| VisitResult cause category·결과 매핑 | 방문 결과 의미와 멱등키 미승인 | 방문 업무·Data 매핑 |
| Retrieval applicability·selection origin | 후보 code만 존재 | 계약 버전·소유자 승인 |
| 승인 후 불변 정책 | APPROVED 의미·권한·예외 미승인 | Service·API 계약과 함께 적용 |

보류 항목은 기술적 32/32 테이블 존재와 분리한다. 계약이 확정되면
기존 Migration을 수정하지 않고 탐색·정규화·제약 추가를 새 Forward
Migration으로 적용한다.
