### 0.3 Python 3.10.20 호환성 검증

Windows CPython `3.10.20`으로 다음을 직접 확인했다.

```text
ai/**/*.py 구문 검사: 138 files, syntax_errors=0
requirements.lock Pin: 84
Python 3.10 Resolver 결과: 85 packages
pip check: No broken requirements found
AI 전체 테스트: 50 passed, 1 skipped, 3 warnings in 4.08s
```

`1 skipped`는 `AI_VECTOR_DSN`과 `AI_EMBEDDING_REVISION`이 없는 경우
의도적으로 건너뛰는 Live pgvector 통합 테스트다. 따라서 Python 3.10.20
문법·Windows Wheel·현재 AI 테스트 호환성에는 차단 문제가 없다.

다만 `requirements.lock`의 “전체 transitive 고정” 표현은 정확하지 않다.
Lock에는 84개 Pin이 있으나 `torch==2.13.0`이 요구하는
`setuptools>=77.0.3`가 없다. 새 Resolver는 `setuptools==83.0.0`을
추가 선택했고, 실제 생성한 Venv는 번들 `setuptools==79.0.1`을
그대로 사용했다. 둘 다 요구 범위를 만족해 실행은 되지만 설치 결과가
하나로 고정되지는 않는다. Hash Pin과 플랫폼 Marker도 없고 첫 줄에
Windows 검증용임을 명시하므로, Linux 배포까지 같은 Lock으로 보증할 수
없다.

현재 AI 전용 Python 3.10 CI가 없고 `ai/Dockerfile`도 설명 주석만
존재한다. 이는 원 10.1의 직접 완료 조건은 아니지만, 배포 단계에서는
별도 Linux/CPU Lock과 실행 가능한 Container 검증이 필요하다는
후속 위험으로 남긴다.

### 0.4 계약 ↔ Runtime 잔여 반례

아래에는 동일한 Python 3.10.20 환경에서 확인한 Schema 거부/Pydantic
수락 반례 6종과 Runtime 매핑 부재 1종을 함께 정리했다.

| 대상 | 반례 | JSON Schema | Pydantic |
|---|---|---|---|
| `MissingField` | 빈 `field_name`·`reason`, `importance="urgent"` | 거부 | 수락 |
| `FollowUpQuestion` | `options` 11개 | 거부 | 수락 |
| `EvidenceReference` | `page_refs=[0]` | 거부 | 수락 |
| `AIErrorResponse` | Schema상 필수지만 Nullable인 식별·상태 필드 4종 생략 | 거부 | 수락 |
| `ModelMetadata` | 빈 모델·Prompt Version, 음수 Token·Latency | 거부 | 수락 |
| `ProcessingTrace` | 101자 `error_code` | 거부 | 수락 |
| `ValidationResult` | 계약 Schema는 존재 | 해당 없음 | 대응 Runtime 모델 없음 |

원인은 다음과 같다.

- `ai/app/schemas/symptom.py`의 `MissingField`와 `FollowUpQuestion`에는
  계약의 길이·Enum·배열 최대 길이가 없다.
- `ai/app/schemas/retrieval.py`의 `page_refs`에는 페이지 최소값 1이 없다.
- `ApiErrorResponse`는 계약에서 Key 존재를 요구하는 Nullable 필드를
  Pydantic에서는 생략 가능한 기본값으로 선언한다.
- `ModelMetadata`와 `ProcessingTrace.error_code`의 계약 경계가 Runtime에
  반영되지 않았다.
- `ValidationResult.schema.json`에 대응하는 Pydantic 모델을 찾을 수 없다.

현재 테스트도 이 차이를 잡지 못한다. 증상 분석 정상 예시는 JSON Schema만
검사하고, 오류·근거 Negative 테스트는 Pydantic만 검사한다. **같은
Payload를 JSON Schema와 Pydantic 양쪽에 넣어 수락/거부 결과가 같은지
비교하는 전체 Parity Matrix**가 필요하다.

### 0.5 Timeout·Retry·구조화 로그 재검증

협력적 취소는 이전보다 개선됐다. HTTP Timeout 시 Token을 설정하고,
Embedding 실행 중 취소됐다면 Embedding 반환 뒤 Token을 재확인해
새 DB Query와 다음 Stage 진입을 막는다. 실제 Slow Embedding 반례
결과는 다음과 같다.

```text
취소 50ms 후: worker_alive=true, store_calls=0
Embedding 반환 후: worker_alive=false,
exception=PipelineCancelledError, store_calls=0
```

이 반례에서는 취소 뒤 DB 진입을 막았지만, 이미 실행 중인 Embedding
작업은 HTTP 504 뒤에도 반환할 때까지 계속된다. 또한 취소가
`store.search()` 진입 뒤 발생하면 Token이 Store에 전달되지 않으므로
진행 중 DB Query를 취소하지 못하고 PostgreSQL 5초 Statement Timeout에
의존한다. 실행 중 Embedding·LLM·DB까지 중단하려면 취소 가능한 외부 API
Timeout·별도 Process·DB Cancel 등의 실행 경계를 사용해야 한다. 현
구조를 유지한다면 잔여 위험과 동시 실행 자원 상한을 문서화하고 PM의
명시 승인을 받아야 한다.

구조화 로그도 완료로 보기 어렵다.

```text
기본 effective log level=WARNING(30)
INFO enabled=false
watercare.ai.analysis handler=0
잘못된 UUID 422: 구조화 로그 0건
Header/Body correlation 불일치 400: 구조화 로그 0건
```

성공 경로 테스트는 `caplog`가 Logger를 강제로 INFO로 바꿔 통과한다.
현재 `AI_LOG_LEVEL=INFO`는 설정 파일에만 있고 Bootstrap에서 소비하지
않는다. Request Validation Handler와 최초 로그 이전에 발생하는
Header 불일치 경로에도 `analysis_failed` 로그를 추가해야 한다.

### 0.6 검색 안전성·pgvector 재검증

다음 개선은 실제 코드와 결과 파일에서 확인했다.

- Allowlist 밖 모델과 `D` 이외 세대를 Embedding·DB Query 전에 차단
- `PGVECTOR_QUERY=7`, `POLICY_BLOCK_*=5`로 실행 경로 분리
- PostgreSQL 16.14, pgvector 0.8.6, 7행, 1024차원
- 평가 12/12, Positive Recall@5 1.0, MRR
  `0.8857142857142858`, 금지 혼입 0
- DDL/UPSERT 분리와 검증 Fixture Transaction Rollback

그러나 `VectorSearchService`는 Store가 반환한 Chunk를 그대로 반환한다.
가짜 Store가 다음 잘못된 Chunk를 반환하도록 한 반례에서도 1건이 그대로
통과했다.

```text
model_code=WRONG
product_generation=S
verification_status=unverified
allowed_use=false
returned_count=1
```

실제 `PgVectorStore` SQL에는 사전 필터가 있지만 Adapter 교체·회귀·잘못된
Store 구현을 막는 검색 후 방어 검증이 없다. `ProductFilter`와
`DocumentPolicyFilter`도 실제 검색 반환 경로에서 사용되지 않는다.

평가 스크립트는 기대 Chunk ID·Document ID·Page를 확인하지만
`document_version`, `embedding_model_revision`, 결과별 제품 세대를 직접
검증하지 않는다. 현재 저장 Row/`RetrievedChunk`에도 Embedding Revision,
Index Version, Chunk Set Hash를 연결하는 Provenance 필드가 없다.
`index_manifest.json`에 Revision이 있다는 사실과 검색 결과가 그
Revision으로 생성됐다는 검증은 서로 다르다.

현재 팀 DB는 `postgres:16.14-bookworm` Container가 정상 실행 중이지만,
읽기 전용 조회에서 `vector` Extension은 설치돼 있지 않고 사용 가능한
Extension 목록에도 없다. T-005 감사 결과는 `NOT_READY`, `12/32`
구현이며 지식·RAG·AI 운영 관련 11개 Table은 모두 미구현이다. 따라서
격리 pgvector 실증과 팀 DB 통합 완료를 계속 분리한다.

### 0.7 2차 재회신에서 받을 완료 증거

이동윤은 다음 범위만 보완해 회신한다.

1. 회신의 `PENDING_COMMIT`을 실제 구현 SHA
   `80265738c28446b7b817c4edbae3c82eb1ae9e99`로 바꾸고,
   `main` 병합 SHA
   `af704969989265e914f3e4c9aa7062c55e52065a`를 함께 적는다.
2. 위 6개 계약 반례를 Runtime이 거부하도록 고치고
   `ValidationResult`의 Runtime 대응 여부를 결정한다.
3. 모든 공통·요청·응답 Schema에 대해 동일 정상·경계·위반 Payload를
   JSON Schema와 Pydantic 양쪽에서 검증하는 Parity Matrix를 추가한다.
4. 운영 Bootstrap에서 `AI_LOG_LEVEL`을 실제 적용하고 성공·422·
   Header 불일치·Timeout·내부 실패 모두에 같은 `correlation_id`를
   가진 구조화 로그가 남는지 검증한다.
5. 실행 중 Embedding/LLM을 실제로 중단할 실행 경계를 마련하거나,
   협력적 취소의 한계를 수치·자원 상한과 함께 기록해 PM 승인을 받는다.
6. 검색 결과에 제품 모델·세대·검증 상태·`allowed_use` 후검증을 적용하고,
   DB Row 또는 Index Build ID에 Provenance를 저장한 뒤 평가에서
   Document/Embedding Revision을 실제 DB 결과와 대조한다.
7. `requirements.lock`에 누락된 `setuptools`를 포함하고 생성 도구·
   Python·OS·플랫폼 범위를 기록한다. 배포용 Lock은 Windows 개발용과
   구분한다.
8. 기존 인계보고서·Walkthrough의 AI `8000`, 개인 절대 경로,
   `PENDING_COMMIT`을 최신 기준으로 정리하거나 문서 상단에
   `SUPERSEDED`와 최신 회신 링크를 명시한다.

반대로 Public UUID, 요청 기본 제약, AI `8001`, 실제 검색 전 Allowlist,
DB Query/정책 차단 분리, 다중 페이지 보존, DDL/UPSERT 분리,
Disposable Guard·Rollback은 다시 구현할 필요가 없다.

## 1. 한 줄 인계

이동윤의 1차 보완 구현은 수령했고 Python 3.10.20 실행 호환성도 확인했다.
그러나 전체 계약 Parity, 운영 구조화 로그, 실행 중 작업 취소, 검색 결과
후검증과 Revision Assertion이 남아 **부분 수용·2차 재반송**한다.
최지용의 `backend/integrations/ai/**`와 팀 DB Wave는 이 잔여 AI 입력을
닫은 뒤 진행한다. AI 테스트 통과와 격리 pgvector PASS는 여전히
Backend-AI 통합 완료 증거가 아니다.

- `ai/configs/retry_policy.yaml`에는 전체 30초, AI 내부 최대 1회,

  수준이다.

  코드가 다르다.
- AI 오류 응답의 `correlation_id` 전달 기준이 확정되지 않았다.
- AI 기본 Port 8000과 Backend의 `AI_SERVICE_BASE_URL` 8001 설정이
  충돌하므로 서비스별 Port·Endpoint 확정이 필요하다.

### RAG 현재 범위

현재 검색은 샘플 텍스트 기반이고 실제 pgvector Exact Search 증거가
없다. 고정 샘플·예시 URL·비표준 문서 Hash가 남아 있으므로
`실제 RAG 완료`로 인계하지 않는다. 이번 문서 작성 과정에서는 AI 전체
테스트를 재실행하지 않았으므로 기존 보고서 수치를 현재 통과 증거로
사용하지 않는다.

   - Backend `8000` / AI `8001` 또는 팀이 결정한 조합을

3. **Timeout·Retry·로그 주장을 Runtime과 맞춘다.**
   - AI 내부 재시도를 실제 구현하지 않을 경우 “최대 1회”와 “실제 0회”를
     구분하고, 구현할 경우 전체 30초 안에서만 동작하게 한다.
   - Timeout 이후 Worker·LLM·DB 작업이 계속되지 않도록 취소 가능한
     하위 호출 Timeout 또는 작업 취소 방식을 검증한다.
   - `correlation_id`, `ai_request_id`, `state_version`, Stage,
     실제 `retry_count`, latency를 구조화 로그로 남기되 원문·Prompt·

4. **검색 안전성 검증을 보강한다.**
   - 지원 모델 Allowlist를 단위 테스트에만 두지 말고 실제 검색 진입
     경로에서 강제한다.
   - “실제 DB Vector 검색 Case”와 “DB 검색 전 정책 차단 Case”를 분리해
     지표를 보고한다.
   - 문서 ID·Revision·페이지·청크·제품 세대가 기대값과 같은지
     Assertion하고, 다중 페이지 참조를 단일 시작 페이지로 축소하지 않는다.
5. **팀 DB용 인덱싱·검증 모드를 분리한다.**
   - `build_vector_index`가 팀 DB에서 `CREATE EXTENSION/TABLE`을 실행하지
     않도록 Schema 초기화와 UPSERT를 분리한다.
   - 팀 DB의 기존 전체 행 수가 7개라고 가정하지 말고 배치·문서·청크
     범위로 적재 결과를 검증한다.
   - `verify_pgvector_runtime`의 검증 Fixture 삽입·삭제는 공유 DB에서
     금지한다. Disposable DB/Schema, 명시적 DB 식별 Guard와 Transaction
     Rollback을 사용한다.

### 10.2 최지용·공동 후속 진행사항

#### A. 계약·인프라 결정

1. 최지용과 윤승혁(PM)은 통합 오류 Registry에
   `AI-VALIDATION-01`, `AI-TIMEOUT-01`을 편입하고 HTTP·`retryable`·
   Fallback 의미를 승인한다.
2. `contracts/codes/**` 주관인 최지용과 부관할 윤승혁(PM)이
   `official_verified`, `team_verified`를
   `contracts/codes/verification-statuses.yaml`에 확정한다. 이동윤은
   AI Runtime 소비자로 검토하고 DB `TextChoices`·테스트가 같은 값을
   쓰게 한다.
3. 김은진(Infra)과 팀 DB의 pgvector 제공 방식을 정한다. 현재
   `docker-compose.yml`은 일반 `postgres:16.14-bookworm`이고 Backend
   환경에는 Python `pgvector` 패키지가 없다. 정확한 pgvector Version
   Tag와 Image Digest를 고정한 공식 Image 또는 검증된 Custom Image와
   Backend 의존성 Manifest를 먼저 마련해야 한다.
4. Backend 기본 Port는 `8000`, AI는 `8001`로 예약하고 Backend의 대체
   Port는 `8001` 이외 값으로 정해 README·Smoke Script를 함께 수정한다.

#### B. T-005 정식 Model·Migration

격리용 `ai_rag_chunks` 단일 테이블을 팀 DB에 복사하지 않는다. T-005의
정규화된 다음 구조에 매핑한다.

```text
knowledge_source_document
→ knowledge_document_page
→ knowledge_document_chunk
→ knowledge_chunk_embedding vector(1024)

knowledge_document_model_scope
knowledge_ingestion_batch
knowledge_data_quality_issue
knowledge_evidence_link

aiops_ai_run
→ aiops_retrieval_run
→ aiops_retrieval_hit
```

구현 순서는 다음과 같다.

1. ERD·테이블 사전·T-005 계약에 맞는 Django Model과 FK·UNIQUE·CHECK·
   SHA-256·활성 상태·버전 필드를 먼저 확정한다.
2. Django Migration에서 `vector` Extension과 1024차원 Vector Column을
   생성한다. 수동 SQL만으로 팀 DB를 맞추지 않는다.
3. AI 적재 계정은 필요한 Table의 `INSERT·UPDATE·SELECT`만, Backend는
   조회·업무 저장 권한만 갖게 하고 AI 계정에는 DDL 권한을 주지 않는다.
4. 적용 전 Backup, 빈 PostgreSQL 적용, 역방향/복구 절차, Seed·UPSERT
   2회, Migration 재적용을 검증한다.
5. 이 Wave가 끝난 뒤 T-005 감사기의 관련 Table을
   `MISSING`에서 `IMPLEMENTED`로 바꾸되, 전체 32개 완료와 혼동하지 않는다.

#### C. Backend AI Adapter·Evidence

1. `backend/integrations/ai/**`에 실제 HTTP Client, Request/Response
   Mapper, JSON Schema Validator, 30초 Timeout, Backend 자동 재시도
   0회와 표준 Exception Mapping을 구현한다.
2. Public UUID `inquiry_id`, `correlation_id`, `ai_request_id`,
   `state_version`을 보존하고 늦게 도착한 결과는 현재 버전과 비교해
   폐기 또는 재처리한다.
3. 같은 `ai_request_id`의 동일 Payload는 멱등 재생하고 다른 Payload
   재사용은 409로 차단한다.
4. `backend/apps/evidence/**`와 AI 실행·검색 이력 Model을 등록하고
   Migration을 만든다. AI가 반환한 `EvidenceReference`를 Backend가
   검증한 뒤 최종 `EvidenceCard`와 업무 이력으로 저장한다.
5. AI 결과는 제안값으로만 소비하며 권한·상태 전환·최종 DB 기록은
   Backend Service·Guard·Transaction이 수행한다.

#### D. 공동 인수 테스트

다음 항목이 같은 Commit과 같은 계약 버전에서 모두 통과해야 최종 완료다.

1. Disposable PostgreSQL에 전체 Migration 적용·Rollback·Restore
2. 승인 7청크 UPSERT 2회 후 중복 0, Vector 1024차원 확인
3. 실제 DB 검색과 정책 차단 Case를 분리한 평가, P0 Recall@5 전부 통과
4. 잘못된 모델·세대·미검증·사용 금지 근거 혼입 0
5. 정상·위험·근거 없음·Schema 오류·Timeout Backend→AI HTTP E2E
6. Header·Body·Backend 로그·AI 로그·DB 이력의 `correlation_id` 일치
7. 중복 `ai_request_id`, stale `state_version`, Timeout 후 작업 지속 차단
8. Prompt·내부 경로·API Key·Token·개인정보 비노출 자동검사
9. Branch, 40자리 SHA, Dirty 여부, 명령, 실행 시각, Exit code와 결과
   파일 보존

### 10.3 최종 마무리 조건

이동윤 반송 보완, 팀 DB 정식 Migration, Backend Adapter·Evidence,
공통 Registry 승인과 공동 E2E가 모두 끝나면 판정을
`BACKEND_AI_INTEGRATION_COMPLETE`로 바꾼다. 그 전까지는

## 11. 금지·주의사항
