# PM 승인 계약고객 이메일 OTP 로컬 E2E 구현·검증

## 1. 문서 목적

PM이 승인한 팀 내부 시험 수신자 6건을 이용해 고객 앱의 회원가입,
로그인, 아이디 찾기, 비밀번호 재설정을 로컬 PostgreSQL과 실제 이메일
수신으로 확인할 수 있도록 Backend·DB 경계를 구현하고 검증한 내용을
정리한다.

이 문서는 실제 이름, 전화번호, 이메일, OTP, SMTP 앱 비밀번호 등
개인정보·Secret을 기록하지 않는다.

## 2. 승인·작업 범위

- 승인 근거: 사용자가 전달한 PM의 팀 내부 로컬 E2E 명시적 승인
- 구현 범위: `backend/**`, Accounts 모델·서비스·Migration·Seed·테스트
- 실행 범위: 로컬 PostgreSQL, 로컬 Django Backend, OTP Outbox Worker
- 확인 범위: 최신 main의 고객 Mobile 앱 빌드·Galaxy Tab 설치·API 연결
- 제외 범위: Mobile·Web·AI 소스 수정, AWS 배포, 운영 실주소 발송
- AI Runtime 8001은 이동윤 담당 작업 이후 별도로 확인한다.

## 3. 핵심 설계

### 3.1 기존 합성 Fixture 보존

기존 `.invalid` 합성 계약 이메일은 계속 `synthetic` 분류와
`RUNTIME_REDIRECT_ONLY` 정책만 사용한다. 기존 Fixture와 Redirect 시험
흐름을 실제 수신자 시험 때문에 완화하지 않았다.

### 3.2 PM 승인 시험 수신자 분리

승인된 로컬 시험 이메일에는 다음 전용 조합을 추가했다.

| 항목 | 값 |
|---|---|
| 데이터 분류 | `approved_test_pii` |
| 발송 정책 | `APPROVED_TEST_RECIPIENT` |
| 허용 환경 | `DEBUG=True` 로컬 환경 |
| 승인 표시 | `--pm-approved-local-e2e` 필수 |

모델 검증과 DB Check Constraint가 분류·정책의 잘못된 조합을 거부한다.
운영 또는 DEBUG가 아닌 환경에서는 승인 시험 주소로 직접 발송하지 않고
Fail-closed 처리한다.

### 3.3 이메일 보호·조회

- DB에는 이메일 평문을 저장하지 않는다.
- 이메일은 정규화 후 Fernet 암호문으로 저장한다.
- 회원 인증 조회는 SHA-256 HMAC으로 비교한다.
- HMAC은 이메일 복원이 아니라 동일 입력 조회에만 사용한다.
- 암호화 키와 HMAC 키는 환경변수에서 읽고 Git에 저장하지 않는다.
- OTP 코드와 복호화된 수신 주소는 API 응답·애플리케이션 로그에 남기지 않는다.

## 4. DB 변경

Migration `accounts.0009_approved_test_contract_email`을 추가했다.

- `ContractEmailContact.data_classification` 선택지 확장
- `ContractEmailContact.delivery_policy` 선택지 확장
- 기존 `ck_contract_email_synthetic_only` 제거
- 새 `ck_contract_email_class_policy` 추가
- 승인 시험 연락처가 남아 있으면 역 Migration 차단
- 팀 통합 Migration Allowlist의 Accounts leaf를 `accounts.0009`로 갱신

로컬 PostgreSQL에 Migration을 적용한 뒤 `makemigrations --check --dry-run`과
`migrate --check`로 Schema 정합성을 확인했다.

## 5. 승인 6건 Seed

관리 명령:

```powershell
python manage.py seed_p1_approved_test_customers `
  --input-file .runtime/<pm-approved-six>.json `
  --pm-approved-local-e2e `
  --json
```

입력 파일은 Git에서 제외되는 `backend/.runtime` 아래만 허용한다.
정확히 6건, 필드 고정, 이름·합성 전화번호 중복 금지, 이메일 HMAC 중복
금지 조건을 모두 통과해야 하나의 Transaction으로 적재된다.

Seed는 가입 전 계약고객 상태만 만든다.

| 항목 | 기대값 |
|---|---:|
| 합성 고객 | 6 |
| 활성 계약 | 6 |
| 활성 이메일 연락처 | 6 |
| 활성 구독 | 6 |
| 제품 모델 | `WPUJAC104DWH` |
| User | 0 |
| CustomerAccountLink | 0 |

`User`와 `CustomerAccountLink`는 OTP 검증을 포함한 회원가입 성공 시점에만
생성된다. 같은 승인 입력으로 재실행하면 기존 행을 검증하고 중복 생성하지
않으며, 기존 행이 승인 범위와 다르면 덮어쓰지 않고 실패한다.

## 6. 인증 기능 연결

승인 시험 연락처도 기존 P1 인증 API에서 HMAC으로 계약고객을 조회한다.

- 회원가입: 이름·이메일 계약 대조 → OTP 확인 → User·계정 연결 생성
- 로그인: 생성된 아이디·비밀번호로 인증
- 아이디 찾기: 이름·이메일 대조와 OTP 확인 후 아이디 반환
- 비밀번호 재설정: 이름·이메일·아이디 대조와 OTP 확인 후 재설정 허용
- 존재 여부와 OTP 값은 Challenge API 응답으로 노출하지 않는다.

## 7. 로컬 Runtime 준비 결과

기존 PC의 8000 포트를 점유한 별도 실행선을 건드리지 않기 위해 새 Backend를
`127.0.0.1:18000`에서 실행했다. Galaxy Tab에는 다음 ADB Reverse를 적용했다.

```text
tablet tcp:8000 -> host tcp:18000
```

확인한 API는 `/health`, 회원가입 OTP Challenge, 로그인, 아이디 찾기 OTP
Challenge, 비밀번호 재설정 OTP Challenge이며 모두 로컬 Backend에 도달했다.
OTP Worker를 새 정책 코드로 실행했고 SMTP 연결·인증까지 확인했다.

사용자가 앱에서 OTP 발급을 요청하기 전에는 실제 시험 메일을 보내지 않았다.
따라서 현재 판정은 `로컬 E2E 시험 준비 완료`이며, 사용자 수신함에서 OTP를
확인해 전체 시나리오를 완료한 최종 E2E PASS는 아니다.

## 10. 사용자 E2E 확인 순서

1. 앱에서 승인된 이름·이메일로 회원가입 OTP를 요청한다.
2. 해당 실제 이메일 수신함에서 6자리 OTP를 확인한다.
3. OTP와 아이디·비밀번호를 제출해 회원가입을 완료한다.
4. 새 계정으로 로그인하고 계약 제품 연동을 확인한다.
5. 로그아웃 후 아이디 찾기와 비밀번호 재설정을 각각 확인한다.
6. 상담 문진까지 진행하되 AI 호출 이후 단계는 Runtime 8001 인계 후 확인한다.
