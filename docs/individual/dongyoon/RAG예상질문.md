## 1. 발표자가 먼저 고정할 핵심 메시지

다음 네 문장은 질문이 달라져도 일관되게 유지한다.

1. 현재 구현은 고객 증상을 구조화하고 안전 규칙을 먼저 적용한 뒤, 허용된
   공식 문서만 검색해 안내 상태와 근거를 반환하는 AI·RAG 독립 서비스다.
2. `BAAI/bge-m3`는 직접 학습하거나 파인튜닝한 모델이 아니라 Revision을
   고정해 적용한 사전학습 임베딩 모델이다.
3. 격리 pgvector에서 12개 평가를 통과했지만 제품 1종·D세대·공식 문서 1개·
   승인 청크 7개 범위이며 팀 공용 DB 완료 결과는 아니다.
4. 현재 안내 생성은 규칙·Template 기반이다. 외부 LLM 생성과 Backend 저장
   E2E는 완료했다고 말하지 않는다.

## 2. 가장 나올 가능성이 높은 질문

### Q1. 이 프로젝트에서 RAG를 왜 사용했나요?

**짧은 답변**

일반 언어 모델의 기억에 의존하지 않고, 제품과 세대가 확인된 공식 매뉴얼을
검색 근거로 사용하기 위해 도입했습니다. 근거가 없으면 임의 답변을 만들지
않고 상담 필요 상태로 전환합니다.

**추가 설명**

- 대상 제품 코드와 세대를 검색 전에 제한합니다.
- 공식 검증과 고객 안내 허용 상태를 통과한 청크만 사용합니다.
- 반환 결과에는 문서명·버전·페이지·청크 ID·유사도·검증 상태가 포함됩니다.

**피해야 할 표현**

- “RAG라서 환각이 없습니다.”
- “모든 정수기 문제에 정확히 답합니다.”

---

### Q2. 전체 동작 과정을 한 번에 설명해 주세요.

**짧은 답변**

Backend 요청을 받으면 증상을 구조화하고, 안전 규칙으로 위험을 먼저
판정합니다. 위험하면 검색을 건너뛰고 사용 중지 안내를 반환합니다. 일반 또는
주의 단계이면 bge-m3로 질문을 임베딩하고 pgvector에서 공식 청크를 검색한 뒤,
근거 유무와 위험도를 조합해 사용 안내를 결정하고 마지막으로 금지 표현과
안전 일관성을 검증합니다.

**발표용 순서**

```text
Backend 요청
→ 계약 검증
→ 증상 구조화
→ 안전 규칙 우선 판정
→ 허용 범위 검사
→ bge-m3 질의 임베딩
→ pgvector Exact Search
→ 문서·제품·Hash 후검증
→ 안내 상태 결정
→ 금지 표현 검증
→ Backend 응답
```

### Q3. 생성형 AI를 사용하지 않는데 RAG라고 할 수 있나요?

**짧은 답변**

현재는 검색 증강의 검색·근거 검증 부분과 규칙 기반 안내까지 구현한 기준선입니다.
외부 LLM이 근거를 읽고 자연어 답변을 합성하는 단계는 공식 기준선에 포함하지
않았습니다. 따라서 발표에서는 “완성형 생성형 RAG”보다 “공식 근거 검색 기반
안내 엔진”이라고 표현하는 것이 정확합니다.

**추가 설명**

현재 `generation` Stage는 검색된 본문의 내용을 재작성하지 않고, 위험도와
근거 존재 여부를 이용해 네 가지 안내 상태를 결정합니다.

---

### Q4. 어떤 데이터를 임베딩하고 DB에는 무엇을 저장하나요?

**짧은 답변**

공식 검수된 매뉴얼 청크의 `chunk_text`만 bge-m3로 임베딩해 1024차원 Vector로
저장합니다. 제품 코드, 세대, 페이지, 문서 Hash, 검증 상태, 허용 행동은
임베딩하지 않고 검색 필터와 출처 검증용 메타데이터로 별도 저장합니다.

**추가 설명**

현재 인덱싱 대상은 `WPUJAC104DWH` D세대의 승인 청크 7개입니다. `chunk_id`를
기준으로 UPSERT해 동일 Batch를 다시 실행해도 비의도 중복 행을 만들지 않습니다.

---

### Q5. 왜 bge-m3를 선택했나요?

**짧은 답변**

한국어를 포함한 다국어 문장 임베딩을 지원하는 사전학습 모델이고, 현재
SentenceTransformers와 pgvector로 재현 가능한 기준선을 만들 수 있어
선택했습니다. 모델 Revision과 1024차원을 고정해 적재와 검색이 같은 조건을
사용하도록 했습니다.

**방어 답변**

모델 간 비교 실험으로 bge-m3가 항상 최선이라고 결론 내린 것은 아닙니다.
현재는 MVP 기준 모델이며, 데이터가 확대되면 후보 모델을 동일 평가셋으로
비교해야 합니다.

---

### Q6. 직접 학습하거나 파인튜닝했나요?

**짧은 답변**

아닙니다. Hugging Face의 사전학습 `BAAI/bge-m3`를 고정 Revision으로 적용했습니다.
제가 구현한 부분은 공식 문서 청크 구성, 인덱싱, pgvector 검색, 정책 필터,
안전 가드레일, 평가와 API 계약입니다.

**피해야 할 표현**

- “bge-m3 학습을 완료했습니다.”
- “저희 데이터로 모델을 훈련했습니다.”

---

### Q7. 왜 별도 Vector DB가 아니라 PostgreSQL pgvector인가요?

**짧은 답변**

현재 MVP는 제품 1종과 승인 청크 7개로 검색 규모가 작고, Backend도
PostgreSQL을 사용합니다. pgvector를 사용하면 문서 메타데이터 필터와 Vector
검색을 한 DB 경계에서 관리할 수 있어 별도 Vector DB의 동기화와 운영 부담을
줄일 수 있습니다.

**추가 설명**

향후 문서와 제품이 크게 늘고 검색 부하가 증가하면 ANN Index나 별도 검색
엔진을 비교 검토할 수 있습니다. 현재 선택을 대규모 환경의 영구 정답으로
주장하지는 않습니다.

---

### Q8. 왜 ANN이 아니라 Exact Search를 사용했나요?

**짧은 답변**

현재 승인 청크가 7개라 근사 검색의 속도 이점이 사실상 필요하지 않습니다.
Exact Search는 모든 후보와의 거리를 계산해 작은 평가셋에서 결과를 재현하고
검증하기 쉽습니다.

**추가 설명**

청크 수와 동시 검색량이 증가하면 HNSW 같은 ANN 방식의 지연시간·Recall·운영
비용을 비교해 전환 여부를 결정해야 합니다.

---

### Q9. `Top-K=5`, Threshold `0.4`는 어떻게 정했나요?

**짧은 답변**

현재 MVP 평가를 위한 초기 기준값입니다. 7개 승인 청크 안에서 관련 근거를
놓치지 않도록 Top-5를 사용하고, 너무 낮은 유사도 결과를 제거하기 위해 0.4를
적용했습니다. 대규모 통계 튜닝으로 최적값을 확정한 것은 아닙니다.

**추가 설명**

데이터가 확장되면 증상별 정답 청크가 포함된 검증셋으로 Precision·Recall과
Fallback 비율을 함께 비교해 다시 조정해야 합니다.

---

### Q10. 다른 제품 매뉴얼이 잘못 검색되는 문제는 어떻게 막았나요?

**짧은 답변**

검색 전에 지원 모델과 D세대를 검사하고, SQL에서도 `model_code`와
`product_generation`을 조건으로 사용합니다. 검색 후에는 제품 코드·세대·
공식 검증 상태·사용 허용·문서 Hash·Embedding Revision·Chunk Set Hash를 다시
검사합니다.

**추가 설명**

현재 허용 모델은 `WPUJAC104DWH` 하나이며, `WPUIAC425SNW`, `WPU-IAC506`,
S세대와 미확인 모델은 차단 평가에 포함했습니다.

---

### Q11. 위험한 증상인데 검색 결과가 잘못되면 어떻게 하나요?

**짧은 답변**

누수·전기·스파크·화상 같은 명시적 위험 규칙을 RAG보다 먼저 실행합니다.
`danger`로 판정되면 검색 결과와 무관하게 `NORMAL`을 반환할 수 없고, 전체 또는
해당 기능 중지와 상담·기사 연결을 안내합니다.

**추가 설명**

LLM이나 검색 점수보다 `safety_rules.yaml`의 명시 규칙이 우선합니다. 최종
검증에서도 `danger + NORMAL` 조합을 다시 차단합니다.

---

### Q12. RAG가 환각을 완전히 막을 수 있나요?

**짧은 답변**

완전히 막는다고 말할 수는 없습니다. 현재는 공식 문서만 허용하고 근거가 없을
때 답변 생성을 중단하며, 확정 진단·안전 보증·직접 수리 표현을 차단해 위험을
낮췄습니다. 외부 LLM 생성이 추가되면 근거 일치 평가와 공격 입력 검증이 더
필요합니다.

**피해야 할 표현**

- “환각률 0%입니다.”
- “공식 문서라서 모든 답변이 안전합니다.”

---

### Q13. 검색 결과가 0건인 경우와 DB 설정 오류는 어떻게 구분하나요?

**짧은 답변**

정상적으로 검색했지만 적합한 근거가 없으면 HTTP 200의 `FALLBACK`과
`PENDING_CONSULTATION`을 반환합니다. 반면 `AI_VECTOR_DSN`이나 모델 Revision이
없어 검색을 시작하지 못하면 HTTP 503의 비재시도 설정 오류로 반환합니다.

**핵심 구분**

```text
정상 검색 0건 = 고객 판단 보류, 상담 연결
검색 구성 없음 = 서비스 구성 실패, Backend 오류 처리
```

### Q14. 현재 성능 수치를 설명해 주세요.

**짧은 답변**

2026년 7월 30일 개인 격리 pgvector에서 12개 평가가 모두 통과했습니다. 양성
7건의 Recall@5는 `1.0`, MRR은 `0.8857`, 금지 Hit는 `0`이었습니다. 다만 제품
1종·공식 문서 1개·승인 청크 7개에 한정된 기능 검증 결과입니다.

**지표 설명**

- Recall@5 `1.0`: 양성 질의의 기대 청크가 상위 5개 안에 모두 포함됨
- MRR `0.8857`: 기대 청크가 평균적으로 상위 순위에 나타났지만 항상 1위는 아님
- 금지 Hit `0`: 차단해야 할 모델·세대·미검증 자료가 최종 근거에 포함되지 않음

### Q15. 12건으로 성능을 주장하기에는 너무 적지 않나요?

**짧은 답변**

맞습니다. 12건은 통계적인 일반화 성능이 아니라 현재 MVP 범위의 기능과 정책
경계를 검증하는 최소 기준선입니다. 그래서 전체 제품 정확도나 운영 성능으로
확대 해석하지 않고, 제품과 문서가 늘어날 때 평가셋도 함께 확장하는 것을 다음
단계로 두고 있습니다.

**좋지 않은 답변**

- “12건을 모두 통과했으니 정확도 100%입니다.”

---

### Q16. 12개 평가가 모두 실제 DB 검색을 한 건가요?

**짧은 답변**

아닙니다. 양성 7건은 실제 pgvector Query를 수행했고, 음성 5건은 지원하지 않는
제품·세대나 미검증 FAQ 요구를 검색 전에 정책으로 차단했습니다. 따라서
`12/12 PASS`와 `12번 DB 검색 성공`은 다른 의미입니다.

---

### Q17. 단위 테스트가 79, 91, 95로 보이는데 어떤 숫자가 맞나요?

**짧은 답변**

현재 공식 기준은 `95 passed, 3 warnings`입니다. 79와 91은 테스트가 추가되기
전의 이전 실행 기록입니다. 숫자가 증가한 것은 모델 성능이 좋아진 것이 아니라
계약·오류 처리·Timeout·AI 내부 재시도 같은 테스트 항목이 추가됐기 때문입니다.

**추가 설명**

발표에서는 실행 명령, Commit, 기준선 JSON을 함께 제시하고 숫자만 단독으로
비교하지 않습니다.

---

### Q18. Recall과 MRR이 0으로 나온 보고서도 있지 않나요?

**짧은 답변**

Vector Store가 설정되지 않은 오프라인 실행에서는 검색을 수행할 수 없어 0으로
기록될 수 있습니다. 그 값은 검색 품질이 아니라 `vector_store_not_configured`
상태이므로 공식 검색 성능으로 공개하지 않습니다. 검색 품질 수치는 실제
pgvector를 연결해 실행한 이력만 사용합니다.

---

### Q19. 팀 공용 DB에서도 검증이 끝났나요?

**짧은 답변**

아직 아닙니다. PostgreSQL 16.14와 pgvector 0.8.6의 개인 격리 DB에서는 수직
검증을 완료했지만, 팀 공용 DB Migration·승인 청크 UPSERT·Backend 저장 E2E는
남아 있습니다. 그래서 현재 상태를 `ISOLATED_VERIFIED_TEAM_DB_PENDING`으로
표시합니다.

**피해야 할 표현**

- “DB 연동은 모두 끝났습니다.”
- “팀 DB에서 12건을 통과했습니다.”

---

### Q20. 개인 DB에서 먼저 검증한 이유는 무엇인가요?

**짧은 답변**

팀 공용 DB Schema와 Migration이 확정되기 전에 Extension 생성과 실험 데이터를
직접 넣으면 다른 팀원의 데이터에 영향을 줄 수 있기 때문입니다. Disposable
DB에서 인덱싱·검색·Rollback을 먼저 검증하고, 팀 DB에서는 Backend Migration과
최소 권한이 준비된 뒤 승인 청크만 적재하도록 경계를 분리했습니다.

## 3. 기술 꼬리질문

### Q21. 문서가 수정되거나 다른 임베딩 모델로 바뀌면 어떻게 감지하나요?

**답변 예시**

원문 `source_hash`, Embedding 모델 Revision, Index Version, Chunk Set Hash를
Manifest에 기록합니다. 검색 결과가 현재 Manifest와 일치하지 않으면 최종
근거에서 제외합니다. 문서나 모델이 변경되면 새 인덱스를 만들고 평가를 다시
수행해야 합니다.

---

### Q22. 청크는 어떻게 나눴나요?

**답변 예시**

현재는 공식 매뉴얼의 “고장 신고 전 확인하기” 영역을 증상 단위로 정리해
7개 승인 청크를 만들었습니다. 페이지와 원문 Hash를 보존하고 텍스트·시각 검수
완료 자료만 MVP에 포함했습니다. 범용 자동 청킹 품질이 검증된 상태는 아니며,
한 청크가 38~39쪽을 함께 참조하는 사례도 있어 페이지 단위 분리 여부는 별도
결정이 필요합니다.

---

### Q23. 원본 JSONL의 모든 정책 정보가 DB에 저장되나요?

**답변 예시**

아닙니다. 현재 Runtime DTO에는 청크 원문, 제품·세대, 문서·페이지, 검증 상태,
허용 여부, Source Hash, 안전 행동과 인덱스 증빙을 저장합니다. 원본의
`risk_level`, `prohibited_actions`, `escalation_conditions` 같은 일부 필드는 현재
적재 Metadata에 보존되지 않습니다. LLM 기반 안내를 확장하려면 이 필드의
Schema와 저장 경계를 보완해야 합니다.

---

### Q24. 13번째 정책 차단 Case는 무엇이고 완료됐나요?

**답변 예시**

기존 5개 음성 Case는 대부분 DB 검색 전에 범위를 차단합니다. 13번째는 제품과
세대는 정상이라 DB Query는 수행하지만, 문서 정책상 사용할 수 없는 후보가
최종 근거에 들어오지 않는지 확인하려는 Case입니다. 아직 Data Owner와 원천
문서·차단 사유·기대값을 확정하지 않아 공식 완료로 보고하지 않습니다.

**추가 방어**

현재 SQL이 `allowed_use=true`와 공식 검증 상태를 먼저 적용하므로, “SQL에서
제외된 것”과 “Python 후검증에서 제거된 것”을 구분할 수 있도록 평가 설계도
보완해야 합니다.

---

### Q25. 일시적으로 DB 연결이 끊기면 어떻게 처리하나요?

**답변 예시**

연결·Timeout·일시적 Provider 오류에 한해 AI 내부에서 최대 1회, 0.5초 대기 후
재시도합니다. 설정 오류나 정책 오류는 재시도하지 않습니다. 전체 AI Timeout은
30초이고 Backend 자동 재시도는 중복 호출을 막기 위해 0회입니다.

---

### Q26. 동시 요청이 많아지면 어떻게 하나요?

**답변 예시**

현재 기본 동시 Worker Slot은 2개이며 포화되면 HTTP 503으로 명확히 반환합니다.
다만 운영 부하 테스트와 용량 산정은 아직 완료되지 않았습니다. 팀 DB와 Backend
E2E 후 실제 지연시간·동시성·자원 사용량을 측정해 Worker와 배포 구성을
조정해야 합니다.

---

### Q27. 고객 개인정보나 원문은 로그에 남나요?

**답변 예시**

현재 구조화 로그는 추적 ID, Stage, 상태, 지연시간, 재시도 횟수와 오류 코드를
중심으로 남기고 고객 `raw_symptom`을 그대로 기록하지 않습니다. DB 연결 문자열도
문서·Git·로그에 저장하지 않고 Secret 경로로 전달합니다.

---

### Q28. Prompt Injection은 어떻게 막나요?

**답변 예시**

현재 공식 기준선에는 외부 LLM 호출이 없어 입력 문장이 시스템 명령을 바꾸는
형태의 Prompt Injection 표면은 제한적입니다. 대신 미검증 자료를 단독 근거로
요구하는 질의와 지원 범위 밖 모델은 정책으로 차단합니다. 향후 LLM을 연결하면
명령과 문서 분리, 출력 Schema 강제, 근거 인용 검증과 공격 입력 평가를 별도로
추가해야 합니다.

---

### Q29. Backend와 AI의 책임은 어떻게 나뉘나요?

**답변 예시**

AI는 증상 구조화, 위험 분류, 근거 검색, 안내 상태 제안을 담당합니다. 고객
권한, 문의 상태 전환, 중복·stale 응답 차단, 최종 DB 저장과 공개용
EvidenceCard 조립은 Backend 책임입니다. AI가 Backend 업무 상태나 운영 DB를
직접 변경하지 않습니다.

---

### Q30. 지금 가장 중요한 미완료 작업은 무엇인가요?

**답변 예시**

첫째는 최지용의 Backend Adapter와 팀 DB Migration을 기준으로 실제 수직 E2E를
완료하는 것입니다. 둘째는 김은진과 13번째 정책 차단 Case를 확정하고 팀 DB에서
독립 재검증하는 것입니다. 그 다음에 평가셋과 제품 범위를 확대하고 외부 LLM
생성 여부를 검토해야 합니다.

## 4. 시연 중 나올 수 있는 상황 질문

### Q31. 시연에서 Mock 결과를 보여주는 건가요?

**답변 예시**

Mock는 Backend·Frontend 계약과 화면 표시 확인용입니다. 실제 RAG 성능으로
설명하지 않습니다. 실제 검색 시연은 `local` 모드에 pgvector DSN과 고정 모델
Revision을 연결했을 때만 pgvector 결과라고 표시합니다.

---

### Q32. 시연 중 Vector DB 연결이 실패하면 어떻게 설명할 건가요?

**답변 예시**

설정 실패는 검색 결과 0건으로 숨기지 않고 HTTP 503과 `RETRIEVING` 실패로
분리됩니다. 발표에서는 사전 검증된 격리 pgvector 리포트와 실행 환경을 함께
준비하고, Mock 화면은 계약 시연임을 명확히 표시하겠습니다.

---

### Q33. 누수 입력인데 RAG 근거가 없어도 답할 수 있나요?

**답변 예시**

네. 누수와 전기 위험은 공식 검색보다 안전 규칙이 먼저이므로 Vector Store가
없어도 사용 중지와 상담 안내를 반환할 수 있습니다. 다만 구체적인 매뉴얼 근거
카드는 비어 있을 수 있고, Backend가 이를 근거가 있는 답변으로 표시하면 안
됩니다.
