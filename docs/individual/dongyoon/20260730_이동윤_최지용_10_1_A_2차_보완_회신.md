## 1. 계약 Parity

- `MissingField`: 필드명 1~100자, 사유 1~500자, 중요도 3개 Enum
- `FollowUpQuestion`: ID·질문·대상 필드 길이, 선택지 최대 10개와 항목 길이
- `EvidenceReference.page_refs`: 각 페이지 1 이상
- `ApiErrorResponse`: 계약상 Required이면서 Nullable인 Key를 Runtime에서도
  Required로 강제하고 직렬화 시 Null Key를 보존
- `ModelMetadata`: 모델·Prompt Version 길이와 Token·Latency 0 이상
- `ProcessingTrace.error_code`: 최대 100자
- `ValidationResult`: 계약 대응 Runtime 모델 추가
- 계약 Schema 16개 전체의 Runtime 매핑, 정상 Payload, 추가 필드 거부와
  보고 반례의 경계값을 JSON Schema·Pydantic 양쪽에서 동일 판정

## 2. 운영 로그·Timeout

- Bootstrap이 `AI_LOG_LEVEL`을 소비하며 기본값 `INFO`를 실제 Logger에 적용
- 성공 `started → completed`
- 422와 Header 불일치: `failed` 단일 Event
- Timeout과 내부 실패: `started → failed`
- 안전한 식별자가 없으면 서버 Trace ID를 생성
- 로그 허용 필드는 식별자·Stage·Status·Retry·Latency·Error Code로 제한하고
  고객 원문·Prompt·Secret·Stack Trace·내부 예외 원문은 제외
- PostgreSQL 연결·Statement Timeout과 취소 Token의 Stage 경계 차단 유지
- Local Torch Thread는 강제 종료할 수 없으므로 실제 종료 전까지 Worker
  Slot을 반환하지 않으며 `AI_MAX_IN_FLIGHT_WORKERS` 기본 2, 범위 1~32 적용

Local CPU Embedding의 Hard Kill은 별도 Process 또는 외부 API 실행 경계가
필요하다. 현재 상한·협력적 취소 설계를 유지할지에 대한 PM 명시 승인은
별도 필요하다.

## 3. 검색 결과 방어·Provenance

- Store 반환 후 요청 `model_code`, D세대, `official_verified`,
  `allowed_use=true`를 다시 검사하며 위반 Chunk는 최종 근거에서 제거
- Embedding Client와 Index Manifest의 모델명·Revision·차원을 검색 시작 전에
  대조
- 적재 Row metadata에 Embedding Model·Revision, Index Version,
  Chunk Set SHA-256 저장
- Document ID별 Source SHA-256을 Manifest와 검색 결과에서 대조
- 평가 결과에 결과별 Model Code·Generation·Document Version·Embedding
  Revision·Index Version·Chunk Set SHA-256 기록

## 6. 남은 사항

이동윤 개인 구현에서 남은 전달 Gate는 최종 Commit·Push·PR과 SHA 기입이다.
Local Embedding Hard Kill 미적용은 구현 누락으로 숨기지 않고 자원 상한을 둔
잔여 위험으로 기록하며 PM 승인 또는 별도 Process 설계를 결정한다.

T-005 팀 DB Migration, Backend Adapter·Evidence, 공통 Registry, 최종 E2E는
최지용·PM과의 공동 후속 범위다.
