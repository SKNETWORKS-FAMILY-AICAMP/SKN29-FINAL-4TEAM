- 상담·방문 처리 완료 기준

### 3.2. Inquiry State Machine 계약 작성

다음 디렉터리를 기준으로 Inquiry State Machine 계약 초안을 작성하였다.

```text
contracts/state-machine/
```

작성한 핵심 계약 파일은 다음과 같다.

| 파일 | 역할 |
|---|---|
| `inquiry-states.yaml` | 문의 상태 13종과 종료 상태 정의 |
| `inquiry-events.yaml` | 고객·담당자·시스템 이벤트 정의 |
| `transition-rules.yaml` | 현재 상태와 이벤트에 따른 다음 상태 정의 |
| `transition-guards.yaml` | 역할·소유권·담당자·입력·안전·완료 조건 정의 |
| `allowed-actions.yaml` | 상태와 역할에 따라 외부에 노출할 행동 정의 |
| `role-permissions.yaml` | 역할별 실행 가능 이벤트와 리소스 접근 범위 정의 |
| `completion-policy.yaml` | 자가조치·상담·방문 완료와 재개 정책 정의 |
| `concurrency-policy.yaml` | `state_version`, 멱등성, 트랜잭션과 충돌 처리 기준 정의 |

추가로 다음 보조 자료도 작성하였다.

## 4. 주요 설계 결정

### 4.1. 문의 상태와 세부 처리 상태 분리

문의의 업무 상태는 다음 13종으로 통일하였다.

```text
DRAFT
QUESTIONNAIRE_IN_PROGRESS
AI_GUIDANCE
CONSULTATION_REQUIRED
CONSULTATION_IN_PROGRESS
VISIT_REVIEW_PENDING
VISIT_SCHEDULING
VISIT_SCHEDULED
COMPLETION_PENDING
REVISIT_REQUIRED
REOPENED
RESOLVED
CANCELLED
```

`AI_GUIDANCE`는 AI가 처리 중이라는 의미가 아니라, 검증된 AI 안내가 준비되어 고객이 확인하는 문의 상태로 정의하였다.

AI 내부의 구조화·검색·생성·검증 단계와 방문 진행 상태는 Inquiry 상태와 별도로 관리하도록 분리하였다.

### 4.2. Backend를 상태 전이의 최종 권위로 지정

Web·Mobile·AI가 다음 상태를 직접 지정하지 않도록 하였다.

- 클라이언트는 행동별 API를 호출한다.
- AI는 분석 결과를 내부 이벤트 후보로 전달한다.
- Backend가 현재 상태, 역할, 담당자, 입력값, 안전 조건과 버전을 검증한다.
- 모든 조건을 통과한 경우에만 상태와 이력을 변경한다.

이에 따라 프론트엔드는 상태만 보고 버튼을 임의로 계산하지 않고, Backend가 반환한 `allowed_actions`만 노출하도록 기준을 정하였다.

### 4.3. 상담·방문 완료 정책 확정

자가조치 단독 해결과 상담·방문 처리 완료의 최종 주체를 구분하였다.

#### 자가조치 단독 해결

```text
AI_GUIDANCE
→ CUSTOMER_REPORTED_SELF_RESOLVED
→ RESOLVED
```

고객이 직접 해결 완료를 확정한다.

#### 상담·방문 처리 후 완료

```text
상담 또는 방문 처리 완료
→ COMPLETION_PENDING
→ 고객의 해결됨 피드백 저장
→ 마지막 처리 담당자의 FINALIZE_INQUIRY
→ RESOLVED
```

상담이나 방문이 끝났다는 이유만으로 바로 `RESOLVED`로 이동하지 않도록 하였다.

### 4.4. 방문 불필요 분기 보완

초기 계약에는 `VISIT_REVIEW_PENDING` 상태에서 방문이 필요하지 않다고 판단한 경우의 반대 분기가 없었다.

다음 이벤트와 전이를 추가하여 보완하였다.

```text
VISIT_REVIEW_PENDING
+ VISIT_NOT_NEEDED
→ COMPLETION_PENDING
```

관련하여 다음 파일을 함께 수정하였다.

- `inquiry-events.yaml`
- `transition-rules.yaml`
- `transition-guards.yaml`
- `allowed-actions.yaml`
- `role-permissions.yaml`
- `completion-policy.yaml`

### 4.5. 동시성 및 중복 요청 처리 기준 확정

모든 상태 변경 요청은 최신 `state_version`을 검증하도록 하였다.

```text
요청 state_version != 현재 state_version
→ 409 STATE_VERSION_CONFLICT
```

외부 쓰기 요청은 `Idempotency-Key`를 사용하며, 같은 키와 같은 요청은 기존 응답을 재사용하고 다른 요청 본문에 같은 키를 재사용하면 충돌로 처리하도록 하였다.

Backend와 AI 연동은 다음 기준을 사용한다.

- Backend→AI 타임아웃: 30초
- AI 내부 재시도: 최대 1회
- Backend 자동 재시도: 0회
- 오래된 AI 결과는 상태 전이에 적용하지 않음

## 6. 검증 결과

계약 간 참조를 확인하는 검증 스크립트를 작성하고 실행하였다.

```text
scripts/contracts/validate_state_machine.py
```

검증 결과는 다음과 같다.

| 검증 항목 | 결과 |
|---|---:|
| 문의 상태 | 13개 |
| 이벤트 | 30개 |
| 전이 규칙 | 34개 |
| Guard | 39개 |
| 외부 허용 행동 | 23개 |
| 누락된 상태·이벤트 참조 | 0개 |
| 누락된 Guard 참조 | 0개 |
| 종료 상태의 후속 행동 | 0개 |
| 중복 코드·전이 ID | 0개 |

주요 불변 조건도 함께 확인하였다.

- `RESOLVED`, `CANCELLED`는 종료 상태이며 후속 전이를 허용하지 않음
- AI 시스템 이벤트는 외부 `allowed_actions`에 노출되지 않음
- 상태가 변경되는 전이는 상태 이력을 기록함
- 방문 상태가 변경되는 전이는 방문 이력을 기록함
- `FINALIZE_INQUIRY`는 마지막 처리 담당자와 최신 고객 해결 피드백을 요구함
- `VISIT_NOT_NEEDED` 반대 분기가 상태·이벤트·권한·행동 계약에 모두 연결됨

## 7. 협업 및 인계 사항

### 최지용 — Backend·DB

- State Machine Service와 Django 상태 Enum 구현 시 계약 코드 사용
- 행동별 API에서 이벤트를 생성하고 Guard 평가 후 전이
- `state_version`, `Idempotency-Key`, 상태 이력, 업무 이벤트 로그 반영
- API 응답에 `allowed_actions` 포함

### 이동윤 — AI·RAG

- AI가 Inquiry 상태를 직접 변경하지 않도록 구현
- 분석 결과를 다음 내부 이벤트 후보로 Backend에 전달
  - `SAFE_GUIDANCE_READY`
  - `DANGER_DETECTED`
  - `NO_EVIDENCE`
  - `PRODUCT_VALIDATION_FAILED`
- 공식 근거와 안전 검증 조건을 충족한 결과만 전달

### 한예나·양정현 — Web·Mobile

- 상태 코드만으로 행동 가능 여부를 임의 계산하지 않음
- Backend가 반환한 `allowed_actions` 기준으로 버튼과 메뉴 노출
- 쓰기 요청에 `state_version`과 새 `Idempotency-Key` 포함
- 409 충돌 시 최신 상태와 허용 행동으로 화면 갱신

### 김은진 — 데이터·QA·DevOps

- 대표 전이 예시를 Contract Fixture와 QA 기준으로 활용
- 검증 스크립트를 CI 또는 계약 테스트에 연결
- 잘못된 역할, 오래된 버전, 중복 요청, 종료 상태 수정 등의 오류 사례 검증
