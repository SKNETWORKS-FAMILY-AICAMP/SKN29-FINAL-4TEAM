# 상담사·운영자 Web API 연동 점검 및 Backend 요청사항

> 기준일: 2026-08-01
> 작성: 한예나 Web 작업 범위
> 결론: **부분 연동 가능 / 화면 핵심 업무 API 미구현으로 전체 실연동 불가**

## 1. 먼저 보는 결론

- 현재 공식 기계 계약은 `contracts/api/openapi.yaml`이며 OpenAPI Operation은 9개다.
- 실제 Django Runtime Route가 있는 것은 7개다.
- 로그인 관련 API 4개, 문의 생성·취소 2개, Health 1개는 연결 대상이 존재한다.
- 상담사 화면에서 필요한 문의 목록·상세·상담 저장·기사 요청·일정 조율 API 5개는 아직 OpenAPI와 Runtime이 없다.
- 운영자 대시보드 집계 API도 아직 OpenAPI와 Runtime이 없다.
- 따라서 현재 상담사·운영자 화면의 업무 데이터는 공식 합성 Mock을 유지한다. 화면에서 실데이터처럼 표시하지 않는다.
- Web에는 `/health`를 15초마다 확인하는 실시간 연결 표시를 추가했다. 서버 연결 여부와 화면 업무 데이터의 Mock 여부를 별도로 표시한다.

## 2. 현재 API 구현 현황

| 구분 | Method | Runtime Path | 현재 Web 사용 가능 여부 |
|---|---|---|---|
| Health | GET | `/health` | 연결 상태 확인에 사용 |
| 데모 로그인 | POST | `/api/v1/auth/demo-login` | `VITE_USE_MOCK_API=false`에서 사용 가능 |
| 토큰 갱신 | POST | `/api/v1/auth/refresh` | 사용 가능 |
| 로그아웃 | POST | `/api/v1/auth/logout` | 사용 가능 |
| 내 정보 | GET | `/api/v1/me` | 사용 가능 |
| 문의 생성 | POST | `/api/v1/inquiries` | 고객 문의 작성 화면용, 현재 상담사·운영자 화면 범위 아님 |
| 문의 취소 | POST | `/api/v1/inquiries/{id}/cancel` | 고객 문의 취소용 |
| 설문 누적 | PATCH | `/api/v1/inquiries/{id}/questionnaire` | OpenAPI-only, Runtime 없음 |
| 조치 결과 | POST | `/api/v1/inquiries/{id}/action-results` | OpenAPI-only, Runtime 없음 |

근거 문서: `docs/api/runtime_implementation_status.md`

## 3. Web에 반영한 내용

### 3.1 실시간 API 연결 표시

- Web은 15초마다 `GET /health`를 호출한다.
- HTTP 200뿐 아니라 `X-Correlation-ID` 응답 Header까지 확인한다.
- 이 Header가 없으면 Vite가 반환한 SPA HTML을 API 정상 응답으로 잘못 판단하지 않고 연결 실패로 처리한다.
- 상담사 상단과 운영자 화면에서 아래 상태를 볼 수 있다.
  - `API 확인 중`
  - `API 서버 연결됨`
  - `API 서버 연결 대기`
- 현재 화면의 목록·상세·통계가 Mock이라는 문구를 함께 유지한다.

### 3.2 개발 프록시

Vite 개발 서버에서 아래 요청을 Backend로 전달한다.

| Web 요청 | 기본 전달 대상 |
|---|---|
| `/api/**` | `http://127.0.0.1:8000` |
| `/health` | `http://127.0.0.1:8000` |

환경변수 `VITE_BACKEND_PROXY_TARGET`으로 Backend 주소를 변경할 수 있다. 이 방식은 로컬 개발 중 포트 차이로 발생하는 CORS 문제를 줄이기 위한 것이다.

### 3.3 인증 표시 수정

로그인 화면은 `VITE_USE_MOCK_API` 값에 따라 `MOCK` 또는 `API`를 표시한다. 실제 API 모드인데도 `Mock 계정 로그인`이라고 표시하던 혼동을 제거했다.

## 4. Backend에 요청할 필수 API

아래 경로는 기존 설계 기준 문서 `docs/api/watercare_api_specification.md`에 이름만 존재하며 `DESIGN_BASELINE_ONLY` 상태다. 구현 전에 `contracts/api/paths/*.yaml`과 Schema를 먼저 확정해야 한다.

### 4.1 상담사 문의 Queue

`GET /api/v1/counselor/inquiries`

필요 Query:

| Query | 용도 |
|---|---|
| `bucket` 또는 `status` | 새 문의 / 처리 중 / 처리 완료 탭 |
| `q` | 문의 번호·고객 표시명·제품·증상 검색 |
| `risk_level` | 일반·주의·긴급 필터 |
| `priority` | 우선순위 필터 |
| `assignee` | 본인 배정·미배정 구분 |
| `from`, `to` | KST 접수 기간 |
| `sort` | 최근 변경·대기 시간 정렬 |
| `page`, `size` | 서버 Pagination |

최소 응답 필드:

- `inquiry_id`: Public UUID. URL 식별자로 사용
- `inquiry_number`: 사용자 표시용 문의 번호
- `status`, `state_version`
- `risk_level`: API는 소문자 `general`, `caution`, `danger` 권장
- `priority`
- `symptom_summary`, `customer_message`
- 역할별 마스킹이 적용된 `customer_display_name`
- `product_model_code`
- `assigned_counselor`
- `received_at`, `updated_at`, `waiting_seconds`
- Backend Guard가 계산한 `allowed_actions`
- `page_info`: `page`, `size`, `total_items`, `total_pages`

### 4.2 상담용 문의 상세

`GET /api/v1/counselor/inquiries/{id}`

필요 응답 묶음:

- 문의 기본 정보, 최신 `state_version`, `allowed_actions`
- 마스킹 고객 정보, 제품·구독·케어 기록
- 고객 문의 내용과 증상·문진 답변
- 조치 결과, AI 안내, 공식 근거 문서
- 상담 기록과 AI 초안·상담사 확정본
- 방문 요청·기사 배정·일정
- 상태 변경 이력
- 하위 영역 일부 조회가 실패할 경우 `section_errors` 같은 부분 실패 표현

주의:

- 화면은 상태 값으로 버튼을 추측하지 않고 `allowed_actions`만 사용한다.
- 내부 RAG Chunk ID, 검색 점수, Prompt, Trace, 내부 파일 경로는 Web에 내려주지 않는다.

### 4.3 상담 저장·완료

설계 후보: `POST /api/v1/counselor/inquiries/{id}/consultations`

현재 한 경로로 모두 처리할지, 행동별 Endpoint로 나눌지가 미확정이다. 다음 행동은 분리 계약을 권장한다.

- 상담 시작
- 상담 메모 임시 저장
- AI 요약 수정본 저장
- 상담 요약 확정
- 상담 완료
- 방문 필요 검토

모든 쓰기 요청에 필요한 공통값:

- `Idempotency-Key` Header
- `X-Correlation-ID` Header
- 최신 Inquiry `state_version`
- 상담 레코드 자체 버전이 있다면 `consultation_version`

성공 응답에는 최신 `status`, `state_version`, `allowed_actions`와 갱신된 상담 정보를 반환해야 한다.

### 4.4 방문 요청과 기사 일정 조율

- `POST /api/v1/counselor/inquiries/{id}/visit-requests`
- `PATCH /api/v1/visits/{visit_id}/schedule`

필요 입력:

- 방문 필요 사유
- 고객 희망 일시
- 기사 또는 기사 후보
- 점검 우선순위
- 기사 전달사항과 안전 유의사항
- Inquiry `state_version`과 Visit `visit_version`

상담사 화면은 상담부터 기사 배정·일정 조율까지 한 Drawer에서 처리한다. 두 API 성공 응답에 최신 문의와 방문 상태를 함께 주면 추가 재조회가 줄어든다.

### 4.5 운영자 대시보드

`GET /api/v1/operations/dashboard`

필요 Query:

- `from`, `to`, `product_model`, `assignee`, `status`, `risk_level`

필요 응답:

- 전체·신규·처리 중·완료·위험 문의 KPI
- 증상·상태·위험도 분포
- 지연·오류·근거 부족·담당자 미배정 같은 운영 예외
- 조건별 문의 목록 또는 별도 Page Endpoint
- `aggregated_at`, 집계 기준 시간대, 갱신 주기
- 합성/실데이터 여부를 나타내는 `data_source`

기존 설계에는 `GET /api/v1/operations/exceptions`도 있다. 예외를 Dashboard 응답에 포함할지 별도 Pagination API로 분리할지 Backend와 PM 결정이 필요하다.

## 5. 오류와 동시성 계약 요청

Backend는 아래 동작을 OpenAPI 예시와 통합 테스트로 제공해 주어야 한다.

| 상태 | Web 처리에 필요한 값 |
|---|---|
| 401 | 토큰 갱신 시도 후 실패하면 로그인 이동 |
| 403 | 권한 부족 안내, 입력 보존 |
| 404 | 삭제·권한 범위 외 객체를 구분하지 않는 정책 확인 |
| 409 State Conflict | 최신 `state_version`, 최신 상태, 최신 `allowed_actions` |
| 409 Duplicate Event | Replay 가능 여부와 기존 처리 결과 |
| 422 | `field_errors`의 필드명·메시지 구조 |
| 5xx | 공통 Error Wrapper와 `correlation_id` |

Web은 409에서 사용자 입력을 보존하고 자동 재전송하지 않는다. 사용자가 최신 상태를 확인한 뒤 다시 실행한다.

## 6. Backend·PM에 전달할 질문

1. 위 5개 상담사 API와 운영 Dashboard API의 OpenAPI 작성·Runtime 구현 일정은 언제인가?
2. 상담 저장·요약 확정·완료·방문 검토는 행동별 Endpoint인가, 단일 Command Endpoint인가?
3. Queue의 탭 구분은 `bucket`으로 제공할지, canonical `status` 여러 개로 조회할지?
4. 고객 표시명과 연락처의 역할별 마스킹 규칙은 무엇인가?
5. `allowed_actions` 객체의 필수 속성은 `code`, `label`, `operation_id`, `method`, `href` 중 무엇인가?
6. 운영 예외를 Dashboard 한 응답에 포함할지 `/operations/exceptions`로 분리할지?
7. 운영 KPI의 집계식·시간대·갱신 주기는 무엇인가?
8. Web 개발 Origin `http://localhost:5173`, `http://localhost:5174`를 CORS 허용할 것인가? 개발 프록시만 공식 지원할 것인가?

현재 `backend/.env.example`에는 `5173`만 등록되어 있다. 운영자 확인용 `5174`에서 프록시 없이 절대 API URL을 사용할 계획이라면 아래 Origin도 추가해야 한다.

- `http://localhost:5174`
- `http://127.0.0.1:5174`

## 7. 로컬 실연동 검증 차단 사항

2026-08-01 현재 이 PC에서는 Backend를 실행할 수 없어 HTTP 왕복 검증은 완료하지 못했다.

- `backend/.venv`가 삭제된 Python 3.13.13 경로를 가리켜 실행 불가
- 현재 시스템 Python에는 Django가 설치되어 있지 않음
- PostgreSQL 5432가 실행 중이지 않음
- Docker 명령을 사용할 수 없음

따라서 `/health` 상태 UI와 프록시·단위 테스트는 검증할 수 있지만 실제 로그인/토큰/DB API의 왕복 검증은 Backend 실행 환경이 준비된 뒤 진행해야 한다.

## 8. Backend 준비 후 실연동 확인 순서

1. Backend를 `127.0.0.1:8000`에서 실행한다.
2. Web 환경변수를 설정한다.

```env
VITE_API_BASE_URL=/api/v1
VITE_BACKEND_PROXY_TARGET=http://127.0.0.1:8000
VITE_USE_MOCK_API=false
VITE_MOCK_AUTHENTICATED=false
```

3. Web을 다시 실행한다.
4. 화면의 `API 서버 연결됨` 표시를 확인한다.
5. 데모 로그인 → `/me` → 토큰 갱신 → 로그아웃을 Network 탭에서 확인한다.
6. Backend가 상담·운영 API를 제공하면 Mock Adapter를 실제 Adapter로 교체한다.
7. 401·403·409·422·5xx와 느린 응답·부분 실패를 함께 검증한다.

## 9. 완료 판정 기준

다음 조건 전에는 “상담사·운영자 API 연동 100% 완료”라고 보고하지 않는다.

- 상담사 필수 5개와 운영자 필수 1개가 OpenAPI에 등록됨
- 실제 Django Route·View·Serializer가 존재함
- Backend 계약 테스트와 Web Mapper 단위 테스트가 통과함
- 브라우저에서 실제 DB 데이터의 목록·상세·상담 저장·방문 일정·운영 집계 왕복 확인
- 409 동시성, 권한, Validation, 장애 상태 확인
- Mock 표시 제거 및 Mock Adapter가 개발 전용으로 격리됨
