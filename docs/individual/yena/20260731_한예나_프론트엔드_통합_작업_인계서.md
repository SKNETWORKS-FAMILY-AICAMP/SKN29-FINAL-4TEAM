## 0. 가장 먼저 확인할 내용

### 0.1 현재 Git 상태

문서 작성 시점의 `yena` HEAD는 `origin/yena`, `origin/main`과 같은 `765047c`다. 다만 아래 최신 화면 개편은 **로컬 변경이며 아직 Commit·Push되지 않았다.**

| 구분 | 경로 | 상태 |
| --- | --- | --- |
| 상담사 운영형 레이아웃·디자인 | `web/src/pages/consultant/ConsultantDashboardPage.css` | 로컬 수정 |

| 팀 인계 문서 | `docs/individual/yena/20260731_한예나_프론트엔드_통합_작업_인계서.md` | 신규 문서 |

따라서 팀원이 `main` 또는 `origin/yena`를 Pull하는 것만으로는 이 문서에 첨부한 최신 디자인을 볼 수 없다. PM이 검토할 때는 다음 순서를 지킨다.

1. 한예나가 현재 로컬 변경을 별도 Commit으로 생성한다.
2. `yena`에 Push하고 40자리 Commit SHA를 공유한다.
3. PM이 변경 파일과 검증 결과를 확인한다.
4. PM이 `main`에 병합한 후 팀 기준 SHA를 다시 공유한다.
5. Backend·Data·QA는 그 기준 SHA에서 연동 검증을 수행한다.

### 0.2 이번 문서의 한 줄 요약

- 상담사 화면은 `새 문의 / 처리 중 / 처리 완료` 3개 업무만 먼저 보이고, 문의를 선택해야 상세 상담·기사 일정 조율 기능이 열리는 구조다.

## 1. 최종 구현 화면과 사용 흐름

## 1.1 상담사 화면

### 접근 경로

| 용도 | 경로 | 권한 |
| --- | --- | --- |
| 상담사 기본 업무 화면 | `/consultant/inquiries` | `CONSULTANT` |
| 전체 문의 상세 | `/consultant/inquiries/:inquiryId` | `CONSULTANT` |
| 방문 전환 전용 화면 | `/consultant/inquiries/:inquiryId/visit-transition` | `CONSULTANT` |

`inquiryId`에는 화면용 문의 번호가 아니라 외부 공개 UUID인 `public_id`를 사용한다. 화면에는 사람이 식별하기 쉬운 `inquiry_code` 또는 `inquiry_number`를 별도로 표시한다.

### 최신 레이아웃

상담사는 전화 응대 중 빠르게 사용해야 하므로 한 화면에 모든 상세 정보를 펼쳐 놓지 않았다.

- 좌측 고정 업무 레일
  - 새로 들어온 문의
  - 처리 중인 문의
  - 처리 완료된 문의
- 우측 상단
  - 현재 선택한 업무 상태
  - 실시간 새 문의 건수
  - 문의 검색
- 우측 본문
  - 선택한 상태의 문의 목록
  - 위험도, 대기 시간, 대표 증상, 고객 표시명, 제품 모델, 현재 상태 표시
- 문의 선택 시
  - 우측 상세 Drawer가 열림
  - 고객·제품·증상·안전 안내·공식 근거 확인
  - 상담 시작과 상담 기록
  - 방문 필요 판단
  - 기사 배정과 고객 희망일·방문 일정 조율
  - 처리 결과에 따른 다음 문의 이동

1280×720, 브라우저 배율 100% 기준으로 기본 상담사 화면은 전체 페이지 스크롤 없이 표시되고, 목록만 내부 스크롤한다. 상세 Drawer는 내용이 길면 Drawer 내부에서만 스크롤한다.

### 3개 업무 Bucket 정의

| Bucket | 포함 상태 | 상담사에게 보이는 의미 |
| --- | --- | --- |
| `NEW` | `CONSULTATION_REQUIRED`, `REOPENED` | 새 상담 대기 또는 다시 열린 문의 |
| `IN_PROGRESS` | 완료·취소·NEW 이외의 상담사 노출 상태 | 상담, 방문 검토, 일정 조율, 최종 완료 확인 중 |
| `COMPLETED` | `RESOLVED`, `CANCELLED` | 처리 완료 또는 취소된 이력 |

Bucket은 화면 탐색용 그룹이다. **서버 상태 코드가 아니며 DB에 저장하지 않는다.** Backend는 상태 머신의 canonical 상태를 반환하고 Web Mapper가 화면 Bucket으로 묶는다.

### 상담사 Queue 노출 기준

현재 Mock에서 상담사 Queue는 다음 두 조건을 모두 만족한 문의만 사용한다.

1. `routingTarget === CONSULTANT`
2. 상담사가 처리하거나 완료 이력을 확인할 수 있는 상태

문진 중인 문의는 AI 담당 분류 전이므로 상담사 Queue에 넣지 않는다. 일반 위험도 문의는 AI 판단 이후 방문기사로 자동 인계되는 Mock 정책이므로 상담사 Queue에서 제외한다.

## 2. 디자인·사용성 개편 내용

### 공통 방향

- 색상: 베이비블루·화이트 기반, 선셋오렌지 강조, 딥 네이비 내비게이션
- 글래스 효과: 큰 배경 전체가 아니라 Header·주요 카드·버튼에만 제한
- 레이아웃: 빠른 업무 탐색을 위한 고정 사이드 레일과 집중형 콘텐츠 패널로 구성
- 내비게이션: 상담사 업무 레일과 운영자 사이드바 모두 딥 네이비로 통일
- 오렌지 사용 위치: 새 문의, 운영 개요, 상담 시작, 일정 확정 등 핵심 행동
- 위험·상태 색상: 브랜드 색과 분리해 기존 위험도 의미를 유지
- 데이터 목록: 가독성을 위해 불투명한 밝은 표면 사용

### 상담사 사용성 개선

- 상담사에게 필요하지 않은 상세 내용을 첫 화면에서 제거했다.
- 3개 업무 상태를 좌측 고정 레일에 크게 배치했다.
- 문의 클릭 전에는 목록 탐색에 집중한다.
- 문의 클릭 후에만 상담과 기사 일정 조율 기능을 표시한다.
- 상담과 기사 배정 화면을 분리하지 않고 같은 상세 Drawer 안에서 연결했다.
- 상세 처리 후 상태가 바뀌면 해당 문의가 적절한 업무 Bucket으로 이동한다.

### 운영자 사용성 개선

- 단순 상단 메뉴 대신 고정 관리 사이드바를 추가했다.
- 긴 운영 화면에서 개요·조건·현황으로 바로 이동할 수 있다.
- 필터, KPI, 분포, 예외, 전체 목록을 시각적으로 분리했다.
- 운영 개요는 강한 오렌지 영역으로, 실제 데이터 영역은 차분한 흰색 카드로 구분했다.

## 3. 데이터 원천과 화면 변환 규칙

## 3.1 현재 사용하는 데이터

| 데이터 | 원천 | 용도 |
| --- | --- | --- |
| 문의 22건 | `data/synthetic/fixtures/inquiries.json` | 상담·운영 화면 공통 Mock |
| 고객 공개 ID | 공식 고객 Fixture | 내부 ID를 외부 UUID로 변환 |
| 구독 공개 ID | 공식 구독 Fixture | 문의와 구독 연결 |
| 공식 근거 Registry | `data/processed/structured/evidence/jac104_evidence_registry.jsonl` | 공개 가능한 Evidence 표시 |

Web은 `web/` 폴더만 복사해서 실행하는 구조가 아니다. 저장소 상위 `data/` Fixture를 참조하므로 저장소 전체를 Pull해야 한다.

### 합성 데이터 원칙

- 실제 고객 이름·전화번호·주소를 사용하지 않는다.
- 화면에는 `합성 고객 0**`, `010-****-0000 (합성)` 형태의 표시값만 사용한다.
- 합성 데이터라고 표시된 주소·연락처를 실제 연락이나 업무 처리에 사용하면 안 된다.
- Raw 데이터의 내부 정수 PK를 Route나 화면 식별자로 사용하지 않는다.

## 3.2 식별자 규칙

| 목적 | 필드 | 예시·규칙 |
| --- | --- | --- |
| API·Route 외부 식별자 | `public_id`, `inquiryId` | UUID |
| 사람용 문의 번호 | `inquiry_number`, `inquiryCode` | `INQ-...` |
| 내부 DB 관계 | 정수 PK | Web에 직접 노출 금지 |

Backend가 상세 API를 구현할 때 `/consultant/inquiries/:inquiryId`의 `inquiryId`는 `public_id` UUID와 일치해야 한다.

## 3.3 위험도 최초 라우팅 규칙

현재 팀 피드백을 반영한 Mock 규칙은 다음과 같다.

| 위험도 | AI 판단 후 담당 | 이유 |
| --- | --- | --- |
| `GENERAL` | `FIELD_TECHNICIAN` | 일반 문의는 AI가 방문기사에게 자동 인계 |
| `CAUTION` | `CONSULTANT` | 상담사가 안내 내용을 먼저 확인 |
| `DANGER` | `CONSULTANT` | 상담사가 안전 안내를 먼저 확인 |
| `UNKNOWN` | `CONSULTANT` | 안전하게 상담사가 먼저 확인 |

중요한 경계:

- `DRAFT`, `QUESTIONNAIRE_IN_PROGRESS`에서는 아직 담당 분기를 적용하지 않는다.
- 문진 완료 후 AI 판단 시점에 라우팅한다.
- 위 표는 현재 화면 검증용 Mock 정책이다.
- 실제 서비스에서는 Backend가 상태·담당·`allowed_actions`를 결정한다.
- Web이 위험도만 보고 실제 담당자나 서버 상태를 다시 계산해서는 안 된다.

## 3.4 상태 코드

현재 Web이 표시할 수 있는 canonical 상태는 다음과 같다.

```text
DRAFT
QUESTIONNAIRE_IN_PROGRESS
AI_GUIDANCE
CONSULTATION_REQUIRED
CONSULTATION_IN_PROGRESS
VISIT_REVIEW_PENDING
VISIT_SCHEDULING
VISIT_SCHEDULED
COMPLETION_PENDING
REVISIT_REQUIRED
REOPENED
RESOLVED
CANCELLED
UNKNOWN
```

상태 이름을 화면 문구에 맞춰 새로 만들거나 DB 값과 Web 값을 임의로 혼용하면 안 된다. 상태 머신 계약을 우선하고, 별칭이 필요하면 Backend·PM 합의 후 Mapper에서만 처리한다.

## 3.5 위험도 대소문자

- 현재 공통 계약·DB 방향: `general`, `caution`, `danger`
- 일부 과거 Mock: `GENERAL`, `CAUTION`, `DANGER`
- 현재 Web Mapper: 입력을 대문자로 정규화하고 알 수 없는 값은 `UNKNOWN`

실제 API 연결 시 Backend가 반환할 canonical 대소문자를 하나로 확정해야 한다.

## 3.6 일시 처리

- API 원천은 `+09:00`이 포함된 ISO 8601을 사용한다.
- Web은 시간대를 다시 UTC 또는 브라우저 시간대로 변환하지 않는다.
- 계약 문자열의 연·월·일·시·분을 한국어 표시 형식으로만 바꾼다.
- Backend와 Data는 날짜 경계가 바뀌지 않도록 `+09:00`을 보존해야 한다.

## 4. Backend 담당자가 참고할 연동 계약

## 4.1 현재 실제 연동 여부

| 영역 | 프론트 상태 | 실제 Backend 상태 |
| --- | --- | --- |
| Auth Client | Login·Refresh·Logout·`/me` Client 있음 | 실제 브라우저 E2E 필요 |
| 상담 목록 | 화면·필터·상태 구현 | Mock |
| 상담 상세 | 화면·부분 실패·근거·이력 구현 | Mock |
| 상담 시작·저장·완료 | Form·성공·403·409·422 처리 구현 | Provisional Mock |
| 방문 검토·기사 배정·일정 확정 | 화면·Validation 구현 | 메모리 Mock |
| 운영 대시보드 | 필터·지표·분포·예외 구현 | 프론트 집계 Mock |

`VITE_USE_MOCK_API=false`로 바꾸기 전에 `contracts/api/paths/consultations.yaml`과 관련 Schema가 실제 속성·경로를 가져야 한다. 비어 있는 계약을 근거로 Endpoint를 추측해 구현하거나 호출하지 않는다.

## 4.2 목록 API에 필요한 입력

현재 화면 계약을 유지하려면 목록 API에서 아래 조건을 지원하거나 Backend Adapter에서 동등하게 처리해야 한다.

| 조건 | Web 필드·Query |
| --- | --- |
| 검색 | `q` 또는 합의된 검색 Query |
| 상태 | `status` |
| 위험도 | `risk` |
| 우선순위 | `priority` |
| 담당 조건 | `assignee` |
| 접수 시작일 | `from` |
| 접수 종료일 | `to` |
| 정렬 | `sort` |
| 페이지 | `page` |

응답은 최소한 아래 정보를 제공해야 한다.

- 외부 공개 문의 UUID
- 표시용 문의 번호
- 고객 마스킹 표시명
- 제품 모델
- 대표 증상과 고객 메시지 요약
- 위험도·우선순위·현재 상태
- 접수·변경 시각
- 현재 담당 주체
- 페이지 정보와 전체 건수

우선순위와 담당 주체는 Web이 자체 점수로 계산하지 않고 Backend 반환값을 사용해야 한다.

## 4.3 상세 API에 필요한 정보

- 고객 마스킹 표시 정보
- 제품·구독·케어 정보
- 원문 문의와 구조화 증상
- 문진 답변
- 위험도와 사용 제한 안내
- AI 요약 초안과 상담사 수정·확정본
- 공개 가능한 공식 근거
- 상태 변경 이력
- 현재 `state_version`
- 현재 사용자가 실행할 수 있는 `allowed_actions`
- 방문 검토·배정·일정 정보

부분 실패가 가능해야 한다. 예를 들어 Evidence 검색이 실패해도 고객·제품·상담 Form 전체를 500 화면으로 가리면 안 된다. AI, Evidence, Timeline의 부분 오류를 Section 단위로 표현할 수 있는 계약이 필요하다.

## 4.4 쓰기 API 공통 규칙

상담 시작·저장·요약 확정·상담 완료·방문 검토·일정 저장·방문 확정은 서로 다른 논리 행동이다.

모든 상태 변경 요청에서 다음을 지킨다.

| 항목 | 규칙 |
| --- | --- |
| `state_version` | 사용자가 본 최신 버전 전송, 성공 시 증가 |
| `Idempotency-Key` | 같은 네트워크 재시도에는 유지, 새 행동·Payload 변경·성공 후에는 새 키 |
| `X-Correlation-ID` | 전송 시도마다 새 UUID |
| `allowed_actions` | Backend Guard가 계산한 결과만 반환 |
| 성공 응답 | 최신 상태·버전·허용 행동을 포함한 Snapshot 반환 권장 |
| 409 | 최신 Snapshot을 반환하되 Web이 자동 재전송하지 않음 |
| 422 | `field_errors`로 입력 필드별 오류 전달 |

### 현재 프론트 오류 처리

| HTTP | 화면 처리 |
| --- | --- |
| 401 | Refresh single-flight 후 원요청 1회 재시도 |
| 403 | 권한 없음 표시, 작성 중 입력 보호 |
| 404 | 리소스 없음 또는 접근 은닉 정책 표시 |
| 409 | 작성 내용 유지, 최신 Snapshot·`state_version` 반영, 사용자 재시도 요청 |
| 422 | 작성 내용 유지, 필드 오류 표시 |
| 5xx·Network | 재시도 안내, 무한 자동 재시도 금지 |

`DUPLICATE-EVENT-01`처럼 오류 `details`가 비어 있으면 최신 상태 Snapshot으로 해석하지 않는다.

## 4.5 운영 집계 API에 필요한 결정

프론트에서 22개 문의 전체를 내려받아 집계하는 방식은 운영 규모에 적합하지 않다. 실제 운영에서는 Backend 집계 API가 필요하다.

Backend·PM이 확정할 항목:

- 집계 기준 시각과 Timezone
- 페이지와 전체 건수의 관계
- 증상·상태 분포 집계 단위
- 위험 문의의 정의
- 상담·방문 전환의 정의
- 처리 완료에 취소를 포함할지 여부
- 처리 지연 SLA
- 운영 예외 해제 조건
- 부분 집계 실패 응답
- OPERATOR에게 공개할 고객 정보 범위

## 4.6 CORS와 개발 환경

로컬 Web 기본 포트는 상담사 `5173`, 운영자 `5174`다. 실제 Backend 연동 시 다음 Origin을 개발 환경 정책에 맞게 허용해야 한다.

- `http://localhost:5173`
- `http://localhost:5174`
- 내부망 시연이 필요할 때만 승인된 사설 IP Origin

개발 편의를 이유로 운영 CORS를 `*`로 열지 않는다. Cookie 기반 인증을 사용할 경우 Credentials와 CSRF 정책을 별도로 합의한다.

2. 위험도 대소문자와 상태 코드 정합성을 확정한다.
3. `+09:00` 일시와 SLA 기준 필드를 검증한다.
4. 마스킹 공개 필드와 Evidence 공개 범위를 승인한다.

### AI

1. 문진 완료 후 위험도 분류·담당 라우팅 계약을 Backend와 연결한다.
2. 공식 근거 없음·부분 실패 응답을 확정한다.
3. AI 초안과 상담사 확정본을 분리한다.

### PM

1. 라우팅·완료·SLA·운영 예외 정의를 승인한다.
2. 현재 로컬 디자인을 시연 후 승인한다.
3. `yena` Push SHA를 검토하고 `main` 병합 기준 SHA를 공유한다.
4. 동일 Commit 통합 E2E 일정을 잡는다.

### 프론트 한예나

1. 현재 로컬 변경을 팀 커밋 규칙에 맞춰 Commit·Push한다.
2. Backend 계약이 준비되면 Mock Adapter를 실제 API Adapter로 교체한다.
3. 실제 API 기준 401·403·409·422 E2E를 추가한다.
4. PM이 확정한 SLA·지표·라벨만 화면에 반영한다.

## 13. 인계 결론

상담사·운영자 Web의 프론트 화면, Mock 데이터 흐름, 오류 상태, 권한 Guard, 공통 API 기반, 테스트와 최신 운영형 레이아웃은 로컬에서 검증됐다. 다음 단계의 핵심은 화면을 더 추가하는 것이 아니라 Backend·Data·AI 계약을 확정하고 현재 Mock 입력부를 실제 API Adapter로 교체하는 것이다.

팀원은 다음 세 문장을 기준으로 작업하면 된다.

1. 상태와 `allowed_actions`의 최종 결정자는 Backend다.
2. Web은 외부 UUID·마스킹 데이터·공개 Evidence만 소비한다.
3. 실제 연동 완료 판정은 같은 Commit에서 통합 E2E가 통과한 뒤에만 한다.
