## 2. 수정된 제품 방향

### 한 줄 목표

> 고객이 등록 제품의 증상을 자연어로 말하면 AI가 공식 근거로 해결을 안내하고,
> 위험하거나 해결되지 않은 문의만 상담사에게 넘겨 상담사의 반복 업무를 줄인다.

### 사용자와 가치

| 구분 | 확정 방향 |
| --- | --- |
| 구매 관점 | 기업·고객센터 운영 조직 |
| 핵심 사용자 | 반복 문의를 처리하는 상담사 |
| 고객 역할 | 자연어로 문의하고 자가 해결 안내를 받는 사용자 |
| 핵심 가치 | 안전한 AI 자가 해결과 상담사 반복 업무 감소 |
| 안전 조건 | 위험 문의 이관 누락 0, 근거 없는 단정 0 |

### P0 대표 흐름

```text
고객 자연어 문의
→ Backend 문의·원문 저장
→ Triage/Router가 추가 질문·답변·상담 이관 후보 결정
→ 공식 근거 검색·검증
→ Grounded Answer가 근거 안에서 고객 안내 생성
→ Backend가 결과 저장·State Event 적용
→ 고객이 해결 완료 또는 상담사 연결 선택
→ 상담사는 대화·요약·이관 사유·제품 정보를 확인
```

AI는 업무 상태의 최종 권위가 아니다. AI는 Route·Event 후보만 반환하고,
Backend State Machine이 Guard·`state_version`·권한을 검증해 최종 전이를
적용한다.

## 3. P0·P1 범위 재정렬

### 3.1 P0 유지·추가 범위

- 고객 구독 제품 조회와 문의 생성
- 자연어 증상 입력
- 동일 Inquiry 안의 추가 질문 최대 2회
- 공식 근거 검색과 검증된 고객 안내
- 위험·근거 없음·Provider 오류의 상담 Fallback
- 고객의 `해결됐어요`·`상담사 연결` 행동
- 상담사 문의 목록·상세·우선순위·AI 처리 결과·이관 사유 확인
- 상담 시작·기록·완료 Runtime
- Backend State·권한·멱등성·동시성·추적성
- `CR-001` 전화 문의 등록의 승인된 최소 Slice 마감
- 실제 LLM·팀 pgvector·Backend HTTP의 최소 수직 연결

### 3.2 P1 하향 범위

- 방문기사 앱과 방문 실행 Runtime
- 방문 일정 생성·확정·변경 UI와 API
- 방문 결과·교체 항목·기사 확정 리포트
- 방문 결과의 케어 이력·다음 일정 자동 반영
- 기사 사전 점검·브리핑 Agent
- 기사 위치 추적과 지도 기능
- 운영 담당자·Supervisor 전용 화면과 Dashboard
- 범용 장기 기억 챗봇, 무제한 대화, Streaming, 음성·파일 첨부
- 선제적 필터 교체 알림·자동 예약 등 예방 관리 고도화

### 3.3 기존 WBS Task 처리 제안

| Task | 수정안 |

| `T-025` | 7개 Agent 동시 완성 대신 2개 핵심 Agent와 결정론적 Tool의 실제 Routing으로 범위 축소 |
| `T-026` | 기존 추가 질문·답변·중복 방지 Runtime을 제한형 챗봇의 대화 기반으로 재사용 |

| `T-046` | 고객→AI→상담 최소 Slice는 P0, 방문기사 구간은 P1로 분리 |
| `T-047`·`T-048`·`T-050` | 문의·AI·상담·안전 검증은 P0, 방문기사 전용 Case는 P1로 분리 |

조건에서 제외하고 후속 구현과 호환되는 계약으로 유지한다.

## 4. 제한형 자유입력 챗봇 완료 경계

### 포함

- 고객은 등록 제품 증상을 자연어로 입력한다.
- 지원 Domain은 정수기 증상·사용 안내·관리 문의로 제한한다.
- 한 Inquiry 안에서만 문맥을 유지한다.
- 추가 질문은 최대 2회다.
- 고객은 언제든 `해결됐어요` 또는 `상담사 연결`을 선택할 수 있다.
- 답변은 검증된 공식 근거 안에서만 생성한다.
- 제품·세대 불일치, 근거 없음, 누수·감전·화상 등 위험 신호는 추측하지
  않고 안전 안내 후 상담사에게 이관한다.
- Backend가 권한·멱등성·`state_version`·저장·상태 전이를 통제한다.
- 기존 InquiryQA·FollowupAnswer·AI Run·Replay를 우선 재사용한다.

### 제외

- 별도 범용 Chat Session·Message Platform
- 정수기와 무관한 자유 질의응답
- 여러 Inquiry 사이의 장기 기억
- 무제한 Turn과 무한 재질문
- 공식 근거 밖의 일반 지식 답변
- AI가 Inquiry·Consultation·Visit 상태를 직접 변경하는 기능

### 최소 AI 실행 구조

| 구성 | 책임 | 구현 방식 |
| --- | --- | --- |
| `Triage/Router Agent` | 추가 질문·근거 답변·상담 이관 Route 후보 | 구조화 출력 |
| `Grounded Answer Agent` | 검증 Evidence 안에서만 고객 안내 생성 | 실제 LLM + Structured Output |
| Safety | 위험 신호와 금지 행동 차단 | 기존 결정론적 Rule 우선 |
| Retrieval | 제품·세대가 일치하는 공식 근거 검색 | 기존 Adapter·Exact Filter 재사용 |
| Validation | 근거·Schema·금지 표현 최종 검증 | 기존 결정론적 Validator 우선 |

Agent 수를 완료 지표로 사용하지 않는다. 위 흐름이 실제 Runtime에서
Routing·Fallback·Trace와 함께 재현되는지를 완료 기준으로 사용한다.

## 5. 팀원별 수정 업무

### 5.1 윤승혁 — PM·기술 통합

#### 필수 업무

1. `CR-002`, `CR-003`의 승인 여부와 P0/P1 경계를 확정한다.
2. 고객→AI→상담 흐름, 2개 Agent 책임, Backend State 권위를 한 장의 흐름도로
   정리한다.
3. 기존 7개 Agent Gate를 2개 핵심 Agent+Safety/Retrieval/Validation Tool
   Gate로 변경할지 결정한다.
4. 기존 Event·Action 재사용 여부와 필요한 최소 계약 변경만 승인한다.
5. 팀 설명 후 각 담당자가 자신의 입력·출력·선행조건을 다시 설명하게 한다.
6. 매일 같은 Commit의 Integration Gate와 P0/P1 이탈 여부를 판정한다.

#### 완료 증거

- 승인된 변경 결정 기록
- P0 전체 흐름도와 책임표
- 담당자별 입력·출력·완료 기준
- 최종 기준 Commit과 Gate 판정

### 5.2 최지용 — Backend·Database

#### 필수 업무

1. 기존 문의 생성·증상 제출·추가 질문·Replay Runtime을 챗봇 흐름에서
   재사용 가능하게 연결한다.
2. AI 응답의 Route 후보·추가 질문·안내·이관 사유를 검증하고 기존 원장에
   저장한다.
3. Backend State Machine이 최종 Event·State를 결정하도록 유지한다.
4. `state_version`, Idempotency, 권한, Correlation·AI Run Trace를 보존한다.
5. AI `chunk_id`를 검증된 Crosswalk로 Backend `public_id`에 연결하고 고객
   DTO에서 내부 식별자·경로·원문 전체를 숨긴다.
6. 상담 대기 목록·상세·시작·기록·완료 Runtime을 Web에 제공한다.
7. `CR-001` 전화 문의 등록은 현재 승인 범위의 Web 공동 Smoke까지 마감한다.

#### 제외·후순위

- 방문 생성·일정·확정·완료 Runtime 신규 확장
- 범용 Chat Session·Message DB 신설

#### 완료 증거

- 정상·추가 질문·위험·근거 없음·Timeout API Test
- PostgreSQL·Migration Drift·권한·멱등성·동시성 결과
- Backend→AI 실제 HTTP와 DB·State·Trace 결과

### 5.3 이동윤 — AI·RAG

#### 필수 업무

1. `Triage/Router Agent`와 `Grounded Answer Agent`를 우선 구현한다.
2. Safety·Retrieval·Validation은 기존 결정론적 구조를 재사용하고 생성형
   Agent로 불필요하게 확대하지 않는다.
3. 실제 LLM Provider와 Structured Output, Timeout·Rate Limit·Fallback을
   구현한다.
4. 팀 pgvector와 제품·세대 Exact Filter를 실제 Runtime에 연결한다.
5. AI가 Backend State를 직접 변경하지 않고 Route·Event 후보만 반환한다.
6. 모델 비교는 결정적 Baseline과 실제 후보 2개 이하를 같은 Case에서 비교해
   선택 근거를 남긴다.
7. 신규 검색 기법을 넓히기보다 현재 검증된 Retrieval 기준선과 공식
   Evidence 연결을 우선 닫는다.

#### 완료 증거

- Agent Unit·Routing·Handoff·최대 Hop Test
- 실제 LLM Schema·Grounding·Latency·Fallback 결과
- 팀 pgvector 검색 결과
- 정상·추가 질문·위험·근거 없음·Provider 실패 결과

### 5.4 김은진 — Data·QA·DevOps

#### 필수 업무

1. 같은 Commit에서 Backend·AI·Mobile·Web이 실행되는 통합 검증 환경을
   제공한다. 공유 환경은 통합용으로 사용하고 단위 Test는 격리 DB를 유지한다.
2. 공식 Evidence와 평가 질문·기대 Route·기대 답변을 2인 검수한다.
3. 모델·청킹 선택은 같은 평가 Case의 정확성·Grounding·응답 시간·비용으로
   비교하고 실제 결과와 가설을 구분한다.
4. 실제 LLM·팀 pgvector·Backend HTTP 5개 Case를 독립 재현한다.
5. CI·Test·Exit Code·환경·Commit을 하나의 QA 증거로 취합한다.
6. 방문기사 전용 Test는 P1로 분리하고 P0 Gate를 차단하지 않게 한다.

#### 완료 증거

- 승인된 평가 Case·Evidence 목록
- 동일 SHA의 5개 통합 Case 결과
- Contract·Data·Backend·AI·Client 회귀 결과
- Mock·실제 Runtime·NOT_RUN 구분이 있는 QA 보고

### 5.5 양정현 — Mobile

#### 필수 업무

1. 고객이 등록 제품을 선택하고 자연어 증상을 입력하는 채팅 UI를 구현한다.
2. 기존 문의·추가 질문·답변 API를 대화 말풍선 형태로 소비한다.
3. 추가 질문 최대 2회, 응답 대기, 재시도, 중복 전송 방지 상태를 처리한다.

5. `해결됐어요`와 `상담사 연결` 행동을 서버의 `allowed_actions`와 일치시킨다.
6. 위험·근거 없음·503·Timeout·409에서 입력을 보존하고 안전한 복구 또는
   상담 이관을 제공한다.

#### 제외·후순위

- 방문기사 앱 Remote 전환과 방문 실행 화면
- 장기 기억·Streaming·음성·파일 첨부 UI

#### 완료 증거

- 고객 챗봇 Unit·UI Test
- 실제 Backend Remote Smoke
- Build·APK·실단말 결과
- 정상·위험·근거 없음·오류 화면 증거

### 5.6 한예나 — Web

1. 상담 대기 목록과 상세를 실제 Backend Remote Repository로 소비한다.

   처음 보는 상담사에게도 드러나게 한다.
3. 상세에서 고객 대화, 제품, AI 구조화 결과, 검증 Evidence, 이관 사유와

4. 상담 시작·기록·완료 Action과 서버 `allowed_actions`, 409 복구를 유지한다.
5. `CR-001` 전화 문의 등록의 Remote Adapter·결과 없음·오류·공동 Smoke를
   마감한다.
6. 필요한 API Gap은 목적·입력·기대 출력·완료 기준·기한의 짧은 형식으로
   Backend에 요청한다.

#### 제외·후순위

- Visit UI 실제 API 전환
- 운영 담당자·Supervisor Dashboard

#### 완료 증거

## 6. 공통 Gate와 일정

### 6.1 남은 5주차 실행 순서

| 순서 | 작업 | 담당 | 종료 조건 |
| --- | --- | --- | --- |
| 1 | P0/P1·챗봇·Agent 범위 결정 | 윤승혁·전원 | 변경 결정과 흐름도 승인 |
| 2 | 기존 계약·Runtime 재사용 Gap 확정 | 윤승혁·최지용·이동윤 | 신규 State·DB 최소화 |
| 3 | Backend·AI 최소 수직 Slice | 최지용·이동윤 | 실제 HTTP·Schema·DB·State·Trace |
| 4 | Mobile 고객 흐름·Web 상담 흐름 연결 | 양정현·한예나 | Remote Smoke와 오류 처리 |
| 5 | 동일 SHA 독립 QA | 김은진·전원 | 5개 Case와 회귀 결과 기록 |
| 6 | PM Exit 판정 | 윤승혁 | PASS·CONDITIONAL_PASS·HOLD와 인계 기록 |

### 6.2 필수 검증 Case

| Case | 기대 결과 |
| --- | --- |
| 정상·근거 있음 | 공식 근거 안내 후 고객이 해결 완료 가능 |
| 정보 부족·Replay | 최대 2회 질문, 중복 처리·추가 AI 실행 없음 |
| 위험 | 자가조치 확대 없이 안전 안내와 우선 상담 이관 |
| 근거 없음 | 임의 답변 없이 판단 보류와 상담 이관 |
| 503·Timeout | 고객 입력 보존, 오류 기록, 안전한 재시도 또는 상담 이관 |

### 6.3 5주차 Exit 판정

```text
PASS
= 승인된 P0 범위가 실제 LLM·팀 pgvector·Backend·Mobile·Web에서
  같은 Commit으로 5개 Case를 통과

CONDITIONAL_PASS
= 계약과 최소 수직 Slice는 통과했으나 외부 환경 검증 일부가
  담당자·목표일·해제 조건과 함께 인계됨

HOLD
= Backend↔AI 실제 연결, 안전한 상담 이관 또는 공식 근거 검증이
  재현되지 않음
```

방문기사·운영자 기능이 미완료라는 이유만으로 수정된 P0 Exit를 차단하지
않는다. 반대로 Mock·Fixture만 성공한 결과를 실제 Runtime PASS로 기록하지
않는다.

## 7. 업무량 통제 규칙

1. 챗봇을 위해 범용 대화 Platform을 새로 만들지 않는다.
2. 2개 핵심 Agent가 실제로 동작하기 전 Agent를 추가하지 않는다.
3. 새로운 Chunking·Hybrid·Reranker 실험은 현재 P0 실패를 직접 해결하는
   근거가 있을 때만 승인한다.
4. 방문기사·운영자 범위는 P0 담당자에게 되돌리지 않는다.
5. Frontend 대기 시간은 다른 영역 Runtime 구현이 아니라 고객·상담사 UX,
   Mock Adapter, 평가 질문·기대 결과 작성에 사용한다.
6. 한 시간 이상 차단되면 같은 날 담당자와 PM에게 요청한다.
7. 인계 문서는 새 장문 요청서를 반복하지 않고 다음 다섯 줄로 작성한다.

```text
목적=
입력=
기대 출력=
완료 기준=
기한=
```
