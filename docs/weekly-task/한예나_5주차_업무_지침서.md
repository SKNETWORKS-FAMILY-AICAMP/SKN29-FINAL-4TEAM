>
> 대상 기간: **2026년 8월 10일 ~ 8월 14일**
>
> 5주차 운영 컨셉: **WBS 5주차 Web Remote 전환 · 상담/방문 실제 API 경계 연결 · 조기 E2E 조건부 실행**
>
> 핵심 Remote 연동 동결 목표: **2026년 8월 13일 오후**
>
> 최종 Web 회귀·E2E 기준선 목표: **2026년 8월 14일**
>
> 5주차 운영 원칙: 4주차까지 구현한 상담사 UI·Mock 업무 흐름·오류 처리·권한 Guard를 더 넓히는 것이 아니라, **Mock Repository와 화면 내부 업무 판단을 실제 Backend API·DTO·State·`allowed_actions` 소비 구조로 교체하는 것**을 최우선으로 한다.
>
> 한예나는 5주차에 새로운 상담사 화면을 많이 추가하는 역할이 아니다. 현재 Web은 상담 목록·상세·상담 기록·방문 전환·409 처리·멱등성·오류 UI 등 실제 연동을 위한 화면 기반이 이미 상당히 구현되어 있다. 따라서 5주차에는 화면 확장보다 **Remote Repository 도입, 서버 Pagination·Filter, 실제 상담 Action, 실제 Visit 흐름, AI/Evidence 결과 소비, E2E 참여**에 집중한다.
>
> 6주차 가용 시간이 제한되므로 WBS 5주차의 상담사 Remote 경계를 우선 확보한다. 대표 E2E와 전체 Feature Complete는 선행 Gate가 조기에 닫힌 경우에만 앞당긴다.
>
> 운영 Dashboard와 신규 운영 통계는 P1로 두며, 5주차 P0 Remote 전환보다 우선하지 않는다.

현재 코드 검사 기준으로 Web에는 다음 기반이 이미 존재한다.

1. React·Vite·TypeScript 기반 Web 구조와 상담사·운영 Route가 존재한다.
2. 로그인·Refresh·Logout·`/me`를 처리하는 실제 Auth API Client가 존재한다.
3. 공통 HTTP Client에는 Bearer Token, `X-Correlation-ID`, Idempotency Key, Timeout, 401 Refresh Single-flight, Error Mapping이 구현되어 있다.
4. `AuthGuard`, `RoleGuard` 기반 역할 접근 제어가 존재한다.
5. 상담사 문의 큐·검색·Filter·정렬·Pagination UI가 Mock 기준으로 구현되어 있다.
6. 문의 상세에는 고객·제품·AI 요약·Evidence·상담 기록·Timeline·방문 전환 UI가 구현되어 있다.
7. 403·409·422·Network·Loading·Empty·Partial Error UI가 존재한다.
8. 409 State Conflict 발생 시 작성 내용 보존, 최신 `stateVersion`·`allowed_actions` 반영, 자동 재전송 방지 기반이 있다.
9. Idempotency Key 재사용과 중복 클릭 방지 기반이 있다.
10. 현재 상담 업무 Repository는 `dataSource: "MOCK"`로 고정된 동기 Interface이며 실제 Backend Remote Repository는 없다.
11. `VITE_USE_MOCK_API=false`여도 업무 데이터는 실제 API가 아니라 Mock Preview를 반환하는 상태다.
12. 상담사 목록·상세·상담·방문 OpenAPI 계약은 8월 8일 기준 상당 부분 확정되었으므로, 5주차에는 “계약이 없어서 못 붙임”이 아니라 **Runtime 제공 즉시 실제 API를 소비하는 단계**로 이동해야 한다.
13. 현재 방문 화면은 `datetime-local`, `desiredAt`, `confirmedAt` 중심인데 확정 P0 계약은 `preferred_date`, `confirmed_date`의 **date-only**이다.
14. 현재 상담사 상세 Mock에는 서비스 주소가 포함되지만 상담사 P0 Projection은 주소 비노출 정책이므로 실제 Remote 전환 시 수정해야 한다.
15. Web Test·Lint·TypeScript·Production Build의 4주차 저장 증거는 존재하지만 5주차에는 최신 Commit에서 다시 실행해야 한다.

따라서 5주차의 핵심 전환은 다음이다.


# 2. 5주차 역할 목표

1. **8월 10일 오전까지 Web 기준선과 실제 Backend Runtime 상태를 재검증한다.**

   Test·Lint·TypeScript·Build를 다시 실행하고 상담사 문의 목록·상세, 상담 Action, 방문 Action, AI·Evidence Endpoint를 실제 `main` 기준으로 `READY`, `RUNTIME_DONE`, `BLOCKED_BY_BACKEND`, `CONTRACT_ONLY`로 구분한다.

2. **8월 10일까지 Mock 전용 Repository 경계를 비동기 Remote 대응 구조로 전환한다.**

   기존 Mock Repository를 제거하지 않고 명시적 Demo Adapter로 유지하되, 실제 기본 흐름은 비동기 `RemoteConsultantRepository`가 사용할 수 있도록 Interface·Query State·Loading·Error 구조를 변경한다.

3. **8월 11일까지 상담사 Inquiry 목록·상세를 실제 Backend API로 전환한다.**

   `GET /api/v1/inquiries`, `GET /api/v1/inquiries/{id}`를 실제 호출하고, Web 로컬 Filter·Sort·Pagination을 서버 Query·`page_info` 기반으로 바꾼다. 실제 계약에 없는 Filter는 제거·비활성·P1로 분리한다.

4. **8월 12일까지 상담 시작·기록·요약 확정·상담 완료를 실제 API로 연결한다.**

   Mock `submitConsultationMock()`과 화면 내부 `nextStatus` 계산을 제거하고, Backend가 반환한 `status`, `state_version`, `allowed_actions`를 그대로 사용한다.

5. **8월 12일까지 AI·Evidence·Fallback 표시를 실제 Backend 공개 DTO로 연결한다.**

   AI 내부 `chunk_id`, 검색 점수, 파일 경로, Prompt를 화면에 노출하지 않고, Backend가 공개한 역할별 Guidance·Evidence·Summary만 표시한다.

6. **8월 13일까지 Visit 흐름을 실제 계약에 맞춰 재구성하고 Backend Runtime에 연결한다.**

   `datetime-local`을 date-only 입력으로 수정하고, “기사 선택 후 방문 생성”이 아니라 **Visit 생성→기사 선택·일정 저장→방문 확정** 흐름으로 맞춘다.

7. **3장 필수 Remote 연동이 조기에 완료된 경우에만 상담사 대표 Web E2E를 5장 조건부 업무로 실행한다.**

   로그인→상담 큐→상세→AI 결과 확인→상담 시작→요약 수정·확정→방문 필요 판단→Visit 생성→기사·일정→확정까지 실제 Backend를 통해 재현한다.

8. **8월 14일까지 WBS 5주차 Web 범위의 Test·Lint·TypeScript·Build 결과와 6~7주차 잔여 범위를 고정한다.**

   6주차에는 신규 P0 화면이나 Mock 제거 작업을 남기지 않고 배포·UI 마감·잔여 버그·Release Candidate 검증으로 전환한다.

5주차 완료 기준은 “Remote API 함수가 존재한다”가 아니다. **WBS 5주차 대상 상담사 화면이 Remote Repository를 사용하고 목록·상세·상담·Visit 연동 경계가 실제 Backend State를 반영해야 한다.**

# 3. 5주차 필수 업무

> 이 장은 현행 WBS의 **5주차 범위**만 필수로 다룬다. WBS상 6~7주차에 배정된 전체 E2E·전체 회귀·후행 Runtime·최종 Feature Complete 업무는 5장의 조기 완료 업무로 분리한다.

## 3.1 Web Entry Gate·Backend Runtime 대응표 재검증

### 작업 목적

4주차의 Mock·`BACKEND_BLOCKED` 문구를 그대로 이어가지 않고 현재 Backend Runtime과 계약을 기준으로 Web 연동 가능 범위를 다시 판정한다. 실연동 작업 중 오래된 Mock 계약이나 잘못된 Endpoint를 기준으로 구현하지 않게 한다.

### 작업 위치

```text
web/
├─ package.json
├─ vite.config.ts
├─ tsconfig*.json
├─ .env.example
├─ src/**
├─ tests/**
└─ README.md

contracts/api/**
contracts/state-machine/**
contracts/error-codes/**
backend/config/api_urls.py
backend/apps/inquiries/**
backend/apps/consultations/**
backend/apps/visits/**
```

### 세부 작업 지침

1. 최신 `main` 또는 PM이 지정한 기준 Commit을 기록한다.
2. Node·npm Version을 기록한다.
3. 의존성을 설치한다.
4. 다음 Gate를 실행한다.

```cmd
cd web
npm test
npm run lint
npm run typecheck
npm run build
```

5. 실제 Script 이름이 다르면 `package.json`의 현재 Script를 따른다.
6. 4주차 저장 결과를 현재 PASS로 재사용하지 않는다.
7. 상담사 P0 Endpoint를 실제 Backend Route와 OpenAPI로 대조한다.
8. 다음 상태로 분류한다.
   - `RUNTIME_DONE`
   - `READY_FOR_WEB_INTEGRATION`
   - `BLOCKED_BY_BACKEND`
   - `CONTRACT_ONLY`
   - `MOCK_ONLY`
   - `NOT_P0`
9. 최소 다음 Endpoint를 확인한다.

```text
GET   /api/v1/inquiries
GET   /api/v1/inquiries/{id}

POST  /api/v1/inquiries/{id}/start-consultation
PATCH /api/v1/inquiries/{id}/consultation-summary
POST  /api/v1/inquiries/{id}/consultation-summary/confirm
POST  /api/v1/inquiries/{id}/complete-consultation

POST  /api/v1/inquiries/{id}/visit-review
POST  /api/v1/inquiries/{id}/visits
POST  /api/v1/inquiries/{id}/visit-not-needed
PATCH /api/v1/visits/{visit_id}/schedule
POST  /api/v1/visits/{visit_id}/confirm
```

10. 실제 Runtime이 아직 없는 Endpoint는 `BLOCKED_BY_BACKEND`로 표시한다.
11. 계약이 존재하는 Endpoint를 “계약 미정”이라고 문서에 남기지 않는다.
12. `VITE_USE_MOCK_API`의 현재 의미를 확인한다.
13. Remote Mode에서 Mock을 자동 반환하는 부분을 목록화한다.
14. Web 업무 흐름에 남아 있는 `dataSource: "MOCK"` 고정 Interface를 확인한다.
15. 화면 내부 `nextStatus`, Routing Decision, 로컬 `allowed_actions` 추론 코드를 목록화한다.
16. 실제 계약과 불일치하는 Filter를 목록화한다.
17. 상담사 화면의 주소·PII 노출 지점을 확인한다.
18. Visit 날짜·시간 입력 계약 불일치를 확인한다.
19. AI Evidence의 공개·비공개 필드를 확인한다.
20. Blocker에 제공자·해제 조건·목표 일자를 붙인다.

### 완료 기준

- 최신 Commit에서 Test·Lint·TypeScript·Build 결과가 있다.
- 상담사 P0 Endpoint의 Runtime 상태가 최신 Backend와 일치한다.
- Mock 자동 대체 구간이 모두 목록화되어 있다.
- 실제 계약과 다른 Filter·날짜·PII·State 처리 항목이 명확하다.
- 5주차에 제거할 Web 내부 업무 판단 로직이 정리되어 있다.
- Backend가 열리는 즉시 작업할 순서가 정해져 있다.

## 3.2 Mock 전용 Repository를 비동기 Remote Repository 구조로 전환

### 작업 목적

현재 동기 `MOCK` 전용 Repository를 실제 HTTP 기반 비동기 Repository로 확장한다. 화면 Component가 Mock·Remote 구현 세부사항에 직접 의존하지 않게 하고, 실제 API를 사용할 때 Loading·Error·Retry·Cancel을 정상 처리한다.

### 작업 위치

```text
web/src/common/api/**
web/src/entities/**
web/src/features/consultant/**
web/src/features/inquiry/**
web/src/features/consultation/**
web/src/features/visit/**
web/src/features/workflow-action/**
web/src/pages/consultant/**
web/tests/**
```

### 권장 구조

```text
ConsultantRepository
├─ MockConsultantRepository
└─ RemoteConsultantRepository

RemoteConsultantRepository
├─ listInquiries(query)
├─ getInquiryDetail(inquiryId)
├─ startConsultation(...)
├─ saveConsultationSummary(...)
├─ confirmConsultationSummary(...)
├─ completeConsultation(...)
├─ reviewVisit(...)
├─ createVisit(...)
├─ scheduleVisit(...)
└─ confirmVisit(...)
```

### 세부 작업 지침

1. `dataSource: "MOCK"`로 고정된 Interface를 실제 구현 선택이 가능한 구조로 바꾼다.
2. Repository method를 실제 네트워크 호출에 맞게 비동기화한다.
3. Component에서 직접 `fetch`하지 않는다.
4. 기존 `httpClient.ts`를 재사용한다.
5. Token Refresh·Correlation·Timeout 로직을 Feature마다 중복 구현하지 않는다.
6. `AbortController` 또는 현재 구조에 맞는 취소 처리를 검토한다.
7. 화면 이동 후 완료된 오래된 요청이 최신 State를 덮어쓰지 않게 한다.
8. Repository가 Backend DTO를 그대로 UI 전체에 퍼뜨리지 않게 한다.
9. API DTO와 Web ViewModel 사이 Mapper를 둔다.
10. Mock Fixture Type과 Backend DTO Type을 동일 Type으로 억지 통합하지 않는다.
11. Mock Repository는 개발·Fallback 시연용으로 명시적으로 유지할 수 있다.
12. Remote 실패 시 자동으로 Mock Repository를 호출하지 않는다.
13. `VITE_USE_MOCK_API=false`가 실제 Remote를 사용하도록 의미를 바꾼다.
14. `VITE_USE_MOCK_API=true`는 명시적 Mock Mode로만 사용한다.
15. 화면 상단에 실제 Remote인데 “Mock” 또는 반대 상태가 표시되지 않게 한다.
16. Loading·Empty·Error·Partial Error를 Remote Query State에 연결한다.
17. 일반 API 오류와 Network/Timeout을 구분한다.
18. 401은 공통 Client에서 처리하고 Feature가 별도 Refresh를 수행하지 않는다.
19. 동일 Write Action 재시도에는 Idempotency Key를 재사용한다.
20. 새로운 Write Action에는 새 Key를 사용한다.
21. Repository Boundary Test를 Mock·Remote 각각 보강한다.
22. Remote Mode에서 Mock 호출이 발생하지 않는 Test를 추가한다.

### 완료 기준

- 동기 Mock 전용 Interface가 실제 비동기 Remote 구조로 전환되어 있다.
- Component가 Mock·Remote 구현에 직접 의존하지 않는다.
- Remote Mode에서 실제 HTTP가 호출된다.
- Remote 실패를 Mock 성공으로 대체하지 않는다.
- API DTO→ViewModel Mapper가 존재한다.
- Loading·Error·Retry가 비동기 요청과 연결된다.

## 3.8 Web 공통 State·`allowed_actions`·오류 처리 실제 Runtime 정합화

### 작업 목적

4주차 Mock에서 준비한 State·409·멱등성 기반을 실제 Backend 응답에 연결한다. 화면별로 상태 판단을 중복 구현하지 않고, Backend State Machine과 UI Action이 같은 계약을 사용하게 한다.

### 작업 위치

```text
web/src/features/workflow-action/**
web/src/common/api/**
web/src/common/model/**
web/src/entities/inquiry/**
web/src/entities/visit/**
web/tests/**
contracts/state-machine/**
contracts/error-codes/**
```

### 세부 작업 지침

1. `allowed_actions`를 실행 버튼 표시의 기준으로 사용한다.
2. State→Action을 Web에서 별도 Lookup하여 덮어쓰지 않는다.
3. 화면 편의를 위한 `getCounselorRoutingDecision(risk)`를 업무 결정에 사용하지 않는다.
4. 위험도는 표시 정보이지 Web Workflow 권위가 아니다.
5. `state_version`을 모든 State-changing Action에 포함한다.
6. Write Hook이 최신 Version을 사용하게 한다.
7. 성공 Response의 Version을 즉시 반영한다.
8. 409 Response의 최신 Version·Action이 있으면 반영한다.
9. 409 발생 시 Draft·입력값을 유지한다.
10. 자동 Retry는 금지한다.
11. Network 실패는 사용자 재시도 시 같은 Idempotency Key를 재사용한다.
12. 서버가 응답을 받았으나 화면 업데이트 중 실패한 경우 중복 요청을 피한다.
13. 401은 공통 Session 처리와 일치시킨다.
14. 403은 역할 접근 오류와 객체 권한 오류를 구분 가능한 범위에서 표시한다.
15. 404는 타 사용자 Resource 존재 여부를 추측하게 하지 않는다.
16. 422는 Field Error를 가능한 범위에서 입력 UI에 연결한다.
17. 5xx는 재시도 가능 UI를 제공한다.
18. Timeout을 일반 Validation Error로 표시하지 않는다.
19. `correlation_id`가 Error 화면·로그에서 추적 가능하되 Token·PII를 노출하지 않는다.
20. Action별 Error Test를 보강한다.
21. State Contract Test를 최신 Registry와 맞춘다.
22. 오래된 상태 코드가 Fixture에 남지 않게 한다.

### 완료 기준

- Web Action이 Backend `allowed_actions`를 따른다.
- Web이 State·Routing을 최종 결정하지 않는다.
- `state_version`·Idempotency가 실제 Write에 적용된다.
- 409 후 Draft가 보존되고 최신 상태가 반영된다.
- 401·403·404·409·422·5xx·Timeout이 구분된다.
- State·Error Contract Test가 통과한다.

5주차 종료 시점에는 **“상담사 화면은 완성됐지만 데이터는 Mock”이라는 상태를 끝내고, 상담사가 실제 고객 Inquiry와 AI 결과를 확인하고 상담·방문 업무를 실제 Backend를 통해 처리하는 상태**가 되어야 한다.
