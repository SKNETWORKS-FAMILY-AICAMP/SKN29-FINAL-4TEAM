# 3. 8월 13일 — 통합 환경과 수직 연결 닫기

## 3.1 공용 통합 실행 환경 확정

각자 로컬에서 따로 DB와 서비스를 띄우는 상태를 끝내고, E2E 검증 시 모두가 동일한 Backend·DB·AI 환경을 바라볼 수 있게 한다.

### 해야 할 일

1. Backend·AI·PostgreSQL/pgvector가 함께 실행되는 **공용 통합 환경**을 우선 확보한다.
2. 팀원이 같은 환경에 접속할 수 있도록 필요한 환경 변수와 접속 방법을 정리한다.
3. Mobile과 Web 담당자가 자신의 클라이언트에서 같은 Backend 주소를 바라보도록 연결을 지원한다.
4. Secret 원문은 문서나 Git에 남기지 않는다.
5. 공용 환경은 **통합 검증용**으로 사용하고, 개별 단위 테스트까지 하나의 공유 DB에 의존하게 만들지 않는다.

### 완료 기준

- Backend Health 확인
- DB 연결 확인
- AI Health 또는 실제 호출 가능 확인
- Mobile → Backend 요청 성공
- Web → Backend 요청 성공

환경 구축 자체를 완벽하게 자동화하는 데 시간을 과도하게 쓰지 않는다. **8월 14일 E2E를 돌릴 수 있을 정도면 충분하다.**

## 3.2 Backend ↔ AI 실제 Baseline 연결 검증

현재 Mock HTTP 검증은 이미 있으므로, 이번에는 **현재 Baseline AI를 실제 Backend 호출 경로에 연결하는 것**이 핵심이다.

```text
고객 증상 입력
→ Backend 저장
→ AI 실제 호출
→ 현재 Baseline RAG/LLM 처리
→ 응답 Schema 검증
→ Backend 결과 저장
→ 상태·allowed_actions 반영
```

### 김은진 역할

- 실행 환경과 테스트 입력을 준비한다.
- 같은 `correlation_id`로 Backend 요청 → AI 실행 → DB 저장을 추적한다.
- 오류가 발생하면 `ENVIRONMENT_BLOCKED`, `CODE_FAILED`, `INTEGRATION_BLOCKED` 중 하나로 즉시 분류한다.
- 코드 결함은 해당 담당자에게 **재현 명령 + 기대 결과 + 실제 결과**만 전달하고 직접 대신 구현하지 않는다.
- 수정이 올라오면 전체 테스트를 처음부터 다시 돌리지 말고 **실패 구간부터 빠르게 재검증**한다.

### 이번에 하지 않는 것

- 모델 비교
- 임베딩 비교
- Chunking 비교
- Retriever 비교
- Multi-Agent 성능 비교
- 새 평가 Dataset 확장

현재 Baseline이 품질상 완벽하지 않아도 **호출 → 처리 → 저장이 정상적으로 이어지면 통과**로 본다.

# 4. 8월 14일 — 고객 → AI → 상담사 E2E 완성

## 4.1 대표 P0 E2E를 최우선으로 실행

```text
고객 Mobile
→ 로그인·제품 확인
→ 문의 생성·증상 입력
→ Backend 저장
→ AI Baseline 처리
→ 고객에게 AI 안내 표시
→ 미해결 또는 상담 필요 처리
→ 상담사 연결
→ 상담사 Web에서 문의 확인
→ 상담 시작·처리
→ 완료 상태 반영
→ 고객 화면에서 최종 상태 확인
```

방문기사 흐름은 P1으로 내렸으므로 **이번 E2E의 완료 조건에 포함하지 않는다.**

---

## 4.2 E2E 진행 방식

### 1순위 — Happy Path 한 건 완주

처음부터 오류 Case를 많이 만들지 않는다. **정상 시나리오 한 건을 끝까지 통과시키는 것을 가장 먼저 완료한다.**

### 2순위 — 시연을 막는 오류만 수정

Happy Path가 성공한 뒤 다음 정도만 빠르게 확인한다.

- 중복 요청 시 같은 문의가 두 번 생성되지 않는지
- 상태가 바뀐 뒤 오래된 요청이 들어오면 409가 정상 처리되는지
- AI 호출 실패 시 서비스 전체가 멈추지 않는지
- 상담사 Web에서 고객 문의와 필요한 정보가 실제로 보이는지

광범위한 회귀·성능·안전 실험은 이번 이틀의 목표가 아니다.

---

## 4.3 전화 문의 등록 최소 Smoke

`CR-001` 전화 문의 등록은 이미 착수 중이고 이번 변경에서 유지하기로 했으므로, 핵심 E2E가 닫힌 뒤 **최소 Smoke Test만 수행**한다.

```text
상담사 Web에서 고객 조회
→ 전화 문의 등록
→ 기존 Inquiry Workflow로 진입
→ DB 저장
→ 이후 기존 상담 처리 가능
```

이 기능 때문에 핵심 Mobile → AI → Web E2E가 늦어지면 **핵심 E2E를 먼저 완료**한다.

# 5. Blocker 처리 규칙

이번 이틀 동안 김은진은 “모든 걸 검증하는 QA”가 아니라 **E2E를 빨리 완성시키는 통합 QA**로 움직인다.

```text
[Blocker]
구간: Mobile → Backend / Backend → AI / Backend → Web 등
기준 Commit: <SHA>
재현 방법: <명령 또는 화면 동작>
기대 결과: <정상 결과>
실제 결과: <오류>
로그/응답: <핵심 부분>
담당자: <이름>
우선순위: E2E_BLOCKER
```

### 원칙

- 한 사람이 고칠 때까지 기다리지 말고 다른 연결 구간을 병렬로 확인한다.
- 수정 Commit이 올라오면 해당 구간부터 즉시 재검증한다.
- E2E Blocker가 아니면 별도 Backlog로 넘긴다.
- UI 미세 조정, 모델 품질 개선, 문구 개선 등은 이번 기간 Blocker로 취급하지 않는다.
