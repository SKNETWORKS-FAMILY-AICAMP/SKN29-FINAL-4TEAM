2. 구조화, 누락 정보 확인, 안전 판단, Retrieval, Generation, Validation Stage가 분리되어 있다.

4. `ai/app/integrations/llm/llm_client.py`, `model_router.py`, `token_usage.py`는 실제 Provider Runtime이 완성되지 않았다.
5. 증상 구조화·추가 질문은 결정적 Rule 기반 구현과 평가 Dataset이 존재한다.
6. 안전·위험·근거 없음·금지 표현 Guard는 비교적 강한 기준선이 존재한다.
7. `BAAI/bge-m3`, 1024차원 Embedding, pgvector 검색 Adapter와 실제 pgvector Integration Test가 존재한다.
8. 개인 격리 DB pgvector 평가 결과는 존재하지만 팀 DB 기준선 결과는 별도로 확보해야 한다.
9. Backend에는 `AIClient`, Request/Response Mapper, Schema Validator, `InquiryAIService` 기반이 존재하지만 고객 증상 제출 이후 실제 Runtime에서 AI 호출이 자동 연결되는 수직 흐름은 완전히 닫히지 않았다.
10. `consultation_summary`, `technician_report` 디렉토리와 Schema·Formatter 골격은 존재하지만 실제 Agent Runtime은 미완성이다.
11. `ai/tests/integration/llm/**`, `ai/tests/integration/pipeline/**`, `tests/integration/backend-ai/**`, `tests/e2e/**`는 실제 통합 Test가 부족하다.
12. 4주차 저장 증거 기준 AI Unit Test는 100개 이상 존재하지만, 5주차에는 반드시 최신 Commit에서 다시 실행하고 환경·Commit·실패 수를 재기록해야 한다.

따라서 5주차 이동윤의 핵심은 **새로운 AI 아이디어를 많이 추가하는 것**이 아니라 다음 여섯 가지를 실제로 닫는 것이다.

```text
Single RAG
→ Multi-Agent Runtime
→ 실제 LLM
→ 실제 팀 DB pgvector
→ 실제 Django Backend HTTP
→ 전체 서비스 E2E
```

# 2. 5주차 역할 목표

1. **8월 10일 오전까지 AI·RAG·LLM·Vector DB 실행 Gate를 최신 `main`에서 다시 닫는다.**

   AI Unit·Contract·Safety·Pipeline Test, FastAPI Local, 팀 DB pgvector, bge-m3 Model Revision, Backend AI Adapter 상태를 같은 Commit에서 확인한다. 환경 부족과 코드 실패를 구분하고, 오후부터 기능 구현을 막는 Blocker가 남지 않도록 한다.

2. **8월 10일 오후까지 Multi-Agent Architecture와 Agent 책임 계약을 확정한다.**

   `Supervisor/Router`, `Symptom Agent`, `Safety Agent`, `Retrieval Agent`, `Guidance Agent`, `Validation Agent`와 `Consultation Summary Agent`를 P0 필수 책임으로 확정한다. `Technician Briefing Agent`는 이번 주에는 Formatter/Prototype 수준의 조건부 범위로 두고, 미착수 시 현행 WBS의 후속 일정으로 유지한다. Agent 간 State·Routing·Handoff·Fallback은 문서와 코드가 같은 구조를 가지게 한다.

3. **8월 11일까지 실제 LLM Provider를 제한된 책임으로 연결한다.**

   LLM은 구조화·고객 안내·요약처럼 자연어 생성이 필요한 지점에 제한적으로 사용한다. 위험 판단, 제품 범위, 공식 근거 허용, 금지 행동은 Rule/Validator 우선으로 유지한다. 실제 Provider 실패 시 결정적 Rule·Template 또는 상담 Fallback으로 복귀한다.

4. **8월 11일까지 팀 DB pgvector 기준선을 확정한다.**

   개인 Disposable DB 결과를 팀 공식 결과로 재사용하지 않는다. 팀 공용 PostgreSQL·pgvector에서 공식 Chunk를 적재하고 Retrieval 평가를 다시 수행하여 Recall@5·MRR·금지 Hit·제품·세대·문서 정책 차단 결과를 고정한다.

5. **8월 12일까지 Backend↔AI 실제 HTTP 수직 흐름을 닫는다.**

   고객 증상 제출 이후 Django Backend가 실제 FastAPI를 호출하고, Multi-Agent 결과가 Schema 검증 후 AI Run·구조화 증상·추가 질문·Evidence·Guidance로 저장되며, Backend State Machine이 결과를 바탕으로 다음 Event를 적용하는 흐름을 실제로 실행한다.

6. **8월 12일까지 상담·기사 역할별 AI 결과를 최소 Runtime으로 구현한다.**

   고객 안내만 만드는 AI가 아니라 상담사에게 전달할 요약과 기사 사전 점검·브리핑을 같은 공식 근거와 Inquiry Context에서 생성한다. 각 역할별 출력은 서로 다른 공개 범위와 Schema를 사용한다.

7. **3장 필수 Gate가 조기에 닫힌 경우에만 Multi-Agent 전체 Test와 대표 E2E를 5장 조건부 업무로 실행한다.**

5주차에는 Agent Unit, Routing, Handoff, LLM, pgvector, Backend API, Timeout, Fallback, Safety, Schema의 필수 범위를 검증한다. 전체 E2E와 공식 결과 보고서는 선행 Gate가 조기에 닫힌 경우에만 수행한다.

8. **8월 14일까지 WBS 5주차 AI 통합 기준선과 6~7주차 잔여 범위를 확정한다.**

   실제 코드·실행 결과를 기준으로 AI 시스템 아키텍처와 멀티 에이전트 테스트 계획·결과 보고서를 완료하고, 6주차에 신규 핵심 Agent 개발이 남지 않도록 한다.

5주차 완료 기준은 “LangGraph를 사용한다”, “Agent 파일이 여러 개다”, “테스트 파일이 존재한다”가 아니다. **핵심 Agent가 실제 Runtime에서 Routing·Handoff되고, LLM·VectorDB·Backend 최소 수직 연결과 Fallback이 같은 Commit에서 검증되어야 한다.**

## 3.2 Multi-Agent Architecture 확정과 실제 Runtime 전환

### 작업 목적

현재 `SingleRAGPipeline`의 Stage 분리를 실제 역할 기반 Multi-Agent 구조로 승격한다. 여러 Python 파일을 Agent라고 이름만 바꾸는 방식이 아니라 각 Agent가 고유 입력·출력·책임을 가지고 Supervisor/Router가 조건에 따라 호출하며, Shared State와 Handoff가 추적 가능하게 한다.

### 작업 위치

```text
ai/app/orchestration/
├─ pipeline_context.py
├─ pipeline_result.py
├─ pipeline_router.py
├─ pipelines/
│  ├─ single_rag_pipeline.py
│  └─ selective_pipeline.py
├─ agents/**
├─ routing/**
└─ state/**

ai/app/structuring/**
ai/app/safety/**
ai/app/retrieval/**
ai/app/generation/**
ai/app/validation/**
ai/app/schemas/**
contracts/ai/**
ai/tests/unit/agents/**
ai/tests/integration/pipeline/**
```

### P0 Agent 구성

최소 다음 Agent를 실제 Runtime 책임으로 구성한다.

```text
Supervisor / Router
        │
        ├─ Symptom Agent
        │   ├─ 증상 구조화
        │   └─ 누락 정보·추가 질문
        │
        ├─ Safety Agent
        │   ├─ 위험 신호
        │   ├─ 사용 제한
        │   └─ 즉시 상담 필요 여부
        │
        ├─ Retrieval Agent
        │   ├─ Query 구성
        │   ├─ bge-m3 Embedding
        │   ├─ pgvector 검색
        │   └─ 공식 근거 검증
        │
        ├─ Guidance Agent
        │   ├─ 공식 근거 기반 고객 안내
        │   └─ 자가조치·제한 기능
        │
        └─ Validation Agent
            ├─ Schema
            ├─ Grounding
            ├─ 금지 표현
            └─ 역할별 공개 범위
```

상담 흐름에 필요한 다음 역할 Agent는 5주차 필수 최소 Runtime에 포함한다.

```text
Consultation Summary Agent
```

`Technician Briefing Agent`는 5장 조건부 업무에서 Formatter/Prototype으로 검증하거나 현행 WBS의 후속 일정으로 유지한다.

### 세부 작업 지침

1. `SingleRAGPipeline`을 즉시 삭제하지 않는다.
2. 기존 Pipeline을 회귀 기준선으로 유지하면서 `selective_pipeline.py` 또는 별도 Multi-Agent Runtime을 구현한다.
3. Agent마다 다음을 명시한다.
   - 책임
   - 입력 Schema
   - 출력 Schema
   - 읽을 수 있는 Shared State
   - 수정할 수 있는 Shared State
   - 실패 유형
   - Retry 가능 여부
4. Supervisor는 Agent 내부 비즈니스 로직을 직접 수행하지 않는다.
5. Supervisor는 다음 기준으로 Routing한다.
   - 위험 신호 존재
   - 누락 필드 존재
   - 근거 검색 필요
   - 근거 없음
   - 생성 결과 검증 실패
   - 상담·기사 역할 Output 필요

## 3.6 Multi-Agent Timeout·Retry·Fallback·안전성 완성

### 작업 목적

Agent 수가 늘어남에 따라 한 Agent 장애가 전체 시스템 무응답으로 이어지지 않게 한다. 전체 30초 시간 예산 안에서 Agent별 Timeout·Retry·Fallback을 관리하고, 위험 입력은 외부 의존성이 실패해도 안전한 결과를 우선 반환한다.

### 작업 위치

```text

ai/app/common/retry/**
ai/app/common/errors/**
ai/app/orchestration/**
ai/app/safety/**
ai/app/validation/**

ai/configs/retry_policy.yaml
ai/tests/integration/pipeline/**
ai/tests/integration/llm/**
tests/safety/**
```

### 세부 작업 지침

1. Backend 전체 AI Timeout 30초 기준을 유지한다.
2. Agent별 시간 예산을 정의한다.
3. Embedding·Retrieval·LLM·Validation 시간을 분리한다.
4. 전체 합계가 Backend Timeout을 넘지 않게 한다.
5. AI 내부 자동 Retry는 최대 1회로 제한한다.
6. Backend 자동 Retry 0회 정책과 충돌하지 않는다.
7. 재시도 가능한 오류만 Retry한다.
8. Schema Error는 무조건 Retry하지 않는다.
9. Unsupported Product는 Retry하지 않는다.
10. Safety 정책 위반은 Retry하지 않는다.
11. LLM Rate Limit은 남은 시간 예산이 있을 때만 1회 Retry한다.
12. Vector DB 일시 연결 오류는 1회 Retry할 수 있다.
13. Retrieval 결과 0건은 장애가 아니라 `NO_EVIDENCE`로 처리한다.
14. 위험 신호는 Vector DB 장애와 관계없이 Safety Agent 결과를 반환한다.
15. LLM 장애 시 Rule·Template Fallback을 사용한다.
16. Guidance 생성 실패 시 근거 없는 자유 답변을 만들지 않는다.
17. Validation 반복 실패 시 상담 Fallback으로 종료한다.
18. Agent 무한 Loop를 금지한다.
19. 최대 Agent Hop 수를 정의한다.
20. Supervisor가 동일 Agent를 무제한 재호출하지 않게 한다.
21. Fallback 경로를 Architecture Diagram에 포함한다.
22. 각 실패 경로에 Error Code를 연결한다.
23. `correlation_id`로 Agent 실패·Retry를 연결한다.
24. 실패 단계와 소요 시간을 기록한다.
25. 안전 테스트에 위험+LLM 장애를 포함한다.
26. 위험+VectorDB 장애를 포함한다.
27. 근거 없음+LLM 정상 Case를 포함한다.
28. Validation 실패 Case를 포함한다.
29. Agent Timeout Case를 포함한다.
30. 전체 Timeout 직전 Cancel 처리가 동작하는지 확인한다.

### 완료 기준

- Agent별 Timeout이 정의되어 있다.
- 전체 30초 시간 예산을 초과하지 않는다.
- Retry는 최대 1회로 제한된다.
- 무한 Routing·무한 재생성이 없다.
- 위험 입력은 외부 장애 상황에서도 안전하게 처리된다.
- LLM·VectorDB 장애 시 구조화 Fallback이 존재한다.
- 실패 단계·Retry·Latency가 추적 가능하다.
- Fallback 경로가 코드·테스트·아키텍처 문서에서 일치한다.

# 7. AI·RAG·Multi-Agent 역할 수행 시 주의사항

- AI가 `Inquiry`, `Consultation`, `Visit`의 최종 상태를 직접 변경하지 않는다.
- Backend State Machine이 업무 상태의 최종 권위다.
- Agent 수가 많다는 이유만으로 Multi-Agent 완료로 판정하지 않는다.
- Agent마다 독립 책임·입출력·Routing이 실제 Runtime에 존재해야 한다.
- Stage 이름만 Agent로 바꾸는 작업은 완료로 인정하지 않는다.
- 실제 LLM을 연결하지 않은 상태에서 “LLM 기반 Multi-Agent”라고 표현하지 않는다.
- Mock Provider 결과를 실제 Provider 결과로 보고하지 않는다.
- 개인 Disposable DB 결과를 팀 DB 공식 결과로 보고하지 않는다.
- 실제 pgvector 결과와 Mock Retrieval 결과를 구분한다.
- bge-m3를 직접 학습하거나 파인튜닝한 모델로 표현하지 않는다.
- 위험 판단을 LLM 단독 결과에 맡기지 않는다.
- 제품·세대·공식 문서 범위 판단을 LLM에 맡기지 않는다.
- 공식 근거가 없으면 그럴듯한 해결 방법을 생성하지 않는다.
- 미검증 FAQ를 공식 매뉴얼과 같은 수준으로 사용하지 않는다.
- 위험 입력은 Retrieval·생성보다 Safety를 우선한다.
- Agent 간 Shared State에 개인정보·Token·Backend 내부 PK를 넣지 않는다.
- Prompt·Log에 API Key·Token·실제 개인정보를 남기지 않는다.
- Agent Handoff마다 전체 고객 원문을 무조건 복제하지 않는다.
- Validation 실패 결과를 Backend에 정상 결과로 저장하지 않는다.
- Schema를 맞추기 위해 임의 기본값으로 중요한 필드를 채우지 않는다.
- Retry는 최대 1회 정책을 지킨다.
- Backend 자동 Retry 0회와 충돌하지 않는다.
- Agent Loop·재생성 Loop에 최대 횟수를 둔다.
- LLM Provider 장애가 전체 서비스 무응답으로 이어지지 않게 한다.
- Vector DB 장애와 검색 결과 없음은 다른 상태로 처리한다.
- E2E를 통과시키기 위해 DB State를 직접 강제 변경하지 않는다.
- Backend를 우회해 FastAPI를 직접 호출한 결과를 전체 E2E로 기록하지 않는다.
- Web·Mobile이 AI FastAPI를 직접 호출하게 만들지 않는다.
- 상담사·기사 출력에 고객용보다 많은 정보가 필요하더라도 개인정보 최소화 원칙을 지킨다.
- 역할별 결과가 서로 모순되지 않게 Cross-role Validation을 수행한다.
- 테스트 실패를 제거·Skip 처리하여 PASS율을 인위적으로 높이지 않는다.
- 환경 부족 SKIP은 PASS로 계산하지 않는다.
- 테스트 개수보다 정상·위험·근거 없음·장애 흐름의 실제 재현을 우선한다.
- 8월 13일 오후 이후 신규 핵심 Agent·Provider·Vector 기술을 추가하지 않는다.
- 8월 14일에는 신규 기능보다 전체 회귀·E2E·산출물 확정에 집중한다.
- Graph DB는 5주차 P0에 도입하지 않는다.
- 새로운 Embedding Model 비교 실험은 필수 E2E 완료 후에만 수행한다.
- Fine-tuning은 5주차 P0에 포함하지 않는다.
- 별도의 Agent Framework 추가 도입은 현재 LangGraph 구조로 해결 불가능한 명확한 이유가 있을 때만 검토한다.

# 8. 6주차 인계 기준

5주차 종료 시 AI 영역은 다음 상태를 목표로 한다.

```text
Multi-Agent
= Supervisor + 역할별 Agent + Routing + Handoff

LLM
= 실제 Provider + Structured Output + Fallback

RAG
= bge-m3 + 팀 DB pgvector + 공식 Evidence + 평가

Backend Integration
= 실제 Django → FastAPI HTTP + DB 저장 + State Event

Role Outputs
= Customer Guidance + Consultation Summary + Technician Briefing Formatter/Prototype(조건부)

Validation
= Schema + Safety + Grounding + Cross-role Consistency

Quality
= Agent Unit + Routing + LLM + VectorDB + Backend + Fallback + E2E

Official Deliverables
= AI 시스템 아키텍처 + 멀티 에이전트 테스트 계획 및 결과 보고서
```

6주차에 남겨도 되는 AI 업무는 다음 중심으로 제한한다.

- Prompt 미세 조정
- Model Profile 조정
- Latency·Token 최적화
- 배포 환경 Base URL·환경변수 보정
- Container·Model Cache 안정화
- 잔여 버그
- 최종 시연 Scenario 보강
- 문서 표현·이미지 정리

다음 항목은 조기 완료하지 못하면 현행 WBS의 6~7주차 일정으로 인계한다.

- 실제 Multi-Agent Routing 미완료
- 실제 LLM Provider 미연동
- 팀 DB pgvector 미검증
- Django→FastAPI 실제 HTTP 미연결
- 상담 요약 Agent 미구현
- 기사 브리핑 Agent 미구현
- LLM Integration Test 없음
- Backend↔AI 실제 Integration Test 없음
- 대표 E2E 미통과
- 공식 AI 아키텍처 미완료
- 공식 멀티 에이전트 테스트 결과 미완료

본 지침서의 핵심은 **4주차까지 존재하는 단일 RAG·규칙 기반·pgvector 기준선을 “멀티 에이전트처럼 보이게” 포장하는 것이 아니라, 실제 역할 분리 Multi-Agent Runtime으로 완성하고 WaterBridge 전체 서비스에 연결하는 것**이다.

이동윤의 5주차는 8월 10일 환경·기준선을 닫고, 실제 LLM과 팀 DB RAG, Django Backend 최소 수직 연결, 핵심 Routing·Fallback과 상담 요약 최소 Runtime을 우선 완료한다. 기사 브리핑 Formatter/Prototype, 역할별 전체 검증, 대표 E2E와 후속 최종 산출물은 선행 Gate가 조기에 닫힌 경우에만 5장 업무로 수행한다.

5주차 종료 시점에는 **실제 Multi-Agent 핵심 Runtime이 실제 LLM·VectorDB·Backend와 최소 수직 연결되고 안전한 Fallback이 동작하는 것**을 필수 완료 기준으로 한다. 고객→상담→기사 전체 E2E는 조기 완료 또는 WBS 후속 일정에서 판정한다.
