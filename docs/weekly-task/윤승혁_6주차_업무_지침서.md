# 윤승혁 6주차 업무 지침서

> 담당자: 윤승혁  
> 역할: PM·기술 통합  
> 적용 기간: 2026-08-18 ~ 2026-08-21  
> 핵심 원칙: **6주차에는 새로운 대형 기능을 직접 맡기보다, P0 범위를 통제하고 팀원 5명의 결과를 하나의 실제 E2E로 연결하며, AI 구조와 전체 기술 흐름을 설명 가능한 상태로 만든다.**

---

# 1. 6주차 완료 목표

6주차가 끝났을 때 아래 상태가 실제로 만들어져 있어야 한다.

- [ ] 고객 Mobile → Backend → 실제 AI → 상담사 Web → 고객 최신 상태 흐름이 하나의 신규 Inquiry로 끝까지 동작한다.
- [ ] 각 팀원의 P0 완료 여부가 명확하게 판정되어 있다.
- [ ] 남아 있는 Blocker는 담당자·원인·처리 여부가 모두 정해져 있다.
- [ ] 방문기사 관련 기능은 P1로 분리되어 P0 완료 판정을 방해하지 않는다.
- [ ] 이동윤의 3-Agent 구조가 역할·Shared State·Handoff 기준까지 확정되어 있다.
- [ ] `Symptom Analysis Agent ↔ Evidence Analysis Agent ↔ Care Decision Agent` 협업 구조를 직접 설명할 수 있다.
- [ ] Single RAG와 Multi-Agent의 차이와 비교 이유를 설명할 수 있다.
- [ ] Web·Mobile에서 발생한 Backend 요구는 PM 승인 절차를 거쳐 P0/P1로 구분된다.
- [ ] State Machine의 `allowed_actions`, `state_version`, Idempotency, 권한, 409 흐름을 실제 프로젝트 기준으로 설명할 수 있다.
- [ ] Backend/DB 리뷰노트의 핵심 개념을 우리 프로젝트 코드·기능과 연결하여 설명할 수 있다.
- [ ] 한예나가 준비하는 주간발표의 기술 내용이 실제 구현과 일치하는지 최종 검수할 수 있다.
- [ ] 7주차에는 신규 핵심 기능을 추가하지 않고 품질·안정성·성능 개선으로 넘어갈 수 있는 상태가 된다.

> **6주차 종료 시점에 “각자 기능은 있는데 전체 흐름은 안 된다”는 상태가 남아 있으면 PM 과업 완료로 판정하지 않는다.**

# 2. 이번 주 핵심 업무

## A. 이동윤 AI/RAG 설계 지원

직접 AI 기능 전체를 대신 구현하는 것이 아니라, 이동윤이 구현에 집중할 수 있도록 **구조 결정 부담을 가져간다.**

확정할 것:

- Agent 수: 3개
- Agent별 책임과 금지 범위
- Shared State 구성
- Agent 간 Handoff 조건
- Evidence 부족 시 재질문 조건
- 무한 재질문 방지 기준
- Safety Rule 우선 원칙
- Single RAG vs Multi-Agent 비교 기준
- 상담사용 AI 인계 범위

최종 구조:

```text
Symptom Analysis Agent
        ↕
Evidence Analysis Agent
        ↕
Care Decision Agent
```

핵심 협업 흐름:

```text
고객 입력
→ Symptom Analysis Agent
→ Evidence Analysis Agent

Evidence 충분
→ Care Decision Agent

Evidence 부족
→ Symptom Analysis Agent에 추가 정보 요청
→ 고객 추가 답변
→ Evidence 재검색
```

공통 Tool/Stage는 Agent로 늘리지 않는다.

```text
Safety Rule
Embedding
Retriever
pgvector
Evidence Validator
Output Validator
Timeout / Cancellation
Trace / Logging
```

PM 완료 기준:

- 3-Agent 책임이 겹치지 않는다.
- Agent가 Backend 상태를 직접 바꾸지 않는다.
- Safety 결과를 Agent가 뒤집지 못한다.
- Evidence 부족 시 실제 Handoff가 존재한다.
- 상담사용 AI 인계 구조가 명확하다.
- 이동윤이 설계 결정 때문에 구현을 멈추는 상황이 없도록 한다.

## B. P0 / P1 Scope Gate 운영

6주차에는 신규 요구사항이 계속 들어올 가능성이 높다.

모든 요청은 다음 기준으로 판단한다.

> **이 기능이 없으면 금요일 실제 E2E가 안 되는가?**

```text
YES
→ P0
→ 이번 주 처리

NO
→ P1 / 7주차 Backlog
```

Web/Mobile 요청 처리:

```text
Web / Mobile
      ↓
재현 가능한 Blocker Evidence
      ↓
윤승혁 확인
      ↓
P0 E2E를 막는가?
   ↓ YES       ↓ NO
P0 승인         P1 / Backlog
   ↓
최지용 또는 해당 담당자 처리
```

P0 예시:

- 실제 E2E 불가
- 데이터 저장 불가
- 상태 전이 불가
- 실제 AI 결과 조회 불가
- 상담 요청 불가
- 상담 시작·저장·완료 불가
- 권한 오류
- 409 오동작
- 중복 데이터
- 필수 계약 필드 누락
- 공용 환경에서만 재현되는 Blocker

P1/Backlog 예시:

- 있으면 편한 기능
- 디자인 편의 API
- 추가 Dashboard
- 방문기사 기능
- 운영 관리자 기능
- 신규 화면
- 발표용 편의 기능
- 현재 API로 가능한 기능의 중복 구현

## C. 전체 E2E 통합 책임

김은진이 독립 QA를 담당한다면, 윤승혁은 **통합 의사결정과 Blocker 제거를 책임진다.**

매일 아래 흐름에서 어디까지 실제로 연결됐는지 확인한다.

```text
고객 Mobile
   ↓
Backend
   ↓
실제 AI
   ↓
pgvector / LLM
   ↓
Backend 저장
   ↓
고객 Guidance / Evidence
   ↓
상담 요청
   ↓
상담사 Web
   ↓
상담 시작 / 저장 / 완료
   ↓
고객 최신 상태 재조회
```

각 담당자의 “내 기능은 끝났다”와 프로젝트 완료를 구분한다.

```text
Mobile PASS
AI PASS
Web PASS

하지만 상담 요청 후 Web 목록에 문의가 안 뜸
→ 프로젝트 E2E = BLOCKED
```

이 경우 PM은:

1. 어느 구간에서 끊기는지 확인
2. 재현 Evidence 확보
3. 담당 영역 판정
4. P0 여부 결정
5. 담당자에게 즉시 재분배
6. 수정 후 재검증

대표 Inquiry 최소 1건을 아래 식별자로 추적한다.

```text
inquiry_id
correlation_id
ai_request_id
state_version
```

## D. 공용 계약·Architecture Freeze

6주차 종료 시 아래 항목은 더 이상 흔들리지 않아야 한다.

| 구분 | 확정 대상 |
|---|---|
| 범위 | P0 / P1 |
| AI | 3-Agent 구조 |
| RAG | 최종 검색·Embedding·LLM 구성 |
| 상태 | 핵심 State Machine 경로 |
| Backend | API·권한·상태 계약 |
| Mobile | 고객 핵심 Flow |
| Web | 상담사 핵심 Flow |
| E2E | 대표 고객→AI→상담사 시나리오 |
| Demo | 계정·Inquiry·증상·시연 순서 |

PM이 직접 설명할 수 있어야 하는 것:

```text
왜 이 구조를 선택했는가?
어디까지가 P0인가?
각 팀원 결과가 어떻게 연결되는가?
AI가 어떤 역할을 하고 무엇을 하지 않는가?
Backend가 왜 상태의 최종 권한자인가?
실제 E2E는 어떤 순서로 검증되는가?
```

## E. 리뷰노트 설명 및 주간발표 기술 검수

리뷰노트는 단순 요약으로 준비하지 않는다.

각 개념을 아래 세 단계로 연결한다.

```text
리뷰노트 개념
↓
우리 프로젝트 코드 / 계약
↓
실제 서비스에서의 동작
```

예:

```text
리뷰노트:
낙관적 동시성 제어

우리 프로젝트:
state_version

실제 동작:
상담사 A가 version 5 조회
→ 상담사 B가 먼저 상태 변경
→ version 6
→ A가 version 5로 저장 시도
→ Backend 409
```

우선 설명할 Backend/DB 개념:

- State Machine
- `allowed_actions`
- `state_version`
- 409 Conflict
- Idempotency
- PostgreSQL Row Lock
- 역할·권한
- Inquiry 누적 저장
- AI 결과 저장
- `correlation_id`
- 실제 E2E 데이터 흐름

한예나에게 전달·검수할 기술 내용:

- 이번 주 Architecture 최종 구조
- 3-Agent 구조
- Single RAG vs Multi-Agent
- Backend State Machine
- `allowed_actions`
- `state_version`
- Idempotency
- 실제 고객 → AI → 상담사 E2E
- 주요 Blocker와 해결 내용
- P1 제외 항목
- 7주차 품질 개선 방향

구현되지 않은 내용이 발표 자료에 완료된 것처럼 들어가지 않도록 최종 검수한다.

# 3. 실제 E2E 및 완료 판정 기준

윤승혁의 6주차 최종 Gate:

```text
1. 고객 Mobile 로그인
2. 실제 정수기 선택
3. 신규 Inquiry 생성
4. 고객 증상 입력
5. 필요한 경우 추가 질문
6. 고객 추가 답변
7. Backend → 실제 AI
8. 실제 pgvector / LLM
9. Guidance / Evidence 저장
10. 고객 Mobile에서 안내 확인
11. 고객 상담 요청
12. 상담사 Web 로그인
13. 같은 inquiry_id의 문의 조회
14. AI 인계 / Evidence 확인
15. 상담 시작
16. 상담 기록 저장
17. 상담 완료
18. 고객 Mobile에서 같은 Inquiry 최신 상태 재조회
```

필수 조건:

- 실제 Mobile
- 실제 Backend
- 실제 PostgreSQL
- 실제 AI
- 실제 pgvector
- 실제 생성형 LLM
- 실제 Web
- 동일 `inquiry_id`
- Mock/Fake 성공 대체 금지

팀원별 최종 판정:

```text
양정현 / Mobile:
PASS | PASS WITH LIMITATION | BLOCKED

최지용 / Backend:
PASS | PASS WITH LIMITATION | BLOCKED

이동윤 / AI:
PASS | PASS WITH LIMITATION | BLOCKED

한예나 / Web:
PASS | PASS WITH LIMITATION | BLOCKED

김은진 / QA·DevOps:
PASS | PASS WITH LIMITATION | BLOCKED
```

최종 질문:

> **각자 기능이 아니라 전체 P0가 실제로 연결되어 있는가?**
