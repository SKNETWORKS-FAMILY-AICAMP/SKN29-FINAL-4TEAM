# 최지용 6주차 업무 지침서

> 담당자: 최지용  
> 역할: Backend·DB  
> 적용 기간: 2026-08-18 ~ 2026-08-21  
> 핵심 원칙: **6주차에는 기존 Backend P0 미완료·미착수 항목을 먼저 마감하고, 이후 Mobile·Web의 실제 Remote E2E 과정에서 발견된 Backend Blocker 중 PM이 P0에 필요하다고 승인한 항목만 추가 작업한다. 신규 편의 기능이나 P1 요구사항은 추가하지 않는다.**

---

# 1. 6주차 완료 목표

6주차가 끝났을 때 아래 기능이 **실제 Backend·PostgreSQL 환경에서 동작해야 한다.**

- [ ] 고객 Mobile에서 만든 신규 Inquiry가 실제 PostgreSQL에 저장된다.
- [ ] 고객 증상·추가 질문 답변·AI 결과가 같은 `inquiry_id`에 계속 누적된다.
- [ ] Backend가 실제 AI 서버를 호출하고 Guidance·Evidence를 저장한다.
- [ ] 일반·위험·근거 없음·AI Timeout/오류 결과를 각각 정상 저장하고 조회할 수 있다.
- [ ] 고객이 상담 요청하면 실제 상담 요청 상태로 전이된다.
- [ ] 상담 요청된 문의가 상담사 Web의 실제 목록·상세에 나타난다.
- [ ] 상담사가 상담 시작 → 기록 저장 → 상담 완료를 실제 Backend API로 수행할 수 있다.
- [ ] 상담 완료 후 고객 Mobile에서 같은 Inquiry의 최신 상태를 다시 조회할 수 있다.
- [ ] 동일 요청을 여러 번 보내도 Inquiry·답변·상담 기록이 중복 생성되지 않는다.
- [ ] 오래된 `state_version`으로 쓰기 요청을 보내면 409가 발생하고 기존 데이터가 보존된다.
- [ ] 권한 없는 상담사는 다른 상담사의 문의를 조회·수정하지 못한다.
- [ ] 두 상담사가 같은 문의를 동시에 처리해도 PostgreSQL 동시성 제어가 정상 동작한다.
- [ ] `inquiry_id`, `correlation_id`, `ai_request_id`, `state_version`으로 Mobile → Backend → AI → DB → Web 흐름을 추적할 수 있다.
- [ ] Mobile·Web 실제 연동 중 발견된 P0 Backend Blocker는 PM 승인 후 이번 주 안에 해결된다.
- [ ] 방문기사 관련 Runtime은 P1로 유지하고 6주차 완료 조건에서 제외한다.

> **Inquiry 저장, 실제 AI 결과 저장, 상담 요청, 상담 시작·저장·완료, 최신 상태 재조회, Idempotency·409·권한 검증이 완료되지 않으면 6주차 Backend 과업 완료로 판정하지 않는다.**

이번 주 Backend의 최종 목표는 아래 흐름에서 **Backend 때문에 막히는 지점을 0개로 만드는 것**이다.

```text
고객 Mobile
   ↓
Backend
   ↓
PostgreSQL
   ↓
실제 AI
   ↓
Guidance / Evidence 저장
   ↓
고객 상담 요청
   ↓
상담사 Web
   ↓
상담 시작 / 기록 / 완료
   ↓
고객 Mobile 최신 상태
```

## B. Inquiry·AI·상담 Runtime 완주

### Inquiry 누적 저장

다음 정보가 같은 `inquiry_id`로 이어져야 한다.

```text
고객 원문
선택 증상
추가 질문
추가 답변
AI Guidance
Evidence
상담 요청
상담 기록
최종 상태
```

필수 조건:

- 중간 단계마다 새 Inquiry를 만들지 않는다.
- 재시도 시 중복 Row를 만들지 않는다.
- 최신 상태와 이력 상태를 구분한다.
- 상담사 Web과 고객 Mobile이 같은 Inquiry를 조회한다.

### Backend → AI 실제 연동

정상 경로:

```text
Backend
→ AI Request
→ 실제 AI
→ 실제 pgvector / LLM
→ AI Response
→ Backend 저장
→ Mobile 조회
```

최소 추적 정보:

```text
inquiry_id
correlation_id
ai_request_id
state_version
AI status
Guidance
Evidence
risk / safety 결과
next_action
requires_consultation
failure_stage
retry_count
```

실제 필드명은 공용 계약을 따른다.

### AI 예외 경로

반드시 아래 네 경로를 실제 Runtime에서 확인한다.

```text
일반
→ Guidance / Evidence 저장
→ 정상 조회

위험
→ Safety 결과 저장
→ 사용 제한
→ 상담 전환

근거 없음
→ 임의 자가조치 정상 Guidance 처리 금지
→ 재질문 또는 상담 전환

Timeout / Provider 오류
→ 데이터 손상 없음
→ 중복 Inquiry 없음
→ 명시적 실패 또는 Fallback
→ 재조회 가능
```

### 상담 Runtime

```text
고객 상담 요청
→ allowed_actions 검증
→ state_version 검증
→ 상담 요청 상태 저장
→ 상담사 Web 조회

상담 시작
→ 권한 검증
→ state_version 검증
→ 상태 저장

상담 기록
→ PostgreSQL 저장
→ Refresh 후 유지

상담 완료
→ 상태 전이
→ 최신 Inquiry 저장
→ 고객 Mobile 재조회
```

필요한 경우 기존 완료 정책에 따라 `COMPLETION_PENDING` 이후 `FINALIZE_INQUIRY`까지 확인한다.

> 상담을 완료했는데 Inquiry가 영구적으로 중간 상태에 남아 고객이 결과를 확인할 수 없는 상태를 허용하지 않는다.

## C. 상태·DB 무결성 검증

이번 주 Backend 품질에서 가장 중요한 부분이다.

### Idempotency / Replay

최소 다음 쓰기 요청에서 검증한다.

- Inquiry Create
- Symptom Submit
- Answers Submit
- Consultation Request
- Consultation Save
- Consultation Complete
- AI 결과 저장

테스트:

```text
같은 Idempotency-Key로 동일 요청 2회
```

예상:

```text
새 Row 중복 생성 없음
중복 상태 이력 없음
계약된 Replay 응답
```

### state_version / 409

시나리오:

```text
Client A
→ version 5 조회

Client B
→ 상태 변경
→ version 6

Client A
→ version 5로 쓰기 시도
```

예상:

```text
409 Conflict
기존 데이터 보존
최신 state_version 확인 가능
```

### 상담사 권한

```text
상담사 A 담당 문의
→ A 조회·처리 가능

상담사 B
→ 정책에 따라 조회·수정 차단
```

확인:

- 목록 노출
- 직접 URL
- 상세 조회
- 상담 시작
- 상담 저장
- 상담 완료

Frontend에서 버튼을 숨기는 것으로 권한 처리를 대신하지 않는다.

### PostgreSQL Row Lock / 동시성

필수 시나리오:

```text
상담사 A와 상담사 B가
같은 Inquiry를 거의 동시에 처리
```

확인:

- 중복 담당
- 중복 상태 전이
- 중복 상담 기록
- Lost Update
- Deadlock
- 최종 상태

완료 기준:

> 동시 요청에서도 상태가 하나의 일관된 결과로 수렴해야 한다.

### Migration / DB 정합성

김은진과 함께 확인:

- 적용 Migration
- 미적용 Migration
- `makemigrations --check`
- `migrate --check`
- Seed Replay
- Schema Drift
- FK / Constraint
- DB Role 권한
- 데이터 중복

최종 후보 SHA에서 코드와 DB Schema가 일치해야 한다.

최지용의 6주차 작업 원칙은 다음과 같다.

- 있으면 편한 정렬 API
- 디자인용 부가 필드
- 추가 Dashboard 집계
- 방문기사 기능
- 운영 관리자 기능


그리고 아래 Backend 공통 정책이 함께 통과해야 한다.

```text

state_version
409
Idempotency / Replay
상담사 권한
PostgreSQL Row Lock
AI Timeout / 오류

```

최종 판정 질문은 하나다.

> **실제 고객→AI→상담사→고객 P0 흐름에서 Backend 때문에 막히는 지점이 남아 있는가?**

남아 있으면 완료가 아니다.

- 추가 동시성 테스트
- 세부 리팩터링

```text

운영 관리자 신규 API

화면 디자인 편의를 위한 임시 API
발표용 가짜 데이터 전용 API
기존 계약 우회 Shortcut
타 영역 제품 코드 직접 수정
필요 이상의 리팩터링
신규 프레임워크 도입
```

핵심 원칙:

> **P0 실제 E2E가 끝나기 전에는 “있으면 좋은 Backend 기능”을 추가하지 않는다.**
