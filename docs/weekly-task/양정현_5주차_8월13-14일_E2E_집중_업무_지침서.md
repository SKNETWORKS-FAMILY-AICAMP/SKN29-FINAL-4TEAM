8월 14일은 주간 발표 준비일로 사용한다. 원칙적으로 신규 기능 개발은 하지 않고, 전날 완성한 Mobile E2E를 다시 확인하고 발표 자료·시연 순서를 정리한다.

# 4. 8월 13일 — 개발 완료일

## 4.1 오전 1순위 — Mobile 작업 범위 즉시 동결

작업 시작 후 가장 먼저 현재 `main`을 기준으로 Mobile 상태를 맞춘다.

```cmd
cd mobile
verify-build.bat
```

이 단계의 목적은 Mobile 전체를 다시 검증하는 것이 아니라 **오늘 작업을 시작할 수 있는 정상 기준선을 확인하는 것**이다.

### 확인할 것

- 고객 앱 Build 가능
- 기존 Remote 제품·구독·문의 흐름 유지
- Backend Base URL이 팀 통합 환경을 바라보는지 확인
- 기사 앱 작업은 P1로 두고 건드리지 않음

기존 PASS를 다시 문서화하는 데 시간을 많이 쓰지 않는다.

---

## 4.2 오전~오후 1순위 — AI Guidance·Evidence Remote 연결

Backend가 고객용 Guidance·Evidence 응답을 제공하는 즉시 Mobile에 연결한다.

### 목표 흐름

```text
고객 증상·추가 답변 제출
→ Backend
→ AI Baseline 처리
→ Backend 저장
→ Mobile Snapshot/Guidance 조회
→ 고객 화면에 AI 안내 표시
```

### 구현 범위

- Retrofit API 연결
- Response DTO
- Domain Mapper
- Repository
- ViewModel / UiState
- 기존 고객 안내 화면에 실제 응답 연결

### 화면에서 반드시 보여줄 것

- AI 사용 안내
- 고객이 할 수 있는 다음 행동
- 공개 가능한 공식 근거
- 상담이 필요한 경우 상담 연결 행동

### 화면에서 보여주지 않을 것

- 내부 `chunk_id`
- Vector score
- 서버 내부 파일 경로
- 전체 원문 문서
- AI 내부 Trace

화면 디자인을 새로 뜯어고치지 않는다. **현재 화면에 실제 데이터를 연결하는 것이 먼저다.**

---

## 4.3 오후 1순위 — 상담 요청까지 고객 E2E 닫기

AI Guidance가 보이면 바로 다음 흐름을 연결한다.

```text
AI 안내 확인
→ 고객이 상담 요청
→ Backend requestConsultation
→ 최신 Inquiry Snapshot 재조회
→ 상담 필요 상태 확인
→ 고객 화면에 현재 처리 상태 표시
```

버튼 노출은 Mobile이 임의로 판단하지 않고 Backend가 내려준 `allowed_actions`를 기준으로 한다.

### 반드시 확인할 것

- 상담 요청이 실제 Backend에 저장되는가
- 요청 후 `state_version`이 갱신되는가
- 새로고침 후에도 상태가 유지되는가
- 상담사 Web에서 같은 Inquiry를 조회할 수 있는가

Web 자체 구현은 한예나 담당이다. 양정현은 **고객 앱에서 상담사 Web으로 넘어갈 수 있는 데이터를 정상적으로 만드는 것**까지 책임진다.

# 5. 8월 13일 대표 Mobile E2E

기능 연결이 끝나면 테스트 Case를 여러 개 넓히기 전에 **정상 시나리오 한 건을 실제 기기에서 끝까지 완주**한다.

## 대표 흐름

```text
1. 고객 로그인
2. 내 구독 제품 조회
3. WPUJAC104DWH 선택
4. 문의 생성
5. 출수량 저하 증상 제출
6. 추가 질문 확인
7. 추가 답변 제출
8. AI Baseline 안내 확인
9. 공식 근거 확인
10. 상담 요청
11. 최신 문의 상태 재조회
12. 상담사 Web에서 같은 문의 확인
```

방문기사 단계는 포함하지 않는다.

### 성공 기준

- Fake 없이 실제 Backend를 사용한다.
- AI FastAPI를 Mobile에서 직접 호출하지 않는다.
- Mobile → Backend → AI → Backend → Mobile 흐름이 실제로 동작한다.
- 상담 요청 후 Web에서 같은 문의를 확인할 수 있다.
- 앱을 새로고침하거나 재진입해도 문의 상태가 유지된다.

# 6. 8월 13일 최소 오류 대응

Happy Path가 성공한 뒤 아래 네 가지만 확인한다.

### 1. 409 Conflict

- 사용자가 작성한 입력을 지우지 않는다.
- 최신 Snapshot을 다시 조회한다.
- 최신 `state_version`과 `allowed_actions`로 화면을 다시 그린다.

### 2. AI 503 / Timeout

- 앱이 종료되거나 무한 Loading에 빠지지 않는다.
- 사용자가 다시 시도하거나 상담으로 넘어갈 수 있는 상태를 제공한다.

### 3. Evidence 없음

- 존재하지 않는 근거를 Mobile에서 임의 생성하지 않는다.
- Backend 응답에 따라 안전하게 안내한다.

### 4. 중복 전송

- 동일 버튼 연타로 같은 Business 요청이 반복되지 않게 한다.

이보다 넓은 Error Case·성능·UI Test 확대는 8월 13일 필수 범위가 아니다.

# 7. Blocker가 생겼을 때의 규칙

Backend 또는 AI가 막혀 있다고 기다리고만 있지 않는다.

발견 즉시 다음 형식으로 담당자에게 전달한다.

```text
[Mobile E2E Blocker]
구간: <예: Guidance 조회>
기준 Commit: <SHA>
Endpoint: <Method / Path>
입력: <핵심 값>
기대 결과: <기대 Response/State>
실제 결과: <실제 Response/Error>
Mobile 영향: <어떤 화면에서 막히는지>
필요 담당자: <최지용 / 이동윤 / 김은진 등>
```

### 처리 원칙

- Backend 문제면 최지용에게 즉시 전달한다.
- AI 결과 문제면 이동윤에게 전달한다.
- 공용 환경·DB·배포 문제면 김은진에게 전달한다.
- State·`allowed_actions` 해석 문제면 윤승혁에게 확인한다.
- 수정 Commit이 올라오면 해당 구간부터 바로 재검증한다.
- **Backend가 없다고 Fake Endpoint를 새로 만들지 않는다.**

# 8. 8월 13일 작업이 조기에 끝났을 경우

Mobile 독립 작업이 끝났는데 다른 파트 때문에 E2E가 대기 중이면 디자인 작업으로 돌아가지 않는다.

다음 순서로 팀 E2E를 지원한다.

1. 김은진과 함께 고객 Mobile 실제 기기 Smoke Test 수행
2. 고객 API의 404·409·422·503 재현 지원
3. Mobile 화면과 Backend 로그의 `correlation_id` 대조
4. 한예나와 같은 Inquiry가 Web에 정상 표시되는지 Cross-client 확인
5. 발견된 API·DTO 불일치를 담당자에게 전달
6. 시연용 대표 고객 계정·제품·문의 흐름을 한 번 더 실행

양정현이 Backend·AI 코드를 대신 구현하는 것은 기본 업무가 아니다. **Mobile 소비자 관점에서 E2E를 깨는 문제를 빠르게 찾아주는 역할**을 추가로 맡는다.
