# 2. 3주차 역할 목표

1. **7월 29일까지 DB와 Backend 공통 기반을 재현 가능한 상태로 만든다.**
    
    최신 ERD·Django Model·Migration·Seed 기준을 맞추고, 빈 PostgreSQL에서 서버 실행·Migration·테스트 계정 적재를 재현할 수 있게 한다.
    
2. **고객 문의 생성·증상 제출·추가 입력 누적의 최소 API를 제공한다.**
    
    제품 소유권·MVP 지원 범위·필수값을 검증하고, 하나의 `inquiry_id`에 고객 원문·구조화 증상·문진 답변이 유실 없이 연결되게 한다.
    
3. **State Machine과 API 계약을 다른 담당자가 사용할 수 있는 수준으로 고정한다.**
    
    상태·이벤트·가드·`allowed_actions`·`state_version`·`idempotency_key`·오류 코드를 구현하고, Web·Mobile·AI 담당자에게 OpenAPI·예시 JSON·테스트 계정을 전달한다.

# 3. 3주차 필수 업무

## 3.1 ERD·Django Model·Migration과 데이터베이스 설계 문서 마감

### 작업 목적

서비스의 사용자·제품·구독·케어·문진·문의·상담·방문·상태 이력·AI 실행·공식 근거를 하나의 승인된 데이터 구조로 맞춘다. ERD·Model·Migration·문서가 다르면 이후 API와 테스트의 기준이 달라지므로 가장 먼저 마감한다.

### 작업 위치

```
backend/apps/*/models/**
backend/apps/*/migrations/**
backend/common/models/{base,soft_delete,versioned}.py
backend/tests/migrations/**
backend/tests/factories/**
backend/tests/fixtures/**

scripts/database/**
data/synthetic/fixtures/**                 # 김은진과 협의 후 편집

docs/architecture/database/**
docs/submission/database-storage-design.md
```

### 세부 작업 지침

1. 최신 ERD의 엔터티를 Django App과 연결한다.
    - `accounts`: 사용자·역할·고객 프로필
    - `products`: 지원 모델 레지스트리·고객 제품
    - `subscriptions`: 고객과 제품·관리 유형 연결
    - `care`: 케어 이력·예정 일정
    - `questionnaires`: 문진 세션·답변
    - `inquiries`: 문의·증상·고객 입력
    - `consultations`: 상담 기록·확정 요약
    - `visits`: 방문 일정·결과
    - `workflow`: 현재 상태·상태 이력·멱등성
    - `evidence`: 공식 문서·페이지·근거 참조
    - `audit`: 사용자 행동·AI 실행 기록
2. 누락되기 쉬운 `questionnaire_session`, 상태 이력, 고객 추가 답변, AI 실행·근거 참조 관계를 확인한다.
3. 주요 업무 테이블은 자동 증가 정수형 PK를 사용하고, 외부 API용 `public_id` UUID와 `DEMO-*`·`SYN-*` 업무 식별자를 별도 필드로 관리한다. 테이블별 PK·FK·UNIQUE·NOT NULL·CHECK·Index·삭제 정책을 문서화한다.
4. `WPUJAC104DWH`와 매뉴얼 적용 모델, D세대·후속 모델·`removed_legacy`를 구분할 필드를 둔다.
5. 문의 상태·역할·사용 안내 상태 등 고정 코드는 문자열 칼럼과 Django `TextChoices`로 관리한다. 사용 안내 상태는 `NORMAL`, `PARTIAL_STOP`, `TOTAL_STOP`, `PENDING_CONSULTATION`으로 통일한다. `created_at`, `updated_at`, 상태 버전, 논리 삭제 여부를 공통 Model 기준으로 정리한다.
6. 빈 PostgreSQL에서 Migration을 처음부터 적용하고, 역순 또는 초기화 절차도 문서에 기록한다.
7. Seed는 반복 실행 시 중복을 만들지 않도록 Upsert 또는 명확한 초기화 정책을 적용한다.
8. pgvector는 AI 담당 영역과 중복 테이블을 만들지 말고 문서·페이지·청크·Embedding 버전 연결 키를 확정한다. `BAAI/bge-m3` 원본 1024차원과 동일한 VectorField를 사용하며, MVP 검색은 별도 HNSW·IVFFlat Index 없이 Exact Search를 사용한다.
9. 데이터베이스·저장소 설계 문서에 실제 테이블명, 파일 경로, 저장소 구분, 보안·백업·복구·보존 정책을 반영한다.
10. 문서의 예시 사용자·테이블·수치는 실제 합성 ID와 현재 스키마 기준으로 교체한다.

### 완료 기준

- ERD·Django Model·Migration·설계 문서의 엔터티와 관계가 일치한다.
- 빈 PostgreSQL에 전체 Migration이 오류 없이 적용된다.
- 주요 FK·UNIQUE·NOT NULL·CHECK 제약 검증이 통과한다.
- Seed를 2회 실행해도 예상하지 않은 중복이 발생하지 않는다.
- 내부 정수 PK, 외부 `public_id` UUID와 업무 식별자가 분리되어 있다.
- 고정 상태 코드가 Django `TextChoices`와 계약 파일에서 일치한다.
- 문진 세션, 문의 입력, 상태 이력, AI 근거의 연결 키가 확인된다.
- 데이터베이스·저장소 설계 문서가 **7월 29일까지 검토 가능한 상태**로 작성되어 있다.
- 미확정 사항은 임의 구현하지 않고 담당자·결정 기한·임시 기준이 기록되어 있다.

### 산출물

- 최신 ERD·데이터 사전
- Django Model·Migration
- Seed·Fixture 적재 절차
- Migration·무결성 검증 결과
- 데이터베이스·저장소 설계 문서 초안 완료본

### 세부 작업 지침

1. Python·Django·DRF·PostgreSQL Driver·테스트 도구의 버전을 고정한다.
2. `base`, `local`, `test`, `production` 설정을 분리하고 DB·JWT·AI URL·CORS·로그 수준은 환경변수로 관리한다.
3. `GET /health`를 구현한다. 서버 생존과 DB 연결 확인을 분리할 경우 응답 의미를 README에 기록한다.
4. 공통 성공 응답, 오류 응답, 페이지네이션, 응답 Metadata 구조를 `contracts/api/**`와 일치시킨다. 날짜·시간은 DB에 UTC로 저장하고 API에는 `+09:00`이 포함된 ISO 8601 형식으로 반환한다.
5. 전역 예외 Handler에서 입력 오류, 인증·권한, 리소스 없음, 상태 충돌, 외부 AI 오류, 내부 오류를 구분한다.
6. 요청마다 `correlation_id`를 생성하거나 전달받고 응답 Header·Metadata·구조화 로그에 연결한다.
7. 로그에서 토큰·전화번호·주소·고객 원문 전체·AI Prompt를 마스킹한다.
8. `backend/README.md`에 설치, 환경변수, DB 생성, Migration, Seed, 실행, 테스트 명령을 기록한다.
9. View–Serializer–Service–Repository 책임을 지키고 View에서 복잡한 ORM·상태 전환을 수행하지 않는다.
10. `/api/v1` 하위 URL 구조를 고정하고 임시 Endpoint는 `mock` 또는 `test`임을 명확히 표시한다. 설명 문서와 계약 파일이 충돌하면 `contracts/**`를 최종 기준으로 사용한다.

## 3.3 가상 로그인·역할 기반 접근 제어 구현

### 작업 목적

고객·상담사·방문기사·운영자가 자신의 권한 범위 안에서만 API와 데이터를 조회·수정하도록 한다. 화면에서 역할을 숨기는 것만으로는 권한 제어가 되지 않으므로 Backend에서 객체 단위 접근을 검증한다.

### 작업 위치

```
backend/apps/accounts/
├─ api/{urls,views,serializers}.py
├─ models/{user,customer_profile}.py
├─ services/{authentication_service,account_service}.py
├─ repositories/account_repository.py
├─ permissions.py
└─ migrations/**

backend/common/authentication/{jwt_authentication,claims}.py
backend/tests/permissions/**
backend/tests/unit/accounts/**
backend/tests/api/**
contracts/api/**/auth*
contracts/codes/roles.*
```

### 세부 작업 지침

1. 3주차에는 합성 사용자용 로그인, 현재 사용자 조회, Access Token 재발급, 로그아웃의 최소 흐름만 구현한다.
2. Access Token과 Refresh Token을 함께 사용한다. Access Token 유효기간은 60분, Refresh Token 유효기간은 최초 발급 시점부터 7일로 고정하며, 재발급 시 Refresh Token 만료일을 연장하지 않는다. JWT Claim에는 사용자 ID·역할·토큰 버전 등 최소 정보만 넣고 개인정보를 넣지 않는다.
3. `CUSTOMER`, `CONSULTANT`, `TECHNICIAN`, `OPERATOR` 역할 Permission을 구현한다.
4. 고객은 본인 제품·구독·문진·문의만 접근할 수 있게 객체 소유권을 검사한다.
5. 방문기사는 자신에게 배정된 방문 건만 조회·변경하도록 제한한다.
6. 상담사와 운영자의 조회 범위는 화면·요구사항 기준으로 구분한다.
7. 역할상 허용되지 않은 기능 접근은 `403 Forbidden`, 다른 사용자가 소유하거나 담당하는 개별 리소스 접근은 존재 여부를 숨기기 위해 `404 Not Found`를 반환한다.
8. Access Token 만료 시 유효한 Refresh Token으로 새 Access Token을 발급한다. 로그아웃 시 Refresh Token은 서버에서 즉시 폐기하고 Access Token은 클라이언트에서 삭제한 뒤 최대 60분 안에 자연 만료시킨다.
9. 비활성 사용자, 잘못된 토큰, 만료 토큰, 폐기된 Refresh Token, 역할 부족, 타 고객 데이터 접근을 테스트한다.
10. 한예나·양정현에게 역할별 테스트 계정, 로그인·재발급 요청, Token Header, 오류 예시를 전달한다. 완성형 회원가입·비밀번호 재설정·소셜 로그인은 구현하지 않는다.

### 완료 기준

- 정상 로그인과 현재 사용자 조회가 동작한다.
- 미인증·토큰 만료는 401, 역할 부족은 403, 타 사용자 리소스는 404로 구분된다.
- Access Token 만료 후 재발급이 동작하고, 로그아웃으로 폐기된 Refresh Token은 재사용할 수 없다.
- 고객 IDOR와 기사 미배정 건 접근이 차단된다.
- 역할별 테스트 계정이 Seed로 적재되고 반복 실행 가능하다.
- JWT Claim·응답·로그에 불필요한 개인정보가 없다.
- Web·Mobile이 사용할 인증 예시와 권한 오류 예시가 제공된다.

### 산출물

- 가상 로그인·현재 사용자·Token 재발급 API
- JWT 인증·역할 Permission
- 역할별 합성 테스트 계정
- 권한 테스트 결과
- 인증 OpenAPI·예시 JSON

## 3.4 문의 생성·증상 제출·추가 입력 누적 API 구현

### 작업 목적

고객의 최초 자연어 증상과 대표 증상 선택, 추가 질문 답변을 하나의 문의에 누적하여 AI·상담·방문 흐름이 같은 `inquiry_id`를 사용하게 한다. 고객 원문은 보존하고 구조화 결과나 AI 결과가 덮어쓰지 않게 한다.

### 작업 위치

```
backend/apps/inquiries/
├─ api/{urls,views,serializers}.py
├─ models/{inquiry,inquiry_symptom,customer_input}.py
├─ services/{inquiry_service,symptom_service,input_accumulation_service}.py

├─ permissions.py

backend/apps/products/services/product_validation_service.py
backend/apps/questionnaires/models/**
backend/apps/questionnaires/services/**
backend/tests/unit/inquiries/**
backend/tests/api/**
contracts/api/**/inquiries*
contracts/api/examples/inquiries/**
```

### 세부 작업 지침

1. `START_INQUIRY`에 해당하는 신규 문의 생성 Endpoint를 구현한다.
2. 인증 고객이 소유한 구독 제품인지, MVP 지원 제품인지, 필수 입력이 있는지 AI 호출 전에 검증한다.
3. 출수량 저하·물맛/냄새·누수·냉온수 이상·기타를 복수 선택할 수 있게 하고, 대표 증상 미선택 시 자연어 원문을 필수로 한다.
4. 고객 원문, 구조화 증상, 발생 조건, 표시 문구·오류 코드, 진입 유형을 분리 저장한다.
5. 동일 문의에 고객 보충 설명·문진 답변·AI 추가 질문 답변을 순서와 작성자·생성 시각과 함께 누적한다.
6. 종료된 문의, 타 고객 문의, 존재하지 않는 문의, 허용되지 않은 입력 유형은 차단한다.
7. 문의 생성과 입력 저장의 트랜잭션 경계를 정해 실패 시 반쪽 데이터가 남지 않게 한다.
8. AI 실패·Timeout이 발생해도 고객 입력과 문의는 유지되고 다시 조회·재시도할 수 있게 한다.
9. 응답에는 내부 정수 PK가 아닌 공개 UUID `inquiry_id`, 별도 업무 번호 `inquiry_code`, 현재 상태, `state_version`, `allowed_actions`, 다음 처리 여부를 포함한다.
10. 정상·자연어 단독·복수 증상·필수값 누락·미지원 제품·타 고객·중복 제출 테스트를 작성한다.

### 완료 기준

- 신규 문의가 생성되고 고유 `inquiry_id`가 반환된다.
- 같은 문의에 증상·보충 설명·답변이 순서대로 누적된다.
- 자연어 단독 입력과 복수 증상 선택이 모두 처리된다.
- 타 고객 제품·미지원 제품·필수값 누락이 AI 호출 전에 차단된다.
- AI 실패 후에도 저장된 문의와 입력이 조회된다.
- 고객 원문과 구조화 증상·AI 결과가 서로 덮어써지지 않는다.
- 양정현이 Mock을 교체할 수 있는 Request·Response·오류 예시가 제공된다.

## 3.5 State Machine 행동별 API와 상태 이력 구현

### 작업 목적

문의·상담·방문 상태를 역할과 이벤트에 따라 일관되게 전환하고, 중복 클릭과 동시 수정으로 상태와 이력이 왜곡되는 것을 막는다. Backend가 상태의 최종 권위를 가지며 다른 영역은 행동별 Endpoint만 요청한다.

### 작업 위치

```
backend/apps/workflow/
├─ api/{urls,views,serializers}.py
├─ models/{workflow_snapshot,state_transition_history,idempotency_record}.py
├─ services/{state_machine_service,allowed_action_service,idempotency_service}.py
├─ guards/{role_guard,state_guard,payload_guard}.py
├─ repositories/{workflow_repository,history_repository}.py
└─ migrations/**

backend/common/models/versioned.py
backend/tests/unit/workflow/**
backend/tests/api/**
contracts/state-machine/**
contracts/codes/**
contracts/api/examples/workflow/**
```

### 세부 작업 지침

1. 문의 상태와 방문 상태를 별도 Django `TextChoices`와 Snapshot으로 관리한다.
2. 외부 API는 `/request-consultation`, `/start-consultation`, `/finalize` 등 행동별 Endpoint로 제공하고, 각 Endpoint 내부에서 공통 State Machine Service를 호출한다. `START_INQUIRY`, `SUBMIT_SYMPTOM`, `SAFE_GUIDANCE_READY`, `DANGER_DETECTED`, `NO_EVIDENCE`, `REQUEST_CONSULTATION` 등 3주차 최소 이벤트부터 구현한다.
3. 이벤트별 허용 현재 상태, 실행 역할, 필수 Payload, 다음 상태를 검증한다.
4. 현재 상태와 사용자 역할을 기준으로 `allowed_actions`를 계산해 조회·쓰기 응답에 포함한다.
5. `state_version`으로 오래된 요청을 감지하고 최신 상태를 덮어쓰지 않도록 409를 반환한다. 409 응답에는 오류 코드·메시지와 최신 `current_status`, `state_version`, `allowed_actions`를 포함한다.
6. `idempotency_key`로 동일 쓰기 요청이 재전송되어도 상태 변경·이력이 한 번만 발생하게 한다.
7. 이전 상태, 다음 상태, 이벤트, 수행자, 사유, 시각, `correlation_id`를 상태 이력에 저장한다.
8. 사용자 입력 저장, 상태 전이, Snapshot·이력 저장을 하나의 DB 트랜잭션으로 묶는다.
9. 자가조치 단독 해결과 상담·방문 경로의 `COMPLETION_PENDING`·`FINALIZE_INQUIRY` 정책을 구조에 반영하되, 3주차 테스트는 최소 전이로 제한할 수 있다.
10. AI는 위험·다음 행동을 제안할 뿐 DB 상태를 직접 변경하지 못하게 하고 Backend Service가 AI 결과를 이벤트 후보로 변환한다.
11. 잘못된 역할, 잘못된 순서, 누락 Payload, 중복 Key, 오래된 Version을 테스트한다.

### 완료 기준

- 대표 정상 전이가 실제 PostgreSQL에서 동작한다.
- 권한 없는 역할과 허용되지 않은 상태의 이벤트가 거부된다.
- `allowed_actions`가 현재 상태·역할에 따라 달라진다.
- 오래된 `state_version`이 최신 상태를 덮어쓰지 않는다.
- 같은 `idempotency_key`로 상태 이력이 중복 생성되지 않는다.
- 이전·다음 상태·이벤트·수행자·사유가 이력에 남는다.
- 409 응답에 최신 상태·`state_version`·`allowed_actions`가 포함된다.
- 한예나·양정현이 행동별 Endpoint와 409 응답 예시를 사용할 수 있다.

### 산출물

- 행동별 상태 변경 API
- `allowed_actions` 계산
- 상태 Snapshot·전이 이력·멱등성 기록
- 동시성·멱등성·권한 테스트
- 상태 전환 API 예시

## 5.3 Backend·DB 역할 수행 시 주의사항

- View에서 복잡한 ORM Query나 상태 전환을 직접 구현하지 않는다.
- Serializer에서 AI 호출·상태 전환·DB 트랜잭션을 수행하지 않는다.
- Model `save()`에서 외부 서비스 호출이나 업무 흐름 변경을 수행하지 않는다.
- Repository는 조회·저장에 집중하고 역할·상태 판단은 Service·Guard에서 수행한다.
- 화면이나 AI가 상태를 직접 바꾸게 하지 않고 이벤트 API를 사용한다.
- Migration 대신 수동 SQL로만 로컬 DB를 맞추지 않는다.
- 프론트 편의를 위해 Enum·오류 코드·응답 필드를 임의로 추가하지 않는다.
- `contracts/**`, `data/**`, `tests/**`, `infra/**` 수정 시 해당 주관할 담당자와 협의한다.
- 실제 개인정보·운영 Token·비밀키·실제 고객 상담 원문을 저장소에 넣지 않는다.
- 기능 개수보다 권한·상태·이력·중복 방지·재현 가능한 실행 증거를 우선한다.
