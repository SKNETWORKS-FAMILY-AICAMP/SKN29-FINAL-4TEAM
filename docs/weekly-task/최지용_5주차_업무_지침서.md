# 최지용 5주차 업무 지침서

> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템
>
> 대상 기간: **2026년 8월 10일 ~ 8월 14일**
>
> 5주차 운영 컨셉: **WBS 5주차 Backend Runtime · AI 최소 수직 연결 · 조기 E2E 조건부 실행**
>
> 핵심 API 동결 목표: **2026년 8월 13일 오후**
>
> 최종 Backend 회귀·E2E 기준선 목표: **2026년 8월 14일**
>
> 5주차 운영 원칙: 4주차까지 작성·승인된 API 계약과 State Machine 계약을 다시 넓게 설계하는 것이 아니라, **이미 확정된 계약을 실제 Django Runtime으로 구현하고 Web·Mobile·AI가 기다리지 않도록 순차적으로 API를 개방하는 것**을 최우선으로 한다.
>
> 5주차에는 Backend 기반 코드·Model·Migration·계약 파일이 존재한다는 이유로 완료 처리하지 않는다. WBS 5주차 대상 URL과 인증·권한·Service·Repository·Transaction·State Machine·멱등성·오류 응답이 연결되고, 실제 PostgreSQL과 AI FastAPI를 거친 최소 통합 Test가 통과해야 완료로 인정한다. 대표 E2E는 선행 Gate가 닫힌 경우에만 조기 수행한다.
>
> 특히 현재 저장소는 인증·구독·문의 생성·증상 제출·취소·공통 Workflow·AI Adapter 기반은 강하지만, **상담사 문의 목록·상세, 추가 질문 답변, 상담 Runtime, 방문 Runtime, Backend→AI 실제 Wiring, 방문 이후 후반 State Operation**이 주요 공백이다. 5주차는 이 공백을 닫아 6주차에 신규 P0 Backend 기능을 남기지 않는 것을 목표로 한다.
>
> 6주차 가용 시간이 제한되므로 5주차 안에 WBS 대상 Backend Runtime과 Backend↔AI 최소 연결을 우선 완료하고, 대표 E2E는 필수 범위를 해치지 않는 범위에서만 앞당긴다.

현재 코드 검사 기준으로 Backend는 다음 상태다.

1. Django·DRF 공통 구조와 PostgreSQL Migration 기반은 상당히 안정화되어 있다.
2. JWT·RBAC·합성 계정 관리와 Public UUID·객체 권한 기반이 존재한다.
3. `GET /api/v1/me/subscriptions`, `GET /api/v1/me/subscriptions/{subscription_id}` Runtime이 구현되어 있다.
4. `POST /api/v1/inquiries`, `POST /api/v1/inquiries/{id}/submit`, `POST /api/v1/inquiries/{id}/cancel` Runtime이 구현되어 있다.
5. 문의 증상 제출에는 `state_version`, Idempotency, 409 Conflict, Transaction·Concurrency Test가 존재한다.
6. State Machine 계약과 Validator·Crosswalk는 강하지만 외부 Action 대비 실제 Runtime Operation 수는 아직 부족하다.
7. `backend/integrations/ai/**`와 `InquiryAIService`는 구현되어 있으나 실제 고객 Runtime에서 `analyze_inquiry()`가 자동 호출되는 수직 연결은 미완료다.
8. 상담·방문 Model·Migration은 존재하지만 API·Serializer·Service·Repository는 대부분 골격 수준이다.
9. OpenAPI에는 상담·방문 핵심 Operation이 `CONFIRMED` 상태로 존재하므로 5주차에는 계약 반복 작성보다 Runtime 구현이 우선이다.
10. 현재 계약만으로는 방문 시작·완료·고객 해결 피드백·최종 Inquiry 종료까지의 일부 Action이 `DEFERRED` 상태이므로, 대표 E2E에 필요하면 윤승혁 PM 승인 후 계약을 먼저 확정해야 한다.

따라서 5주차의 Backend 우선순위는 다음과 같다.

```text
상담사 조회
→ 추가 질문·AI Runtime
→ 상담 Runtime
→ 방문 Runtime
→ 기사/고객 E2E 후반 Operation
→ 5주차 필수 범위 회귀·후속 인계
```

# 2. 5주차 역할 목표

1. **8월 10일 오전까지 Backend·PostgreSQL·OpenAPI·State Machine 기준선을 최신 `main`에서 재검증한다.**

   전체 Migration, 주요 Backend Test, OpenAPI·Crosswalk·State Machine Validator, Seed·Fixture, 실제 Runtime Route를 다시 확인한다. 계약만 존재하는 Operation과 Runtime 구현 Operation을 명확히 분리한다.

2. **8월 10일까지 상담사 Inquiry 목록·상세와 고객 추가 질문 답변 API를 제공한다.**

   한예나가 Web Mock을 실제 API로 전환하고 양정현이 고객 문진을 실제 API로 연결할 수 있도록 상담사 목록·상세와 질문 답변 Runtime을 가장 먼저 개방한다.

3. **8월 11일까지 Backend↔AI 실제 HTTP Runtime을 완료한다.**

   고객 증상 제출 또는 확정된 호출 시점 이후 Django가 실제 FastAPI를 호출하고, AI Run·구조화 증상·질문·Evidence·Guidance가 저장되며 Backend State Machine이 결과에 따라 다음 Event를 적용하도록 한다.

4. **8월 11~12일까지 상담 Runtime을 완료한다.**

   상담 시작, 상담 요약 저장, 확정, 상담 완료 또는 방문 검토 진입까지 확정 계약 범위의 Operation을 실제 Service·Repository·Permission·Transaction으로 구현한다.

5. **8월 12~13일까지 방문 Runtime을 완료한다.**

   방문 필요 검토, Visit 생성, 일정 제안·확정, 기사 배정·조회까지 P0 대표 E2E에 필요한 범위를 구현하고 Mobile 기사 앱이 실제 API를 소비할 수 있게 한다.

6. **8월 12일까지 E2E 후반부에 필요한 `DEFERRED` Operation의 계약 필요 여부를 PM에게 확정 요청한다.**

   기사 방문 시작·완료, 고객 해결 피드백, 최종 Inquiry 종료가 대표 E2E 필수 범위라면 최지용이 임의로 URL을 만들지 않고 윤승혁의 계약 승인 후 Runtime 구현을 진행한다.

7. **3장 필수 Runtime과 Gate가 조기에 닫힌 경우에만 대표 E2E Backend 구간을 5장 조건부 업무로 실행한다.**

   고객·상담사·기사의 실제 역할 Token, 같은 Inquiry·Visit, 실제 PostgreSQL·AI FastAPI를 사용하여 State와 DB가 끝까지 일치하는지 확인한다.

8. **8월 14일까지 WBS 5주차 Backend 범위의 회귀 결과와 6~7주차 잔여 범위를 고정한다.**

   6주차에는 신규 핵심 Backend API 개발보다 배포·성능·잔여 버그·v1.0 Release 안정화로 전환할 수 있게 한다.

5주차 완료 기준은 “OpenAPI에 Operation이 있다”, “Model이 있다”, “Test 파일이 있다”가 아니다. **WBS 5주차 대상 URL→Permission→Service→Repository→DB→Workflow→외부 AI 최소 연결과 핵심 정상·오류 Case가 최신 Commit에서 재현되어야 한다.**

# 3. 5주차 필수 업무

> 이 장은 현행 WBS의 **5주차 범위**만 필수로 다룬다. WBS상 6~7주차에 배정된 전체 E2E·전체 회귀·후행 Runtime·최종 Feature Complete 업무는 5장의 조기 완료 업무로 분리한다.

## 3.1 Backend·PostgreSQL·계약·Runtime Entry Gate 재검증

### 작업 목적

5주차 대량 Runtime 구현 전에 현재 Backend 기준선을 정확히 고정한다. 4주차에 생성된 과거 테스트 결과나 문서의 구현 상태를 그대로 사용하지 않고 최신 `main`에서 Migration·Route·OpenAPI·State Machine·Seed·Test를 다시 확인한다.

### 작업 위치

```text
backend/
├─ config/api_urls.py
├─ config/settings/**
├─ apps/**
├─ integrations/**
├─ tests/**
└─ README.md

contracts/
├─ api/**
├─ state-machine/**
├─ codes/**
└─ error-codes/**

scripts/
├─ contracts/**
└─ database/**

docs/testing/backend/**
```

### 세부 작업 지침

1. 5주차 기준 Commit SHA를 기록한다.
2. Python·Django·DRF·PostgreSQL Version을 기록한다.
3. 빈 또는 독립 QA PostgreSQL에서 전체 Migration을 적용한다.
4. `showmigrations`로 미적용 Migration이 없는지 확인한다.
5. `makemigrations --check`를 실행한다.
6. Demo Seed·합성 사용자 Import를 실행한다.
7. Seed를 2회 실행하여 Replay·Upsert·중복 정책을 확인한다.
8. Backend 전체 Test 또는 합의된 표적 + 전체 Test를 실행한다.
9. PostgreSQL 의존 Test를 SQLite 결과와 구분한다.
10. State Machine Validator를 실행한다.
11. State Diagram Check를 실행한다.
12. OpenAPI Validator를 실행한다.
13. Action–Operation Crosswalk Validator를 실행한다.
14. 계약 Operation과 실제 Django URL을 비교한다.
15. Operation을 다음으로 분류한다.
    - `RUNTIME_DONE`
    - `RUNTIME_PARTIAL`
    - `CONTRACT_ONLY`
    - `DEFERRED`
    - `NOT_P0`
16. 현재 `/api/v1`에 연결된 App을 다시 확인한다.
17. `subscriptions`, `inquiries` 외 새 Domain Runtime이 병합되어 있으면 상태표에 반영한다.
18. 4주차 문서보다 코드가 앞선 경우 문서를 최신화한다.
19. 코드보다 문서가 앞선 경우 Runtime 완료로 표시하지 않는다.
20. 상담·방문 Operation 중 Web·Mobile 선행 차단 항목을 표시한다.
21. E2E 후반 `DEFERRED` Operation을 별도 목록으로 만든다.
22. 각 Blocker에 담당자·결정 필요자·목표 시간을 붙인다.
23. 8월 10일 오전 안에 개발 환경·Migration·Seed Blocker를 닫는다.

### 완료 기준

- 최신 Commit에서 Migration·Seed가 재현된다.
- Backend Test의 현재 결과가 기록되어 있다.
- State Machine·OpenAPI·Crosswalk Validator가 현재 상태로 기록되어 있다.
- 실제 Runtime과 계약만 존재하는 Operation이 구분되어 있다.
- Web·Mobile·AI를 막는 Backend Blocker가 명확하다.
- E2E 후반 계약 결정 필요 항목이 PM에게 전달되어 있다.
- 5주차 기능 개발 기준선이 하나의 문서로 고정되어 있다.

## 3.2 상담사 문의 목록·상세 Runtime 구현 및 Web 선행 Blocker 해제

### 작업 목적

상담사 Web이 더 이상 Mock 문의 목록·상세에 의존하지 않도록 실제 Inquiry 조회 Runtime을 최우선 제공한다. 역할·배정 여부·PII Projection·`allowed_actions`·State Version을 Backend에서 통제한다.

### 작업 위치

```text
backend/apps/inquiries/
├─ api/
│  ├─ urls.py
│  ├─ views.py
│  └─ serializers.py
├─ services/**
├─ repositories/**
└─ permissions.py

backend/apps/accounts/**
backend/apps/workflow/**
backend/tests/api/inquiries/**
backend/tests/integration/permissions/**
contracts/api/**
```

### 필수 Runtime

```text
GET /api/v1/inquiries
GET /api/v1/inquiries/{inquiry_id}
```

### 세부 작업 지침

1. 현재 POST 전용 문의 Collection Route를 GET과 공존하도록 구현한다.
2. 상담사는 권한 범위 내 문의만 조회한다.
3. 운영자·고객·기사 역할의 Projection을 동일 Serializer로 무리하게 처리하지 않는다.
4. 목록과 상세 Projection을 분리한다.
5. 고객 본인 조회가 필요하면 고객 Projection을 별도 정의한다.
6. 상담사 목록의 PII는 승인된 정책에 맞게 Mask·비노출한다.
7. 상담사 권한 상세에서도 주소는 P0 기본 비노출 원칙을 유지한다.
8. 실제 개인정보가 아닌 합성 데이터만 사용한다.
9. `status_code`, 담당자, 생성일, 위험도, 제품 정보, 현재 State를 계약대로 반환한다.
10. `allowed_actions`는 Workflow Engine 결과를 사용한다.
11. `state_version`을 반환한다.
12. Pagination을 계약대로 구현한다.
13. 미정 Query Parameter는 422 또는 계약 오류로 처리한다.
14. 초과 Page는 계약된 결과로 처리한다.
15. 잘못된 UUID는 404 또는 계약 정책을 따른다.
16. 타 고객·타 담당자 Resource 존재 여부가 노출되지 않게 한다.
17. Query 수를 확인하고 N+1을 방지한다.
18. 목록에서 필요 없는 Evidence 원문·고객 원문 전체를 조회하지 않는다.
19. 상세에서 AI 결과가 아직 없으면 Nullable 계약을 지킨다.
20. 한예나에게 실제 요청·응답 Example을 전달한다.
21. API 변경 시 OpenAPI를 먼저 또는 동시에 갱신한다.
22. Web이 같은 날 Remote Adapter를 붙일 수 있도록 8월 10일 안에 병합 가능한 상태를 목표로 한다.

### 완료 기준

- 상담사 Inquiry 목록·상세가 실제 Runtime으로 동작한다.
- 역할·객체 권한이 QuerySet·Permission에서 검증된다.
- PII Projection이 승인 정책과 일치한다.
- `allowed_actions`·`state_version`이 반환된다.
- Pagination·Query 오류가 계약과 일치한다.
- N+1이 방지된다.
- 한예나가 Mock을 실제 API로 교체할 수 있는 Example이 제공되어 있다.

### 산출물

- 상담사 Inquiry 목록·상세 Runtime
- 역할별 Projection
- 권한·Pagination·N+1 Test
- Web 인계용 API Example

## 3.3 추가 질문 답변·문의 현재 상태 조회·고객 문진 Runtime 완성

### 작업 목적

고객 증상 제출 이후 AI가 추가 질문을 반환하는 경우 Mobile이 실제 답변을 저장하고 같은 Inquiry에 누적할 수 있게 한다. 409 Conflict 이후 최신 상태를 재조회할 수 있는 기반도 제공한다.

### 작업 위치

```text
backend/apps/inquiries/**
backend/apps/questionnaires/**
backend/apps/workflow/**
backend/tests/api/**
backend/tests/integration/**
contracts/api/**
```

### 필수 Runtime

계약 기준으로 다음 범위를 확정한다.


# 4. 5주차 일정 운영 기준

> 이 일정에서 5장으로 이동된 업무는 **조기 완료 조건부 목표**다. 3장 필수 업무보다 우선하지 않으며, 조건이 충족되지 않으면 현행 WBS의 6~7주차 일정으로 유지한다.

> 공통 적용 규칙: **3장에 없는 업무는 4장의 필수 목표가 될 수 없다.** 5장 업무를 일정에 표시할 때는 반드시 **`[조건부 — 3장 Gate PASS 시]`**로 구분한다.

5주차는 Web·Mobile·AI가 Backend를 기다리는 시간을 최소화하기 위해 **완성되는 API를 금요일에 한꺼번에 넘기지 않고 매일 순차 제공**한다.

## 5.1 E2E 후반 `DEFERRED` Operation 계약 폐쇄 및 Runtime 구현

### 작업 목적

5주차 대표 E2E를 방문 일정 확정에서 끝내지 않고 가능하면 기사 조치→고객 해결 확인→Inquiry 종료까지 연결한다. 단, 현재 계약에서 `DEFERRED`인 Action을 최지용이 임의 Endpoint로 구현하지 않고 PM·State 계약 승인 후 구현한다.

### 우선 검토 Action

```text
START_VISIT
VISIT_COMPLETED
REVISIT_NEEDED
SUBMIT_RESOLUTION_FEEDBACK
CUSTOMER_REPORTED_UNRESOLVED
RESUME_CONSULTATION
FINALIZE_INQUIRY
UPDATE_PREVISIT_REPORT
CONFIRM_PREVISIT_REPORT
```

### 작업 위치

```text
contracts/state-machine/**          # 윤승혁 주관
contracts/api/**                    # 최지용 주관, PM 승인 선행
backend/apps/visits/**
backend/apps/inquiries/**
backend/apps/consultations/**
backend/apps/workflow/**
backend/tests/integration/e2e/**
tests/e2e/**
```

### 세부 작업 지침

1. 8월 10일 Entry Gate에서 E2E 후반 필요 Operation을 목록화한다.
2. 대표 E2E에 반드시 필요한 것과 P1로 미뤄도 되는 것을 분리한다.
3. 윤승혁에게 최소 Operation Set을 결정 요청한다.
4. 계약 승인 전 Runtime을 임의 구현하지 않는다.
5. 승인된 Operation만 OpenAPI·Error Matrix·DTO를 먼저 갱신한다.
6. Contract Test를 작성한다.
7. Contract Test PASS 후 Runtime을 구현한다.
8. 기사 방문 시작 Operation을 구현하는 경우 기사 본인 배정 여부를 검증한다.
9. 방문 완료는 조치 결과·필수 필드 Guard를 검증한다.
10. 재방문 필요는 기존 Visit과 새 Visit 관계를 명확히 한다.
11. 고객 해결 피드백은 고객 본인 Inquiry·Visit에만 허용한다.
12. 고객 미해결 응답은 상담 재개 State로 연결한다.
13. 최종 Inquiry 종료는 모든 필수 Guard를 검증한다.
14. Mobile·Web이 State를 자체 변경하지 않게 한다.
15. Action별 `allowed_actions`를 최신 계약에서 계산한다.
16. 모든 Operation에 `state_version`을 적용한다.
17. State 변경 Operation에 Idempotency를 적용한다.
18. 감사 이력·Transition History를 기록한다.
19. 정상 흐름과 미해결→재상담 흐름을 모두 Test한다.
20. 8월 12일까지 계약 승인 여부를 닫고, 승인 범위는 13일 E2E에 포함한다.

### 완료 기준

- 대표 E2E에 필요한 Deferred Action이 PM 결정으로 정리되어 있다.
- 승인된 Operation은 계약→Contract Test→Runtime 순서를 지킨다.
- 기사 조치·고객 해결 피드백·최종 종료가 승인 범위에서 실제 동작한다.
- 미해결 고객은 재상담 흐름으로 연결된다.
- 각 Operation이 State·권한·멱등성·감사 이력과 연결된다.
- 미승인 Action을 Backend 편의로 임의 추가하지 않는다.

## 5.2 역할·PII·객체 권한·멱등성·동시성 전체 회귀

### 작업 목적

5주차에 상담·방문 Runtime이 대량 추가되면서 인증만 통과하면 모든 데이터가 보이거나 동시에 상태가 덮어써지는 회귀를 방지한다. 고객·상담사·기사·운영자 역할을 실제 PostgreSQL에서 재검증한다.

### 작업 위치

```text

backend/tests/integration/idempotency/**
backend/tests/integration/concurrency/**
backend/tests/integration/workflow/**
backend/tests/security/**
tests/integration/permissions/**
```

### 세부 작업 지침

1. 고객은 본인 구독·문의만 조회한다.
2. 다른 고객 UUID는 404 concealment로 처리한다.
3. 상담사는 승인된 업무 범위만 조회한다.
4. 상담사는 P0에서 고객 주소를 보지 않는다.
5. 운영자는 P0 최소 합성 정보만 사용한다.
6. 기사는 본인 배정 Visit만 조회한다.
7. 기사는 배정 Visit에서만 필요한 합성 고객 정보·주소를 본다.
8. 미배정 Visit은 404 또는 계약 정책으로 숨긴다.
9. 모든 State 변경 Operation에 역할 Guard를 적용한다.
10. 상담사 배정·기사 배정 Guard를 검증한다.
11. 같은 `state_version` 동시 요청은 하나만 성공하게 한다.
12. 동일 `idempotency_key`·동일 Payload Replay를 검증한다.
13. 동일 Key·다른 Payload는 409로 처리한다.
14. Transaction Rollback을 검증한다.
15. PostgreSQL Row Lock·Unique Constraint 의존 Test를 실제 PostgreSQL에서 실행한다.
16. SQLite에서 통과했다고 PostgreSQL 회귀를 생략하지 않는다.
17. PII가 Error Detail·Log·`correlation_id` 로그에 포함되지 않는지 확인한다.
18. 고객 원문 전체·Prompt 전체를 Log에 남기지 않는다.
19. Public UUID와 내부 PK가 혼용되지 않는지 검증한다.
20. 새 Runtime마다 최소 정상·401·403·404·409·422·5xx Case를 확인한다.

### 완료 기준

- 역할별 객체 권한이 실제 PostgreSQL에서 검증된다.
- 상담·기사 PII Projection이 승인 정책과 일치한다.
- 미배정·타 사용자 Resource가 노출되지 않는다.
- 동시 수정은 하나만 성공한다.
- 멱등 Replay·Conflict가 일관되게 동작한다.
- 실패 Transaction이 부분 저장을 남기지 않는다.
- Log·오류 응답에서 PII·Token이 노출되지 않는다.

# 7. Backend·DB 역할 수행 시 주의사항

- Model·Migration·Service 파일 존재를 Runtime 완료로 계산하지 않는다.
- OpenAPI에 Operation이 있다는 이유만으로 구현 완료로 표시하지 않는다.
- `api/urls.py`, `views.py`가 Placeholder인 Domain을 완료로 표시하지 않는다.
- View에서 복잡한 ORM·State 전이·AI 호출을 직접 처리하지 않는다.
- Serializer에서 DB Transaction·외부 호출을 처리하지 않는다.
- Model `save()`에서 Workflow·AI 호출을 수행하지 않는다.
- Repository는 조회·저장 책임에 집중한다.
- Service에서 업무 흐름을 조합하고 Workflow Guard를 사용한다.
- Backend가 State Machine의 최종 권위다.
- AI가 제안한 `next_action`을 검증 없이 State로 적용하지 않는다.
- Web·Mobile의 요청대로 계약에 없는 State를 임의 추가하지 않는다.
- 확정되지 않은 Deferred Operation을 임의 Endpoint로 구현하지 않는다.
- 계약 변경이 필요하면 윤승혁의 승인 후 OpenAPI·Contract Test부터 갱신한다.
- `contracts/ai/**` 의미 변경은 이동윤과 협의한다.
- `tests/**`, QA DB·CI 변경은 김은진과 협의한다.
- 내부 정수 PK를 외부에 노출하지 않는다.
- 외부 Public UUID와 내부 PK를 혼용하지 않는다.
- 타 사용자 Resource 존재 여부를 403 Detail로 노출하지 않는다.
- 상담사에게 고객 주소를 P0 기본으로 노출하지 않는다.
- 기사에게 미배정 Visit의 PII를 노출하지 않는다.
- 실제 개인정보 대신 합성 데이터를 사용한다.
- 고객 원문 전체·Prompt 전체·Token을 Log에 기록하지 않는다.
- AI Timeout을 일반 성공으로 처리하지 않는다.
- Vector DB 장애를 `NO_EVIDENCE`와 혼동하지 않는다.
- 같은 Idempotency Key의 Payload Hash를 검증한다.
- 동시 수정은 마지막 저장 승리 방식으로 처리하지 않는다.
- SQLite Test만으로 PostgreSQL 동시성 완료를 주장하지 않는다.
- E2E를 통과시키기 위해 DB State를 수동 수정하지 않는다.
- 방문 계약이 날짜만 요구하면 P0에서 시간 슬롯을 임의 추가하지 않는다.
- 상담·Visit Runtime은 Web·Mobile보다 하루 이상 늦게 넘기지 않도록 우선한다.
- 8월 13일 오후 이후 대규모 Schema·Migration·Contract 변경을 피한다.
- 8월 14일에는 신규 기능보다 회귀·E2E·문서 정합성에 집중한다.
- 성능 튜닝은 기능·권한·상태 회귀가 모두 닫힌 뒤 수행한다.
- 운영 Dashboard·Graph DB·Kubernetes 등 P1 영역을 5주차 Backend Runtime보다 우선하지 않는다.

# 8. 6주차 인계 기준

5주차 종료 시 Backend는 다음 상태를 목표로 한다.

```text
Customer
구독 조회
+ 문의 생성
+ 증상 제출
+ 추가 질문
+ AI 결과
+ 상담 요청

Consultant
문의 목록
+ 문의 상세
+ 상담 시작
+ 요약
+ 확정
+ 완료
+ 방문 검토

Visit / Technician
방문 생성
+ 일정
+ 확정
+ 기사 조회
+ 승인된 조치 흐름

AI
Django → FastAPI 실제 HTTP
+ 결과 저장
+ Backend State Event

Common
RBAC
+ Object Permission
+ State Version
+ Idempotency
+ Concurrency
+ Audit
+ PostgreSQL
+ E2E
```

6주차에 남겨도 되는 Backend 업무는 다음 중심으로 제한한다.

- 배포 환경 설정
- Nginx·Gunicorn·Container 연동 지원
- Query·Index 최적화
- 잔여 버그
- 운영 로그·Observability 보완
- 문서 마감
- v1.0 Release Candidate 검증

다음 항목은 조기 완료하지 못하면 현행 WBS의 6~7주차 일정으로 인계한다.

- 상담사 Inquiry 목록·상세 미구현
- 추가 질문 답변 Runtime 미구현
- Backend→AI 실제 HTTP 미연결
- 상담 시작·요약·확정·완료 미구현
- Visit 생성·일정·확정 미구현
- 기사 앱이 실제 Visit을 조회하지 못함
- 대표 E2E Backend 구간 미통과
- 핵심 Permission·State·Idempotency Test 실패
- PostgreSQL Migration·Concurrency 미검증

본 지침서의 핵심은 **4주차까지 강하게 구축된 Backend 기반과 계약을 실제 서비스 Runtime으로 전환하여, 다른 팀원이 더 이상 Backend 미구현을 이유로 Mock·Fixture에 머물지 않게 하는 것**이다.

최지용은 상담사 조회·고객 문진 API와 Backend↔AI 실제 HTTP, WBS에 명시된 상담·방문 선행 Runtime을 우선 닫는다. E2E 후반 Deferred Action·대표 E2E·전체 회귀는 3장 필수 Gate가 조기에 닫힌 경우에만 5장 업무로 수행한다.

5주차 종료 시점에는 **WBS 5주차 대상 Runtime과 Backend↔AI 최소 연결에서 Backend가 실제 원장·State 권위로 동작하는 것**을 필수 목표로 한다. 고객→AI→상담→방문 전체 E2E는 조기 완료 또는 현행 WBS의 후속 일정에서 판정한다.
