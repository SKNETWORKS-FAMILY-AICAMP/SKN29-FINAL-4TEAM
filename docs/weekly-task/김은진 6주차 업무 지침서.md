# 김은진 6주차 업무 지침서

> 담당자: 김은진  
> 역할: 데이터·QA·DevOps  
> 적용 기간: 2026-08-18 ~ 2026-08-21  
> 핵심 원칙: **6주차에는 공용 비운영 환경을 실제로 사용할 수 있게 만들고, 같은 기준 Commit에서 Mobile → Backend → AI → RDS → Web 흐름을 독립 QA로 검증한다. 환경 구축만으로 완료 처리하지 않는다.**

---

# 1. 6주차 완료 목표

6주차가 끝났을 때 아래 항목이 실제 환경에서 확인되어야 한다.

- [ ] 팀원이 같은 비운영 환경에서 Backend와 AI를 실행하고 AWS RDS PostgreSQL을 사용할 수 있다.
- [ ] Backend와 AI가 서로 다른 DB 권한을 사용하고, 비밀값이 Git·문서·로그에 노출되지 않는다.
- [ ] 실제 고객 Mobile에서 생성한 신규 문의가 같은 `inquiry_id`로 Backend → 실제 AI → RDS → 상담사 Web까지 이어진다.
- [ ] 상담 처리 후 고객 Mobile에서 같은 문의의 최신 상태를 다시 확인할 수 있다.
- [ ] 일반 증상은 실제 pgvector 검색 + 실제 생성형 LLM 경로를 통과한다.
- [ ] 위험 증상은 Safety Rule이 우선하며 잘못된 사용 가능 안내가 나오지 않는다.
- [ ] 근거 없음 상황에서는 임의 자가조치가 생성되지 않고 재질문 또는 상담 전환이 이루어진다.
- [ ] AI Timeout·검색 실패·잘못된 입력에서도 데이터가 깨지거나 중복 저장되지 않는다.
- [ ] 동일 요청 재전송과 동일 합성 데이터 재적재에서도 불필요한 중복 데이터가 생기지 않는다.
- [ ] 두 상담사가 같은 문의를 동시에 처리하려 할 때 동시성 제어와 권한 검사가 정상 동작한다.
- [ ] 화면·API·Backend 로그·AI 로그·DB 기록을 `inquiry_id`, `correlation_id`, `ai_request_id`, `state_version`으로 추적할 수 있다.
- [ ] RDS 백업을 실제 복원하고 핵심 데이터 조회까지 확인한다.
- [ ] 최신 후보 Commit을 `PASS / PASS WITH LIMITATION / BLOCKED` 중 하나로 명확히 판정한다.

> **실제 E2E, 실제 AI, 실제 RDS, 동시성·중복·복구 중 핵심 항목이 확인되지 않으면 6주차 QA 완료로 판정하지 않는다.**

# 2. 이번 주 핵심 업무

## A. 공용 비운영 환경과 RDS 준비

환경을 만드는 것보다 **팀이 실제로 사용할 수 있는 상태**가 목표다.

필수 확인:

- AWS RDS PostgreSQL 연결
- 허용된 서버·환경만 접근 가능하도록 설정
- TLS 등 통신 암호화
- Backend / AI DB Role 분리
- Secret 환경변수·승인된 저장 방식 사용
- 배포 Commit SHA 기록
- Backend / AI Base URL 기록
- Health Check
- 기본 로그·상태 확인
- 비용 알림 또는 사용량 확인 수단

완료 기준:

```text
Backend 실행
→ RDS 연결
→ Health 정상

AI 실행
→ RDS / pgvector 조회
→ Health 정상

Backend와 AI가 서로 다른 DB 권한 사용
```

---

## B. DB 무결성·권한·동시성 QA

### Migration / Seed

확인할 것:

- 승인된 Migration만 적용
- `makemigrations --check`
- `migrate --check`
- Seed 1회 실행
- 동일 Seed 2회 실행
- Importer Replay 가능 시 재실행
- 예상하지 않은 Row 증가 여부
- Schema Drift

완료 기준:

```text
동일 Seed를 재실행해도 불필요한 데이터가 늘지 않는다.
승인되지 않은 Schema 변경이 없다.
```

### DB 권한

Backend:

- 필요한 조회·수정 가능
- 허용되지 않은 객체 접근 차단

AI:

- 필요한 RAG 조회 가능
- 허용되지 않은 UPDATE / DELETE / DDL 차단
- 필요한 View만 조회 가능

> AI가 업무 DB를 임의 수정할 수 있으면 완료 처리하지 않는다.

### 동시성·중복·재요청

필수 시나리오:

- 두 상담사가 같은 문의를 동시에 선택
- 동일 `Idempotency-Key` 재전송
- 오래된 `state_version` 요청
- 네트워크 실패 후 동일 쓰기 요청 재전송
- 동일 합성 데이터 재적재
- 상담 저장 버튼 연속 클릭
- AI 결과 저장 재전송

확인할 것:

- 중복 Row
- 상태 이력 중복
- 잘못된 최종 상태
- 409 처리
- 기존 입력 보존
- PostgreSQL Row Lock

완료 기준:

```text
동일 요청이 두 번 들어와도
결과가 한 번만 반영되거나 계약된 Replay 응답을 반환한다.
```

## C. AI 통합 QA

최소 네 경로를 실제 Runtime에서 확인한다.

### 일반

```text
고객 증상
→ 실제 AI
→ 실제 pgvector
→ 실제 LLM
→ 공식 Evidence 기반 안내
→ Backend 저장
```

### 위험

```text
위험 증상
→ Safety Rule 우선
→ 잘못된 사용 가능 안내 없음
→ 사용 제한
→ 상담 전환
```

### 근거 없음

```text
Evidence 없음
→ 임의 자가조치 생성 금지
→ 재질문 또는 상담 안내
```

### 오류 / Timeout

```text
검색 실패 / AI Timeout / Provider 오류
→ 무응답 금지
→ 데이터 중복·오염 없음
→ 명시적 오류 또는 Fallback
```

완료 기준:

- 네 시나리오 모두 실제 Runtime에서 실행
- 화면·API·로그·DB Evidence 확보
- Mock 응답만으로 PASS 처리 금지

## D. 고객 → AI → 상담사 → 고객 E2E

방문기사 흐름은 P1이므로 이번 주 P0 E2E에 포함하지 않는다.

실제 흐름:

```text
1. 고객 Mobile 로그인
2. 실제 구독 제품 선택
3. 신규 Inquiry 생성
4. 증상 입력
5. 필요한 경우 추가 질문
6. 고객 추가 답변
7. 실제 AI 실행
8. 실제 pgvector 검색
9. 실제 LLM 안내
10. Backend AI 결과 저장
11. Mobile Guidance / Evidence 표시
12. 고객 상담 요청
13. 상담사 Web 로그인
14. 같은 inquiry_id 조회
15. AI 인계 내용 확인
16. 상담 시작
17. 상담 기록 저장
18. 상담 완료
19. 고객 Mobile에서 최신 상태 재조회
```

필수 조건:

- Mock/Fake 자동 대체 금지
- 실제 RDS
- 실제 AI Runtime
- 실제 pgvector
- 실제 생성형 LLM
- 동일 `inquiry_id`
- 동일 후보 Commit
- 화면·API·로그·DB 대조 가능

> 하나의 신규 Inquiry로 처음부터 끝까지 통과해야 한다.

## E. 추적성·회귀·복구

### 추적성

대표 Inquiry 하나를 잡고 다음을 연결한다.

```text
Mobile 화면
→ Backend API
→ Backend Log
→ AI Log
→ PostgreSQL
→ Web 화면
```

최소 식별자:

```text
inquiry_id
correlation_id
ai_request_id
state_version
```

### 회귀

최소 확인:

- Backend 핵심 회귀
- AI Unit / Integration
- Web Test / Lint / Build
- Mobile Unit / Build
- 실제 물리 Android Smoke
- State Machine 계약
- Data QA

`SKIPPED`를 PASS로 계산하지 않는다.

### Backup / Restore

실제로 수행한다.

```text
백업 생성
→ 별도 격리 환경 또는 복원 DB 준비
→ 복원
→ 합성 사용자·구독·문의·상담 데이터 조회
→ Query 또는 서비스 Smoke
→ 결과 기록
```

> “백업 설정이 켜져 있다”가 아니라 실제 복원 후 데이터를 읽을 수 있어야 한다.

# 3. 최종 QA 판정 기준

김은진은 6주차 종료 시 후보 SHA를 아래 셋 중 하나로 판정한다.

## PASS

- P0 최소 E2E PASS
- 실제 RDS / AI / pgvector / LLM 확인
- Blocker 없음
- 핵심 회귀 PASS
- 동시성·중복·권한 PASS
- Backup / Restore PASS

## PASS WITH LIMITATION

- 핵심 E2E는 PASS
- 발표를 막지 않는 제한사항만 존재
- 제한사항과 우회 방법이 명확함

## BLOCKED

다음 중 하나라도 존재하면 BLOCKED 가능:

- 실제 AI 미검증
- 실제 RDS 미검증
- P0 E2E 미완주
- 데이터 중복·손상 위험
- 권한 오동작
- 동일 Inquiry 추적 불가
- 재현 가능한 핵심 회귀 실패
- 복구 불가

최종 보고에는 최소 다음을 남긴다.

```text
candidate_sha
environment
P0_E2E
AI_QA
DB_QA
concurrency
idempotency
regression
backup_restore
known_blockers
final_decision
```
