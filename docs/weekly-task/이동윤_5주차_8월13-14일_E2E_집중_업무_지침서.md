# 1. 이번 이틀의 목표

이번 이틀에는 **AI 기술을 더 비교하거나 고도화하는 것보다, 현재 AI를 실제 서비스에 연결해 E2E가 끝까지 동작하도록 만드는 것**을 최우선으로 한다.

현재 AI 영역에는 RAG 실험, Retrieval 평가, Safety·Fallback 기준선, Backend→FastAPI 실제 소켓 Mock 검증 등이 이미 존재한다. 반면 실제 LLM Provider, 실제 RAG Runtime, Backend 저장까지 이어지는 수직 연결은 아직 완전히 닫히지 않았다.

따라서 8월 13~14일에는 다음 한 가지에 집중한다.

> **현재 Baseline AI를 고정하고, Backend → AI → RAG → LLM → Backend 저장까지 실제로 연결한다.**

챗봇 전환, 모델 비교, 청킹 실험, Retriever 실험, Multi-Agent 확대는 E2E 완료 이후 다시 검토한다.

# 2. E2E용 AI Baseline 고정

이번 이틀 동안 아래 구성을 **임시 운영 Baseline**으로 사용한다. 이 선택은 “가장 좋은 조합”이라는 의미가 아니라, **이미 준비된 자산을 최대한 재사용해 가장 빨리 E2E를 완성하기 위한 기준선**이다.

| 항목 | 8/13~8/14 Baseline |
| --- | --- |
| AI Workflow | 현재 동작 가능한 `SingleRAGPipeline` |
| 생성형 LLM | OpenAI `gpt-4.1-mini` |
| LLM 출력 | Structured Output / 기존 AI Response Schema 준수 |
| Embedding | `BAAI/bge-m3` |
| Embedding Revision | `5617a9f61b028005a4858fdac845db406aefb181` |
| Embedding Dimension | `1024` |
| Vector Store | PostgreSQL + pgvector |
| Chunking | 현재 승인된 **7개 청크 그대로 사용** |
| 공식 검색 범위 | `WPUJAC104DWH`, JAC104/JCC104 REV.00 37~39쪽 |
| Retriever | Dense Cosine Exact Search |
| Top-K | `5` |
| Threshold | `0.4` |
| 제품 필터 | 제품·세대 Exact Filter 유지 |
| Reranker | 사용하지 않음 |
| Hybrid/BM25 추가 | 사용하지 않음 |
| Safety | 기존 Rule·Validator 우선 |
| No-Evidence | 추측 답변 금지, 기존 Fallback 적용 |

현재 `bge-m3` 1024차원, Exact Search, Top-K 5, Threshold 0.4, 승인 7청크 기준선은 이미 저장소에 존재하므로 그대로 재사용한다.

### 중요한 원칙

- **새로운 청킹을 하지 않는다.**
- **재임베딩이 필요하지 않으면 하지 않는다.**
- 더 좋은 Retrieval 조합을 찾기 위한 실험을 하지 않는다.
- 기존 Dense/BM25·Alias Expansion 등 실험 결과가 있어도 이번 E2E에 새로 적용하지 않는다.
- Multi-Agent 구현 때문에 E2E를 늦추지 않는다. 현재 `SingleRAGPipeline`으로 먼저 연결한다.
- E2E가 끝난 뒤 동일 평가 Case로 LLM·Embedding·Chunking·Retriever를 비교하고 선택한다.

# 3. 8월 13일 — 실제 AI Runtime 닫기

## 3.1 생성형 LLM 실제 연결

현재 LLM Interface 골격에 실제 Provider 호출을 연결한다.

최소 범위는 다음뿐이다.

```text
RAG Context
→ gpt-4.1-mini 호출
→ 구조화된 고객 안내 생성
→ Schema 검증
→ AI Response 반환
```

### 필수 조건

- API Key는 환경 변수로만 관리한다.
- 출력은 Backend와 합의된 Schema를 반드시 지킨다.
- 자유 형식 응답을 그대로 Backend에 넘기지 않는다.
- Provider Timeout·호출 실패 시 기존 Fallback으로 종료한다.
- 위험 판단과 공식 근거 허용 여부를 LLM 단독 판단에 맡기지 않는다.
- Token·Latency 기록은 남기되 **성능 비교 실험은 하지 않는다.**

LLM 연결이 성공하면 모델 품질을 평가하느라 멈추지 않고 바로 Backend 수직 연결로 넘어간다.

---

## 3.2 현재 RAG Baseline 실제 실행

현재 승인 Corpus와 `bge-m3`를 그대로 사용해 실제 Retrieval이 동작하도록 한다.

대표 Case는 기존 E2E와 동일하게 **`WPUJAC104DWH` 출수량 저하**를 우선 사용한다.

```text
고객 증상
→ 제품·세대 Filter
→ pgvector 검색
→ Top-K 5
→ Threshold 0.4
→ 공식 Evidence
→ LLM Guidance
```

### 완료 기준

- 실제 pgvector에서 검색된다.
- 승인된 공식 문서 밖의 근거를 사용하지 않는다.
- Evidence가 AI 응답에 연결된다.
- 검색 결과가 없으면 임의 답변을 생성하지 않는다.

팀 공용 pgvector 환경이 준비되어 있으면 해당 환경을 사용한다. 환경 문제로 막히면 김은진에게 즉시 Blocker를 전달한다.


### 이동윤 책임

Backend 저장·State 적용 문제는 최지용에게 즉시 전달하고, 환경·DB 문제는 김은진과 바로 해결한다.

# 4. 8월 14일 — 서비스 E2E 참여 및 Blocker 제거

8월 14일에는 새로운 AI 기능을 만들지 않는다. 전날 만든 Baseline AI를 사용하여 **고객 Mobile → Backend → AI → Backend → 상담사 Web** 전체 흐름에 참여한다.

## 4.1 정상 시나리오 1건 완주

우선 다음 한 건을 끝까지 통과시킨다.

```text
고객이 출수량 저하 문의
→ 추가 질문·답변
→ Backend가 AI 호출
→ RAG 공식 근거 검색
→ AI 안내 생성
→ Mobile에 Guidance 표시
→ 고객이 상담 요청
→ 상담사 Web에서 같은 문의 확인
```

AI 기준 성공 조건은 다음이다.

- 실제 LLM 호출이 발생한다.
- 실제 pgvector 검색이 발생한다.
- 공식 Evidence가 존재한다.
- Response Schema가 정상이다.
- Backend가 결과를 정상 저장한다.
- 고객 Mobile이 해당 결과를 소비할 수 있다.

방문기사 관련 Agent·브리핑은 이번 E2E 완료 조건에서 제외한다.

---

## 4.2 정상 흐름 후 최소 Fallback 확인

Happy Path가 성공한 뒤 다음 세 가지만 확인한다.

1. **No-Evidence**  
   검색 결과가 없을 때 근거 없는 답변을 만들지 않고 기존 Fallback으로 종료한다.

2. **위험 입력**  
   기존 Safety Rule이 우선 적용되고 일반 자가조치 안내로 흘러가지 않는다.

3. **LLM Timeout·실패**  
   Backend 요청 전체가 깨지지 않고 정의된 Fallback 또는 상담 전환이 가능해야 한다.

추가적인 모델 성능·Prompt·비용 비교는 하지 않는다.

# 6. Blocker 처리 규칙

AI 작업 중 다른 영역에서 막히면 혼자 우회 구현하지 않는다.

```text
[AI E2E Blocker]
구간: Backend → AI / AI → pgvector / AI → LLM / AI → Backend
기준 Commit: <SHA>
입력 Case: <Case ID 또는 증상>
기대 결과: <정상 결과>
실제 결과: <Error/Response>
담당자: <최지용 / 김은진 / 윤승혁 등>
```

- Backend Adapter·저장 문제 → **최지용**
- DB·pgvector·공용 환경 문제 → **김은진**
- State·Event·P0 범위 판단 → **윤승혁**
- Mobile에서 Guidance 소비 문제 → **양정현**
- Web 상담 흐름 문제 → **한예나**

수정 Commit이 올라오면 실패 구간부터 즉시 재검증한다.

# 8. E2E 완료 후 다시 시작할 것

E2E가 완성된 뒤에는 현재 Baseline을 기준으로 다음을 순서대로 비교한다.

```text
생성형 LLM
→ Embedding
→ Chunking
→ Retriever / Reranker
→ Multi-Agent 구조
```

그때는 같은 평가 Dataset과 같은 지표를 사용해 실제 결과를 비교하고, 더 좋은 후보가 확인되면 Baseline을 교체한다.

따라서 이번 이틀의 목표는 **최적의 AI를 결정하는 것**이 아니다.

> **“비교 가능한 AI 서비스를 먼저 완성하는 것.”**

이 상태를 확보한 뒤 실험 결과를 근거로 고도화한다.
