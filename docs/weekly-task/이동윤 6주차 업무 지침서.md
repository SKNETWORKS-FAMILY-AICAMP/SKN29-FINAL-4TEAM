# 1. 6주차 완료 목표

6주차가 끝났을 때 아래 기능이 **실제 서비스 흐름에서 동작해야 한다.**

- [ ] 고객이 증상을 입력하면 AI가 증상을 구조화하고 필요한 정보만 추가 질문한다.
- [ ] 이미 답한 내용은 다시 묻지 않고, 정보가 충분하면 추가 질문을 종료한다.
- [ ] 일반 증상에서는 실제 pgvector에서 공식 근거를 검색하고 실제 생성형 LLM이 근거 기반 안내를 생성한다.
- [ ] 위험 증상에서는 Safety Rule이 LLM보다 우선하며 잘못된 사용 가능 안내가 나오지 않는다.
- [ ] 근거가 부족하면 억지 자가조치를 생성하지 않고 재질문 또는 상담 전환한다.
- [ ] `Symptom Analysis Agent`, `Evidence Analysis Agent`, `Care Decision Agent`가 하나의 Inquiry를 공유하며 협업한다.
- [ ] Evidence가 부족하면 Evidence Agent가 Symptom Agent에 추가 정보 요청을 보내고, 고객 답변 후 다시 검색할 수 있다.
- [ ] 고객이 상담 요청하면 같은 `inquiry_id`의 AI 인계 내용을 상담사 Web에서 확인할 수 있다.
- [ ] 청킹·Retriever·Embedding·생성형 LLM 비교실험을 끝내고 최종 조합 하나를 확정한다.
- [ ] 실제 Backend·PostgreSQL·pgvector·AI Runtime·Mobile·Web을 사용한 **고객 → AI → 상담사 최소 E2E가 PASS**한다.

> **위 핵심 경로가 실제로 동작하지 않으면 6주차 AI 과업 완료로 판정하지 않는다.**

이번 주 종료 시 아래 항목은 더 이상 미정 상태로 남기지 않는다.

```text
Agent 수와 책임
Agent Routing / Handoff
Chunking
Retriever
Embedding
Vector Search
생성형 LLM
고객 안내 기본 흐름
```

# 2. 이번 주 핵심 업무

## A. 5주차 AI/RAG 잔여 과업 마감

가장 먼저 현재 남아 있는 AI/RAG 핵심 Runtime을 닫는다.

필수 확인:

- 실제 팀 PostgreSQL + pgvector 검색
- 실제 Embedding 실행
- 실제 생성형 LLM 호출
- 일반 증상 RAG 경로
- 위험 증상 Safety 우선 경로
- 근거 없음 Fallback
- 검색 실패 Fallback
- AI Timeout / Retry
- 추가 질문 생성
- 중복 질문 방지
- Backend AI 결과 저장
- Backend 재조회

실제 Runtime에서 최소 다음 네 경로를 확인한다.

```text
일반 증상
→ Evidence 검색
→ LLM 안내
→ Backend 저장

위험 증상
→ Safety Rule 우선
→ 위험 안내
→ 상담 전환

근거 없음
→ 임의 안내 금지
→ 재질문 또는 상담 전환

AI 오류 / Timeout
→ 무응답 금지
→ 오류 상태 또는 상담 Fallback
```

## B. RAG 비교실험 종료 및 최종 구성 확정

동일 평가 세트를 기준으로 현재 구현 가능한 후보만 비교한다.

비교 대상:

- Chunking
- Retriever / 검색 방식
- Embedding
- 생성형 LLM
- 필요 시 Top-k
- 필요 시 Parent-Child
- 필요 시 Reranking

최소 평가 기준:

| 항목 | 확인 내용 |
|---|---|
| 검색 적중 | 정답 Evidence가 Top-k에 포함되는가 |
| 근거 일치 | 생성 답변이 실제 Evidence와 일치하는가 |
| 안전성 | 위험·근거 없음에서 잘못된 자가조치를 생성하지 않는가 |
| 응답 품질 | 고객이 이해 가능한 안내인가 |
| Latency | 실제 서비스에서 사용할 수 있는가 |
| 비용 | LLM·Embedding 호출 비용이 과도하지 않은가 |

최종 결과는 하나로 확정한다.

```text
Chunking:
Retriever:
Embedding:
Vector Search:
Top-k:
Reranker:
LLM:
Agent Structure:
```

완료 기준:

- 비교 결과가 표 또는 보고서로 남아 있다.
- 최종 선택 이유가 기록되어 있다.
- 7주차에는 핵심 RAG 조합을 다시 선정하지 않는다.

## C. 3-Agent 협업 구조 구현

최종 Agent 구성은 아래 3개로 고정한다.

### 1) Symptom Analysis Agent

담당:

- 고객 자연어 증상 분석
- 증상 구조화
- 이전 답변 반영
- 누락 정보 확인
- 추가 질문 생성
- 중복 질문 제거

주요 출력:

```text
structured_symptom
missing_fields
followup_questions
clarification_needed
```

하지 않는 일:

- 최종 위험 판정
- 공식 근거 확정
- 고객 최종 대응 결정

### 2) Evidence Analysis Agent

담당:

- 구조화된 증상 기반 Retrieval
- 제품·세대 Filter
- Embedding / pgvector 검색
- Evidence 검증
- 근거 충분 여부 판단
- 부족 시 Symptom Agent에 재질문 요청

주요 출력:

```text
evidence
evidence_status
evidence_sufficient
request_more_information
```

하지 않는 일:

- 고객 최종 문구 생성
- Safety 정책 변경
- 근거 없는 추론

### 3) Care Decision Agent

담당:

- Symptom + Evidence 결과 종합
- 고객용 Guidance 생성
- 안전한 자가조치
- 사용 제한
- 다음 행동
- 상담 필요 여부
- 상담 요청 시 상담사용 AI 인계 생성

주요 출력:

```text
usage_guidance_status
usage_guidance_message
restricted_functions
next_actions
requires_consultation
consultation_handoff
```

하지 않는 일:

- Backend 상태 직접 변경
- 상담 완료 판단
- 방문 필요 최종 결정
- 확정 진단

## D. Agent 간 Handoff / Feedback Loop 구현

단순히 Agent 3개를 순서대로 실행하는 것만으로는 완료로 보지 않는다.

필수 흐름:

```text
고객 입력
   ↓
Symptom Analysis Agent
   ↓
Evidence Analysis Agent
   │
   ├─ 근거 충분
   │      ↓
   │  Care Decision Agent
   │
   └─ 근거 부족 / 정보 부족
          ↓
      Symptom Analysis Agent
          ↓
       추가 질문
          ↓
       고객 답변
          ↓
      Evidence Analysis Agent 재검색
```

필수 규칙:

- 무한 재질문 금지
- 이미 답한 질문 반복 금지
- Agent 간 전달은 구조화된 Shared State 사용
- Agent가 Backend 상태를 임의 변경하지 않음
- Safety Rule 결과를 Agent가 뒤집을 수 없음

아래 기능은 Agent로 새로 만들지 않고 공통 Tool/Stage로 유지한다.

```text
Safety Rule
Embedding
Retriever
pgvector
Evidence Validator
Output Validator
Timeout / Cancellation
Trace / Logging
```

## E. Single RAG vs Multi-Agent 비교 및 상담 인계 연결

현재 Single RAG는 Baseline으로 유지한다.

```text
Single RAG
Structuring
→ Safety
→ Missing Fields
→ Retrieval
→ Generation
→ Validation
```

비교 대상 Multi-Agent:

```text
Symptom Analysis Agent
        ↕
Evidence Analysis Agent
        ↕
Care Decision Agent
```

비교할 것:

- 정답 Evidence 검색률
- 답변 근거 일치성
- 추가 질문 정확도
- 중복 질문 발생 여부
- 근거 없는 답변 비율
- Safety 위반 여부
- 상담 전환 적절성
- Latency
- Token
- 비용

최종적으로 “Multi-Agent를 만들었다”가 아니라 **Single RAG 대비 장점·단점을 실제 결과로 남긴다.**

상담 요청 시 같은 Inquiry에 최소 다음 AI 인계 정보가 남아야 한다.

```text
고객 원문
추가 질문
고객 추가 답변
구조화 증상
위험도
현재 사용 안내
제한 기능
공식 Evidence
고객에게 제공한 안내
상담사가 추가 확인할 사항
```

# 3. 실제 E2E 및 품질 검증

## 고객 → AI → 상담사 최소 E2E

6주차 AI 과업의 최종 Gate다.

```text
1. 고객 Mobile 로그인
2. 실제 구독 제품 선택
3. 고객 증상 입력
4. Symptom Analysis Agent 실행
5. 필요한 경우 추가 질문
6. 고객 추가 답변
7. Evidence Analysis Agent 실제 pgvector 검색
8. 실제 생성형 LLM 호출
9. Care Decision Agent 고객 안내 생성
10. Backend 결과 저장
11. Mobile Guidance / Evidence 표시
12. 고객 상담 요청
13. 상담사 Web 로그인
14. 동일 inquiry_id 조회
15. AI 인계 정보 확인
```

필수 조건:

- Mock/Fake로 정상 응답 대체 금지
- Mobile/Web이 AI FastAPI 직접 호출 금지
- 실제 pgvector 사용
- 실제 생성형 LLM 사용
- 같은 `inquiry_id` 유지
- 같은 기준 Commit 사용
- Backend 저장 확인
- 상담사 Web 조회 확인
