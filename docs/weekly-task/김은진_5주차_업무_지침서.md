> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템

> 8월 13일 운영 원칙: 3장 필수 범위를 마감하고, 선행 Gate가 닫힌 경우에만 대표 P0 E2E를 조기 실행한다.
> 8월 14일 운영 원칙: 5주차 필수 회귀와 실패 수정을 마치고 조기 완료 결과와 6~7주차 인계를 분리한다.

4주차 종료 시점에는 Data QA·Finalize·결정적 재생성 기반이 복구되었고 Web도 Test·Lint·Build 기준선이 존재하지만, 5주차 진입 문서에는 Vector 검색, Backend 공식 환경, Backend↔AI 최소 수직 연결, Mobile Build Gate가 여전히 차단 또는 미완료 상태로 기록되어 있다. 또한 현재 저장소의 `tests/**`는 계약 검사 일부를 제외하면 `integration`, `e2e`, `safety`, `smoke` 하위 경로가 대부분 골격만 존재한다.

따라서 5주차에는 **Data 자체의 반복 검증만으로 완료 처리하지 않고, WBS 5주차 범위의 서비스 간 최소 통합 테스트를 실제 테스트 자산으로 채우는 것**을 우선한다.

김은진은 다른 담당자의 Runtime 기능을 대신 구현하지 않는다. Backend·AI·Web·Mobile의 기능 결함은 해당 주관 담당자가 수정하며, 김은진은 재현 조건·Fixture·테스트·로그·Gate를 제공하고 수정 후 동일 조건에서 재검증한다.

# 2. 5주차 역할 목표

1. **8월 10일까지 5주차 진입 Gate를 현재 `main` 또는 PM이 고정한 기준 Commit에서 다시 판정한다.**  
   `W5-G01`, `W5-G03`, `W5-G04`, `W5-G06`, `W5-G08`, `W5-G09`를 중심으로 Data·Backend·AI·Web·Mobile의 환경과 테스트 상태를 같은 형식으로 재현하고, 과거 PASS와 현재 PASS를 구분한다.

2. **팀 DB와 실제 pgvector 검색 Gate를 이동윤과 함께 닫는다.**  
   `BAAI/bge-m3` 1024차원 임베딩, 제품·세대 Filter, 공식 문서·페이지, 금지 자료 차단, 평가 Dataset을 현재 팀 DB에서 다시 검증하고 Mock·저장 결과·실제 Query를 분리한다.

3. **최지용·이동윤과 Backend↔AI 최소 수직 연결의 통합 테스트를 8월 11일까지 확보한다.**  
   증상 제출 → Backend → AI HTTP 호출 → Schema 검증 → Event·State 반영 → DB 저장 → `correlation_id` 추적의 최소 1건을 실제 Runtime에서 통과시킨다.

4. **5주차 공식 산출물인 멀티 에이전트 테스트 계획 및 결과 보고서를 주관한다.**  
   Agent 단위, Routing, LLM, Vector DB, Backend 연동, Fallback, 안전을 5주차 필수 결과로 정리하고, 전체 E2E는 후속 실행 계획과 조건부 결과를 구분해 기록한다. 이동윤의 AI 구현 결과와 최지용의 Backend 연동 결과는 같은 기준으로 취합한다.

5. **Root `tests/**`에서는 이번 주에 필요한 최소 통합·안전 경계를 실제 테스트로 승격한다.**
   `backend-ai`, `backend-vector-store`, 핵심 `safety` 경로를 필수 대상으로 삼고 재사용 가능한 Fixture·Helper·Test를 작성한다. 그 밖의 `backend-database`, `workflow`, `permissions`, `tracing`, `e2e`, `smoke` 골격은 5장 조건부 업무 또는 현행 WBS의 후속 일정으로 유지한다.

6. **3장 필수 Gate가 조기에 닫힌 경우에만 P0 대표 E2E를 5장 조건부 업무로 실행한다.**
   고객 문의 → 증상 입력 → AI 구조화·위험·근거 → 상담 전환 → 방문 필요 시 방문 처리 → 결과 확인까지의 대표 흐름을 동일 Inquiry·DB·State 기준으로 검증한다. 가능하면 자가 해결, 상담 해결, 방문 해결, 위험 전환, 근거 없음 Fallback을 분리한다.

7. **8월 14일까지 5주차 필수 범위의 QA 기준선과 6~7주차 잔여 범위를 확정한다.**
   Data·Backend·AI·Web·Mobile·Contract·필수 Integration 결과를 같은 Commit에서 집계하고, E2E는 조기 착수한 경우에만 별도 결과로 포함한다. 이후 일정의 차단 요소와 인계 범위를 함께 정리한다.

5주차 완료 기준은 개별 담당자가 “기능 구현 완료”라고 보고하는 것이 아니다. **계약, Runtime, DB, Client, 테스트와 로그가 같은 기준선에서 연결되고, 대표 P0 흐름이 실제로 재현되어야 한다.**

# 3. 5주차 필수 업무

> 이 장은 현행 WBS의 **5주차 범위**만 필수로 다룬다. WBS상 6~7주차에 배정된 전체 E2E·전체 회귀·후행 Runtime·최종 Feature Complete 업무는 5장의 조기 완료 업무로 분리한다.

## 3.1 5주차 진입 Gate 복구 및 동일 Commit QA 기준선 확정

### 작업 목적

4주차에서 승계된 PASS 결과와 5주차 현재 실행 결과를 구분하고, 환경 부족·코드 결함·연동 미완료를 각각 다른 상태로 기록한다. 이후 통합 개발이 서로 다른 Commit·DB·Fixture·환경을 기준으로 진행되지 않게 한다.

### 작업 위치

```text
docs/planning/
├─ week5-entry-criteria.md
├─ week5-priority-backlog.md
├─ week5-dependency-map.md
└─ WBS.md

docs/testing/
├─ results/week5-entry-gate-result.md
├─ results/week5-service-regression-baseline.md
└─ matrices/week5-gate-matrix.md

docs/handoffs/week5/**
tests/reports/raw/**

```

### 세부 작업 지침

1. 윤승혁이 확정한 5주차 기준 Commit 전체 SHA를 기록한다.
2. 각 테스트 결과에는 최소 다음을 포함한다.
   - Commit SHA
   - OS·Runtime Version
   - DB·Vector DB Version
   - 실행 명령
   - PASS·FAIL·SKIP 수
   - Exit Code
   - Fixture·Dataset Version
   - 결과 파일·로그 경로
3. `week5-entry-criteria.md`의 Gate를 현재 실행 결과로 다시 판정한다.
   - `W5-G01` 기준선·Issue
   - `W5-G03` 대표 Data·Seed
   - `W5-G04` Vector 검색
   - `W5-G06` Backend Test·Migration
   - `W5-G08` Web Test·Lint·Build
   - `W5-G09` Mobile Test·Build
4. 기존 문서의 `67/67`, `113 passed` 같은 수치를 현재 결과로 복사하지 않는다. 테스트가 추가·삭제되었으면 현재 Test Count를 다시 계산한다.
5. Data는 다음 핵심 명령을 현재 Commit에서 재실행한다.

```bash
python -B -m unittest discover -s data/tools/tests -v
python -B data/tools/pipeline.py qa --verify-rebuild
python -B data/tools/pipeline.py finalize
git diff --exit-code -- data
```

6. Backend는 최지용과 함께 공식 Python 3.13.13 환경에서 환경·PostgreSQL·Migration·전체 Test Gate를 재현한다. 기존 README의 `check_environment.py --full`, `--postgresql`, `migrate --check` 절차를 우선한다.
7. AI는 이동윤과 함께 Unit Test와 실제 pgvector 통합 Test를 분리하여 실행한다.

```powershell
.\ai\.venv\Scripts\python.exe -m pytest ai\tests\unit
.\ai\.venv\Scripts\python.exe -m ai.scripts.verify_pgvector_runtime
.\ai\.venv\Scripts\python.exe -m pytest ai\tests\integration\test_pgvector_runtime.py -v
```

8. `AI_VECTOR_DSN`, 모델 Revision 등 비밀 또는 환경값은 결과 보고서에 원문을 남기지 않는다.
9. Web은 한예나와 함께 아래 Gate를 현재 Commit에서 다시 확인한다.

```powershell
npm.cmd run lint
npm.cmd run test
npm.cmd run build
npm.cmd run fixtures:generate
```

10. Mobile은 양정현과 함께 SDK·JDK·Gradle 환경을 먼저 확인하고 아래 Test·Build를 재현한다.

```cmd
gradlew.bat clean
gradlew.bat :core:testDebugUnitTest
gradlew.bat :customer-app:testDebugUnitTest
gradlew.bat :customer-app:assembleDebug
gradlew.bat :technician-app:assembleDebug
```

11. 실행 환경이 없어 실패한 경우 `ENVIRONMENT_BLOCKED`, Assertion·Runtime 오류는 `CODE_FAILED`, 대상 Operation 미구현은 `INTEGRATION_BLOCKED`로 구분한다.
12. SKIP이 발생하면 이유와 해제 조건을 적는다. 필요한 서비스·환경이 없어서 자동 Skip된 테스트를 PASS 수치에 포함하지 않는다.
13. 각 Gate가 PASS로 바뀌려면 문서상 승인뿐 아니라 재현 명령·로그·결과 경로가 있어야 한다.
14. 다른 담당자가 수정한 뒤에는 수정 Commit에서 실패 항목만 재실행한 뒤, 최종적으로 전체 Gate를 다시 실행한다.
15. 8월 10일 종료 시점에 열린 Blocker를 윤승혁에게 전달하고 WBS·Issue의 상태와 맞춘다.

- 과거 PASS를 현재 PASS로 재사용하지 않았다.

- Blocker마다 담당자·협업자·재현 명령·해제 조건·증거가 있다.
- WBS·Issue·Gate Matrix의 상태 의미가 일치한다.

## 3.2 팀 DB·Vector DB·AI 실행환경 통합 검증

### 작업 목적

AI가 Mock이나 저장된 과거 검색 결과가 아니라 현재 팀 DB의 pgvector와 실제 모델 설정을 사용하여 공식 근거를 검색할 수 있는지 검증한다. 이후 멀티 에이전트 테스트와 Backend E2E가 동일한 Vector 검색 기반을 사용하도록 한다.

### 작업 위치

```text
ai/tests/unit/**
ai/tests/integration/**
ai/evaluation/**
ai/evaluation/reports/**
ai/app/integrations/vector_store/**
ai/app/integrations/embedding/**
ai/app/retrieval/**

data/config/rag/**
data/processed/structured/rag/**
data/processed/structured/evidence/**
data/processed/metadata/**

tests/integration/backend-vector-store/**
tests/fixtures/ai/**
tests/reports/raw/ai/**

docs/testing/results/week5-vector-ai-runtime-result.md
```

### 세부 작업 지침

1. 이동윤에게 현재 AI 실행 기준을 전달받아 기록한다.
   - Python Version
   - 임베딩 모델 ID
   - 모델 Revision
   - 임베딩 차원
   - Vector DB Version
   - 거리 함수
   - 실제/Mock 실행 Mode
   - LLM Provider 실행 Mode
2. 팀 DB에서 pgvector Extension·Table·Index·Dimension을 실제 Query 또는 제공된 검증 Script로 확인한다.
3. 대표 제품 `WPUJAC104DWH`와 현재 승인된 제품·세대 Filter가 검색 전·후 어디에서 적용되는지 확인한다.
4. 기존 Retrieval 평가 Case를 현재 팀 DB에서 다시 실행한다.
5. 양성 Case는 공식 문서·페이지·근거가 Top-k에 포함되는지 검사한다.
6. 부정 Case는 미지원 모델·다른 세대·제외 문서·미검증 FAQ가 근거로 승격되지 않는지 검사한다.
7. Recall@5, MRR 또는 현재 승인된 검색 지표를 계산하되 지표 수치만으로 Case 실패를 숨기지 않는다.
8. 실제 pgvector Query 결과, Local Mock/Fallback 결과, 과거 저장 결과를 문서에서 분리한다.
9. LLM을 실제 외부 Provider로 호출하는 Mode가 활성화되어 있으면 정상 응답·Schema 실패·Timeout을 최소 1회씩 검증한다. 실제 Provider 사용이 준비되지 않았다면 이를 Mock 결과와 구분하여 `EXTERNAL_LLM_NOT_VERIFIED`로 남긴다.
10. 비밀 Key·DSN·Prompt 내부 민감정보·실제 고객정보를 Test Log에 남기지 않는다.
11. Embedding·Vector·LLM 장애 시 Fallback이 상위 Pipeline에 어떤 오류·상태로 전달되는지 확인한다.
12. AI 단위 Test가 PASS해도 실제 pgvector가 Skip되면 `W5-G04`를 PASS로 올리지 않는다.
13. Vector DB 실제 실행 결과는 3.3~3.5의 통합·E2E Test에서 동일 환경을 재사용한다.

### 완료 기준

- 팀 DB에서 실제 pgvector 검색이 재현된다.
- 모델·Revision·차원·거리 함수·Dataset Version이 기록되어 있다.
- 제품·세대·문서 Filter가 실제 검색에서 검증되었다.
- 양성·부정 평가 Case가 현재 실행 결과와 연결되어 있다.
- Mock·Fallback·실제 Vector Query가 명확히 구분되어 있다.
- LLM 실제 연동 여부가 사실대로 기록되어 있다.

# 5. 조기 완료 시 추가 업무

> 아래 업무는 3장의 5주차 필수 업무와 해당 선행 Gate가 모두 PASS한 경우에만 착수한다. 미착수·미완료는 5주차 필수 업무 실패로 계산하지 않으며, 완료하지 못한 항목은 현행 WBS의 6~7주차 일정으로 유지한다.

## 5.1 P0 대표 E2E 시나리오 구축·검증

### 작업 목적

5주차를 단순 Integration Ready 상태로 끝내지 않고, **WaterBridge v0.9 Feature Complete 기준선**을 만들기 위해 고객→AI→상담→방문→결과 흐름을 실제 API·DB·State로 통과시킨다. Root `tests/e2e/**`에 이미 준비된 시나리오 골격을 실제 테스트로 승격한다.

### 작업 위치

```text
tests/e2e/
├─ assertions/**
├─ clients/**
└─ scenarios/
   ├─ self-resolution/**
   ├─ consultation-resolution/**
   ├─ visit-resolution/**
   ├─ danger-escalation/**
   ├─ no-evidence-fallback/**
   └─ reopened-inquiry/**

tests/safety/**
tests/smoke/**
tests/fixtures/**
tests/helpers/**
tests/reports/raw/e2e/**

docs/testing/results/week5-e2e-result.md
docs/testing/evidence/week5-e2e/**
```

### 세부 작업 지침

1. 윤승혁과 5주차 필수 대표 시나리오 ID를 확정한다.
2. 최소 필수 정상 시나리오는 다음 두 단계로 구성한다.
   - **필수 1:** 고객 문의 → AI 처리 → 상담 전환 또는 자가 해결까지
   - **필수 2:** 상담 전환 → 상담 처리 → 방문 필요 시 방문 처리 → 결과 확인까지
3. 가능하면 다음 Scenario를 독립 Test로 구성한다.
   - `self-resolution`: 공식 근거가 있고 위험하지 않은 증상
   - `consultation-resolution`: AI 이후 상담사가 원격 해결
   - `visit-resolution`: 상담 후 방문기사 조치
   - `danger-escalation`: 위험 징후로 자가조치 차단·상담 우선
   - `no-evidence-fallback`: 공식 근거가 없어 생성 차단·상담 전환
4. `reopened-inquiry`는 Runtime이 준비된 경우만 5주차 필수 회귀에 포함하고, 미완료 기능을 E2E 완료로 보이게 하기 위해 Fake로 채우지 않는다.
5. 모든 시나리오는 합성 고객·제품·구독·문의만 사용한다.
6. 동일 Inquiry ID에서 다음을 추적한다.
   - 사용자 Action
   - Backend Operation
   - State·State Version
   - AI 결과
   - Evidence
   - 상담·방문 이력
   - 최종 상태
   - `correlation_id`
7. Web·Mobile이 실제 API를 소비하는 구간은 한예나·양정현의 Gate가 열린 경우 Client E2E에 포함한다.
8. Client Gate가 막혀 있으면 API 레벨 E2E PASS와 화면 E2E PASS를 구분한다. API E2E를 전체 서비스 E2E라고 부르지 않는다.
9. Web의 Mock Repository, Mobile의 Fake Repository가 대표 시나리오에 섞이면 해당 시나리오는 `MOCK_ASSISTED`로 표시하고 Feature Complete PASS로 사용하지 않는다.
10. 방문기사 흐름은 본인에게 배정된 합성 방문 건만 접근 가능한지 확인한다.
11. 상담사·기사·관리자 역할을 바꾸어 IDOR·권한 회귀를 최소 1회 확인한다.
12. State 충돌·중복 요청·409가 발생했을 때 사용자 입력을 자동 재전송하거나 잘못된 최종 상태로 진행하지 않는지 확인한다.
13. E2E 실패 시 첫 실패 경계를 기록하고 해당 담당자에게 재현 명령과 Fixture를 전달한다.
14. 수정 후 실패 Scenario만 먼저 재검증하고, 최종적으로 필수 Scenario 전체를 다시 실행한다.
15. 8월 13일 종료 시 최소 대표 정상 E2E 1개는 실제 Runtime 기준으로 PASS해야 한다. 미달 시 8월 14일 신규 기능·문서 작업보다 우선하여 해제한다.

### 완료 기준

- Root `tests/e2e/**`에 실제 실행 가능한 대표 Test가 존재한다.
- 최소 1개의 정상 P0 대표 흐름이 실제 API·DB·State 기준으로 끝까지 PASS한다.
- AI 근거·위험·Fallback이 E2E 흐름에서 검증된다.

## 6.4 데이터·QA·DevOps·통합 역할 수행 시 주의사항

- 과거 PASS 리포트는 현재 Commit의 PASS를 대신하지 않는다.
- `SKIP`은 PASS가 아니다. 실제 서비스·DB·SDK 부족으로 실행하지 못한 항목은 별도 상태로 기록한다.
- `.gitkeep`이나 빈 테스트 폴더가 존재한다는 이유로 통합·E2E 구현 완료로 처리하지 않는다.
- Root Integration Test는 서비스 내부 Unit Test 복사가 아니라 서비스 경계 실패를 검출해야 한다.
- 실제 pgvector와 Mock Vector Store 결과를 섞어 보고하지 않는다.
- 실제 LLM Provider Test와 Stub/Fixture Test를 구분한다.
- 모델·세대·문서 정책 Filter가 틀리면 유사도가 높아도 검색 성공으로 보지 않는다.
- AI가 Backend State나 업무 원장을 직접 변경하도록 테스트 편의를 위해 우회하지 않는다.
- Backend가 AI 오류를 Mock 성공 응답으로 숨기지 않는다.
- E2E에서 Web Mock Repository나 Mobile Fake Repository가 사용되면 실제 전체 E2E PASS로 표시하지 않는다.
- 실제 개인정보·실제 상담·방문 기록을 Fixture·Log·스크린샷에 사용하지 않는다.
- Token, LLM Key, DB Password, DSN 원문, Prompt 내부 비밀값을 Test Log에 출력하지 않는다.
- 상태·Action·오류 Code의 의미를 QA 담당자가 단독 변경하지 않는다. 변경 필요 시 윤승혁·주관 담당자와 계약을 먼저 수정한다.
- 실패한 Assertion을 삭제하거나 기대값을 임의로 낮춰 Gate를 통과시키지 않는다.
- 5주차에는 신규 Data 종류·신규 제품 확대·운영 Dashboard P1·Graph DB·Kubernetes·대규모 성능 튜닝을 우선하지 않는다.
- 8월 13일 이후에는 신규 기능보다 E2E 실패와 Release Blocker 수정이 우선이다.
- 8월 14일에는 새로운 범위를 추가하지 않고 전체 회귀와 증거 고정을 우선한다.

- Raw 결과는 `tests/reports/raw/**`, 사람이 승인한 요약은 `docs/testing/results/**`로 구분한다.

본 지침서의 5주차 핵심은 **김은진이 같은 Commit에서 Data·Backend·AI·Web·Mobile의 Gate를 재현하고 WBS 5주차 범위의 최소 통합 결과를 검증하는 것**이다. 전체 E2E와 Feature Complete 증명은 3장 완료 후 조기 착수하거나 현행 WBS의 6~7주차로 인계한다.

5주차 종료 시점에는 최소한 **Backend↔AI 실제 수직 연결, 팀 DB pgvector 검색, 멀티 에이전트 Routing·Fallback의 필수 검증**이 같은 기준선과 증거로 연결되어 있어야 한다. 대표 P0 E2E와 공식 보고서는 조기 완료 또는 WBS 후속 일정으로 관리한다.

6주차에 핵심 기능 개발이 대량으로 남지 않도록, 5주차에는 다소 업무 강도가 높더라도 **통합 실패·E2E 실패·Release Blocker를 뒤로 미루지 않고 즉시 담당자와 닫는 것**을 우선한다.
