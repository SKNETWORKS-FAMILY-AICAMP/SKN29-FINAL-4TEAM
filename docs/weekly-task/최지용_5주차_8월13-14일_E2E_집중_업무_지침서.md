# 1. 이번 이틀의 목표

이번 이틀 동안 최지용의 최우선 목표는 **이미 구현된 Backend 기능을 실제 Mobile·AI·Web과 연결하여 고객 문의가 처음부터 끝까지 흐르는 상태를 만드는 것**이다.

현재 Backend는 인증·구독·문의·추가 문진·상담 Runtime과 PostgreSQL 기반이 높은 수준까지 구현되어 있다. Backend→FastAPI 실제 소켓 Mock과 저장 경계도 검증되어 있다. 이제 필요한 것은 새로운 Backend 기능을 넓히는 것이 아니라 **실제 AI Runtime을 붙이고, 고객 Mobile과 상담사 Web이 같은 Inquiry를 실제로 처리할 수 있도록 연결을 닫는 것**이다.

> **8월 14일까지 “Backend 기능이 많다”가 아니라 “Mobile → Backend → AI → Backend → Web이 실제로 연결된다”를 증명한다.**

# 4. 8월 13일 — Backend 연결 완료일

## 4.1 오전 — 현재 Runtime 기준선 확인

전체 Backend를 다시 개발하는 것이 아니라, 오늘 E2E 작업을 시작할 수 있는지 빠르게 확인한다.

최소 확인:

```text
Migration Drift 없음
PostgreSQL 연결 정상
Demo Seed 정상
문의·추가문진 API 정상
상담사 목록·상세 API 정상
상담 Runtime 정상
AI Adapter 설정 가능
```

과거 PASS를 다시 길게 문서화하지 않는다. 실패가 없다면 바로 실제 AI 연결로 넘어간다.

---

## 4.2 최우선 — Backend ↔ 실제 AI Runtime 연결

기존 Mock HTTP 경로에 실제 Baseline AI를 연결한다.

```text
고객 증상·답변 제출
→ Backend Commit
→ FastAPI 실제 HTTP 호출
→ RAG / LLM 처리
→ AI Response Schema 검증
→ AIRun 저장
→ Assessment / Guidance / Evidence 저장
→ Backend State 반영
→ 최신 Snapshot 반환
```

### 필수 조건

- Mobile이나 Web이 AI FastAPI를 직접 호출하게 하지 않는다.
- AI 호출 실패가 고객의 원본 문의·답변을 잃게 만들지 않는다.
- AI Response가 Schema에 맞지 않으면 잘못된 상태를 적용하지 않는다.
- 같은 요청 Replay에서 AI 결과가 중복 저장되지 않게 한다.
- `X-Correlation-ID`를 Backend → AI → 저장 결과까지 이어서 추적한다.
- AI 모델 품질이 마음에 들지 않는다는 이유로 E2E 연결을 멈추지 않는다.

### 이번에 하지 않는 것

- Durable Outbox 등 새로운 대형 구조 도입
- 새로운 Retry 시스템 설계
- AI 모델별 Backend 분기
- 챗봇 전용 API 신설

현재 구조로 E2E가 가능하면 **현재 구조를 유지한다.**

---

## 4.3 고객 Guidance·상담 전환 API 마감

양정현이 고객 앱 E2E를 끝낼 수 있도록 다음 흐름을 실제 API 기준으로 닫는다.

```text
Snapshot 조회
→ AI Guidance / Public Evidence 확인
→ allowed_actions 확인
→ 고객 상담 요청
→ CONSULTATION_REQUIRED
→ 최신 Snapshot 재조회
```

### 확인 사항

- Guidance·Evidence가 고객 공개 DTO에 존재한다.
- 내부 `chunk_id`, 서버 파일 경로, Vector score 등 내부 정보는 노출하지 않는다.
- 상담 요청이 기존 State Machine과 `state_version`을 따른다.
- 성공 후 상담사 Web 목록에 같은 Inquiry가 나타난다.
- 409 발생 시 Client가 최신 상태를 다시 가져올 수 있는 응답을 유지한다.

Backend 계약이 이미 존재하면 새 Operation을 만들지 말고 기존 것을 사용한다.

---

## 4.4 상담사 Web Remote 흐름 공동 Smoke

한예나와 함께 다음 최소 흐름을 실제 브라우저에서 확인한다.

```text
상담사 로그인
→ 상담 필요 문의 목록
→ 고객 Inquiry 상세
→ 고객 원문·추가 답변·AI Guidance 확인
→ 상담 시작
→ 상담 기록
→ 상담 완료
```

Web 화면 결함은 한예나가 수정하고, Backend 응답·권한·State·저장 문제는 최지용이 즉시 수정한다.

**방문 검토·Visit 생성으로 진행하지 않고 상담 완료 경로를 우선 사용한다.**

# 5. 8월 14일 — 대표 E2E 완주와 최소 회귀

8월 14일에는 신규 Backend 기능을 늘리지 않는다. 8월 13일에 연결한 기능으로 **고객 → AI → 상담사** 대표 흐름을 실제로 완주한다.

## 5.1 Happy Path 1건 우선

```text
1. 고객 Mobile 로그인
2. 구독 제품 조회
3. 문의 생성
4. 증상 제출
5. 추가 질문·답변
6. Backend가 실제 AI 호출
7. Guidance·Evidence 저장
8. Mobile에서 AI 안내 확인
9. 고객 상담 요청
10. 상담사 Web에서 같은 문의 조회
11. 상담 시작·처리
12. 상담 완료
13. 고객이 최신 상태 확인
```

### Backend 완료 기준

- 모든 단계가 같은 Inquiry를 사용한다.
- 실제 PostgreSQL에 상태와 이력이 유지된다.
- AI Run과 Guidance가 실제 호출 결과로 저장된다.
- `state_version`이 정상적으로 증가한다.
- 각 Role의 `allowed_actions`가 실제 상태와 맞는다.
- 새로고침·재조회 후에도 결과가 유지된다.
- 방문기사 기능 없이 흐름이 종료 가능하다.

---

## 5.2 Happy Path 이후 최소 오류 확인

정상 흐름이 성공한 뒤 다음 네 가지만 확인한다.

1. **409 stale version** — 잘못된 쓰기를 막고 최신 상태를 재조회할 수 있는가
2. **중복 요청** — 같은 Idempotency Key에서 중복 Business Record가 생기지 않는가
3. **AI Timeout/503** — 문의 원본이 보존되고 서비스 전체가 깨지지 않는가
4. **Schema/No-Evidence 오류** — 잘못된 AI 결과로 State가 오염되지 않는가

전체 Backend 회귀를 반복해서 E2E 시간을 소모하지 않는다. 최종 통합 시 필요한 표적 회귀와 기존 핵심 Test만 수행한다.

# 6. 전화 문의 등록 마감

전화 문의 등록은 이미 Runtime 구현이 진행되어 있으므로 신규 설계를 하지 않는다.

핵심 E2E가 닫힌 뒤 다음 최소 Smoke만 확인한다.

```text
상담사 Web
→ 고객 조회
→ 전화 문의 등록
→ 기존 Inquiry 생성
→ DB 저장
→ 상담 Workflow 진입 가능
```

확인 항목:

- 상담사 권한
- 고객·구독 연결
- 중복 등록 방지
- 등록 후 목록·상세 조회
- 기존 상담 Runtime 재사용

전화 문의 등록 때문에 **Mobile → AI → 상담사 E2E가 늦어져서는 안 된다.**

# 8. Blocker 처리 규칙

Backend는 여러 파트의 중앙에 있으므로 Blocker를 오래 들고 있지 않는다.

```text
[Backend E2E Blocker]
구간: Mobile→Backend / Backend→AI / Backend→Web
기준 Commit: <SHA>
Method·Path: <API>
기대 State: <상태·Version>
실제 결과: <응답·오류>
DB 영향: <저장 여부>
필요 협업자: <이름>
```

- AI Response·FastAPI 문제 → **이동윤**과 즉시 공동 확인
- DB·공용 환경 문제 → **김은진**
- Mobile 소비 문제 → **양정현**
- Web 소비 문제 → **한예나**
- State·계약 해석 문제 → **윤승혁**

E2E를 살리기 위해 임의 State·URL·DTO를 만들어 Client와 맞추지 않는다.
