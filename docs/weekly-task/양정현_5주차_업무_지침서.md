# 양정현 5주차 업무 지침서

> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템
>
> 대상 기간: **2026년 8월 10일 ~ 8월 14일**
>
> 5주차 운영 컨셉: **P0 Feature Complete · Mobile 실연동 · 대표 E2E 완료**
>
> 필수 기능 동결 목표: **2026년 8월 13일 오후**
>
> 최종 회귀·E2E 기준선 목표: **2026년 8월 14일**
>
> 5주차 운영 원칙: 4주차에 만든 고객·기사 Compose 화면과 Repository 골격을 더 넓히는 것이 아니라, **실제 Backend API가 준비된 경로에서 Fake·Fixture를 제거하고 고객 앱과 방문기사 앱이 실제 서비스 E2E에 참여하도록 만드는 것**을 최우선으로 한다.
>
> 5주차에는 새 화면 수를 늘리는 것보다 **고객 로그인 → 내 구독 조회 → 문의 생성 → 증상 제출 → AI 안내·추가 질문 → 상담·방문 상태 확인**, 그리고 **기사 로그인 → 배정 방문 조회 → 사전 점검 → 조치 결과 등록**의 실제 연결을 우선한다.
>
> 6주차는 배포·안정화·v1.0 Release Candidate 정리에 집중할 수 있도록, 5주차 종료 시점에는 Mobile P0 핵심 흐름이 `Mock-only` 상태에서 벗어나고 대표 E2E가 최소 1회 이상 실제 API·DB·State 기준으로 재현되어야 한다.

4주차 이후 코드 검사 기준으로 Mobile에는 다음 기반이 이미 존재한다.

1. 고객 앱의 Demo 로그인·Token 처리·`/me` 조회가 실제 Backend와 연결되어 있다.
2. 고객 문의 생성과 증상 제출은 실제 API를 호출하는 Remote Repository가 존재한다.
3. `idempotency_key`, `state_version`, 409 Conflict, 일반 API 오류 Mapping 기반이 존재한다.
4. 고객 제품·구독 홈은 아직 Fake Repository를 사용하지만, Backend에는 `GET /api/v1/me/subscriptions`, `GET /api/v1/me/subscriptions/{subscription_id}` Runtime이 추가되어 Mobile 연동이 가능한 상태다.
5. 고객 AI Guidance는 여전히 Fixture/Fake에 의존하며, 실제 Backend↔AI 결과 소비 경로는 Backend Runtime 제공 여부에 따라 연결해야 한다.
6. 상담 요청·문의 최신 상태 조회·추가 질문은 Backend Runtime과 계약 제공 시 즉시 연결해야 한다.
7. 방문기사 앱은 로그인 기반은 존재하지만 방문 목록·상세·사전 점검은 `FakeTechnicianVisitRepository` 중심이다.
8. Mobile에는 단위 테스트와 일부 Compose Instrumentation Test, `verify-build.bat` 기반 Build Gate가 존재하지만 전체 서비스 E2E와 기사 실단말 검증은 부족하다.

따라서 5주차의 완료 기준은 “화면이 보인다” 또는 “Mock에서 시연된다”가 아니다.

```text
고객 앱
로그인
→ 실제 구독 조회
→ 문의 생성
→ 증상 제출
→ 추가 질문 또는 AI 안내
→ 상담·방문 상태 확인

방문기사 앱
로그인
→ 실제 배정 방문 조회
→ 방문 상세·사전 점검
→ 지원되는 상태 전이·조치 결과 등록

공통
→ 실제 Backend API
→ 실제 DB·State
→ 실제 AI 결과 또는 명시적 Fallback
→ 동일 Commit에서 Mobile Test·Build·대표 E2E PASS
```

위 흐름 중 Backend Runtime이 최종적으로 제공되지 않은 구간은 `BLOCKED_BY_BACKEND`로 명시하고 Fake 성공으로 대체하지 않는다. 다만 5주차 전체 프로젝트 목표가 E2E 완료이므로, 차단 Endpoint는 발견 즉시 최지용·윤승혁에게 올리고 같은 주 안에 해제 여부를 추적한다.

# 2. 5주차 역할 목표

1. **8월 10일까지 Mobile 기준선과 실제 연동 가능 API를 확정한다.**

   `verify-build.bat`, 고객·기사 Unit Test, APK Build를 다시 실행하고, Backend `main`에 존재하는 제품·구독·문의·AI·상담·방문 Endpoint를 계약과 Runtime 기준으로 구분한다. `READY_FOR_MOBILE_INTEGRATION`, `BLOCKED_BY_BACKEND`, `MOCK_ONLY`를 명확히 표시한다.

2. **8월 11일까지 고객 제품·구독 홈의 Fake를 제거한다.**

   실제 `GET /api/v1/me/subscriptions`와 상세 조회 API를 Mobile `WaterCareApi`·DTO·Repository·ViewModel에 연결하고, 고객이 자신의 실제 합성 구독을 선택하여 문의를 시작하도록 한다.

3. **8월 12일까지 문의·증상 제출·추가 질문·AI 안내의 실제 서비스 흐름을 가능한 범위까지 연결한다.**

   4주차에 이미 구현한 문의 생성·증상 제출 Remote 흐름을 기준으로, Backend가 제공하는 추가 질문·Guidance·Evidence·상담 전환 Endpoint를 즉시 소비한다. AI 내부 API를 Mobile에서 직접 호출하지 않는다.

4. **8월 13일까지 방문기사 앱의 핵심 Fixture를 실제 Backend 계약으로 교체한다.**

   방문 목록·상세·사전 점검·상태 전이·조치 결과 중 Backend Runtime이 열린 항목부터 실제 Remote Repository로 전환한다. 기사에게 배정되지 않은 방문 접근과 개인정보 비노출 정책을 함께 검증한다.

5. **8월 13일까지 고객 앱과 기사 앱을 포함한 대표 Mobile E2E를 1차 통과시킨다.**

   고객 앱에서 시작된 문의가 Backend·AI·상담·방문 흐름을 거쳐 기사 앱에 노출되고, 지원되는 경우 기사 조치 후 고객 상태 확인까지 이어지는 수직 흐름을 동일 Fixture·동일 Commit에서 검증한다.

6. **8월 14일까지 Mobile 전체 회귀·APK·실단말 검증을 완료하고 Feature Complete 기준선을 고정한다.**

   고객·기사 Unit Test, Build, Connected Test, 대표 E2E를 재실행하고 실제 연동·Fallback·차단 범위를 문서화한다. 6주차에는 신규 P0 기능을 남기지 않고 배포·안정화·UX 마감으로 넘어갈 수 있게 한다.

5주차 완료 기준은 코드 파일 수나 화면 수가 아니다. **실제 Backend가 제공한 P0 API가 Mobile에 연결되고, Fake·Fixture가 남은 구간은 명시적으로 제한되며, 고객·기사 앱이 대표 E2E에 실제 참여하고, APK와 테스트가 동일 Commit에서 재현되어야 한다.**

# 3. 5주차 필수 업무

## 3.1 Mobile 기준선 재검증·연동 가능 범위 확정

### 작업 목적

5주차 시작 시점의 Mobile 코드·Gradle·APK·테스트·Backend 계약 상태를 다시 확인한다. 4주차 문서의 `BLOCKED_BY_BACKEND`가 현재도 유효한지 그대로 복사하지 않고, 실제 `main` Runtime을 기준으로 연동 가능 여부를 재판정한다.

### 작업 위치

```text
mobile/
├─ settings.gradle.kts
├─ build.gradle.kts
├─ gradle.properties
├─ gradle/wrapper/**
├─ README.md
├─ verify-build.bat
├─ core/src/main/**
├─ core/src/test/**
├─ customer-app/src/main/**
├─ customer-app/src/test/**
├─ customer-app/src/androidTest/**
├─ technician-app/src/main/**
└─ technician-app/src/test/**

backend/
├─ config/api_urls.py
├─ apps/accounts/**
├─ apps/subscriptions/**
├─ apps/inquiries/**
├─ apps/consultations/**
└─ apps/visits/**

contracts/
├─ api/**
├─ codes/**
├─ error-codes/**
└─ state-machine/**
```

### 세부 작업 지침

1. 최신 `main` 또는 PM이 지정한 5주차 기준 Commit에서 다음을 실행한다.

```cmd
cd mobile
verify-build.bat
```

2. `verify-build.bat`가 포함하는 최소 Gate를 확인한다.

```text
:core:test
:customer-app:testDebugUnitTest
:technician-app:testDebugUnitTest
:customer-app:assembleDebug
:technician-app:assembleDebug
```

3. 가능하면 Emulator 또는 실단말에서 다음을 추가 실행한다.

```cmd
gradlew.bat :customer-app:connectedDebugAndroidTest
```

4. 기사 앱의 Instrumentation Test가 없다면 5주차 필수 사용자 흐름에 필요한 최소 UI Test를 추가한다.
5. 실행 환경을 기록한다.
   - OS
   - JDK
   - Android SDK
   - Gradle·AGP
   - Emulator 또는 실단말
   - Backend Base URL
   - 실행 Commit
6. Backend `main`에서 Mobile이 사용하는 Endpoint의 Runtime 존재 여부를 직접 확인한다.
7. API 상태를 최소 다음으로 분류한다.
   - `READY_FOR_MOBILE_INTEGRATION`
   - `INTEGRATED`
   - `BLOCKED_BY_BACKEND`
   - `BLOCKED_BY_CONTRACT`
   - `MOCK_ONLY`
   - `NOT_REQUIRED_P0`
8. 4주차에 Backend 차단이었던 고객 제품·구독 API는 현재 Runtime이 존재하므로 다시 `BLOCKED_BY_BACKEND`로 두지 않는다.
9. 제품·구독 API를 `READY_FOR_MOBILE_INTEGRATION`으로 올리고 즉시 3.2에 착수한다.
10. Guidance·상담·추가 질문·Visit API는 실제 URL·View·Serializer·Test 존재 여부까지 확인한 뒤 상태를 판정한다.
11. 계약 문서만 있고 Runtime이 없으면 `CONTRACT_ONLY` 또는 `BLOCKED_BY_BACKEND`로 표시한다.
12. Mobile에서만 임의로 존재하는 Endpoint·Action·State를 새로 만들지 않는다.
13. 4주차 문서에 남은 잘못된 Route·DTO·파일명·명령을 최신 상태로 수정한다.
14. `Remote`와 `Fake` 전환 조건을 다시 확인하고, 실제 연동 화면이 Fake를 조용히 섞어 반환하지 않도록 한다.
15. 5주차 기준선 결과를 문서로 남긴다.

### 완료 기준

- 고객·기사 Unit Test와 Debug APK Build 결과가 최신 Commit 기준으로 기록되어 있다.
- Mobile이 사용하는 Backend API의 Runtime 존재 여부가 문서화되어 있다.
- 고객 제품·구독 API가 실제 연동 가능 상태로 재분류되어 있다.
- Guidance·상담·Visit 등 미준비 API가 Fake 성공으로 표시되지 않는다.
- Emulator 또는 실단말 Test 가능 여부와 차단 원인이 기록되어 있다.
- 5주차 Mobile 기준 Commit과 환경이 고정되어 있다.

## 3.2 고객 제품·구독 Remote 전환과 홈 Fake 제거 (`T-018` 연계)

### 작업 목적

4주차까지 `FakeCustomerCareRepository`에 남아 있던 고객 홈의 제품·구독을 실제 Backend 조회로 전환한다. 고객 문의가 수동 UUID나 Fixture 상수에 의존하지 않고, 로그인한 고객이 실제로 보유한 합성 구독에서 시작되게 한다.

### 작업 위치

```text
mobile/core/src/main/java/com/skn29/watercare/core/
├─ network/WaterCareApi.kt
├─ model/**
├─ repository/**
└─ auth/**

mobile/customer-app/src/main/java/com/skn29/watercare/customer/
├─ feature/customer/home/**
├─ navigation/**
└─ CustomerApp.kt

mobile/core/src/test/**
mobile/customer-app/src/test/**
```

### 세부 작업 지침

1. Backend의 다음 Runtime을 기준으로 Mobile API를 추가한다.

```text
GET /api/v1/me/subscriptions
GET /api/v1/me/subscriptions/{subscription_id}
```

2. Mobile DTO에는 Backend가 실제 반환하는 필드만 선언한다.
   - `subscription_id`
   - `status_code`
   - `management_type_code`
   - `started_on`
   - `last_care_on`
   - `next_care_on`
   - `product.product_model_id`
   - `product.model_code`
   - `product.model_name`
   - `product.generation_code`
   - `product.manufacturer`
3. DTO 이름을 화면 표시 모델과 분리하고 Mapper를 통해 변환한다.
4. 고객 홈에서 제품·구독 정보를 실제 응답으로 표시한다.
5. `WPUJAC104DWH` 지원 모델을 정상 P0 흐름으로 사용한다.
6. 미지원·비활성 구독은 Backend 응답과 정책에 따라 문의 진입을 제한한다.
7. API 조회 실패 시 Fake 제품을 자동 표시하지 않는다.
8. Remote 실패 화면은 최소 다음을 구분한다.
   - 로딩
   - 빈 목록
   - 인증 만료
   - 권한 오류
   - 데이터 없음
   - 서버 오류
   - 네트워크 오류
9. 고객이 제품을 선택하면 해당 `subscription_id`를 문의 생성 흐름에 전달한다.
10. 수동으로 `DEMO_SUBSCRIPTION_ID`를 입력해야만 고객 흐름이 진행되는 구조를 P0 기본 경로에서 제거한다.
11. 앱 재시작·화면 회전 후 선택한 구독이 필요 이상으로 유실되지 않게 한다.
12. 최근 케어일·다음 케어일 Nullable 상태를 안전하게 표시한다.
13. 날짜는 Backend의 계약된 업무 일자를 그대로 사용하고 Mobile에서 시간대 계산으로 날짜를 임의 변경하지 않는다.
14. 고객 본인이 아닌 구독 UUID를 직접 넣었을 때 안전한 오류로 처리되는지 확인한다.
15. List와 Detail DTO가 서로 다른 필드를 가지면 공통 모델에 억지로 합치지 않는다.
16. Unit Test를 추가한다.
   - 정상 목록
   - 빈 목록
   - 비활성·미지원
   - Nullable 케어일
   - 401
   - 404
   - 네트워크 실패
17. 실제 Backend와 Integration Smoke를 수행한다.

### 완료 기준

- 고객 홈이 실제 Backend 구독 API를 호출한다.
- `FakeCustomerCareRepository.getHome()`이 Remote 기본 경로에서 사용되지 않는다.
- 고객이 실제 `subscription_id`를 선택하여 문의를 생성한다.

- Mobile은 Backend가 소유한 상태·권한·업무 규칙을 재구현하지 않는다.
- AI FastAPI·LLM·Vector DB를 Mobile이 직접 호출하지 않는다.
- Backend가 검증한 고객용 AI DTO만 소비한다.
- `allowed_actions`는 Backend 응답을 기준으로 하고 Mobile이 임의 계산하지 않는다.
- 계약에 없는 상태·Action·Error Code를 UI 편의를 위해 추가하지 않는다.
- Runtime이 없는 기능을 Fake Callback으로 성공 처리하지 않는다.
- Remote API 실패 시 자동으로 Fixture를 섞어 반환하지 않는다.
- Fake Mode는 명시적 Demo/Fallback 용도로만 사용한다.
- 실제 개인정보를 Test·Log·Screenshot에 사용하지 않는다.
- 외부 공개 식별자는 계약된 Public UUID를 사용하고 DB 내부 PK를 노출하지 않는다.
- Token·Authorization Header·비밀값을 Log에 기록하지 않는다.
- 409 Conflict를 단순 일반 오류로 숨기지 않는다.
- 입력 실패 후 고객이 작성한 증상을 불필요하게 잃지 않게 한다.
- AI Timeout·근거 없음·위험 상태를 정상 안내와 동일하게 표시하지 않는다.
- 위험 상태에서 잘못된 완료·해결 버튼을 보여주지 않는다.
- E2E를 통과시키기 위해 DB를 직접 수정하거나 State를 강제하지 않는다.
- 고객·기사 앱의 Fixture와 실제 Runtime 데이터가 화면에서 섞이지 않게 한다.
- Backend Endpoint가 열리면 장기간 `BLOCKED_BY_BACKEND` 상태를 유지하지 않고 즉시 소비 작업을 시작한다.
- Backend가 열리지 않은 경우 Mobile에서 가짜 Endpoint를 만들지 말고 Blocker로 올린다.
- 8월 13일 오후 이후에는 신규 P0 화면·Dependency·대규모 Refactoring을 피한다.
- 8월 14일에는 기능 추가보다 회귀·Build·E2E·증거 정리에 집중한다.
- Hilt·Room·WorkManager·FCM·지도·위치 추적 등은 실제 P0 필수 흐름에 필요하지 않으면 5주차에 새로 도입하지 않는다.
- Compose 화면 수보다 실제 Remote 전환 비율과 E2E 재현성을 우선한다.
- Test가 실패하면 Assertion을 약화하거나 Test를 삭제해 통과시키지 않는다.
- APK 생성만으로 완료 처리하지 않고 실제 API 흐름을 검증한다.
- “시연 가능”과 “실제 연동 완료”를 같은 의미로 사용하지 않는다.

# 8. 6주차 인계 기준

5주차 종료 시 Mobile은 다음 상태를 목표로 한다.

```text
Customer App
실제 인증
+ 실제 구독
+ 실제 문의
+ 실제 증상
+ 실제 AI/Guidance 소비
+ 상담·방문 상태 확인
= P0 Feature Complete

Technician App
실제 인증
+ 실제 배정 방문
+ 실제 방문 상세
+ 지원되는 상태·조치
= P0 Feature Complete

Common
Unit Test
+ UI Test
+ APK
+ Smoke
+ E2E
= Release Candidate 진입 가능
```

6주차에 남겨도 되는 Mobile 업무는 다음 중심으로 제한한다.

- 잔여 버그 수정
- 배포 Backend Base URL 반영
- UI/UX 마감
- 접근성
- 성능·안정성
- Release APK 또는 최종 시연 APK 검증
- v1.0 문서·스크린샷·발표 지원

다음 항목이 6주차로 넘어가면 5주차 Mobile Feature Complete로 판정하지 않는다.

- 고객 구독 조회의 Fake 유지
- 문의 생성·증상 제출의 Fake 유지
- 실제 AI 결과를 전혀 소비하지 못함
- 기사 방문 목록 전체가 Fixture
- 고객·기사 앱이 대표 E2E에 참여하지 못함
- Debug APK Build 실패
- 핵심 Test 실패가 원인 미확정 상태

본 지침서의 5주차 핵심은 **Mobile 화면을 더 많이 만드는 것이 아니라, 이미 만들어진 고객·기사 화면을 실제 Backend·AI·State 흐름에 연결하여 대표 E2E를 통과시키는 것**이다.

특히 고객 제품·구독은 Backend Runtime이 이미 제공된 상태이므로 5주차 초반에 Fake를 제거해야 하며, Guidance·상담·방문 API는 Backend Runtime이 제공되는 즉시 연결한다. 방문기사 앱 또한 4주차의 Fixture 기반 시연 상태에 머무르지 않고, 5주차 종료 시 실제 배정 방문을 소비하는 E2E 참가자로 올라와야 한다.

5주차 종료 시점에는 **“고객 앱은 부분 Remote, 기사 앱은 Demo”라는 상태를 끝내고, Mobile 전체가 WaterBridge P0 Feature Complete 기준선에 포함되는 것**을 목표로 한다.
