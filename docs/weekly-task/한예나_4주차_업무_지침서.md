# 한예나 4주차 업무 지침서

> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템
>
> 대상 기간: **2026년 8월 3일 ~ 8월 7일**
>
> 중간 발표: **2026년 8월 6일**
>
> 발표 기준 Web 동결 목표: **2026년 8월 5일 오후**
>
> 4주차 운영 원칙: 3주차에 만든 상담사·운영자 Mock 화면과 테스트 수를 기능 완료로 간주하지 않는다. 이번 주에는 **상담사 목록·상세·상담 결과·방문 전환이 실제 Backend 응답과 상태 계약으로 동작하는 대표 수직 흐름**을 우선 완성한다.
>
> 발표 전에는 운영 대시보드와 신규 화면을 확대하지 않는다. `DEMO-INQ-002` 대표 문의를 기준으로 로그인, 문의 조회, 상담 입력, 상태 충돌 처리와 방문 전환 중 실제 구현된 범위를 반복 재현할 수 있게 한다. 발표 이후에는 병합 회귀 수정, 중복 코드 정리와 5주차 인계를 우선한다.

한예나는 3주차에 상담사 문의 목록·상세, 상담 입력, 방문 전환, 운영 대시보드와 공통 API·상태 UI를 폭넓게 구현했다. Mock 시나리오와 409·멱등성·Evidence 비노출 처리도 상당히 구체적이었다.

다만 3주차 코드 검사에서 다음 문제가 확인되었다.

- 상담 목록·상세·상담 저장·방문 전환·운영 대시보드의 업무 데이터가 모두 Mock이다.
- 실제 Backend 호출은 인증 4종과 `/health` 확인 수준이다.
- 7월 29일 테스트 보고서 이후 Web 코드가 크게 변경되었지만 최종 소스 기준 Test·Lint·Build 결과가 갱신되지 않았다.
- Runtime에서 사용되지 않는 과거 `inquiry-queue/**`, `inquiry-detail/**` 구현과 새로운 `consultation/**` 구현이 함께 남아 있다.
- 상담사 화면과 Legacy CSS가 중복되고 핵심 CSS 파일이 과도하게 커졌다.
- Mock이 위험도·우선순위·담당자·`allowed_actions`를 프론트에서 계산한다.
- README의 Node.js 지원 버전과 현재 `package-lock.json`의 실제 요구 버전이 일치하지 않는다.
- 운영 대시보드 구현량이 커졌지만 상담사 실제 API 연동과 최종 검증보다 먼저 확장되었다.

따라서 4주차에는 새 화면을 만드는 것이 아니라 다음 순서로 진행한다.

1. 최종 Web 소스의 실행·테스트 기준선을 다시 만든다.
2. 공식 Runtime 경로와 폐기·보류 경로를 구분한다.
3. 상담사 목록·상세를 실제 Backend API로 교체한다.
4. 상담 결과 저장·409 충돌·`allowed_actions`를 실제 계약으로 검증한다.
5. 방문 전환·일정 등록을 실제 저장 흐름에 연결한다.
6. 8월 5일 발표 기준 Web을 동결하고 반복 시연한다.
7. 발표 이후 회귀 수정과 5주차 인계를 수행한다.

프론트엔드는 문의 상태, 위험도, 우선순위, 현재 담당자와 허용 행동을 독자적으로 결정하지 않는다. Backend가 반환한 `status`, `risk_level`, `priority`, `current_assignee`, `allowed_actions`, `state_version`을 표시하고, 상태 변경은 승인된 행동별 API로만 요청한다.

# 2. 4주차 역할 목표

1. **8월 3일까지 3주차 Web 기준선을 현재 소스에서 다시 검증하고 공식 Runtime 구조를 확정한다.**

   의존성 설치, TypeScript 검사, Test, Lint, Production Build를 현재 Commit에서 다시 실행한다. 과거 성공 결과를 재사용하지 않으며, Runtime에서 사용하지 않는 과거 구현과 공식 구현을 구분한다.

2. **8월 4일까지 상담사 목록·상세와 상담 결과 저장을 실제 Backend API에 연결한다.**

   Mock Fixture는 테스트·Fallback 용도로 유지하되 실제 연동 성공과 Mock 성공을 구분한다. 상담사 목록·상세·저장 응답은 Backend 계약을 따르며 프론트에서 업무 규칙을 계산하지 않는다.

3. **8월 5일까지 `T-040`·`T-041` 대표 흐름과 오류 처리를 발표 가능한 기준선으로 고정한다.**

   `allowed_actions`, `state_version`, `idempotency_key`, `correlation_id`, 403·404·409·422·Network 오류를 실제 또는 계약 Mock으로 재현한다. 방문 필요 분기와 방문 일정 저장까지 가능한 범위를 명확히 고정한다.

4. **8월 6일 중간 발표에서 실제 구현 범위와 Mock 범위를 정확히 구분하여 시연한다.**

   실제 API 연결 화면, Mock Fallback 화면, 미구현 기능을 구분한다. 외부 네트워크나 Backend 장애에 대비한 캡처·영상은 준비하되 이를 실제 연동 성공으로 설명하지 않는다.

5. **8월 7일 발표 피드백과 병합 회귀를 반영하고 5주차 인계를 완료한다.**

   상담사 기능의 미완료 Endpoint, 계약 불일치, 중복 Source, CSS 정리 범위, 테스트 실패를 Issue와 인계 문서에 남긴다.

4주차 필수 범위는 상담사 Web의 실제 목록·상세·상담 저장·방문 전환과 발표 안정화이다. 운영 대시보드 고도화, 신규 차트, 반응형 전면 개선, 디자인 시스템 재작성, 전체 E2E와 배포는 필수 업무에서 제외한다.

# 3. 4주차 필수 업무

## 3.1 3주차 Web 기준선 재검증과 공식 Runtime 경로 확정

### 작업 목적

3주차 마지막 Test 보고서 이후 변경된 Web 전체 소스를 현재 Commit에서 다시 검증한다. 파일·테스트가 존재하는 것과 실제 Runtime에서 사용되는 것을 구분하고, 발표와 4주차 개발의 기준 Commit을 고정한다.

### 작업 위치

```text
web/
├─ package.json
├─ package-lock.json
├─ vite.config.ts
├─ tsconfig*.json
├─ eslint.config.*
├─ README.md
├─ src/**
└─ tests/**

web/docs/
├─ week4-web-baseline.md
├─ week4-runtime-source-map.md
├─ week4-test-result.md
└─ week4-open-issues.md
```

### 세부 작업 지침

1. 팀 표준 Node.js 버전을 하나로 고정한다.
   - 현재 Lock File이 요구하는 최소 Node.js 버전을 확인한다.
   - README의 `Node.js 20.19 이상 또는 22.12 이상` 문구를 실제 Package 요구사항과 일치시킨다.
   - 가능하면 팀 공통 버전으로 Node.js `22.22.2` 이상 또는 검증한 Version을 명시한다.
2. 현재 Commit에서 다음 명령을 다시 실행한다.
   - `npm ci`
   - `npm run typecheck` 또는 합의된 TypeScript 검사
   - `npm test -- --run` 또는 합의된 Vitest 명령
   - `npm run lint`
   - `npm run build`
3. 과거 23개 Test File·92개 Test 성공 기록을 현재 결과로 재사용하지 않는다.
4. 현재 Test File 수, Test Case 수, 성공·실패·Skip 수, Node.js·npm Version, Commit SHA를 기록한다.
5. `src/main.tsx`에서 시작하여 실제 Router까지 도달하는 Runtime Import Graph를 기준으로 다음을 분류한다.
   - 공식 사용
   - 테스트 전용
   - Mock 전용
   - 폐기 예정
   - 이후 주차 보류
6. `features/inquiry-queue/**`, `features/inquiry-detail/**`, `features/consultation/**` 중 어느 경로가 공식 구현인지 확정한다.
7. 같은 기능의 오래된 Hook·Mapper·Fixture·CSS가 공식 구현과 동시에 유지되지 않게 한다.
8. 발표 전 대규모 삭제가 위험한 경우 폐기 예정 경로를 문서에 명시하고 신규 Import를 금지한다.
9. `legacy/styles.css`, `staff-desktop-v6.css`, `ConsultantDashboardPage.css`의 적용 순서와 실제 사용 범위를 기록한다.
10. Backend·AI가 준비되지 않아 실패한 항목과 Web 코드 자체 실패를 구분한다.
11. 다른 팀원이 README의 명령으로 같은 결과를 재현하는지 김은진과 교차 확인한다.
12. 8월 3일 종료 시점의 Web 기준 Commit을 기록한다.

### 완료 기준

- 현재 Commit에서 실행한 Test·Lint·Build 결과가 기록되어 있다.
- Node.js·npm 지원 버전이 Lock File과 일치한다.
- 공식 Runtime 구현 경로가 하나로 정해져 있다.
- 사용되지 않는 과거 구현이 삭제되었거나 폐기 예정으로 명시되어 있다.
- Test 수와 결과가 실제 현재 소스와 일치한다.
- Mock 성공, 실제 API 성공, 정적 화면 성공이 구분되어 있다.
- 다른 팀원이 README를 따라 동일한 Web을 실행할 수 있다.

### 산출물

## 3.2 상담사 목록·상세 실제 API Adapter와 Mock 경계 정리

### 작업 목적

3주차에 Mock으로 완성한 상담사 목록·상세 UI를 실제 Backend 응답으로 교체할 수 있게 하고, 실제 API와 Mock Fixture가 화면 내부에서 섞이지 않도록 한다.

### 해당 WBS

- `T-038` 상담사 문의 목록
- `T-039` 상담사 문의 상세
- `T-045` Web 공통
- `T-046` 통합 연계

### 작업 위치

```text
web/src/common/api/**
web/src/features/consultation/
├─ api/
├─ model/
├─ hooks/
├─ mappers/
└─ repositories/

web/src/features/inquiry-queue/**
web/src/features/inquiry-detail/**
web/tests/{unit,integration,fixtures}/**
web/docs/week4-web-api-map.md
```

### 세부 작업 지침

1. 상담 목록·상세의 공식 Repository Interface를 정의한다.
   - `RemoteConsultationRepository`
   - `MockConsultationRepository`
   - 또는 현재 구조에 맞는 동등한 명칭
2. 실행 Mode는 환경변수나 Provider 한 곳에서 선택하고 화면 컴포넌트에서 Mock 여부를 직접 판단하지 않는다.
3. 실제 API Endpoint와 응답 DTO는 최지용과 확정한다.
4. Backend Endpoint가 준비되지 않은 경우 임의 URL을 만들지 않는다.
5. 차단된 Endpoint는 다음 상태 중 하나로 명시한다.
   - `API_READY`
   - `CONTRACT_ONLY`
   - `BACKEND_BLOCKED`
   - `MOCK_ONLY`
6. 목록 응답에서 다음 필드를 Backend 값 그대로 사용한다.
   - 공개 문의 ID
   - 업무용 문의 번호
   - 상태
   - 위험도
   - 우선순위
   - 현재 담당자
   - 접수 시각
   - 최근 변경 시각
   - `allowed_actions`
7. 위험도·우선순위·담당자·대기 시간·상태를 프론트에서 임의 계산하지 않는다.
8. `updated_at - created_at`을 현재 대기 시간으로 표시하지 않는다.
   - Backend가 `waiting_seconds`를 제공하면 해당 값을 사용한다.
   - 제공하지 않으면 `최근 변경까지 경과` 등 실제 의미로 표시하거나 대기 시간을 숨긴다.
9. 상세 응답에서 고객 표시명, 제품, 구독, 증상, 문진, 조치, AI 초안, 상담사 확정본, Evidence, 상태 이력을 Mapper로 변환한다.
10. Web에서 임의로 만든 합성 전화번호·주소·보증 기간·최근 케어일을 실제 API 응답처럼 표시하지 않는다.
11. Backend 응답에 값이 없으면 `미확인`, `제공되지 않음`, `조회 필요`로 표시한다.
12. Evidence는 Backend가 공개한 `EvidenceCardDTO`만 사용한다.
13. `chunk_id`, 내부 경로, 검색 점수, Prompt, 원문 전체를 타입과 화면에서 제외한다.
14. 목록·상세에 다음 상태를 재현한다.
   - Loading
   - Empty
   - Search Empty
   - 401
   - 403
   - 404
   - 5xx
   - Network
   - 부분 실패
15. 실제 API 성공 Test와 Mock UI Test를 파일명·Suite 명칭으로 구분한다.
16. 목록에서 상세로 이동한 뒤 돌아왔을 때 검색·필터·페이지 조건을 유지한다.
17. 실제 Backend가 목록·상세 API를 제공하지 못하는 경우 4주차 완료로 표시하지 않고 차단 사유와 필요한 계약을 기록한다.

### 완료 기준

- 목록·상세가 공식 Repository Interface를 사용한다.
- 실제 API Mode와 Mock Mode가 명확히 분리되어 있다.
- 실제 API가 준비된 영역은 Browser에서 호출되고 응답이 화면에 표시된다.
- 위험도·우선순위·담당자·`allowed_actions`를 Web이 계산하지 않는다.

- 운영 집계 API의 범위와 제공 시점이 최지용·윤승혁과 확정되어 있다.

### 작업 위치

```text
web/src/features/operations-dashboard/**

```

### 작업 내용

- KPI, 상태 분포, 위험도 분포, 장기 대기, AI 실패, 근거 없음에 필요한 API 필드를 문서화한다.
- `waitingMinutes` 등 의미가 불명확한 필드는 Backend 제공 값으로 교체할 계획을 남긴다.

### 완료 기준

- 운영 지표별 데이터 원천과 계산 주체가 문서화되어 있다.
- Frontend가 운영 KPI를 임의 계산하지 않는 구조로 전환 가능하다.
- P1 기능이 상담사 P0 회귀를 만들지 않는다.

## 5.6 웹 역할 수행 시 주의사항

- Mock 화면이 정교하더라도 실제 Backend 저장과 조회가 없으면 실제 기능 완료로 표시하지 않는다.
- 프론트엔드는 위험도·우선순위·상태·담당자·허용 행동을 독자적으로 계산하지 않는다.
- 버튼은 Backend가 반환한 `allowed_actions`를 기준으로 표시한다.
- 쓰기 요청은 `state_version`, `idempotency_key`, `correlation_id` 계약을 따른다.
- 상태 충돌 시 자동 덮어쓰기·자동 재전송을 하지 않는다.
- AI 초안과 상담사 확정본을 같은 값으로 저장하거나 표시하지 않는다.
- 공식 근거는 공개가 허용된 `EvidenceCardDTO`만 표시한다.
- 고객 전화번호·주소·Token·내부 경로·Prompt·검색 점수를 화면과 Log에 남기지 않는다.
- 운영 대시보드 P1보다 상담사 목록·상세·상담·방문 P0 흐름을 우선한다.
- 발표 전 대규모 CSS 재작성·Library 교체·Router 재설계를 하지 않는다.
- Backend API가 없으면 임의 Endpoint를 만들어 계약을 확정하지 않는다.
- 실제 API 연결과 Mock Fallback을 코드·Test·문서·발표에서 구분한다.
- `contracts/**`, `tests/**`, `.github/**`, `infra/**`를 수정할 때는 해당 주관할 담당자와 협의한다.
