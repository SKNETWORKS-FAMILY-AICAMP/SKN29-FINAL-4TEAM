# 윤승혁 5주차 업무 지침서

> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템
>
> 대상 기간: **2026년 8월 10일 ~ 8월 14일**
>
> 5주차 운영 컨셉: **P0 Feature Complete · Multi-Agent/Backend/Web/Mobile 통합 · 대표 E2E 완료**
>
> 전체 범위·계약 재동결 목표: **2026년 8월 10일 오후**
>
> 대표 E2E 1차 통과 목표: **2026년 8월 13일**
>
> Feature Complete 최종 승인 목표: **2026년 8월 14일**
>
> 5주차 운영 원칙: 4주차까지 구축한 State Machine·공통 코드·OpenAPI·Example·Crosswalk를 다시 크게 설계하는 것이 아니라, **5주차에 실제 서비스 통합을 끝내기 위해 필요한 최소 계약을 즉시 닫고, Backend·AI·Web·Mobile·Data/QA가 같은 WBS·같은 Commit·같은 대표 Scenario를 향하도록 강제로 정렬하는 것**을 최우선으로 한다.
>
> 윤승혁은 다른 담당자의 기능을 대신 구현하지 않는다. 대신 `contracts/state-machine/**`, `contracts/examples/**`, `scripts/contracts/**`, WBS·Scope·Dependency·Exit Gate·Issue·대표 E2E Acceptance를 직접 책임지고, 각 담당자가 만든 결과가 하나의 서비스 흐름으로 연결되는지 매일 검증·조정·승인한다.
>
> 5주차는 4주차보다 훨씬 강한 통합 주간으로 운영한다. 4주차까지는 중간 발표 기준으로 실제 Runtime·Mock·계약 전용을 정직하게 구분하는 것이 중요했다면, 5주차에는 **Mock·Contract-only·Deferred 상태를 가능한 한 실제 Runtime으로 닫고, 고객→AI→상담사→방문기사→고객 확인의 대표 흐름을 실제 서비스 기준으로 통과시키는 것**이 핵심이다.
>
> 6주차는 공휴일과 v1.0 안정화·배포·최종 시연을 위한 주간으로 사용할 수 있도록, 5주차 종료 시점에는 신규 핵심 P0 기능·미확정 핵심 계약·대표 E2E Blocker를 남기지 않는 것을 목표로 한다.

# 2. 5주차 역할 목표

1. **8월 10일 오전까지 5주차 전체 WBS·Scope·Dependency·Exit Gate를 Feature Complete 기준으로 다시 고정한다.**

   기존 “7주차 E2E” 또는 “5주차 최소 연결” 계획을 유지하지 않는다. 이번 주 목표를 `P0 Feature Complete + Multi-Agent 통합 + 대표 E2E 완료`로 재기준화하고 모든 팀원 5주차 지침서·WBS·Dependency Map·Issue 상태가 같은 목표를 가리키게 한다.

2. **8월 10일 오후까지 대표 E2E에 필요한 `CONTRACT_ONLY/DEFERRED` Action의 P0 포함 여부를 결정한다.**

   최소 `SUBMIT_ANSWERS`, `REQUEST_CONSULTATION`, `START_VISIT`, `VISIT_COMPLETED`, `SUBMIT_RESOLUTION_FEEDBACK`, `FINALIZE_INQUIRY`를 검토하고, 정상 E2E에 필요한 항목은 즉시 P0로 승격·승인한다. 미해결 재개 흐름이 필요하면 `CUSTOMER_REPORTED_UNRESOLVED`, `RESUME_CONSULTATION`까지 확정한다.

3. **8월 10일까지 Contract CI를 실제 통합 주간 수준으로 강화한다.**

   State Machine·Diagram뿐 아니라 Code Registry·OpenAPI·Example·Crosswalk·Root Contract Test가 계약 변경 PR에서 자동 실행되게 한다. 계약 변경이 CI를 우회해 `main`에 들어가는 상황을 막는다.

4. **8월 11일까지 Backend↔AI 실제 수직 연결 Gate를 판정한다.**

   실제 Django→FastAPI HTTP, Multi-Agent Runtime, 실제 LLM·팀 DB pgvector, AI 결과 DB 저장, State Event 적용까지 같은 Scenario에서 재현되는지 확인한다.

5. **8월 12일까지 Web·Mobile 실제 Remote 소비 Gate를 판정한다.**

   Web 상담 목록·상세·상담 Action·Visit Action과 Mobile 고객 구독·문의·AI·기사 Visit이 실제 Backend API를 소비하는지 확인하고 Mock 자동 대체를 차단한다.

6. **8월 13일까지 대표 고객→AI→상담사→방문기사→고객 흐름을 실제 E2E로 1차 통과시킨다.**

   정상 Scenario와 최소 2개 비정상 Scenario를 같은 Commit에서 실행하고, API·DB·State·`state_version`·`allowed_actions`·화면 증거를 연결한다.

7. **8월 14일까지 전체 팀 Feature Complete를 최종 판정한다.**

   영역별 Test·Build·Migration·RAG·Contract·E2E·문서가 같은 기준 Commit을 가리키는지 확인하고, `PASS / CONDITIONAL_PASS / HOLD` 중 하나로 최종 승인한다.

5주차 완료 기준은 PM 문서를 많이 작성하는 것이 아니다. **팀 전체가 같은 계약과 같은 대표 E2E를 기준으로 실제 통합 완료 상태에 도달하고, 그 증거가 WBS·Issue·Test·Runtime 문서·최종 Gate에 일치해야 한다.**

## 3.2 대표 E2E 범위와 미확정 Action 즉시 승인

### 작업 목적

State Machine에는 고객→AI→상담→방문→해결 확인→`RESOLVED` 대표 흐름이 존재하지만, 일부 외부 Action은 아직 `CONTRACT_ONLY` 또는 `DEFERRED`이다. 5주차 전체 E2E가 Backend 계약 부족으로 막히지 않게 정상 Scenario에 필요한 최소 Operation Set을 월요일에 확정한다.

### 작업 위치

```text
contracts/state-machine/
├─ inquiry-events.yaml
├─ transition-rules.yaml
├─ transition-guards.yaml
├─ allowed-actions.yaml
├─ completion-policy.yaml
└─ examples/**

contracts/api/**
contracts/examples/**
contracts/CHANGELOG.md

docs/decisions/**
docs/planning/week5-scope-and-dod.md
```

### 대표 E2E Event 기준

```text
START_INQUIRY
SUBMIT_SYMPTOM
SUBMIT_ANSWERS
SAFE_GUIDANCE_READY
REQUEST_CONSULTATION
START_CONSULTATION
VISIT_REVIEW_REQUIRED
VISIT_NEEDED
UPDATE_VISIT_SCHEDULE
CONFIRM_VISIT
START_VISIT
VISIT_COMPLETED
SUBMIT_RESOLUTION_FEEDBACK
FINALIZE_INQUIRY
```

### 우선 결정 Action

```text
SUBMIT_ANSWERS
REQUEST_CONSULTATION
START_VISIT
VISIT_COMPLETED
SUBMIT_RESOLUTION_FEEDBACK
FINALIZE_INQUIRY
```

필요 시:

```text
CUSTOMER_REPORTED_UNRESOLVED
RESUME_CONSULTATION
```

### 세부 작업 지침

1. 대표 정상 E2E를 14단계 기준으로 다시 검증한다.
2. 각 Event의 외부 Actor와 시스템 책임을 확인한다.
3. 현재 Action Crosswalk 상태를 확인한다.
4. `RUNTIME_IMPLEMENTED`, `OPENAPI_CONFIRMED`, `CONTRACT_ONLY`, `DEFERRED`를 최신 상태로 재분류한다.
5. 5주차 정상 E2E에 반드시 필요한 Action 중 `CONTRACT_ONLY/DEFERRED`는 즉시 PM 결정 대상으로 올린다.
6. `SUBMIT_ANSWERS`의 정확한 API Operation을 최지용과 확정한다.
7. `REQUEST_CONSULTATION`의 정확한 API Operation을 확정한다.
8. `START_VISIT`, `VISIT_COMPLETED`의 Actor·Guard·Payload를 확인한다.
9. `SUBMIT_RESOLUTION_FEEDBACK`의 고객 역할·Payload를 확인한다.
10. `FINALIZE_INQUIRY`의 최종 실행 Actor·Guard를 확인한다.
11. 완료 정책에 이미 정의된 의미를 임의로 변경하지 않는다.
12. State Machine이 이미 표현하는 비즈니스 규칙을 OpenAPI에 옮기는 수준으로 최소화한다.
13. 새로운 State를 만들지 않는다.
14. 새로운 Event를 만드는 대신 기존 Event의 Operation을 연결하는 것을 우선한다.
15. Visit 후 재방문은 정상 E2E 필수가 아니면 P1 또는 보조 Scenario로 둘 수 있다.
16. 고객 미해결→재상담 Flow는 최소 비정상 Scenario에 넣을지 결정한다.
17. P0 승격 Action은 최지용에게 OpenAPI·Runtime 구현 요청으로 전달한다.

## 3.9 일일 Integration Gate 운영

### 작업 목적

```text

```

### 세부 작업 지침

7. 다른 담당자가 대신 구현하는 방식으로 Blocker를 숨기지 않는다.
8. 계약 Blocker는 윤승혁이 당일 결정한다.
9. Backend Runtime Blocker는 최지용에게 당일 목표를 부여한다.
10. AI Runtime Blocker는 이동윤에게 당일 목표를 부여한다.
11. QA·E2E 증거 Blocker는 김은진과 해결한다.

13. Gate 결과를 `PASS / CONDITIONAL_PASS / HOLD`로 기록한다.
14. `CONDITIONAL_PASS`에는 반드시 종료 시점을 붙인다.
15. 다음 날 오전까지 넘겨도 되는 Blocker와 안 되는 Blocker를 구분한다.
16. 8월 13일 오후 이후에는 신규 기능보다 결함 수정만 허용한다.
17. 모든 Gate 결과를 `week5-exit-gate.md` 또는 일일 Gate 문서에 누적한다.

19. 발표·최종 보고에 사용할 수치도 매일 최신화한다.
20. 과거 수치를 그대로 재사용하지 않는다.

# 7. PM·기술 통합 역할 수행 시 주의사항

- 다른 담당자의 기능을 대신 구현하지 않는다.
- Backend API를 윤승혁이 직접 대량 구현하지 않는다.
- AI Agent 내부 코드를 윤승혁이 대신 작성하지 않는다.
- Web·Mobile UI 수정 업무를 윤승혁에게 끌어오지 않는다.
- PM 역할을 “문서만 쓰는 역할”로 축소하지 않는다.
- WBS·계약·Test·Runtime·E2E 증거를 실제로 대조한다.
- 계약 Validator PASS만으로 서비스 통합 완료를 판정하지 않는다.
- 파일·폴더 존재를 구현 완료로 인정하지 않는다.
- Unit Test PASS를 전체 E2E PASS로 합산하지 않는다.
- Mock 성공을 Runtime 성공으로 인정하지 않는다.
- 개인 DB 결과를 팀 DB 결과로 인정하지 않는다.
- 실제 LLM 미사용 상태를 Multi-Agent LLM 완료로 인정하지 않는다.
- Web·Mobile이 AI FastAPI를 직접 호출하도록 허용하지 않는다.
- AI가 Backend State를 직접 변경하도록 허용하지 않는다.
- State Machine이 이미 정의한 의미를 일정 때문에 임의 변경하지 않는다.
- E2E에 필요한 Action은 월요일에 결정하고 목요일까지 미루지 않는다.
- 새로운 State·Event를 추가하기 전에 기존 계약으로 해결 가능한지 확인한다.
- `DEFERRED`를 P0로 승격할 때 반드시 Runtime·Test 일정까지 함께 연다.
- 계약 변경은 Changelog·Crosswalk·Consumer 영향까지 기록한다.
- Contract CI 실패를 무시하고 병합하지 않는다.
- WBS와 실제 Runtime이 다르면 WBS를 즉시 수정한다.
- Runtime Status 문서가 최신 코드보다 뒤처지지 않게 한다.
- Issue가 실제로 사용되지 않으면 완료 증거로 가정하지 않는다.
- 팀원이 “완료”라고 보고해도 다른 소비자가 연결하지 못하면 통합 완료로 판정하지 않는다.
- 같은 Blocker가 이틀 이상 지속되면 범위·Owner·우선순위를 재조정한다.
- 8월 13일 오후 이후 신규 P0 기능 확대를 금지한다.
- 8월 14일에는 신규 기능보다 회귀·E2E·증거·문서 정합성을 우선한다.
- 운영 Dashboard·Graph DB·Kubernetes·제품 모델 대규모 확대를 P0 E2E보다 우선하지 않는다.
- 최종 발표·보고에서 Mock·계약·Runtime·E2E를 정확히 구분한다.
- 실제 개인정보를 Demo·Test·Screenshot에 사용하지 않는다.
- 팀의 성과를 과장하지 않되, 실제 통과한 Runtime·Test·E2E는 정확한 증거와 함께 적극적으로 표현한다.

본 지침서의 핵심은 **윤승혁이 모든 기능을 직접 구현하는 것이 아니라, 팀 전체가 5주차 안에 실제로 하나의 서비스로 붙도록 범위·계약·일정·Gate·E2E 기준을 강제로 일치시키는 것**이다.

4주차까지 State Machine·Code Registry·OpenAPI·Example·Validator 기반은 상당히 강해졌으므로 5주차에는 이를 다시 설계하는 데 시간을 쓰지 않는다. 대신 8월 10일 기존 WBS와 E2E 계약을 현재 목표에 맞게 재동결하고, 11일 Backend↔AI Gate, 12일 Web·Mobile Consumer Gate, 13일 대표 E2E Gate, 14일 전체 Feature Complete Gate를 연속으로 닫는다.

5주차 종료 시점에는 **“각자 기능은 만들었지만 전체 연결은 나중에 한다”는 상태를 끝내고, 같은 계약·같은 Commit·같은 대표 Scenario에서 WaterBridge P0가 실제로 연결되어 동작한다는 것을 PM이 증거 기반으로 최종 승인하는 것**을 목표로 한다.
