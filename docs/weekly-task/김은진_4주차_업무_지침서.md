김은진은 4주차에 새로운 데이터 종류를 늘리는 역할보다 **현재 저장소가 실제로 통과하는지 증명하고, Vector DB·RAG 결과와 서비스 개발 진척을 발표 가능한 근거로 정리하는 역할**에 집중한다.

3주차 종료 시점의 코드 검사에서는 Data 단위 테스트 67개 중 61개가 통과하고 6개가 실패했으며, `data/tools/pipeline.py qa --verify-rebuild`가 `backend_runtime_document_missing`으로 실패하여 `finalize`도 차단되었다. 따라서 저장된 과거 PASS 결과를 그대로 인용하지 않고, **발표 기준 Commit에서 다시 실행한 결과만 공식 상태로 인정**한다.

현재 프로젝트는 자체 ML/DL 모델을 학습하거나 파인튜닝하지 않는다. `BAAI/bge-m3`와 같은 사전학습 임베딩 모델을 추론 방식으로 활용하므로, 4주차 산출물에서 직접 학습한 모델이 있는 것처럼 포장하지 않는다. 교육 과정의 “머신러닝/딥러닝 학습결과서”는 **사전학습 임베딩 모델 적용 및 검색 성능 평가 결과서**로 해석하여 작성하고, 직접 학습 미수행 사유와 대체 산출물을 명시한다.

전체 E2E, 운영 환경 배포, Kubernetes, 성능 부하 테스트는 아직 4주차 필수 범위가 아니다. 4주차에는 발표 직전의 불안정한 기능 확장보다 **검증 가능한 기준선과 사실에 맞는 발표**를 우선한다.

# 2. 4주차 역할 목표

1. **8월 3일까지 3주차 병합 회귀의 직접 원인과 영향 범위를 확정한다.**  
   누락된 Backend Runtime 검증 증빙과 `backend_import_crosswalk.json`의 연결을 복구하거나 안정적인 증빙 경로로 이전하고, Data CI가 실제 의존 파일 변경을 감지하도록 Trigger 범위를 보완한다.

2. **8월 5일까지 발표 기준 Commit에서 Data QA를 다시 통과시킨다.**  
   Data 테스트, 결정적 재생성, QA, Finalize, 생성 결과 Drift 검사를 모두 재실행하고 실행 환경·Commit·결과 파일 Hash를 남긴다. 실패한 검사를 삭제하거나 성공으로 우회하지 않는다.

3. **Vector DB·RAG 구축 결과를 재현 가능한 공식 산출물로 확정한다.**  
   이동윤의 `bge-m3` 임베딩·pgvector 적재·검색 결과를 데이터 계약과 대조하고, 평가 Case의 Recall@5·MRR·금지 문서 Hit·모델 범위 차단 결과를 동일 기준으로 정리한다.

4. **ML/DL 관련 산출물을 프로젝트의 실제 구현 방식에 맞게 작성한다.**  
   직접 학습·파인튜닝이 없음을 명시하고, 모델 식별자·Revision·입력 데이터·임베딩 차원·검색 정책·평가 결과·재현 명령을 제출 가능한 패키지로 구성한다. 산출물 형식을 맞추기 위해 의미 없는 `.pt`, `.pkl`, `.h5` 파일을 임의 생성하지 않는다.

5. **4주차 기능의 최소 QA를 수행한다.**  
   제품·구독, 케어 이력, 문의, Vector DB, Django Admin 등 실제로 구현된 항목에 한해 정상·오류·권한·데이터 정합성을 확인하고, 코드 골격·Mock·실제 동작을 구분한다.

6. **8월 6일 중간 발표를 김은진이 주도하여 준비하고 발표한다.**  
   발표자료는 실제 구현·검증 결과만 사용하고 윤승혁에게 1차·최종 피드백을 받는다. 시연 실패에 대비한 정적 증빙과 대체 진행 순서를 준비한다.

7. **8월 7일까지 발표 피드백과 최신 병합 결과를 반영한 5주차 진입 기준을 확정한다.**  
   AI·RAG 고도화, Backend 연동, 안전·Fallback 테스트에 필요한 데이터·평가·Fixture·미해결 Issue를 담당자별로 인계한다.

4주차 완료 기준은 발표자료를 제출하거나 과거 PASS 결과를 재사용하는 것이 아니다. **발표 기준 Commit에서 코드·데이터·검증 결과·산출물 수치·발표 내용이 서로 일치하고, 다른 팀원이 같은 명령으로 핵심 결과를 재현할 수 있어야 한다.**

# 3. 4주차 필수 업무

## 3.1 3주차 병합 회귀 수정·Data QA 기준선 복구

### 작업 목적

현재 병합본에서 발생하는 `backend_runtime_document_missing`과 연쇄 테스트 실패를 해결하고, 이후 다른 담당자의 문서·Backend·AI 결과 변경이 Data QA를 깨뜨릴 경우 PR 단계에서 감지되도록 한다. 단순히 누락 파일을 빈 문서로 복원하는 데 그치지 않고, 증빙 경로와 CI 의존 범위를 안정화한다.

### 작업 위치

```text
data/config/handoff/
└─ backend_import_crosswalk.json

data/processed/validation/
├─ latest_qa_summary.json
├─ DATA_STATUS_QA.md
├─ schema/latest_schema_report.json
├─ integrity/latest_integrity_report.json
├─ quality/latest_quality_report.json
└─ reproducibility/latest_reproducibility_report.json

data/tools/
├─ pipeline.py
├─ watercare/validation.py
└─ tests/
   ├─ test_cli_compatibility.py
   ├─ test_qa_reports.py
   └─ test_service_contract_mapping.py

.github/workflows/
└─ data-ci.yml

docs/testing/
├─ evidence/backend/**
└─ results/week4-data-qa-baseline.md
```

### 세부 작업 지침

1. `backend_import_crosswalk.json`이 참조하는 Runtime 증빙 파일이 왜 삭제되었는지 Git 이력과 최지용의 현재 Backend 구현 상태를 확인한다.
2. 다음 두 방식 중 팀 합의된 하나를 적용한다.
   - 실제 실행 증빙 문서를 현재 구현과 실행 결과에 맞게 복원한다.
   - 개인별 작업 경로가 아니라 `docs/testing/evidence/backend/**`와 같은 안정 경로로 이전하고 Crosswalk를 갱신한다.
3. 문서가 실제 실행 증거가 아닌 경우 빈 문서나 형식만 맞춘 문서로 QA를 통과시키지 않는다. 최소한 실행 명령, 환경, Commit, 결과, 제한 사항을 포함한다.
4. `data-ci.yml`의 Trigger가 Data 검증이 실제로 읽는 의존 파일을 감지하도록 수정한다. 최소 검토 대상은 다음과 같다.
   - `backend/**` 중 Crosswalk가 직접 참조하는 파일
   - `docs/testing/evidence/**`
   - `ai/evaluation/reports/**`
   - `contracts/**`
   - `data/**`, `scripts/data/**`, `scripts/contracts/**`
5. 전체 `backend/**`·`docs/**`를 무조건 Trigger에 넣기보다 검증 코드가 읽는 경로를 기준으로 범위를 정한다.
6. `test_cli_compatibility.py`는 Wrapper와 통합 CLI의 결과 동등성 검증과 저장소 전체 QA 성공 조건을 가능한 범위에서 분리한다. 같은 원인으로 여러 Test가 중복 실패하더라도 원인을 파악할 수 있어야 한다.
7. 깨끗한 Worktree에서 다음 명령을 실행한다.

```bash
python -B -m unittest discover -s data/tools/tests -v
python -B data/tools/pipeline.py qa --verify-rebuild
python -B data/tools/pipeline.py finalize
git diff --exit-code -- data
```

8. 실행 전후의 Commit SHA, Python 버전, OS, 실행 시각, 전체·통과·실패 Test 수와 오류 코드를 기록한다.
9. `latest_qa_summary.json`과 사람이 읽는 `DATA_STATUS_QA.md`를 현재 실행 결과로 다시 생성하고 두 파일의 수치가 일치하는지 확인한다.
10. 병합 이후 변경이 발생하면 발표 직전 동일 명령을 다시 실행한다. 8월 3일 PASS는 8월 5일 발표 기준선 PASS를 대신하지 않는다.
11. 실패 원인이 타 담당자 변경에서 시작되었더라도, Data 검증 계약과 CI에 영향을 주는 경우 해당 담당자와 공동 수정하고 Issue에 책임 범위를 구분하여 기록한다.
12. GitHub에 없는 `.gitignore` 대상 파일은 첨부 전체 소스와 로컬 실행 환경에서 확인하되, Git 미추적 자체를 결함으로 판단하지 않는다.

### 완료 기준

- Data 테스트가 발표 기준 Commit에서 모두 통과한다.
- `qa --verify-rebuild`가 종료 코드 0으로 끝난다.
- `finalize`가 QA Gate를 우회하지 않고 정상 완료된다.
- 생성 결과 Drift가 없거나, 변경이 의도된 경우 변경 사유가 기록되어 있다.
- Crosswalk의 모든 파일 경로와 Hash가 실제 파일과 일치한다.
- Data CI가 관련 증빙·Backend·AI 평가 파일의 파괴적 변경을 PR에서 감지한다.
- 최신 PASS 결과가 과거 결과 복사가 아니라 현재 Commit 실행 결과이다.
- Git 미추적 원본·설정 파일과 실제 누락 파일이 명확히 구분되어 있다.

### 산출물

- 수정된 `backend_import_crosswalk.json`
- 안정화된 Backend Runtime 검증 증빙
- 수정된 `.github/workflows/data-ci.yml`
- 최신 Data 단위 테스트 결과
- 최신 QA·재현성·Drift 결과
- `week4-data-qa-baseline.md`
- 회귀 원인과 재발 방지 조치 Issue 또는 PR 설명

## 3.2 Vector DB·RAG 평가 기준선 재검증

### 작업 목적

사전학습 임베딩 모델과 pgvector를 사용한 검색 결과가 현재 공식 문서·모델·세대·페이지 계약을 만족하는지 확인한다. 단순히 검색 결과가 나오는 것만으로 완료 처리하지 않고, 다른 모델·세대·미검증 FAQ가 검색되지 않는지와 평가 결과가 재현되는지를 검증한다.

### 작업 위치

```text
data/processed/
├─ structured/rag/mvp/**
├─ structured/evidence/**
└─ metadata/
   ├─ source_inventory.csv
   └─ model_document_lineage.csv

data/config/rag/
└─ jac104_retrieval_cases.json

data/schemas/config/
└─ ragEvaluationCases.schema.json

ai/app/retrieval/**                 # 이동윤 주관할, 김은진 검수
ai/evaluation/**                    # 이동윤 주관할, 김은진 검수
ai/evaluation/reports/**
ai/tests/**

tests/contract/ai/**
tests/integration/backend-vector-store/**
tests/safety/**

docs/testing/results/
└─ week4-vector-retrieval-evaluation.md
```

### 세부 작업 지침

1. 이동윤에게 다음 실행 정보를 전달받아 기록한다.
   - 임베딩 모델 ID
   - 모델 Revision 또는 고정 버전
   - 임베딩 차원
   - 거리 함수와 검색 방식
   - pgvector Index 또는 Exact Search 설정
   - 적재 청크 수
   - 모델·세대·문서 정책 Filter
   - 평가 실행 명령
2. 현재 평가 Case와 실제 검색 결과의 Schema가 일치하는지 확인한다.
3. 양성 Case는 정답 문서·페이지·청크가 Top-k 안에 포함되는지 검증한다.
4. 부정 Case는 다음 자료가 검색 또는 응답 근거에 포함되지 않는지 확인한다.
   - JAC104 S세대 자료
   - WPU-IAC425 확장 자료
   - WPU-IAC506 `removed_legacy` 자료
   - 미검증 FAQ 단독 근거
   - 존재하지 않거나 지원하지 않는 모델
5. 기존 12개 평가 Case가 현재 요구를 모두 덮는지 확인하고, 동일 제품이지만 정책상 사용 불가한 문서 Case가 독립적으로 필요하면 추가한다. 단, 발표 직전 Case 수를 늘리기 위해 중복 Case를 만들지 않는다.
6. Recall@5, MRR, 금지 문서 Hit 수, 금지 모델 Hit 수, 평가 통과 수를 계산한다.
7. 지표가 좋더라도 특정 Case가 잘못된 페이지를 반환하면 Case별 결과를 숨기지 않는다.
8. `pgvector_verification.json`, `latest_eval_report.json` 등 결과 파일이 서로 다른 환경·목적의 실행 결과라면 파일명과 문서에서 구분한다.
   - 실제 pgvector 검색 결과
   - Vector Store 미연결 Mock·Fallback 결과
   - 과거 실험 결과
9. 평가 Dataset Hash, 청크 Dataset Hash, 결과 파일 Hash가 서로 연결되는지 확인한다.
10. 모델 Weight나 Cache는 Git에 포함하지 않고, 모델 ID·Revision·다운로드·실행 절차로 재현한다.
11. 공개 화면에 전달할 Evidence와 내부 검색 정보가 구분되는지 확인한다. 내부 경로·전체 원문·불필요한 `chunk_id`가 고객 화면으로 노출되어서는 안 된다.
12. 결과 수치는 8월 5일 발표 기준 Commit에서 한 번 더 실행하여 확정한다.

### 완료 기준

- [ ] 5주차 시작 기준 Commit 또는 승인 문서가 고정되어 있다.

## 5.4 데이터·QA·DevOps·발표 역할 수행 시 주의사항

- GitHub에 없는 파일이라도 `.gitignore` 정책에 따라 전체 소스·로컬 환경에 존재하면 정상 자료로 인정한다.
- 반대로 GitHub와 전체 소스 양쪽에 없는데 코드·Crosswalk·문서가 참조하면 실제 누락으로 처리한다.
- 공식 원본은 수정하지 않고 `data/raw/**`에 생성 결과를 저장하지 않는다.
- 공식 원본 PDF·FAQ 원문·실제 `.env`·비밀값은 공개 Git과 제출 패키지에 포함하지 않는다.
- 모델 Cache·Weight를 Git에 올리는 대신 모델 ID·Revision과 재현 명령을 사용한다.
- 데이터 건수·적재 건수·평가 수치는 문서에 맞춰 임의로 작성하지 않고 실행 결과를 사용한다.
- 모델·세대·문서 정책이 틀리면 유사도가 높아도 검색 실패로 처리한다.
- 실제 개인정보·실제 상담·방문 기록을 Fixture·Log·발표 화면에 넣지 않는다.
- AI·API·State Machine 계약의 의미를 QA 담당자가 단독으로 변경하지 않는다.
- 테스트가 실패하면 원인을 기록하고 담당자와 해결하며, 검사를 삭제하거나 성공으로 우회하지 않는다.
- 과거 PASS 리포트는 현재 Commit의 PASS를 대신하지 않는다.
- 결과 파일명이 `latest`여도 실행 시각·Commit·환경을 확인하지 않고 최신 결과로 단정하지 않는다.
- CI·Docker·Kubernetes 구조를 한꺼번에 확장하지 않고 실제 실행 명령이 확보된 항목부터 자동화한다.
- 테스트 결과에는 실행 환경, Commit, 데이터·Schema 버전과 사용 Fixture를 남긴다.
- 원시 리포트는 `tests/reports/**`, 사람이 승인한 결과는 `docs/testing/results/**`에 구분한다.
- 발표자료에서 완료·부분 완료·Mock·미구현을 색상이나 표식으로 구분한다.
- 발표를 위해 기능을 과장하지 않고, 왜 아직 전체 E2E가 아닌지 일정과 선행 관계로 설명한다.
- 8월 5일 이후에는 발표 안정성을 해치는 대규모 Refactoring과 무관한 기능 추가를 피한다.
