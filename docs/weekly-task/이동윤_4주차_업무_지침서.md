>
> 대상 기간: 2026년 8월 3일 ~ 8월 7일

>
> 발표 기준 기능 동결 목표일: **2026년 8월 5일**
>
> 4주차 운영 원칙: 새로운 AI 기능을 넓게 늘리기보다 **3주차에 구현한 AI·RAG 단독 기준선을 Django Backend의 실제 문의 흐름에 연결하고, 증상 구조화·누락 정보 확인·Timeout·Fallback을 재현 가능한 형태로 완성하는 것**을 우선한다.

## 3.2 Django Backend↔FastAPI AI 실제 호출·응답 저장 연결

### 작업 목적

3주차에는 FastAPI AI 서버와 계약만 준비되어 있고 Django Backend의 실제 AI Client·Mapper는 골격에 머물러 있었다. 4주차에는 고객이 증상을 제출하면 Backend가 AI API를 호출하고, 응답을 Schema로 검증한 뒤 AI 실행·검색 근거·안내 결과를 저장하는 최소 수직 흐름을 완성한다.

### 작업 위치

AI 주관 경로:

```text
ai/app/interfaces/http/**
ai/app/schemas/**
ai/app/common/errors/**
ai/app/common/timeout/**
ai/tests/integration/api/**
ai/tests/integration/pipeline/**
```

최지용과 공동 작업 경로:

```text
backend/integrations/ai/
├─ client.py
├─ request_mapper.py
├─ response_mapper.py
├─ schema_validator.py
└─ retry_policy.py

backend/apps/inquiries/**
backend/apps/ai_runs/**
backend/apps/evidence/**
tests/integration/backend-ai/**
```

### 세부 작업 지침

1. 최지용이 구현하는 증상 제출 API에서 AI 호출 시점을 합의한다.
   - `START_INQUIRY` 직후 호출하지 않는다.
   - 고객 원문과 필수 Context가 저장된 뒤 호출한다.
   - 미지원 제품·차단 모델·필수값 누락이면 AI를 호출하지 않는다.
2. Backend 요청 Mapper가 다음 정보를 계약에 맞게 전달하는지 검증한다.
   - 외부 공개 `inquiry_id`
   - `correlation_id`
   - 고객 원문 증상
   - 대표 증상 코드
   - 추가 답변
   - `model_code`
   - `manual_model`
   - `product_generation`
   - 현재 `state_version`
3. Backend 내부 정수형 PK, 개인정보, Token, 내부 파일 경로는 AI 요청에 포함하지 않는다.
4. FastAPI `/api/v1/ai/analyze`가 실제 Backend 요청을 수신하고 계약 응답을 반환하도록 한다.
5. 응답 검증 실패 시 부분 데이터나 임의 기본값으로 저장하지 않는다.
6. Backend에 저장할 최소 결과를 최지용과 확정한다.
   - AI 실행 상태
   - 위험도
   - 사용 안내 상태
   - 제한 기능
   - 상담 필요 여부
   - 검색 근거 참조
   - 실패 단계와 오류 코드
7. AI가 Inquiry 상태를 직접 변경하지 않고, Backend가 검증된 AI 결과를 바탕으로 State Machine Event를 실행하게 한다.
8. 정상·위험·근거 없음·Schema 오류·Timeout Case를 통합 테스트한다.
9. 같은 `correlation_id`로 Backend 요청, AI 로그, 검색 로그, 저장 결과를 연결한다.
10. AI 서버가 내려간 경우 고객 원문이 유실되지 않고 Backend가 재시도 또는 상담 전환 가능한 상태를 유지하도록 한다.
11. CORS는 Browser 직접 호출이 필요한 경우에만 허용 Origin을 명시하고, Django Backend 간 서버 호출에서는 불필요한 전체 허용을 제거한다.
12. 발표 시연은 외부 네트워크 실패에 영향을 덜 받도록 Local 또는 고정 Mock Fallback을 준비하되, 실제 연동 성공과 Mock 성공을 구분한다.

### 완료 기준

- Django 증상 제출 흐름에서 FastAPI AI API가 실제로 호출된다.
- 요청·응답이 `contracts/ai/**`의 JSON Schema를 통과한다.
- Backend 내부 PK·개인정보·비밀값이 AI 요청과 로그에 노출되지 않는다.
- 정상·위험·근거 없음·오류 응답이 Backend DB에 구분되어 저장된다.
- AI가 Inquiry 상태를 직접 변경하지 않는다.
- `correlation_id`로 Backend→AI→검색→저장 흐름을 추적할 수 있다.
- AI 서버 장애·Timeout 시 고객 입력이 보존되고 구조화 오류 또는 상담 Fallback이 반환된다.
- Mock 성공과 실제 FastAPI 호출 성공이 테스트·문서에서 구분되어 있다.
- 8월 5일까지 발표용 최소 수직 흐름이 고정된다.

### 산출물

- Backend↔AI Client·Mapper·Validator 연동 결과
- 정상·위험·근거 없음·오류 통합 테스트
- AI 실행·근거 저장 예시
- `correlation_id` 추적 로그 예시
- 발표용 수직 흐름 실행 절차

## 3.3 `T-026` 증상 구조화·누락 정보 확인·추가 질문 구현

### 작업 목적

현재 최소 Pipeline에서는 고객 원문을 충분히 구조화하지 못하고 `missing_fields`와 `followup_questions`가 빈 배열로 고정되어 있다. 4주차에는 고객이 이미 제공한 정보와 추가로 확인해야 할 정보를 구분하고, 동일 질문을 반복하지 않는 최소 증상 확인 기능을 구현한다.

### 작업 위치

```text
ai/app/structuring/
├─ symptom_structurer.py
├─ symptom_normalizer.py
├─ missing_field_checker.py
├─ followup_question_generator.py
└─ duplicate_question_guard.py

ai/app/orchestration/stages/
├─ structuring_stage.py
└─ missing_fields_stage.py

ai/evaluation/datasets/structuring/**
ai/tests/unit/structuring/**
ai/tests/integration/pipeline/**
contracts/ai/**
```

### 세부 작업 지침

1. 대표 증상과 기타 입력을 표준 구조로 변환한다.
   - 출수량 저하
   - 물맛·냄새 이상
   - 제품 누수
   - 냉·온수 온도 이상
   - 복수 증상 또는 기타 입력
2. 최소 구조화 필드를 계약에 맞게 확정한다.
   - 증상 유형
   - 발생 시점
   - 지속·간헐 여부
   - 영향 기능 또는 출수 유형
   - 누수·전기·화상 등 위험 신호
   - 사용자가 이미 수행한 자가 확인
3. 고객 원문과 기존 추가 답변에서 이미 확인된 필드를 추출한다.
4. 확인되지 않은 필드만 `missing_fields`에 반환한다.
5. 각 누락 필드에 대응하는 추가 질문을 JSON으로 반환한다.
6. 이미 답한 질문, 표현만 다른 동일 질문, 이전 단계에서 거절된 질문은 다시 생성하지 않는다.
7. 위험 신호가 있으면 일반 문진 질문보다 안전 안내를 우선한다.
8. 규칙 기반 최소 구현을 먼저 완성한 뒤 필요 시 LLM Provider를 선택적으로 사용한다.
9. LLM을 사용하는 경우에도 출력 Schema와 금지 표현 Guard를 통과해야 한다.
10. 자유 입력, 짧은 입력, 복수 증상, 오타, 부정문, 이미 답한 항목, 정보 부족 Case를 테스트한다.
11. 김은진의 합성 시나리오와 기대 결과를 사용하되, AI 평가용 변환 Dataset의 출처를 기록한다.
12. 한예나·양정현에게 화면에 필요한 `missing_fields`·질문·선택지 형식을 전달한다.

### 완료 기준

- 대표 증상과 자유 입력이 표준 증상 구조로 변환된다.
- 확인된 정보와 누락 정보가 구분된다.
- 누락된 필드만 추가 질문으로 반환된다.
- 이미 답한 질문이 반복되지 않는다.
- 위험 신호가 있을 때 일반 문진보다 안전 분기가 우선한다.

## 3.4 `T-032` AI·검색 Timeout·내부 재시도·상담 Fallback 구현

### 작업 목적

현재 FastAPI에는 전체 Timeout과 동시 실행 수 제한이 있으나, 검색·임베딩·Pipeline 단계별 Timeout과 AI 내부 최대 1회 재시도가 실제 Runtime 흐름에 완전히 연결되지 않았다. 4주차에는 장애가 발생해도 무응답이나 무한 재시도가 아니라 구조화된 오류와 상담 전환을 반환하도록 한다.

### 작업 위치

```text

ai/app/common/retry/**
ai/app/common/errors/**
ai/app/orchestration/**
ai/rag/embeddings/**
ai/rag/retrieval/**
ai/configs/retry_policy.yaml
ai/configs/runtime.yaml
ai/tests/integration/api/**
ai/tests/integration/pipeline/**
ai/tests/integration/retrieval/**
```

Backend 협업 경로:

```text
backend/integrations/ai/retry_policy.py
backend/integrations/ai/client.py
backend/apps/ai_runs/**
tests/integration/backend-ai/**
```

### 세부 작업 지침

1. 공통 협의 정책을 유지한다.
   - Backend 전체 AI 호출 Timeout: 30초
   - AI 내부 자동 재시도: 최대 1회
   - Backend 자동 재시도: 0회
2. 단계별 Timeout을 분리한다.
   - 요청 검증
   - 임베딩
   - Vector 검색
   - 구조화·생성
   - 최종 검증
3. 재시도 가능한 오류와 비재시도 오류를 구분한다.
   - 재시도 가능: 일시적 DB 연결 실패, 일시적 Provider 오류
   - 재시도 금지: Schema 오류, 지원하지 않는 제품, 정책 차단, 위험 규칙 위반
4. 최초 실행과 내부 재시도가 전체 30초 안에 끝나도록 시간 예산을 설정한다.
5. 재시도 횟수, 실패 단계, 소요 시간, 최종 오류 코드를 Metadata에 기록한다.
6. 최대 재시도 초과 시 무응답 대신 다음을 반환한다.
   - `requires_consultation=true`
   - 재시도 가능 여부
   - 실패 단계
   - 고객 입력 보존 여부
   - 상담 전환 안내
7. Vector DB 연결 실패와 검색 결과 0건을 다른 상태로 구분한다.
8. 위험 입력은 검색·Provider 실패와 관계없이 안전 안내가 우선 반환되도록 한다.
9. Timeout 중 작업 취소가 실제 하위 Task에 전달되는지 확인한다.
10. Semaphore 대기 중 Timeout, 검색 지연, DB 연결 실패, Schema 반복 실패, Provider 일시 오류를 재현한다.
11. `correlation_id` 하나로 최초 실행과 재시도 로그를 연결한다.
12. 발표 환경에서는 외부 Provider를 사용하더라도 Network 실패 시 Local Fallback 시나리오를 준비한다.

### 완료 기준

- 단계별 Timeout이 설정 파일로 관리된다.
- AI 내부 자동 재시도는 최대 1회로 제한된다.
- Backend 자동 재시도 0회 정책과 충돌하지 않는다.
- 비재시도 오류가 반복 호출되지 않는다.
- 최초 실행과 재시도가 전체 30초 안에 종료된다.
- Timeout·재시도 초과 시 구조화 오류와 상담 Fallback이 반환된다.
- Vector DB 장애와 검색 결과 없음이 구분된다.
- 위험 입력은 장애 상황에서도 안전 안내를 우선 반환한다.
- 실패 단계·재시도 횟수·소요 시간이 `correlation_id`와 함께 기록된다.

### 산출물

- 단계별 Timeout·재시도 정책
- AI 내부 재시도 구현
- 상담 Fallback 응답
- 장애·Timeout 통합 테스트
- 발표용 장애 대응 시나리오와 로그 예시

2. `langgraph`, `sentence-transformers`, `psycopg`, `pgvector` Version을 고정한다.
3. `bge-m3` Cache·Revision·Download 절차를 확인한다.
4. Linux에서 AI 단위·계약·검색 Test를 실행한다.
5. CPU 환경의 최초 Model Loading 시간과 Memory 사용량을 기록한다.
6. 실행 실패 시 원인을 환경 문제와 코드 문제로 분리한다.

### 완료 기준

- Linux 또는 Container에서 AI 서버가 실행된다.
- 필수 의존성 Version이 재현 가능하게 고정되어 있다.
- 핵심 Test 결과와 Model Loading 정보가 기록되어 있다.

## 5.4 AI·RAG 역할 수행 시 주의사항

- AI 서비스에서 Inquiry·Consultation·Visit 상태를 직접 변경하지 않는다.
- 직접 수행하지 않은 ML/DL 학습이나 파인튜닝을 수행했다고 기록하지 않는다.
- 사전학습 임베딩 모델 사용을 “자체 학습 모델”로 표현하지 않는다.
- 공식 근거가 없으면 그럴듯한 자가조치를 생성하지 않고 판단 보류·상담 필요로 처리한다.
- 위험 입력은 일반 검색·안내보다 안전 규칙을 우선한다.
- 미검증 FAQ를 공식 매뉴얼과 같은 수준의 근거로 사용하지 않는다.
- `WPUJAC104DWH`와 적용 매뉴얼·D세대 관계를 확인하고 문자열 유사성만으로 적용 범위를 판단하지 않는다.
- `WPUIAC425SNW`, `WPU-IAC506`, JAC104 S세대 자료를 MVP 검색에 임의 포함하지 않는다.
- `source_path`, 고객 원문 전체, Prompt, API Key, 개인정보를 응답·로그·평가 보고서에 노출하지 않는다.
- Mock·Stub·규칙 기반·실제 pgvector·외부 LLM 실행을 문서와 발표에서 구분한다.
- 작은 평가 Dataset의 결과를 전체 제품·전체 증상 성능으로 확대 해석하지 않는다.
- `data/**`를 수정할 때는 김은진, Backend 연동을 수정할 때는 최지용과 협의한다.
- 중간 발표 직전에는 신규 기능보다 재현성·Fallback·수치 정합성을 우선한다.
