# 한예나 6주차 업무 지침서

> 담당자: 한예나  
> 역할: Web Frontend / 상담사 화면 최종화 / 주간발표 준비  
> 적용 기간: 2026-08-18 ~ 2026-08-21  
> 핵심 원칙: **6주차에는 상담사 Web의 기능·레이아웃을 확정하고, 실제 Backend와 연결된 상담 업무를 끝까지 수행할 수 있는 상태로 만든 뒤 Production Build·브라우저 Smoke·주간발표 준비까지 마감한다.**

---

# 1. 6주차 완료 목표

6주차가 끝났을 때 아래 기능과 상태가 **실제 상담사 Web에서 확인되어야 한다.**

- [ ] 상담사가 실제 Web에서 로그인할 수 있다.
- [ ] 실제 Backend에서 새 문의·처리 중 문의·완료 문의를 조회할 수 있다.
- [ ] 고객 Mobile에서 상담 요청한 신규 문의가 상담사 Web 목록에 실제로 나타난다.
- [ ] 해당 문의를 클릭하면 같은 `inquiry_id`의 상세 화면이 열린다.
- [ ] 상세 화면에서 고객 원문, 추가 질문·답변, AI 안내, 공식 Evidence, 상담사용 AI 인계 내용을 확인할 수 있다.
- [ ] 상담사가 상담 시작 → 기록 저장 → 상담 완료를 실제 Backend로 수행할 수 있다.
- [ ] 상담 완료 후 새로고침하거나 다시 진입해도 저장 내용과 최신 상태가 유지된다.
- [ ] 권한 없는 상담사의 접근이 Backend 정책에 맞게 차단된다.
- [ ] 409가 발생해도 작성 중 상담 내용이 가능한 범위에서 유지된다.
- [ ] 401·403·404·409·5xx를 서로 구분하여 상담사용 메시지로 보여준다.
- [ ] Mock이 없어도 Remote Mode에서 핵심 상담 흐름이 동작한다.
- [ ] Production Build가 성공한다.
- [ ] 직접 URL 접근과 Browser Refresh에서도 화면이 정상 동작한다.
- [ ] 1920×1080 발표 환경과 일반 노트북 화면에서 핵심 업무가 정상적으로 보인다.
- [ ] 개발용 문구, Raw Status, 내부 코드, 불필요한 기술정보가 화면에 노출되지 않는다.
- [ ] 메뉴·Route·화면·API 연결이 최종 확정된다.
- [ ] 주요 상담사 화면의 레이아웃과 디자인이 Freeze된다.
- [ ] 한예나가 Mobile → Backend → AI → DB → Web → 고객 결과 확인의 전체 흐름을 설명할 수 있다.
- [ ] 다른 팀원의 핵심 작업이 전체 서비스에서 어떤 역할을 하는지 주간발표에서 설명할 수 있다.
- [ ] 실제 시연 순서, 발표 자료, 예상 질문, Fallback 자료가 준비된다.

> **실제 상담 Remote E2E, 상담 저장·완료, Production Build, 레이아웃 Freeze, 전체 흐름 설명이 완료되지 않으면 6주차 Web 과업 완료로 판정하지 않는다.**

# 2. 이번 주 핵심 업무

## A. 상담사 Web 기능·레이아웃 Freeze

6주차 첫날에 상담사 Web에서 **무엇을 만들지 더 이상 바뀌지 않는 상태**를 만든다.

P0 최종 범위:

- 상담사 로그인
- 업무 대시보드
- 새 문의 목록
- 처리 중 문의 목록
- 완료 문의 목록
- 검색
- 상태 / 위험도 필터
- 페이지네이션
- 문의 상세
- 고객 원문
- 추가 질문·답변
- AI Guidance
- 공식 Evidence
- 상담사용 AI 인계
- 상담 시작
- 상담 기록 저장
- 상담 완료
- 전화 문의 등록
- Loading / Empty / Error / Forbidden / Not Found / State Conflict

P1 / 제외:

```text
방문기사 기능
방문기사 배정
방문 전환 중심 업무
방문기사 Remote Flow
운영 관리자 신규 화면
합의되지 않은 신규 Web 화면
```

이미 구현된 방문 관련 UI가 있다면 유지할 수 있지만, **6주차 P0 완료 조건에는 포함하지 않는다.**

### 기능 Freeze 기준

- 메뉴명과 실제 기능이 일치한다.
- 목록에서 선택한 문의가 올바른 상세로 연결된다.
- Remote Mode에서 실제 데이터를 표시한다.
- Mock과 Remote가 서로 다른 화면 구조를 사용하지 않는다.
- 버튼은 `allowed_actions` 기준으로 표시한다.
- 상태 변경 성공 후 최신 데이터를 다시 조회한다.
- 401·403·404·409·422·5xx를 구분한다.
- 오류 시 작성 중 내용을 가능한 범위에서 보존한다.
- 권한에 맞지 않는 데이터는 노출하지 않는다.
- Freeze 이후 신규 편의 기능을 임의 추가하지 않는다.

### 레이아웃 Freeze 대상

```text
Header
Sidebar
본문 Width
대시보드 Card
목록 Header / Filter / Row
문의 상세 정보 구조
AI 정보 영역
Evidence 영역
상담 Form
Action Button 영역
Loading / Empty / Error / Forbidden / Not Found
```

레이아웃 완료 기준:

- 1920×1080에서 핵심 업무가 첫 화면에 보인다.
- 일반 노트북에서도 핵심 CTA가 사라지지 않는다.
- 불필요한 빈 공간이 과도하지 않다.
- 긴 문의 제목·고객명·제품명·오류 문구가 화면을 깨뜨리지 않는다.
- 선택된 메뉴·탭·필터가 즉시 구분된다.
- 스크롤 영역이 충돌하지 않는다.
- 버튼·입력창·카드·목록 간격이 일관된다.
- 핵심 Action이 긴 스크롤 끝에만 있지 않는다.

Freeze 이후 변경은 **실제 기능 사용이 불가능한 문제**에 한해서만 허용한다.

## B. 실제 상담 Remote E2E 완주

6주차 Web의 가장 중요한 기능 Gate다.

```text
1. 상담사 Web 로그인
2. 실제 Backend 문의 목록 조회
3. 고객 Mobile에서 상담 요청한 신규 Inquiry 확인
4. 같은 inquiry_id의 문의 상세 진입
5. 고객 원문 확인
6. 추가 질문·답변 확인
7. AI Guidance 확인
8. 공식 Evidence 확인
9. 상담사용 AI 인계 확인
10. 상담 시작
11. 상담 기록 작성
12. 상담 기록 저장
13. 상담 완료
14. 최신 Inquiry 재조회
15. Browser Refresh
16. 저장 내용과 최신 상태 유지 확인
```

필수 조건:

- Mock 성공을 Remote E2E PASS로 계산하지 않는다.
- 실제 Mobile에서 만들어진 Inquiry를 사용한다.
- 같은 `inquiry_id`를 사용한다.
- 상담 시작·저장·완료가 실제 Backend에 반영된다.
- 새로고침 후에도 저장 결과가 유지된다.

상담사 화면에는 최소 다음 AI 정보를 확인할 수 있어야 한다.

```text
고객 원문
추가 질문
고객 추가 답변
구조화된 증상
위험도
현재 사용 안내
사용 제한
공식 Evidence
고객에게 제공된 Guidance
상담사가 추가로 확인할 사항
```

Backend/API가 제공하지 않는 값을 Web에서 임의 생성하여 실제 데이터처럼 표시하지 않는다.

## C. 상담 UX·오류·권한 마감

상담 흐름:

```text
상담 시작
→ 상담 내용 작성
→ 저장
→ Backend 반영
→ 최신 데이터 표시
→ 상담 완료
```

반드시 확인:

- 필수값
- Validation
- 저장 Loading
- 저장 성공 피드백
- 저장 실패
- 중복 저장 클릭
- 409
- 입력 보존
- 상담 완료 확인
- 완료 후 수정 정책

### 오류 처리

**401**

```text
세션 만료
→ 상담사용 안내
→ 로그인 화면
```

**403**

```text
권한 없음
→ Forbidden 안내
```

**404**

```text
문의 없음
→ Not Found
→ 목록 이동 Action
```

**409**

```text
상담 기록 작성
→ 다른 Client에서 상태 변경
→ 409
→ 작성 내용 유지
→ 최신 데이터 재조회
→ 재확인 안내
```

**5xx**

```text
일시적 서버 오류
→ 상담사용 메시지
→ Retry
```

Raw HTTP 코드나 내부 오류 코드만 화면에 보여주지 않는다.

## D. 디자인·배포 품질 마감

목표는 “예쁜 화면”이 아니라:

> **상담사가 어디를 보고 무엇을 눌러야 하는지 바로 이해할 수 있는 업무 화면**

정보 우선순위:

```text
고객
↓
제품
↓
증상
↓
위험도 / 현재 상태
↓
AI 분석 / Evidence
↓
상담 기록
↓
현재 가능한 Action
```

### 디자인 방향

- 밝은 하늘색
- 파란색
- 청록색
- 흰색 / 옅은 파란색 카드
- 높은 대비의 본문 색상
- 과하지 않은 그림자·Border
- 긴급·주의·성공 상태의 의미 색상 유지
- 장시간 업무에 적합한 Typography

우선순위:

1. 정보 구조
2. 현재 상태와 다음 Action
3. Card / Button / Input / Filter / Badge / Typography / Spacing 일관성

AI 영역에서는 아래 상태가 혼동되지 않아야 한다.

```text
AI 초안
상담사가 확인한 내용
상담사가 직접 작성한 기록
공식 Evidence
위험 / 주의 정보
```

### 내부 기술정보 제거

불필요하게 UI에 노출하지 않는다.

```text

allowed_actions
correlation_id
ai_request_id
Raw Backend Status
HTTP 401/403/404/409/500
Internal Error Code
Debug Message

Mock
```

Production 확인:

## E. 팀 전체 흐름 이해 및 주간발표 준비

다른 팀원의 코드를 전부 이해하는 것이 목표가 아니다.

각 영역에서 다음 네 가지를 설명할 수 있어야 한다.

```text
왜 필요한가?
무엇을 입력받는가?
무엇을 처리하는가?
다음 파트로 무엇을 넘기는가?
```

### 양정현 — Mobile

설명할 수 있어야 하는 것:

- 고객이 어떤 정보를 입력하는가
- 어떤 상태에서 추가 질문을 받는가
- AI Guidance를 어떻게 확인하는가
- 상담 요청을 어떻게 생성하는가
- 상담 후 어떤 최신 상태를 다시 확인하는가

Web 연결점:

> Mobile의 상담 요청이 같은 Inquiry로 상담사 Web에 이어진다.

### 최지용 — Backend·DB

설명할 수 있어야 하는 것:

- Inquiry가 어떻게 저장되는가
- 상태는 누가 결정하는가
- `allowed_actions`가 왜 필요한가
- `state_version`이 왜 필요한가
- 권한과 409를 어떻게 처리하는가

Web 연결점:

> Web은 상태 머신을 새로 만들지 않고 Backend가 허용한 Action을 표시한다.

### 이동윤 — AI·RAG

설명할 수 있어야 하는 것:

- 고객 증상이 어떻게 분석되는가
- 추가 질문은 왜 생성되는가
- Evidence는 어디서 검색되는가
- Guidance는 어떤 근거로 생성되는가
- 상담사용 AI 인계에는 무엇이 들어가는가

Web 연결점:

> 상담사는 AI 결과를 그대로 확정하지 않고 Evidence와 함께 검수한다.

### 김은진 — QA·DevOps

설명할 수 있어야 하는 것:

- 어떤 환경에서 E2E를 검증했는가
- 같은 Inquiry를 어떻게 추적했는가
- 어떤 오류·동시성·복구 테스트를 했는가
- 최종 후보 SHA가 무엇인가

Web 연결점:

> 실제 환경에서 기능이 연결됐다는 QA 근거를 설명한다.

### 주간발표 구조

```text
문제
↓
사용자 흐름
↓
Mobile
↓
Backend / State Machine
↓
AI / RAG
↓
상담사 Web
↓
실제 E2E 검증
↓
효과와 한계
```

Web 시연 순서:

```text
상담사 로그인
→ 업무 대시보드
→ 새 문의
→ 실제 고객 상담 요청 문의 선택
→ 고객 원문
→ AI 인계
→ Evidence
→ 상담 시작
→ 상담 기록
→ 상담 완료
→ 최신 상태 확인
```

준비할 것:

- 발표 자료
- 발표 대본
- 시연 클릭 순서
- 화면별 한 문장 설명
- 예상 질문·답변
- 발표용 계정
- 발표용 Inquiry
- 발표 환경 URL
- Fallback Screenshot
- Fallback GIF/영상
- 최종 Build 확인

# 3. 실제 E2E 및 완료 판정 기준

6주차 Web의 최종 Gate는 아래 흐름이다.

```text
상담사 로그인
→ 실제 고객 상담 요청 문의 조회
→ 같은 inquiry_id 상세 진입
→ 고객 원문·추가 답변 확인
→ AI 인계 내용 확인
→ 공식 Evidence 확인
→ 상담 시작
→ 상담 기록 저장
→ 상담 완료
→ 새로고침
→ 저장 내용과 최신 상태 유지
```

그리고 아래 품질 Gate를 함께 통과해야 한다.

```text
기능 Freeze
레이아웃 Freeze
Production Build
Browser Smoke
1920×1080
일반 노트북
개발용 정보 미노출
```

마지막으로 한예나는 다음 전체 흐름을 실제 구현 기준으로 설명할 수 있어야 한다.

```text
고객 Mobile
→ Backend / DB
→ AI / RAG
→ 상담 요청
→ 상담사 Web
→ 상담 처리
→ 고객 최신 상태 확인
```

> **“화면이 있다”가 아니라 실제 상담 업무를 끝까지 처리하고, 배포·시연하며, 전체 서비스 흐름을 설명할 수 있어야 PASS다.**

# 6. 7주차 이관 / P1 제외 범위

6주차 P0 완료 후 7주차로 넘길 수 있는 것:

- 미세한 색상 조정
- 추가 접근성 개선
- 세부 Animation
- 추가 화면 캡처 정리

- 추가 브라우저 환경 검증
- 세부 성능 최적화

이번 주 제외:

```text
방문기사 기능
방문기사 Remote Flow
운영 관리자 신규 화면
합의되지 않은 신규 메뉴
기능 Freeze 이후 대규모 레이아웃 재설계
단순 장식 목적 UI 개편
새 라이브러리 교체
발표용 가짜 Backend 데이터
API 미제공 값 실제 정보처럼 표현
Backend·AI·DB 계약 직접 수정
시연 직전 대규모 CSS 구조 변경
테스트 통과 목적 업무 규칙 우회
```

핵심 기능이 끝나기 전에는 신규 화면이나 디자인 실험으로 범위를 넓히지 않는다.
