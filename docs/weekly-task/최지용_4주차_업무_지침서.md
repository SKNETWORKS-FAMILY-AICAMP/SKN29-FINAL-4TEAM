# 최지용 4주차 업무 지침서

> 프로젝트: 정수기 구독 고객 케어 및 A/S 업무 지원 시스템
>
> 대상 기간: **2026년 8월 3일 ~ 8월 7일**
>
> 중간 발표: **2026년 8월 6일**
>
> 발표 기준 Backend 동결 목표: **2026년 8월 5일 오후**
>
> 4주차 운영 원칙: 3주차에 만든 다수의 Model·Migration·계약 파일을 기능 완료로 간주하지 않는다. 이번 주에는 **실제 HTTP 요청이 DB 저장·상태 전이·AI 호출·권한 검증으로 이어지는 수직 흐름**을 우선 완성한다.
>
> 중간 발표 전에는 새 도메인을 넓게 추가하기보다 `DEMO-INQ-002` 대표 흐름이 반복 재현되는 상태를 만든다. 발표 이후에는 발견된 회귀 수정과 5주차 연동 준비를 우선한다.

최지용은 4주차에 새로운 테이블을 많이 추가하는 역할이 아니다. 3주차 코드 검사 결과 계약 테이블 32개와 Migration·공통 Backend 기반은 상당히 구현됐지만, 실제 Runtime은 인증 4개, 문의 생성·취소 2개와 임시 Health 수준에 머물렀다. 특히 3주차 필수 업무였던 **증상 제출, 추가 답변 누적, AI 분석 요청, 상담·방문으로 이어지는 상태 전이**가 실제 API에 연결되지 않았다.

따라서 4주차에는 다음 우선순위를 적용한다.

1. 3주차 미완료 수직 흐름을 먼저 닫는다.
2. 제품·구독과 케어 이력은 발표에 필요한 최소 범위부터 구현한다.
3. State Machine 계약 전체를 한 번에 구현하지 않고 대표 흐름에 필요한 Event를 실제 Runtime에 연결한다.
4. AI가 상태를 직접 변경하지 않도록 Backend가 요청·응답 검증과 상태 전이를 통제한다.
5. 발표자료에 Model 수·Migration 수만 제시하지 않고 실제 호출 가능한 Endpoint와 저장 결과를 증빙한다.

4주차 필수 범위에는 완성형 회원가입, 운영자 통계, 전체 상담·방문 기능, 관리 일정 자동 산정, 전체 E2E, 성능 최적화, 운영 배포가 포함되지 않는다. 해당 기능은 선행 조건이 충족된 경우에만 4장의 추가 업무로 착수한다.

# 2. 4주차 역할 목표

1. **8월 3일까지 3주차 Backend 기준선을 복구하고 제품·구독 조회·등록의 최소 API를 제공한다.**

   현재 Migration·Seed·OpenAPI·Runtime URL을 다시 대조하고, 발표에 사용할 고객·제품·구독 데이터가 실제 API로 조회되는 상태를 만든다.

2. **8월 4일까지 문의 생성 후 증상 제출·추가 입력 누적이 실제로 동작하게 한다.**

   고객 자연어 원문, 대표 증상, 구조화 입력, 추가 답변과 자가조치 결과를 동일 `inquiry_id`에 누적하고 `SUBMIT_SYMPTOM` 전이를 Runtime에 연결한다.

3. **8월 5일까지 대표 흐름에 필요한 State Machine Event와 Backend↔AI 최소 연동을 동결한다.**

   `allowed_actions`, `state_version`, `idempotency_key`, 상태 이력, AI 요청·응답 Schema 검증을 적용하고, 발표 기준 Commit에서 동일 흐름이 반복 재현되게 한다.

4. **8월 5일~6일에 케어 이력 등록·조회 최소 기능을 구현하고 발표 자료의 Backend 사실관계를 검수한다.**

   필터·카트리지 교체, 살균·세척 이력을 제품·구독 기준으로 누적하고, 김은진이 작성한 발표자료의 Endpoint 수·테이블 수·테스트 수·구현 상태가 실제 코드와 일치하는지 확인한다.

5. **8월 6일 중간 발표에서 Backend와 DB가 시연을 방해하지 않게 지원한다.**

   발표 직전 Migration·Seed·Health·인증·대표 문의 흐름을 Smoke Test하고, 실시간 시연 실패 시 사용할 요청·응답·DB 저장 증빙을 준비한다.

6. **8월 7일까지 발표 피드백과 병합 회귀를 반영하여 5주차 AI·상담 연동 진입 기준을 확정한다.**

   미구현 Event, 상담·방문 API, AI 실패·재시도·Fallback, Evidence 저장, 추적 로그를 Issue와 인계 문서로 정리한다.

4주차 완료 기준은 Model·Serializer·Service 파일이 존재하는 것이 아니다. **실제 URL이 등록되고, 인증된 요청이 Service를 거쳐 DB에 저장되며, 상태·권한·멱등성·오류 응답이 테스트로 증명되어야 한다.**

# 3. 4주차 필수 업무

## 3.1 3주차 Backend 기준선·Migration·Runtime 검증 증빙 복구

### 작업 목적

4주차 기능 개발 전에 현재 `main`의 Migration, Seed, Runtime URL, OpenAPI, Backend 검증 문서가 서로 일치하는지 확인한다. 3주차 종료 시 Data QA가 참조하던 Backend Runtime 검증 문서가 누락되어 김은진의 Data Pipeline이 실패했으므로, 실제 실행 결과에 근거한 안정적인 증빙을 다시 제공한다.

### 작업 위치

```text
backend/
├─ config/api_urls.py
├─ config/settings/**
├─ apps/*/migrations/**
├─ tests/migrations/**
├─ tests/database/**
└─ README.md

scripts/database/**
data/config/handoff/backend_import_crosswalk.json     # 김은진과 공동 검수

docs/testing/evidence/backend/**
docs/testing/results/week4-backend-baseline.md
```

### 세부 작업 지침

1. 발표 기준으로 사용할 Python·Django·DRF·PostgreSQL·pgvector 버전을 확인하고 `requirements/**`와 README에 고정한다.
2. 빈 PostgreSQL에서 전체 Migration을 적용하고 `showmigrations`, `makemigrations --check`, 핵심 Table 존재 여부를 확인한다.
3. Seed와 합성 Fixture Import를 실행하여 역할별 계정, 고객 제품, 구독, 문의, 케어 이력이 적재되는지 확인한다.
4. Seed와 Import를 2회 실행하여 Replay 또는 Upsert 정책이 예상대로 동작하는지 확인한다.
5. Runtime에 등록된 URL과 OpenAPI Operation을 대조한다. 계약만 있고 Runtime에 없는 Endpoint는 `OPENAPI_ONLY`, `PLANNED`, `NOT_IMPLEMENTED` 중 하나로 명시한다.
6. `/health`를 다음 두 의미로 분리한다.
   - Liveness: Django Process가 응답하는지 확인
   - Readiness: PostgreSQL 연결과 필수 Migration 상태를 확인
7. 기존 빈 `200 OK` Health를 발표 증빙으로 사용하지 않는다. Readiness 실패 시 `503`과 안전한 오류 코드를 반환한다.
8. 김은진과 협의하여 Backend Runtime 검증 문서를 개인 폴더가 아닌 안정 경로에 작성한다.
9. 문서에는 최소 다음 정보를 포함한다.
   - Commit SHA
   - 실행 환경
   - 실행 명령
   - Migration 결과
   - Seed·Import 결과
   - Runtime Endpoint 목록
   - 테스트 결과
   - 미구현·제한 사항
10. `backend_import_crosswalk.json`이 새 증빙 경로와 실제 Hash를 참조하도록 김은진에게 전달한다.
11. GitHub에 없는 `.gitignore` 파일은 전체 소스 ZIP과 로컬 환경에 존재하면 누락으로 판단하지 않는다. 다만 코드가 참조하는 파일이 Git과 ZIP 양쪽에 없으면 실제 누락으로 처리한다.
12. 실행 결과가 실패한 경우 문서만 PASS로 작성하지 않고 실패 원인과 차단 범위를 기록한다.

### 완료 기준

- 빈 PostgreSQL에서 전체 Migration이 성공한다.
- `makemigrations --check`가 변경 없음으로 종료된다.
- Seed·Fixture Import가 반복 실행 가능하다.
- Runtime URL과 OpenAPI의 구현 상태가 구분되어 있다.
- Liveness와 DB Readiness가 분리되어 동작한다.
- Backend Runtime 검증 문서가 실제 실행 결과를 포함한다.
- Data QA Crosswalk가 존재하는 파일과 일치하는 Hash를 참조한다.
- 다른 팀원이 README 절차로 동일 기준선을 재현할 수 있다.

### 산출물

- 최신 Migration·Seed 검증 결과
- Liveness·Readiness Endpoint
- Runtime–OpenAPI 구현 상태표
- `week4-backend-baseline.md`
- Backend Runtime 증빙과 Crosswalk 전달 자료
- 4주차 Backend 기준선 Commit 또는 PR

## 3.2 제품·구독 조회·등록·수정 최소 API 구현 (`T-018`)

### 작업 목적

고객 문의와 케어 이력이 실제 고객 제품·구독 정보에 연결되도록 한다. 화면에서 임의 모델명을 보내거나 AI가 추정한 모델을 신뢰하지 않고, Backend가 고객 소유권과 MVP 지원 모델을 검증하여 이후 AI·RAG 실행 여부를 결정한다.

### 작업 위치

```text
backend/apps/products/
├─ api/{urls,views,serializers}.py
├─ models/**
├─ services/{product_service,product_validation_service}.py
├─ repositories/product_repository.py
└─ permissions.py

backend/apps/subscriptions/
├─ api/{urls,views,serializers}.py
├─ services/subscription_service.py
├─ repositories/subscription_repository.py
└─ permissions.py

backend/tests/unit/products/**
backend/tests/unit/subscriptions/**
backend/tests/api/products/**
backend/tests/api/subscriptions/**
contracts/api/**/products*
contracts/api/**/subscriptions*
```

### 세부 작업 지침

1. 최소 Endpoint는 다음 범위로 제한한다.
   - 고객 본인 구독 제품 목록 조회
   - 구독 제품 상세 조회
   - 합성 고객 제품 등록
   - 사용 시작일·관리 유형 등 허용 필드 수정
2. 제품 Catalog와 고객 소유 제품을 분리한다. 고객이 요청 Body로 임의 제품 Catalog Row를 생성하게 하지 않는다.
3. MVP 지원 모델은 `WPUJAC104DWH`로 고정하고, 매뉴얼 적용 모델·세대·Revision을 검증한다.
4. `WPUIAC425SNW`, WPU-IAC506 `removed_legacy`, JAC104 S세대 등 차단·확장 모델은 MVP 문의에서 사용되지 않게 한다.
5. 고객은 본인 제품·구독만 조회·수정할 수 있게 QuerySet 단계에서 소유권을 제한한다.
6. 다른 고객의 `public_id` 접근은 존재 여부를 숨기기 위해 `404`를 반환한다.
7. 역할 부족은 `403`, 미인증은 `401`, 미지원 제품은 계약된 업무 오류 코드로 구분한다.
8. 등록·수정 시 내부 정수 PK를 외부 응답에 노출하지 않고 `public_id`를 사용한다.
9. 날짜는 DB에 UTC로 저장하고 API에는 `+09:00`이 포함된 ISO 8601 또는 계약된 날짜 형식으로 반환한다.
10. 중복 제품 등록, 종료된 구독, 비활성 제품, 잘못된 관리 유형을 테스트한다.
11. 문의 생성 Service가 요청 Body의 모델명이 아니라 검증된 구독·제품 Row를 사용하게 한다.
12. 한예나·양정현에게 목록·상세·등록·수정의 정상·오류 예시 JSON을 전달한다.

### 완료 기준

- 고객 본인 제품·구독 목록과 상세 조회가 동작한다.
- 합성 제품 등록과 허용 필드 수정이 동작한다.
- 타 고객 제품 접근이 404로 차단된다.
- 미지원·차단 모델은 문의와 AI 실행 전에 차단된다.
- 제품·구독과 문의가 FK로 연결된다.
- OpenAPI·Serializer·실제 응답 필드가 일치한다.
- 정상·401·403·404·409·업무 오류 테스트가 있다.

### 산출물

- 제품·구독 최소 Runtime API
- 제품 지원 범위 검증 Service
- 객체 권한 Test
- OpenAPI·예시 JSON
- Web·Mobile 인계용 API 사용 문서

## 3.3 문의 증상 제출·추가 답변·자가조치 결과 누적 구현 (`T-022`)

### 작업 목적

현재 구현된 문의 생성·취소 다음 단계인 증상 제출을 실제 Runtime에 연결한다. 고객 자연어 원문, 대표 증상, 구조화 증상, 추가 답변과 자가조치 결과를 동일 문의에 누적하고, 기존 입력을 덮어쓰거나 유실하지 않게 한다.

### 작업 위치

```text
backend/apps/inquiries/
├─ api/{urls,views,serializers}.py
├─ models/{inquiry,inquiry_symptom,customer_input,action_result}.py
├─ services/{inquiry_service,symptom_service,input_accumulation_service,resolution_service}.py
├─ repositories/{inquiry_repository,symptom_repository,input_repository}.py
└─ permissions.py

backend/apps/questionnaires/
├─ models/{questionnaire_session,questionnaire_answer}.py
├─ services/questionnaire_service.py
└─ repositories/questionnaire_repository.py

backend/tests/unit/inquiries/**
backend/tests/api/inquiries/**
backend/tests/integration/inquiry-flow/**
contracts/api/**/inquiries*
```

### 세부 작업 지침

1. 3주차에 Placeholder로 남은 다음 파일을 실제 코드로 구현하거나 불필요한 경우 삭제·통합한다.
   - `symptom_submission.py`
   - `inquiry_transition_service.py`
   - `resolution_service.py`
   - `followup_answer.py`
2. 최소 Endpoint는 다음을 포함한다.
   - 문의 증상 제출
   - 추가 질문 답변 저장
   - 자가조치 결과 저장
   - 문의 입력 이력 조회 또는 현재 누적 상태 조회
3. 증상 제출 시 고객 소유 문의인지, 문의가 수정 가능한 상태인지, 제품이 MVP 지원 범위인지 검증한다.
4. 고객 최초 자연어 원문은 수정본·구조화 결과와 별도 저장한다. AI 결과가 고객 원문을 덮어쓰지 않게 한다.
5. 대표 증상 선택값과 자유 입력을 모두 저장하고, 둘 중 하나만 필수인지 계약에 맞춰 검증한다.
6. 추가 답변은 질문 ID·답변 값·작성자·작성 시각·상태 버전을 함께 기록한다.
7. 자가조치 결과는 조치 코드, 고객 결과, 해결 여부, 추가 상담 필요 여부를 저장한다.
8. 동일 `Idempotency-Key`와 동일 Payload는 기존 응답을 Replay하고, 같은 Key에 다른 Payload는 `409`로 차단한다.
9. `state_version`이 오래된 요청은 상태 충돌로 처리한다.
10. `SUBMIT_SYMPTOM` 성공 시 계약된 다음 상태로 전이하고 상태 이력을 같은 Transaction에 저장한다.
11. 필수값 누락·지원 모델 불일치·차단 모델·취소된 문의·타 고객 문의는 AI 호출 전에 차단한다.
12. 일부 DB 저장 후 AI 호출 실패가 발생해 데이터와 상태가 모순되지 않도록 Transaction 경계를 정한다.
13. AI 호출 전 저장할 데이터와 AI 성공 후 저장할 데이터를 분리한다.
14. 상담사·기사·운영자가 고객 원문을 조회할 수 있는 범위는 역할·화면 요구사항에 맞게 제한한다.
15. 대표 시나리오 `DEMO-INQ-002`로 생성→증상 제출→추가 답변→자가조치 결과 저장을 재현한다.

### 완료 기준

- 실제 Runtime URL로 증상 제출이 동작한다.
- 동일 문의에 고객 원문·대표 증상·추가 답변·자가조치 결과가 누적된다.

## 3.4 State Machine Event API Runtime 확장 (`T-023`)

### 작업 목적

3주차에 구현한 State Machine Engine과 계약을 실제 업무 API에 연결한다. 계약 파일에 Event가 존재하는 것만으로 완료 처리하지 않고, 대표 문의 흐름의 Event가 권한·가드·동시성·멱등성 검증을 거쳐 DB 상태와 이력을 변경하게 한다.

### 작업 위치

```text
backend/apps/workflow/
├─ api/{urls,views,serializers}.py
├─ services/{state_machine_service,transition_service,allowed_action_service}.py
├─ repositories/{workflow_repository,state_history_repository}.py
├─ guards/**
└─ models/**

backend/apps/inquiries/services/inquiry_transition_service.py
backend/common/contracts/**
backend/tests/unit/workflow/**
backend/tests/integration/workflow/**
backend/tests/integration/idempotency/**
backend/tests/integration/concurrency/**
contracts/state-machine/**                  # 윤승혁 주관할, 변경 시 승인 필수
contracts/error-codes/**
```

### 세부 작업 지침

1. 4주차 발표 전 필수 Event를 다음 범위로 제한한다.
   - `START_INQUIRY`
   - `SUBMIT_SYMPTOM`
   - AI 결과에 따른 `SAFE_GUIDANCE_READY`, `DANGER_DETECTED`, `NO_EVIDENCE`, `PRODUCT_VALIDATION_FAILED`
   - 고객의 `REQUEST_CONSULTATION`
   - `CANCEL_INQUIRY`
2. `START_CONSULTATION`, 방문 일정, 완료·재개·최종 종료 전체 Event는 5주차 인계 대상으로 둘 수 있다. 단, 계약과 Runtime 상태표에 미구현을 명확히 표시한다.
3. Event API는 다음 입력을 공통으로 검증한다.
   - `inquiry_id`
   - Event
   - `state_version`
   - `idempotency_key`
   - 수행자 역할
   - 담당자 또는 소유권
   - Event별 Payload Guard
4. 응답에 현재 상태, 새 `state_version`, 현재 담당 주체, 고객 행동 필요 여부, `allowed_actions`를 포함한다.
5. 허용되지 않은 Event는 상태 충돌 또는 업무 오류로 처리하고, 잘못된 역할은 403으로 처리한다.
6. 다른 고객·미배정 담당자의 개별 리소스 접근은 404로 처리한다.
7. 상태 변경과 상태 이력·감사 이벤트·멱등성 기록을 하나의 Transaction으로 처리한다.
8. 동일 요청 Replay와 다른 Payload Conflict를 구분한다.
9. 동시에 같은 `state_version`으로 두 요청이 들어오면 하나만 성공하고 나머지는 409가 되게 한다.
10. AI 응답이 요청했다고 해서 상태를 바로 변경하지 않는다. Backend가 AI JSON Schema·문의 상태·제품 검증·근거 상태를 확인한 뒤 Event를 선택한다.
11. `allowed_actions`는 코드에 별도 하드코딩하지 않고 승인된 State Machine 계약을 기준으로 계산한다.
12. 계약을 변경해야 할 경우 윤승혁에게 변경 사유와 영향 범위를 전달하고 `contracts/state-machine/**`를 먼저 또는 동시에 수정한다.
13. Web·Mobile이 화면 상태를 자체 추론하지 않도록 `allowed_actions`와 상태 Metadata 예시를 제공한다.
14. 최소 대표 흐름의 상태 이력에서 이전 상태, 다음 상태, Event, 수행자, 시각, `correlation_id`, `state_version`을 조회할 수 있게 한다.

### 완료 기준

- 발표 필수 Event가 실제 Runtime API에 연결된다.
- 허용 상태·역할·소유권·담당자에서만 Event가 수행된다.
- `state_version` 동시 충돌이 검증된다.
- `idempotency_key` Replay와 Conflict가 검증된다.
- 상태 변경·이력·감사·멱등성 기록이 Transaction으로 묶인다.
- 응답의 `allowed_actions`가 계약과 일치한다.
- AI가 상태를 직접 변경하지 않고 Backend 검증 후 Event가 선택된다.
- 구현·미구현 Event가 상태표에 구분되어 있다.

### 산출물

- State Machine Event Runtime API
- 대표 Event Guard·Transition Service
- 동시성·멱등성·권한 통합 Test
- 상태 이력 조회 증빙
- Runtime Event 구현 상태표
- Web·Mobile용 상태·행동 예시 JSON

## 3.5 Backend↔AI 최소 수직 연동과 결과 저장 (`T-025`, `T-026` 협업)

### 작업 목적

문의 증상 제출 후 Backend가 AI 서비스에 검증된 입력을 보내고, AI의 구조화 결과·추가 질문·근거·다음 행동을 검증하여 저장하는 최소 연결을 만든다. 이동윤의 AI 모듈과 Backend가 서로 다른 임시 Schema를 사용하지 않게 한다.

### 작업 위치

```text
backend/integrations/ai/
├─ client.py
├─ dto.py
├─ exceptions.py
├─ retry.py
└─ settings.py

backend/apps/inquiries/services/inquiry_ai_service.py
backend/apps/workflow/services/**
backend/apps/evidence/**
backend/apps/audit/**

contracts/ai/**                         # 이동윤 주관할, 최지용 부관할
contracts/api/components/schemas/evidence/**
backend/tests/integrations/ai/**
backend/tests/integration/backend-ai/**
tests/fixtures/ai/**
```

### 세부 작업 지침

1. 이동윤과 Backend 요청·응답 Schema의 버전과 필수 필드를 확정한다.
2. Backend 요청에는 최소 다음을 포함한다.
   - `inquiry_id`
   - 검증된 제품·세대·구독 정보
   - 고객 원문
   - 대표 증상
   - 누적 문진 답변
   - 관련 케어 이력 또는 조회 가능 식별자
   - `correlation_id`
   - Schema 버전
3. AI 응답에는 최소 다음을 검증한다.
   - 구조화 증상
   - 누락 정보 또는 추가 질문
   - 위험도
   - `usage_guidance_status`
   - 제한 기능
   - Evidence 참조
   - `next_action`
   - 상담 필요 여부
4. AI 응답의 내부 `source_path`, 전체 매뉴얼 원문, 검색용 `retrieval_text`가 고객 API에 그대로 노출되지 않게 한다.
5. AI Timeout, 연결 실패, JSON 파싱 실패, Schema 불일치, Evidence 부재를 구분한다.
6. 4주차에는 무제한 재시도하지 않는다. 짧은 Timeout과 제한된 재시도 횟수를 설정하고 실패 시 안전한 상태를 반환한다.
7. AI 호출 실패 시 문의를 잘못된 최종 상태로 변경하지 않는다. `PENDING_CONSULTATION` 또는 계약된 판단 보류 흐름을 윤승혁·이동윤과 확정한다.
8. AI 요청·응답 Metadata와 오류를 Audit 또는 AI 실행 이력에 저장하되 고객 원문 전체와 Prompt 전체를 로그에 남기지 않는다.
9. AI 성공 결과와 상태 전이의 Transaction 경계를 분리하고 중복 Callback·재시도를 고려한다.
10. 실제 AI 연결이 발표 시점에 불안정하면 계약된 Mock을 사용할 수 있으나, 발표자료와 응답 Metadata에 Mock임을 숨기지 않는다.
11. 실제 연결 결과와 Mock 결과를 같은 파일명·같은 수치로 덮어쓰지 않는다.
12. 대표 시나리오에서 다음 흐름을 확인한다.

```text
문의 생성
→ 증상 제출
→ Backend 제품·권한 검증
→ AI 요청
→ AI Schema 검증
→ 결과 저장
→ Backend 상태 전이
→ allowed_actions 반환
```

### 완료 기준

- Backend↔AI 요청·응답 Schema 버전이 일치한다.
- 실제 또는 명시된 Mock AI 호출이 Backend Service에서 수행된다.
- AI 응답이 Schema 검증 후 저장된다.
- Timeout·연결 실패·Schema 오류가 구분된 오류와 안전한 상태로 처리된다.
- AI가 DB 상태를 직접 변경하지 않는다.
- Evidence 내부 필드와 고객 공개 필드가 분리된다.
- 요청·결과·오류가 `correlation_id`로 추적된다.
- 대표 문의의 최소 수직 흐름이 반복 재현된다.

### 산출물

- Backend AI Client·DTO·예외 처리
- AI 요청·응답 저장 Service
- 실제·Mock 구분 실행 결과

## 5.4 Backend·DB 역할 수행 시 주의사항

- Model·Migration·파일 존재를 Runtime 기능 완료로 계산하지 않는다.
- View에서 복잡한 ORM Query·상태 전환·AI 호출을 직접 구현하지 않는다.
- Serializer에서 DB Transaction이나 외부 AI 호출을 수행하지 않는다.
- Model `save()`에서 업무 상태 변경이나 외부 호출을 수행하지 않는다.
- Repository는 조회·저장에 집중하고 역할·상태 판단은 Service·Guard에서 수행한다.
- 화면과 AI가 상태를 직접 변경하게 하지 않고 Backend Event API를 사용한다.
- AI 응답을 신뢰하기 전에 JSON Schema·제품 범위·상태·근거를 검증한다.
- `contracts/state-machine/**` 변경은 윤승혁, `contracts/ai/**` 변경은 이동윤과 협의한다.
- `tests/**`, `.github/workflows/**`, `data/**` 변경은 김은진과 협의한다.
- 내부 정수 PK를 외부 API에 노출하지 않는다.
- 타 사용자 리소스 존재 여부를 권한 오류로 노출하지 않는다.
- 중복 요청과 동시 수정 충돌을 단순 마지막 저장 승리 방식으로 처리하지 않는다.
- AI Timeout이나 오류를 일반 성공 응답으로 위장하지 않는다.
- 고객 원문·Token·주소·전화번호·Prompt 전체를 로그에 기록하지 않는다.
- 발표를 위해 실패 Test를 삭제하거나 검증을 우회하지 않는다.
- `.gitignore` 파일이 GitHub에 없다는 이유만으로 누락으로 판단하지 않는다. 전체 소스와 실행 환경을 기준으로 확인한다.
- 기능 개수보다 **실제 호출, 권한, 상태, 이력, 멱등성, 재현 가능한 실행 증거**를 우선한다.
