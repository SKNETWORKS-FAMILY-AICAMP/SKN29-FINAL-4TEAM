# WaterBridge P1-A 구현·인계 지침

## 0. PM 승인 범위

**담당자: 윤승혁**

### 작업 내용

P1-A의 범위를 다음과 같이 고정한다.

```text
합성 계약고객
→ 계약정보 확인
→ 계약 이메일 OTP
→ WaterBridge ID/PW 생성
→ CustomerAccountLink
→ JWT
→ 일반 로그인
→ 아이디 찾기
→ 비밀번호 재설정
→ 마이페이지
→ 기존 문의/AI 기능 진입
```

다음은 제외한다.

```text
카카오 로그인               → P1-B HOLD
실고객 계약 원장             → NO-GO
실고객 개인정보              → NO-GO
이메일 변경 자동화           → 제외
공용/중복 이메일 자동 연결    → 제외
명의/계약 변경                → 제외
```

승인요청서도 P1-A를 최소 수직 기능으로 정의하고 있으며 P1-B는 선택 기능으로 분리하고 있다.

# 1. 합성 계약고객 Fixture 준비

**주 담당: 김은진**
**협업: 최지용**

이 단계에서는 회원가입 기능부터 만들지 않는다. 먼저 **가입 대상으로 사용할 합성 계약고객 1건**을 확정한다.

## 작업 내용

최소 Fixture:

```text
합성 고객
SYN-CUSTOMER-P1-001

합성 활성 계약
SYN-CONTRACT-P1-001

합성 계약 이메일
customer-p1-001@waterbridge.invalid

활성 구독
→ WPU-JAC104 계열

기존 WaterBridge Account Link
→ 없음
```

실제 사용자 이메일을 DB에 넣지 않는다.

계약 DB에는 `.invalid` 이메일만 존재하고, 실제 메일 발송 단계에서 개발용 시험 메일함으로 Redirect한다.

## 작업 파일

기존 Seed 구조:

```text
backend/apps/accounts/management/commands/seed_demo_accounts.py
backend/apps/subscriptions/management/commands/seed_demo_subscriptions.py
```

두 Seed 파일은 현재 존재한다.

기존 Demo Seed와 P1-A Fixture를 섞지 않으려면 신규 명령을 권장한다.

```text
[신규 권장]
backend/apps/accounts/management/commands/
    seed_p1_account_link_fixture.py
```

필요한 경우 구독 Fixture도 별도 분리:

```text
[신규 권장]
backend/apps/subscriptions/management/commands/
    seed_p1_account_link_subscription.py
```

## 검증

확인 항목:

```text
[ ] 실고객 개인정보 0건
[ ] 계약 이메일은 .invalid
[ ] 활성 계약 1건
[ ] 활성 구독 연결
[ ] product_model 연결
[ ] 중복 계약 이메일 없음
[ ] 기존 Account Link 없음
```

## 완료 후 인계

**김은진 → 최지용**

전달:

```text
customer_code
contract_no
subscription 식별 기준
product_model
합성 계약 이메일 규칙
Fixture 생성 방법
Fixture 초기화 방법
```

비밀번호·실제 시험 이메일 주소·AWS Secret은 문서에 넣지 않는다.

**다음 착수자:** 최지용



# 4. 회원가입·OTP·일반 로그인·계정복구 Backend 구현

**담당자: 최지용**



## 신규 권장 Service

```text

```

필요하다면:

```text

    customer_account_link_repository.py

```

## 구현 순서

### A. 계약 확인

```text
customer_code + contract_no
→ 계약 후보 조회
→ 활성 계약 검증
→ masked_email 반환
```

존재 여부 공격을 방지하기 위해 실패 응답을 가능한 한 동일화한다.

### B. OTP 발급

정책:

```text
6자리 이상 CSPRNG
5분 만료
최대 실패 5회
재발송 60초
새 OTP 생성 → 이전 OTP 폐기
OTP 평문 저장 금지
```

### C. OTP 확인

성공하면:

```text
claim_ticket
```

발급.

claim_ticket은:

```text
단회성
짧은 만료
목적 고정
계약 후보 고정
```

이어야 한다.

### D. 회원가입

하나의 Transaction:

```text
claim_ticket 소비
→ User 생성
→ CustomerAccountLink
→ UserConsent
→ AccountLinkEvent
→ 마지막 JWT 발급
```

### E. 일반 로그인

기존 Django Password Hasher와 JWT를 재사용한다.

```text
username
password
→ User
→ password verify
→ active AccountLink
→ JWT
```

### F. 아이디 찾기

```text
계약정보
→ 계약 이메일 OTP
→ masked username
```

### G. 비밀번호 재설정

```text
계약정보
→ OTP
→ claim_ticket
→ 새 password
→ auth_version 증가
→ 기존 세션 폐기
```

요청서에서도 비밀번호 재설정 시 `auth_version` 증가를 요구한다.

# 5. CustomerAccountLink 기반 Owner Resolver 전환

**담당자: 최지용**

P1-A에서 상당히 중요한 작업이다.

기존:

```text
User
→ CustomerProfile.user
```

중심 접근을 점진적으로:

```text
JWT User
→ CustomerAccountLink
→ Customer
→ Subscription
→ Inquiry / Visit
```

로 전환한다.

## 주요 작업 경로

Accounts:

```text
backend/apps/accounts/repositories/**
backend/apps/accounts/permissions.py
```

Subscription 구조:

```text
backend/apps/subscriptions/permissions.py
backend/apps/subscriptions/repositories/**
backend/apps/subscriptions/services/**
backend/apps/subscriptions/api/**
```

실제 Subscription 앱에 `permissions`, `repositories`, `services`, `api`가 각각 존재한다.

문의:

```text
backend/apps/inquiries/permissions.py
backend/apps/inquiries/services/customer_inquiry_service.py
backend/apps/inquiries/repositories/**
```

방문:

```text
backend/apps/visits/**
```

## 반드시 검증할 것

A 계정에 연결된 고객이 B 고객 UUID를 직접 요청해도:

```text
403 또는 existence-hiding 404
```

여야 한다.

다음 API들이 같은 Owner Resolver를 사용해야 한다.

```text
/me
/me/subscriptions
/me/subscriptions/{id}
/me/inquiries/{id}
/visit 관련 고객 조회
```

## 완료 후 인계

**최지용 → 양정현**

전달:

```text
회원가입 완료 후 조회 가능한 API
/me 응답
/subscriptions 응답
타 고객 접근 기대 상태
```

**최지용 → 이동윤**

전달:


# 공통 인계 규칙

모든 담당자는 다른 담당자에게 작업을 넘길 때 아래 6개를 반드시 같이 전달한다.

```text
1. Commit SHA
2. 변경 파일 목록
3. 무엇을 구현했는지
4. 실행/테스트 명령
5. 실제 테스트 결과
6. 남아 있는 제한사항 또는 Blocker
```

예:

```text
[최지용 → 양정현 P1-A Backend 인계]

Commit:
xxxxxxxx

구현:
- 계약 확인
- OTP 발급/검증
- Signup
- Normal Login
- Username Recovery
- Password Reset

계약:
contracts/api/paths/auth.yaml

검증:
xx passed

실행 조건:
POSTGRESQL 필요
메일 Redirect 필요

제한:
실고객 Runtime NO-GO
Kakao 미지원
```

**Secret, OTP 원문, 실제 이메일, JWT 값은 절대 인계 문서에 기록하지 않는다.**
