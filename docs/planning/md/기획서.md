# 1. 프로젝트 주제

## 1-1. 프로젝트 개요

| 구분 | 내용 |
|---|---|
| 프로젝트명 | 정수기 구독 고객 케어 및 A/S 업무 지원 시스템 |
| 서비스명 | WaterBridge |
| 연계 기업 | SK인텔릭스, SK인텔릭스서비스 |
| 핵심 MVP 사용자 | 합성 계약 고객, 고객센터 상담사 |
| P1 사용자 | 방문기사, 서비스 운영 담당자 |
| 데이터·평가 판매 코드 | `WPUJAC104DWH`, `WPUIAC425SNW`, `WPUIAC606SNW` |
| Public Runtime 활성 | 현행 계약상 `WPUJAC104DWH`만 `INDEXED_MVP`. `WPUIAC425SNW`·`WPUIAC606SNW`는 Activation Gate 전까지 `CONTRACT_BLOCKED_NOT_INDEXED` |
| 검색 정책 | 정확 판매 코드 선필터, 승인 공식 문서만 사용, 교차 모델 fallback 금지 |
| 제외 모델 | `WPU-IAC506` 및 모델이 확인되지 않은 자료 |
| 대표 검증 | 계약 고객 인증 → 증상 입력 → Safety-first AI/RAG → 상담 Handoff → 상담 결과 고객 재조회 |

## 1-2. 주제 정의

> 합성 계약 고객이 정수기 증상을 한 번 입력하면, WaterBridge가 위험도를 먼저 판정하고 정확한 제품의 공식 문서 근거만으로 안전한 다음 행동을 안내한다. 상담이 필요할 때는 문진·고객 조치·위험·근거·AI 결과를 구조화해 상담사에게 인계하고, 상담 결과를 고객 앱에서 다시 확인하게 하는 업무지원 시스템이다.

단순 챗봇이 아니라 고객 입력이 상담 단계로 넘어갈 때 맥락이 손실되지 않도록 하는 **Safety-first 상담 인계 시스템**을 목표로 한다.

## 1-3. 핵심 서비스 범위

### P0 핵심 MVP

- 합성 계약 고객의 계약 정보 확인, 계약 이메일 OTP, ID/PW 가입과 계정 연결
- JWT 로그인, 아이디 찾기, 비밀번호 재설정, 마이페이지와 기존 문의 진입
- 고객 앱의 구독·제품 조회, 증상 입력, 추가 문진과 고객 조치 기록
- 생성 전 위험도 판정과 정확 판매 코드 기반 공식 문서 RAG
- 검증된 일반 문의의 안전 안내, 주의 문의의 사전 사람 검토, 위험·근거 부재·검증 실패의 상담 전환
- 상담 Handoff v2 생성과 상담사용 Web의 문의·근거·조치 확인
- 상담 결과와 현재 상태의 고객 앱 재조회
- 상태·권한·멱등성·감사 이력과 Trace 연계

### P1 확장

- 방문기사 배정·일정·현장 점검·완료·후속 확인 흐름
- 방문기사용 모바일/태블릿 화면과 사전 점검 리포트
- 운영 대시보드, 지연·예외·처리 현황 집계
- 일반 API 성능, 반응형, 규칙·Prompt 유지보수성, 제한된 관리자 권한 위임과 본인 프로필

### 장기 확장

- 실제 고객·실제 개인정보 기반 운영 전환
- 사내 IAM·SSO와 소셜 로그인
- 외부 CRM·실제 SMS·카카오 알림톡·푸시 연동

### 제외·제약

- 실제 개인정보와 실제 계약 고객을 사용하지 않는다.
- 결제·해지·환불, 기사 자동 배정, 외부 알림은 핵심 MVP에서 제외한다.
- AI는 고장을 확정 진단하거나 제품 분해·부품 교체 등 위험한 직접 수리를 안내하지 않는다.
- 문서·테스트 골격이 있다는 이유만으로 구현 또는 운영 검증 완료로 판정하지 않는다.

## 1-4. 대표 이용 시나리오

1. 합성 계약 고객이 계약번호·고객명 등 계약 정보를 확인하고 계약 이메일로 OTP를 검증한다.
2. 고객이 ID/PW 계정을 만들고 자신의 계약·구독 정수기를 연결한다.
3. 고객이 지원 제품을 선택하고 증상을 자연어로 입력한다.
4. AI가 필요한 추가 질문을 수집하고 생성 전에 위험도를 판정한다.
5. 시스템이 정확 판매 코드로 공식 문서를 제한 검색하고 근거·안전·출력 구조를 검증한다.
6. 일반 문의는 검증된 안내를 제공한다. 주의 문의는 `PRE_SEND` 사람 검토를 거치며, 위험·근거 부재·검증 실패는 fail-closed로 상담 전환한다.
7. 상담이 필요하면 증상·문진·고객 조치·위험·근거·AI 결과를 Handoff v2로 생성한다. 요약 합성 실패 시에도 고정 Schema fallback을 제공한다.
8. 상담사가 Web에서 인계 내용을 확인하고 상담 결과를 기록한다.
9. 고객이 앱에서 상담 결과와 현재 문의 상태를 확인한다.

방문기사 배정부터 현장 완료까지의 흐름은 P1 검증 시나리오로 분리한다.

# 2. 문제 정의

## 2-1. 핵심 문제

> 고객이 입력한 제품·증상·문진·조치·위험 정보가 AI 안내와 상담 사이에서 끊기면 같은 질문과 수동 검색이 반복되고, 잘못된 모델 근거 또는 위험한 안내가 고객에게 노출될 수 있다.

| 사용자 | 현재 문제 | 업무·경험상 영향 |
|---|---|---|
| 고객 | 제품에 맞는 안전한 행동과 상담 필요 여부를 스스로 판단하기 어렵고, 상담 시 같은 내용을 반복한다. | 불안, 반복 설명, 위험한 자가조치 가능성 |
| 상담사 | 제품·문진·고객 조치·AI 근거를 여러 화면과 문서에서 다시 확인한다. | 상담 준비 지연, 필수 정보 누락, 응대 편차 |
| QA·운영 | AI가 어떤 제품 문서와 위험 규칙을 사용했는지 추적하기 어렵다. | 모델 혼입·근거 부재·안전 오류의 재현과 감사 어려움 |
| 방문기사(P1) | 상담 결과가 구조화되지 않으면 현장에서 재확인이 필요하다. | 준비 누락과 점검 시간 증가 가능성 |

## 2-2. 해결 방향

```text
Before
고객 설명 → 상담사 재질문 → 매뉴얼 수동 검색 → 결과 단절

After
계약·제품 확인
→ 증상·문진·고객 조치 누적
→ 생성 전 위험 판정
→ 정확 모델 공식 근거 검색
→ 안전 안내 또는 상담 전환
→ Handoff v2
→ 상담 결과 고객 재조회
```

핵심은 답변을 길게 만드는 것이 아니라, 동일한 `inquiry_id`와 검증된 구조로 **제품·증상·위험·근거·조치·결과를 보존**하는 것이다.

## 2-3. 프로젝트 목표

- 정확한 계약·제품 맥락을 고객 문의와 끝까지 연결한다.
- 위험 판단을 생성보다 먼저 수행하고 불확실하면 상담으로 전환한다.
- 정확 판매 코드와 승인 문서만 사용해 다른 모델의 근거 혼입을 차단한다.
- 상담 Handoff의 필수 정보를 고정 Schema로 전달하고 결과를 고객에게 환류한다.
- 상태 변경, 사람 검토, AI 실행과 근거 사용을 추적 가능하게 기록한다.

# 3. 시장조사 및 BM 분석

## 3-1. 시장조사 범위

| 범주 | 조사 대상 | 적용 관점 |
|---|---|---|
| 렌탈·구독 고객지원 | 정수기 제품·관리·자가점검·상담/A/S 접점 | 기존 고객 접점을 대체하지 않고 사전 문진과 상담 인계를 보강 |
| 상담 업무 솔루션 | Case, 상담 요약, 업무 이력, 사람 검토 | 고정 Handoff Schema와 상태 이력으로 핵심 기능을 경량 구현 |
| AI·RAG | 자연어 구조화, 검색·인용, 사람 전환 | 공식 문서 제한, 안전 우선, 모델 격리와 fail-closed를 애플리케이션에서 통제 |

## 3-2. 핵심 차별점

1. 검색 전에 계약에 연결된 정확 판매 코드로 문서를 제한한다.
2. 생성 전에 위험을 판단하고, 결과를 보내기 전 사람 검토가 필요한 범위를 분리한다.
3. 고객 입력을 상담 Handoff v2로 재사용해 상담사가 다시 조립하는 일을 줄인다.
4. AI 답변만 보여주는 것이 아니라 상담 결과와 현재 상태를 고객에게 돌려준다.
5. 근거·상태·사람 검토·Correlation/Trace 식별자를 연결해 재현 가능한 QA를 지향한다.

## 3-3. BM 정의

WaterBridge는 소비자 대상 유료 챗봇이 아니라 고객센터와 서비스 운영 조직을 위한 B2B 업무지원 시스템이다.

| 대상 | 제공 가치 |
|---|---|
| 구독 고객 | 제품에 맞는 안전한 다음 행동, 상담 전환, 상담 결과 확인 |
| 상담사 | 제품·증상·문진·조치·위험·근거가 채워진 구조화 인계 |
| QA·운영 조직 | 근거·검토·상태·오류를 연결한 감사와 회귀 검증 |
| 방문기사(P1) | 상담 결과를 재사용한 사전 점검 정보 |
| 도입 결정자 | 상담 품질 표준화와 검증 가능한 AI 적용 범위 |

## 3-4. 기대 가치와 검증 지표

아래 수치는 성과 확정값이 아니라 검증 목표다. 실제 운영 데이터 확보 전 절감률이나 정확도 달성을 주장하지 않는다.

| 영역 | 기대 가치 | 검증 지표 |
|---|---|---|
| 고객 | 반복 설명과 다음 행동의 불확실성 감소 | 동일 정보 재입력 횟수, 상담 결과 확인 성공률 |
| 상담 | 사전 확인·문서 검색·요약 부담 감소 | Handoff 필수값 충족률, 재질문 수, 근거 확인 시간 |
| 안전 | 위험 안내와 근거 없는 안내 차단 | 위험 오분기, 금지 조치 생성, fail-closed 성공률 |
| 검색 | 제품별 공식 근거 격리 | 정답 근거 포함률, 교차 모델 누출률, 무근거 보류율 |
| 운영 | 상태와 오류 추적 가능성 향상 | 상태 이력 완전성, Correlation/Trace 연결률 |

# 4. 시스템 구성 기획

## 4-1. 논리 아키텍처

```text
고객 Mobile ───────────────┐
                           ↓
상담사 Web ───────→ Backend API·업무 권한/상태
                           │
                           ├─ 계약 고객 인증·CustomerAccountLink·JWT
                           ├─ Inquiry/Consultation·멱등성·감사 이력
                           ├─ EvidenceCardDTO·allowed_actions 조립
                           └─ W3C Trace Context·correlation_id
                                      ↓
                              AI 서비스
                           위험 판정 → 구조화 → 정확 모델 검색
                           → 근거/출력 검증 → 안내 또는 Handoff
                                      ↓
                 외부 PostgreSQL/RDS·pgvector · trace-store
```

Backend가 인증, 객체 권한, 상태, 트랜잭션과 최종 저장을 책임진다. AI는 구조화·검색·생성·검증 결과만 반환하며 업무 상태와 DB를 직접 변경하지 않는다. Web·Mobile은 Backend Public API만 호출하고 Backend가 반환한 `allowed_actions`를 따른다.

## 4-2. 핵심 구성 요소

| 구성 요소 | 주요 역할 |
|---|---|
| 고객 Mobile | 계약 고객 인증, 제품·증상 입력, AI 안내, 상담 결과·상태 조회 |
| 상담사 Web | 상담 대기·상세 조회, Handoff·근거 확인, 상담 결과 기록 |
| Backend | 인증·권한·상태·멱등성·트랜잭션·Handoff 저장·화면 DTO 조립 |
| AI | 위험 판정, 증상 구조화, 정확 모델 RAG, 생성·검증, Handoff 합성 |
| Human Review | 주의 결과의 approve/edit/reject와 검토 Ledger 기록 |
| 업무 DB/Vector | 계약·계정 연결·문의·상담·상태·근거 및 임베딩 저장 |
| trace-store | Backend→AI 및 AI 내부 구간 Trace의 영속 저장·조회 |

## 4-3. Safety/HITL 정책

| 분류 | 처리 원칙 |
|---|---|
| 일반 | 근거·구조·안전 검증을 모두 통과한 결과만 자동 전송 |
| 주의 | 고객 전송 전 `PRE_SEND` 사람 검토; approve/edit/reject를 원본과 함께 기록 |
| 위험 | 자가조치 생성보다 사용 제한·상담 전환 우선 |
| 근거 없음 | 다른 모델 문서로 대체하지 않고 상담 전환 또는 fail-closed |
| 검증 실패·시스템 오류 | 위험도로 위장하지 않고 별도 오류로 기록; 입력 보존 후 재시도/상담 fallback |

Human Review는 Row Lock, `state_version`, `Idempotency-Key`를 사용해 중복 승인과 덮어쓰기를 방지한다.

## 4-4. 상담 Handoff v2

상담이 필요한 경우에만 생성하며 다음을 포함한다.

- 고객 입력 증상과 구조화 결과
- 추가 문진 질문·답변
- 고객이 수행한 조치와 조치 후 상태
- 위험도와 사용 제한
- 공식 근거 카드와 적용 문서·페이지
- AI 안내·검증 결과
- 시스템 오류와 안전 위험의 구분

요약 LLM 호출이 실패해도 기존 입력을 버리지 않고 고정 Schema fallback으로 상담사가 확인할 수 있게 한다.

## 4-5. 상태·동시성·오류 원칙

- 상태 변경은 Backend State Machine과 계약의 `state_version`을 따른다.
- Mutation은 `Idempotency-Key`로 중복 실행을 방지한다.
- 409 충돌 시 기존 입력을 덮어쓰지 않고 최신 상태·버전·허용 행동을 다시 조회한다.
- AI나 Client가 다음 상태를 직접 지정하지 않는다.
- 화면에는 내부 원문·저장 경로·검색 점수·Prompt·Vector 식별자를 노출하지 않는다.

## 4-6. 배포·관측 구성

Production Compose 기준은 4개 Service Container다.

```text
web | backend | ai | trace-store
```

- Mobile APK와 외부 AWS RDS는 Container 수에 포함하지 않는다.
- ECR 애플리케이션 Image는 `web`, `backend`, `ai` 3개다.
- SemVer Tag 기반으로 GitHub Actions → AWS OIDC → ECR → SSM → `docker compose pull/up` → Health/Smoke → 이전 정상 Commit SHA Rollback 흐름을 사용한다.
- 일반 앱 시작 시 Django Migration을 자동 실행하지 않는다. Migration은 Plan·Backup·대상 DB·실행 주체를 확인한 별도 절차로 수행한다.
- `trace-store`는 수집뿐 아니라 재시작 후 영속 보존과 조회가 검증되어야 한다.

| 주체 | 담당 범위 |
|---|---|
| 규칙 | 위험 신호, 사용 제한, 금지 조치, 상태 Guard, 필수값·권한·멱등성 |
| RAG | 정확 판매 코드에 대응하는 승인 공식 문서 검색과 근거 계보 반환 |

| 사람 | 주의 결과 전송 전 검토, 상담 결과와 방문 필요 여부 확정 |

## 5-3. 실행 구조

- 위험 판정, 구조화, 검색, 생성, 검증은 단계별 결과와 실패 원인을 분리한다.
- 기본 경로는 필요한 단계만 순차 실행하고, 상담이 불필요하면 Handoff 합성을 호출하지 않는다.
- 단계별 재시도는 기존 고객 입력과 상태를 보존하며 Backend의 멱등성·동시성 계약을 따른다.

## 5-4. 평가 계획

| 평가 영역 | 주요 지표·검증 내용 |

| 인증 | OTP 재사용·만료·시도 제한, 계약 이메일 불일치, 중복 계정 연결, JWT 권한 |
| 구조화 | 필수 필드 정확도, 누락 질문, 기존 답변 중복 질문 |
| 안전 | 위험 문의 오분기, 금지 조치·확정 진단 생성, PRE_SEND 우회 여부 |
| RAG | 정답 Evidence 포함률, 정확 판매 코드 필터, 교차 모델 누출, 근거 부재 처리 |
| 생성 | 근거 일치성, 이해 가능성, Schema 유효성, fallback 동작 |
| Handoff | 증상·문진·조치·위험·근거·AI 결과 필수값 완전성 |
| 상태 | 허용·금지 전이, `state_version`, 멱등성, 충돌·실패 후 부분 기록 없음 |
| 고객 환류 | 상담 결과·현재 상태 조회와 권한 격리 |
| 관측 | Backend→AI Trace 전파, `correlation_id` 연결, 민감정보 미기록 |

## 5-5. 검증 시나리오

### 기존 데이터 대표 회귀 기준

합성 데이터의 기존 대표 회귀는 `SYN-JAC104-002` / `DEMO-INQ-002`, 판매 코드 `WPUJAC104DWH`, 증상 `출수량 저하`, 사용설명서 38쪽 근거와 후속 확인까지의 계보를 유지한다. 이 기준은 데이터·상태 회귀용이며 방문 단계가 포함되더라도 현재 P0 핵심 MVP 범위를 확장하는 근거로 사용하지 않는다.

1. P1-A 합성 계약 고객이 OTP로 가입하고 계약·구독 제품을 조회한다.
2. 각 지원 판매 코드에 대해 같은 증상을 질의해 자기 모델 근거만 반환되는지 확인한다.
3. 위험·근거 부재·검색 실패 입력에서 자가조치가 생성되지 않는지 확인한다.
4. 주의 결과가 사람 검토 승인 전 고객에게 노출되지 않는지 확인한다.
5. 상담 전환 시 Handoff v2 필수값과 원문 보존, 합성 실패 fallback을 확인한다.
6. 상담사 결과 기록 후 고객이 동일 문의의 결과와 현재 상태를 조회하는지 확인한다.
7. 중복 요청과 409 충돌에서 상태·이력·멱등 행의 부분 기록이 없는지 확인한다.

현재 계약 고객 인증 Contract Test 증거가 있더라도 독립 QA G9와 고객→상담 수직 E2E G10이 완료되기 전에는 P1-A를 최종 완료로 판정하지 않는다.

코드 기준 `95f90f843124373fc97c6cd9e258b1427e0cbde8`의 보호형 Handoff 검증에서는 실제 AI Process→Backend HTTP→PostgreSQL 저장→상담 연결→상담사 API Projection→멱등 Replay가 통과했다. 이는 Handoff 구간 PASS이며 Web UI·실제 Provider·AWS·독립 QA와 전체 고객→상담→고객 서비스 E2E 완료를 뜻하지 않는다.

## 6-2. 수집·전처리·활성화 절차

1. 공식 자료의 출처·문서 버전·페이지 수·SHA-256을 기록한다.
2. 페이지 텍스트와 Source Span을 추출하고 정확 판매 코드를 부여한다.
3. 사람이 핵심 구간을 검수한 뒤 Parent/Child Chunk와 Evidence Group을 생성한다.
4. Schema·참조·중복·해시·결정성을 검증하고 Manifest로 인계한다.
5. Backend 적재와 AI `SELECT_ONLY` 조회를 별도로 검증한다.
6. 제품별 양성·음성 평가와 교차 모델 차단을 통과한 뒤 Runtime을 활성화한다.

## 6-3. 품질·법적 원칙

- 파싱 실패, 제품 불일치, 출처·페이지·필수 메타데이터 누락 자료는 검색에서 제외한다.
- 합성 데이터는 UI·상태·근거 검증에만 사용하며 실제 고장률·문의 빈도·성과 근거로 사용하지 않는다.
- 공식 PDF 원문은 Git에 넣지 않고 URL·버전·SHA-256·페이지·검수 기록만 관리한다.
- 실제 개인정보, 고객 원문 전체, Token, 비밀키를 Fixture·보고서·로그에 사용하지 않는다.
- 데이터 산출물 존재와 운영 적재·조회·정확도 검증 완료를 구분한다.

- 각 담당자는 자신의 Runtime·계약·테스트 증거를 함께 제시한다.
