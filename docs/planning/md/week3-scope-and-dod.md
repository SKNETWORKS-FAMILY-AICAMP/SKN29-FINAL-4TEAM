## 1. 문서 목적

이 문서는 3주차에 팀원 6명이 반드시 확보해야 하는 결과와 완료 판정 기준을 하나로 통일하기 위해 작성한다.

3주차의 목표는 고객·상담사·방문기사 전체 기능을 완성하는 것이 아니다. DB·Backend·AI/RAG·Web·Mobile이 다음 주부터 같은 계약과 같은 합성 데이터로 개발을 이어갈 수 있도록 다음 기반을 확보하는 것이 핵심이다.

- 실행 가능한 서비스·화면 기반
- API·AI·State Machine 공통 계약
- 검증된 데이터·합성 Fixture·검색 평가 기준
- 계약 기반 최소 화면과 Mock
- 정상·오류·권한·안전 검증 기준
- 7월 29일 공식 산출물 검토본
- 4주차에 착수할 수 있는 인계 조건

이 문서는 각 담당자의 3주차 업무 지침서를 대체하지 않는다. 개인 업무 지침서는 세부 구현 지침으로 사용하고, 본 문서는 **팀 공통 범위·우선순위·완료 판정 기준**으로 사용한다.

## 2. 3주차 운영 원칙

1. **7월 29일까지 검토 가능한 결과를 만든다.**  
   구현이 진행 중이라는 설명만으로는 부족하며, 실행 결과·계약 파일·Mock·Fixture·문서·테스트 중 담당 업무에 맞는 증거가 있어야 한다.

2. **7월 30일~31일에는 신규 필수 범위를 확대하지 않는다.**  
   계약 정합성 확인, 실제 연동 확인, 오류 수정, 공식 산출물 보완과 4주차 인계를 우선한다.

3. **계약을 구현보다 먼저 고정한다.**  
   `contracts/**`를 기계 검증 가능한 최종 기준본으로 사용하고, 계약 변경 PR을 해당 계약에 의존하는 구현 PR보다 먼저 병합한다.

4. **Mock과 실제 연동을 구분한다.**  
   Backend·AI가 준비되지 않은 경우 계약 기반 Mock으로 개발할 수 있으나, 이를 실제 API 연동 완료로 표시하지 않는다.

5. **완료 여부는 작업량이 아니라 재현 가능성으로 판단한다.**  
   담당자가 아닌 팀원이 실행·검토할 수 있어야 하며, 실행 방법과 결과물 경로가 남아 있어야 한다.

6. **P1과 후순위 기술을 3주차 필수 업무에 혼입하지 않는다.**  
   필수 업무와 리뷰 대응을 마친 뒤에만 조기 완료 시 추가 업무에 착수한다.

7. **미완료 상태를 숨기지 않는다.**  
   Mock, Stub, 미구현, 차단, 미측정, 수동 검증을 명시적으로 구분한다.

## 3. 3주차 공통 기준선

### 3.1 제품·문서·대표 시나리오

| 항목 | 공통 기준 |
|---|---|
| MVP 판매 코드 | `WPUJAC104DWH` |
| 적용 공식 매뉴얼 | `WPU-JAC104D·WPU-JCC104D REV.00` |
| 제품 세대 | D세대 |
| 대표 수직 검증 증상 | 출수량 저하 |
| 대표 합성 시나리오 | `SYN-JAC104-002` |
| 대표 문의 업무 코드 | `DEMO-INQ-002` |
| 대표 공식 근거 | 매뉴얼 38쪽 |
| 확장 전용 제품 | `WPUIAC425SNW` |
| 활성 범위 제외 제품 | IAC506 계열 |

출수량 저하, 물맛·냄새 이상, 제품 누수, 냉·온수 온도 이상은 P0 대표 증상 범위로 유지한다. 다만 3주차 수직 검증은 `WPUJAC104DWH / SYN-JAC104-002 / DEMO-INQ-002 / 출수량 저하 / 매뉴얼 38쪽` 흐름을 우선한다.

공식 근거가 충분하지 않은 증상은 억지로 정답 청크나 자가조치를 만들지 않고 `insufficient_evidence`, 근거 없음 또는 상담 필요 기대값으로 관리한다.

### 3.2 공통 코드·정책

| 구분 | 확정 기준 |
|---|---|
| 사용자 역할 | `CUSTOMER`, `CONSULTANT`, `TECHNICIAN`, `OPERATOR` |
| 위험도 | `general`, `caution`, `danger` |
| 사용 안내 상태 | `NORMAL`, `PARTIAL_STOP`, `TOTAL_STOP`, `PENDING_CONSULTATION` |
| 업무 DB 시간 저장 | UTC |
| API 일시 표현 | `+09:00`이 포함된 ISO 8601 |
| 내부 식별자 | 자동 증가 정수형 PK |
| 외부 API 식별자 | 공개 UUID `public_id` 또는 공개 `inquiry_id` |
| 업무·시연 식별자 | `inquiry_code`, `scenario_code`, `DEMO-*`, `SYN-*` |
| Access Token | 60분 |
| Refresh Token | 최초 발급 시점부터 7일, 재발급 시 만료 연장 없음 |
| 로그아웃 | 서버에서 Refresh Token 즉시 폐기 |
| 역할상 기능 권한 부족 | 403 |
| 타 사용자 소유·담당 리소스 접근 | 존재 여부를 숨기기 위해 404 |
| 상태 충돌 | 409 + 최신 `current_status`, `state_version`, `allowed_actions` |
| Backend↔AI 전체 Timeout | 30초 |
| AI 내부 재시도 | 최대 1회 |
| Backend AI 자동 재시도 | 0회 |
| Embedding | `BAAI/bge-m3` 원본 1024차원 |
| MVP Vector 검색 | Cosine 기반 Exact Search, HNSW·IVFFlat 미사용 |
| 기본 검색 결과 | Top-5 |
| 대표 P0 검색 합격 | 모든 대표 질의에서 정답 문서·페이지가 Top-5에 포함 |
| 모델·세대·문서 오염 | 허용 0건 |
| 합성 업무 데이터 기준본 | `data/synthetic/fixtures/**` |

### 3.3 책임 경계

- AI는 고객 입력 구조화, 위험 분류, 공식 문서 검색, 근거 참조와 권고 결과를 반환한다.
- AI는 문의 상태를 직접 변경하거나 상담·방문 결과를 확정하지 않는다.
- Backend는 권한 검증, 업무 데이터 저장, State Machine 실행과 최종 상태의 권위를 가진다.
- Web·Mobile은 상태·위험도·우선순위·다음 상태를 임의 계산하지 않는다.
- Web·Mobile의 행동 버튼은 Backend가 반환한 `allowed_actions`를 기준으로 표시한다.
- 고객·상담사·기사 화면에 노출되는 최종 EvidenceCard는 Backend가 공개를 허용한 필드만 사용한다.
- `chunk_id`, 내부 파일 경로, 검색용 원문 전체, Prompt, 내부 Trace는 사용자 화면에 노출하지 않는다.

- [ ] 환경변수·설치·실행·테스트 명령이 README, PR 또는 Issue에 기록되어 있다.
- [ ] 결과물의 저장소 상대 경로와 PR 또는 Commit이 존재한다.
- [ ] 담당자가 아닌 팀원이 실행·검토할 수 있다.
- [ ] 비밀값·실제 개인정보·Token·내부 Prompt가 코드·로그·Mock에 포함되지 않는다.

### 7.2 API·AI·State Machine 계약

- [ ] 401·403·404·409·422·5xx 의미가 계약과 구현에서 일치한다.

- [ ] 화면 공개 필드와 내부 전용 필드가 구분되어 있다.
- [ ] 계약 변경 내용이 `contracts/CHANGELOG.md`에 기록되어 있다.
- [ ] 해당 계약 주관 담당자가 변경을 검토했다.

### 7.3 Mock·Stub 기반 결과

Mock 또는 Stub으로 구현한 결과는 아래 조건을 충족할 때 `Mock 검증 완료` 또는 `기반 완료`로 판정한다.

- [ ] 실제 계약과 동일한 필드명·타입·코드값을 사용한다.
- [ ] 공통 합성 Fixture 기준본에서 생성되었거나, 오류 전용 Fixture임이 구분된다.
- [ ] 정상·위험·근거 없음·오류 중 필요한 대표 상태가 준비되어 있다.
- [ ] 로딩·빈 상태·오류 상태를 구분한다.
- [ ] Stub·미구현 Stage·임시 Endpoint가 명확히 표시되어 있다.
- [ ] 실제 API와 다른 필드·경로·동작을 별도 목록으로 기록한다.
- [ ] 실제 서비스 연동 완료로 표시하지 않는다.

### 7.4 데이터·문서·테스트

- [ ] 예시 문구가 아니라 실제 파일·Schema·테이블·처리 건수가 반영되어 있다.
- [ ] 원본·입력·출력·검증 결과의 저장 경로가 기록되어 있다.
- [ ] 출처·제품·세대·버전·페이지·해시·검증 상태 등 필수 메타데이터가 유지된다.
- [ ] 미측정 값과 미확인 결과를 임의로 채우지 않는다.
- [ ] 실패·경고·제외 건수와 원인 레코드가 확인 가능하다.
- [ ] 재실행 또는 재검토 방법이 기록되어 있다.
- [ ] 테스트 Case에 입력·선행 상태·실행 단계·기대 결과·증빙 위치가 있다.
- [ ] 미구현·차단 Case가 통과로 표시되지 않는다.
- [ ] 관련 담당자의 검토 흔적이 Issue, PR 또는 검토 문서에 남아 있다.

### 7.5 완료로 인정하지 않는 사례

다음 상태는 `완료`로 표시하지 않는다.

- 코드만 작성하고 실행하지 못한 상태
- 화면만 존재하고 입력·Navigation·상태 처리 또는 Mock 흐름이 없는 상태
- 계약과 다른 임의 필드로 만든 Mock
- 요청·응답 예시나 오류 사례가 없는 API
- 검색 결과는 있으나 제품·세대·문서 정책을 검증하지 않은 상태
- 실제 파일·처리 건수 없이 템플릿 문구만 채운 문서
- 본인 환경에서만 실행되고 재현 방법이 없는 결과
- 미구현 기능을 임시 고정 응답으로 숨긴 상태
- PR·Commit·Issue·파일 경로 등 검토 증거가 없는 작업

- 관련 요구사항·WBS·Issue

## 14. 4주차 진입 조건

다음 조건을 충족해야 4주차 기능 구현을 안정적으로 시작할 수 있다.

- [ ] ERD와 주요 표준 코드가 동결되었거나 변경 승인 절차가 정해져 있다.
- [ ] DB Migration·Seed·Backend 실행 방법을 다른 팀원이 재현했다.
- [ ] 문의 생성·입력 누적의 최소 API 또는 계약 기반 Mock이 존재한다.
- [ ] AI 요청·응답 예시가 JSON Schema와 Pydantic 검증을 통과한다.
- [ ] Web·Mobile·Backend·AI가 `data/synthetic/fixtures/**` 기준본에서 생성된 데이터를 사용한다.
- [ ] `BAAI/bge-m3` 1024차원과 DB VectorField 차원이 일치한다.
- [ ] MVP 검색이 Exact Search로 수행되고 대표 P0 질의 모두 Top-5 기준을 통과한다.
- [ ] 다른 모델·세대·확장·미검증 FAQ 오염이 0건이다.
- [ ] 위험·근거 없음 시 사용 제한·상담 전환 원칙이 AI 응답과 화면 Mock에 반영되어 있다.
- [x] State Machine 핵심 상태·이벤트·가드·권한·허용 행동·완료 정책이 계약으로 존재한다.
- [ ] 409 응답의 최신 상태·버전·허용 행동 형식이 확정되어 있다.
- [ ] Backend↔AI Timeout 30초, AI 재시도 1회, Backend 재시도 0회가 계약과 설정에 반영되어 있다.
- [ ] 상담사 Web과 고객 Mobile의 최소 화면을 계약 기반 Mock으로 실행할 수 있다.

### 15.1 범위·일정

- [ ] 팀원 6명의 3주차 필수 업무와 추가 업무가 구분되어 있다.
- [ ] 7월 29일 결과와 7월 30~31일 검토·수정 업무가 구분되어 있다.
- [ ] WBS 일정이 7월 29일 이후인 업무의 3주차 최소 결과가 별도로 정의되어 있다.

- [ ] `contracts/**`가 최종 기준본으로 사용된다.
- [ ] 역할·위험도·사용 안내 상태·오류·식별자·시간 정책이 영역 간 일치한다.
- [ ] State Machine과 행동별 Endpoint의 연결이 정의되어 있다.
- [ ] 합성 업무 데이터 기준본과 서비스별 Fixture의 관계가 기록되어 있다.
- [ ] Embedding 차원·Exact Search·Top-5·오염 0건 기준이 검증된다.

### 15.3 결과물·검증

- [ ] 모든 필수 업무에 담당자·결과물·경로·완료 기준이 있다.

- [ ] 정상·오류·권한·안전 예시와 검증 방법이 있다.
- [ ] 실제 데이터·문서·테스트 결과가 반영되어 있다.
- [ ] PR·Commit·Issue·파일 경로 중 검토 가능한 증거가 있다.
- [ ] Mock·Stub·미연동·미구현 범위가 명시되어 있다.

### 15.4 의존성·인계

- [ ] 핵심 계약·데이터의 선행 관계와 담당자가 공유되었다.
- [ ] 계약 변경이 해당 주관 담당자와 협의되었다.
- [ ] 7월 29일 이후 미완료 작업이 다섯 가지 분류 중 하나로 정리되었다.
- [ ] 차단 사항에 결정권자·담당자·처리 시점이 지정되었다.
- [ ] 팀원이 자신의 최우선 작업과 선행 의존성을 설명할 수 있다.
- [ ] 4주차 첫 작업과 필요한 선행 결과가 명확하다.
