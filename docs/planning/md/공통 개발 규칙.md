# 공통 개발 규칙 항목별 설명 및 선택지

> 대상 프로젝트: **정수기 구독 고객 케어 및 A/S 업무 지원 시스템**
> 
> 
> 목적: 개발을 시작하기 전에 팀이 합의해야 할 공통 규칙의 의미와 가능한 선택지를 정리한다.
> 
> 이 문서는 팀 협의를 통해 확정한 공통 개발 규칙을 기록한다. 각 영역의 구현·테스트·연동은 본 문서와 `contracts/**`의 확정 계약을 따른다.
>

## 1. 저장소와 브랜치 운영

### 무엇을 정하는 항목인가?

코드를 어느 저장소에서 관리하고, 팀원이 어떤 브랜치에서 작업한 뒤 어떤 절차로 합칠지를 정한다.

브랜치가 무분별하게 생성되거나 미완성 코드가 기본 브랜치에 바로 반영되는 문제를 방지한다.

브랜치 종류, 이름, 생성 기준, 병합 대상과 삭제 시점을 함께 정해야 한다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 저장소 구성 | 단일 저장소(Monorepo) | 프론트엔드·백엔드·AI·데이터를 하나의 저장소에서 관리한다. 통합 관리가 쉽지만 저장소가 커질 수 있다. |
| 기본 브랜치 구조 | GitHub Flow | `main`에서 기능 브랜치를 생성하고 PR로 다시 `main`에 병합한다. 배포가 잦은 프로젝트에 단순하고 적합하다. |
| 브랜치 내용 메인에 머지 | PM만 머지 | PM의 절대권한 |
| 기본 브랜치 직접 Push | 금지하고 PR만 허용 | 안정적이지만 모든 변경에 PR 절차가 필요하다. |
| 병합 후 브랜치 | 유지 | 다시 사용할 수 있지만 브랜치가 계속 쌓인다. |

## 2. Issue·커밋·PR 규칙

### 무엇을 정하는 항목인가?

작업을 어떤 단위로 등록하고, 변경 내용을 어떻게 기록하며, 검토 후 코드에 반영할지를 정한다.

Issue는 할 일을 추적하고, 커밋은 코드 변경 이력을 남기며, PR은 병합 전 검토 공간이 된다.

규칙을 통일하면 담당자·요구사항·변경 이유를 나중에도 쉽게 확인할 수 있다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| Issue 생성 기준 | 기능·버그 단위로만 생성 | 관리 부담이 적고 일반적인 팀 프로젝트에 적합하다. |
| Issue 제목 형식 | `[유형][요구사항 ID] 작업명` | 예: `[FE][FR-008] 고객 증상 입력 화면 구현` |
| 커밋 메시지 | 팀 내부에서 정함 | 커밋 메시지 : 작업 일자 | 작업 내용 / 예시 : 2026-07-10 | readme 작성 완료 |
| 커밋 언어 | 한글 | 팀원이 빠르게 이해하기 쉽다. |
| PR 크기 | 하루 작업 단위 | 작성 부담은 적지만 여러 기능이 섞일 수 있다. |
| PR 필수 내용 | 변경 내용만 작성 | 간단하지만 테스트·영향 범위를 놓치기 쉽다. |
| 리뷰 승인 수 | 1명 승인 | 소규모 팀에 현실적인 기준이다. |
| PR 작성자 본인 병합 | 리뷰어만 병합 | 통제는 강하지만 리뷰어 의존도가 높다. |

## 3. 코드 스타일과 네이밍

### 무엇을 정하는 항목인가?

들여쓰기, 따옴표, 줄바꿈, 파일명, 변수명, 클래스명처럼 코드를 작성하는 형식을 정한다.

팀원이 서로 다른 스타일로 작성하면 리뷰가 어려워지고 불필요한 수정이 반복될 수 있다.

가능한 부분은 Formatter와 Linter로 자동 검사하도록 정하는 것이 좋다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 스타일 관리 | Formatter만 사용 | 코드 모양을 자동 통일한다. 예: Prettier, Black. |
| 클래스·컴포넌트명 | `PascalCase` | 예: `InquiryService`, `CustomerHome` |
| 상수명 | `UPPER_SNAKE_CASE` | 예: `MAX_RETRY_COUNT` |
| 파일명 | `snake_case` | 예: `inquiry_service.py` |
| 주석 | 복잡한 규칙·의도만 작성 | 불필요한 주석을 줄이면서 핵심 맥락을 남긴다. (블록 단위로 주석 작성) |

## 4. 디렉터리 및 모듈 구조

### 무엇을 정하는 항목인가?

파일을 어느 폴더에 두고 각 모듈이 어떤 책임을 가질지를 정한다.

구조가 없으면 API, DB, AI, 화면 코드가 뒤섞여 수정 범위와 담당자가 불명확해진다.

공통 코드의 위치와 계층 간 의존 방향도 함께 정해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 최상위 구조 | 역할별 분리 | `frontend/`, `backend/`, `ai/`, `data/`처럼 기술 영역별로 나눈다. 이해하기 쉽다. |
| 백엔드 구조 | Controller–Service–Repository | API, 비즈니스 로직, DB 접근을 분리한다. 가장 이해하기 쉽다. |
| 프론트엔드 구조 | 기능 중심 | 기능별 컴포넌트·API·상태를 함께 둔다. 기능 단위 유지보수에 유리하다. |
| 공통 코드 위치 | 각 영역 내부에 별도 `common/` | 영역별 독립성이 높다. |
| AI 모듈 구조 | 프롬프트·검색·생성·검증 분리 | 단계별 테스트와 재시도가 쉽다. |
| 테스트 위치 | 별도 `tests/` 폴더 | 운영 코드와 테스트 코드를 명확히 분리한다. |

## 5. API 요청·응답 계약

### 무엇을 정하는 항목인가?

프론트엔드·백엔드·AI가 어떤 주소와 데이터 형식으로 통신할지를 정한다.

필드명, 정상·오류 응답, 날짜 형식, 상태 코드가 다르면 통합 과정에서 오류가 반복된다.

API를 구현하기 전에 요청·응답 예시와 변경 절차를 합의해야 한다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| API 방식 | REST API | 이해하기 쉽고 일반적인 웹·앱 프로젝트에 적합하다. |
| URL 버전 | `/api/v1` 사용 | 변경 버전을 명확히 관리할 수 있다. |
| 응답 구조 | 공통 Wrapper 사용 | 예: `success`, `data`, `error`; 일관성은 높지만 응답이 길어진다. |
| 날짜·시간 | DB는 UTC로 저장하고, API는 한국 시간대 오프셋이 포함된 ISO 8601 형식으로 반환 | 예: `2026-07-27T17:30:00+09:00`. 시간대가 없는 형식은 사용하지 않는다. |
| 빈 값 | `null` 사용 | 값이 없음을 명확히 표현한다. |
| 목록 응답 | 페이지 번호 방식 | `page`, `size`, `total`; 일반적인 관리자 화면에 적합하다. |
| API 문서 | `contracts/**`를 최종 기준본으로 사용 | 설명 문서와 계약 파일이 충돌하면 `contracts/**`를 우선한다. |
| 계약 변경 | 계약 PR을 구현 PR보다 먼저 병합 | 계약 확정 전에는 Mock·Stub 작업이 가능하지만 실제 연동 완료로 판정하지 않는다. |

## 6. DB·Migration·Seed 규칙

### 무엇을 정하는 항목인가?

테이블과 필드를 어떻게 만들고 변경하며, 개발용 초기 데이터를 어떻게 넣을지를 정한다.

팀원이 DB를 직접 수정하면 각자의 환경이 달라져 실행 오류가 생길 수 있다.

스키마 변경 이력, 식별자, 삭제 방식과 합성 데이터 관리 기준을 함께 정해야 한다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| DB 변경 방식 | Migration 파일만 사용 | 재현성과 협업 안정성이 높다. |
| Migration 도구 | 프레임워크 기본 도구 | 예: Django Migration, Alembic. 프로젝트와 통합이 쉽다. |
| 기본키 | 자동 증가 정수형 내부 PK와 별도 공개 식별자 사용 | API에는 공개 UUID를 사용하고, `DEMO-INQ-002` 등의 값은 별도 업무·시연 코드로 관리한다. |
| 삭제 방식 | 논리 삭제 | `deleted_at` 등으로 보존한다. 이력 추적에 유리하지만 조회 조건이 복잡해진다. |
| Enum 관리(보류) | 문자열 칼럼과 Django `TextChoices` 사용 | 상태·역할·위험도 등 고정 코드를 애플리케이션에서 통일하며, PostgreSQL DB Enum은 사용하지 않는다. |
| 생성·수정 시각 | 모든 주요 테이블에 공통 적용 | `created_at`, `updated_at`을 일관되게 관리한다. |
| 합성 Fixture·Seed | `data/synthetic/fixtures/**`를 기준본으로 두고 서비스별 Fixture와 Seed를 자동 변환 | Web·Mobile·Backend·AI가 동일한 고객·제품·문의 시나리오를 사용한다. |
| 합성 데이터 초기화 | Upsert 방식 | 반복 실행에 안전하지만 키 관리가 필요하다. |

## 7. 환경 변수와 보안

### 무엇을 정하는 항목인가?

API Key, DB 주소, 인증 비밀키처럼 코드에 공개하면 안 되는 값을 어떻게 관리할지 정한다.

개발·테스트·배포 환경을 분리하고, 역할별 접근 권한과 민감정보 노출 기준도 합의한다.

비밀값이 Git, 로그, 화면 또는 오류 메시지에 포함되지 않도록 해야 한다.

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 로컬 비밀값 | 공용 개발 계정 값 공유 | 환경 통일은 쉽지만 유출 위험이 크다. |
| 환경 변수 예시 | `.env.example` 제공 | 필요한 키 이름을 쉽게 확인할 수 있다. 실제 값은 넣지 않는다. |
| 환경 구분 | 하나의 환경만 사용 | 단순하지만 개발과 배포 설정이 섞인다. |
| 배포 비밀값 | AWS Secrets Manager 등 | 보안과 회전 관리가 좋지만 설정이 복잡하다. |
| 인증 방식 | Access Token과 Refresh Token 사용 | Access Token은 60분, Refresh Token은 최초 발급부터 7일간 유효하다. |
| 권한 검사 | 백엔드에서 모든 요청 검증 | 필수 보안 기준이다. |
| CORS | 개발·배포 주소만 허용 | 안전하지만 환경별 설정이 필요하다. |
| 비밀값 유출 대응 | 즉시 폐기·재발급·이력 확인 | 권장되는 대응 방식이다. |
| 실제 개인정보 | 가명·합성 데이터만 사용 | 현재 MVP 시연에 적합하다. |
| 로그아웃 | Refresh Token을 서버에서 무효화 | Access Token은 클라이언트에서 삭제하고 MVP에서는 별도 Blacklist 없이 자연 만료시킨다. |
| 권한 오류 | 역할 부족은 403, 타 사용자 소유·담당 리소스는 404 | 타 사용자 리소스의 존재 여부가 외부에 노출되지 않도록 한다. |

## 8. 오류 응답과 로그

### 무엇을 정하는 항목인가?

오류가 발생했을 때 사용자에게 무엇을 보여주고, 개발자가 어떤 정보를 기록할지를 정한다.

오류 형식이 다르면 프론트엔드 처리가 복잡해지고 원인 분석이 어려워진다.

오류 코드, 로그 수준, 추적 ID와 민감정보 제외 기준을 함께 정해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 오류 응답 | 코드·메시지·상세 정보 반환 | 예: `code`, `message`, `details`; 화면과 개발 로그를 분리하기 쉽다. |
| 오류 코드 | 업무 오류 코드 추가 | 예: `INQUIRY_NOT_FOUND`, `INVALID_STATE_TRANSITION` |
| 사용자 메시지 | 사용자용 문구와 내부 로그 분리 | 사용자에게는 이해하기 쉬운 문구, 로그에는 상세 원인을 기록한다. |
| 로그 형식 | 구조화 JSON 로그 | 필드별 검색과 분석이 쉽다. |
| 로그 수준 | `DEBUG`, `INFO`, `WARN`, `ERROR` | 개발·운영 상황을 세분화할 수 있다. |
| 로그 저장 | 파일 저장 | 간단하지만 서버가 여러 개면 통합이 어렵다. |
| 요청 추적 | `correlation_id` 사용 | 프론트·백엔드·AI 처리 흐름을 하나로 추적할 수 있다. |
| 로그 보존 | 필요한 메타데이터와 요약만 저장 | 보안과 분석 가능성을 균형 있게 유지한다. |
| 장애 처리 | 입력 보존 후 재시도·상담 전환 | 현재 프로젝트 요구사항에 적합하다. |
| 권한·리소스 오류 | 미인증 401, 역할 부족 403, 미존재 및 타 사용자 리소스 404 | 외부 응답과 내부 로그의 원인을 분리한다. |
| 상태 충돌 | `state_version` 충돌 시 409와 최신 상태 정보 반환 | 응답에 최신 상태, `state_version`, `allowed_actions`를 포함한다. |

## 9. 테스트와 완료 기준

### 무엇을 정하는 항목인가?

어떤 기능을 어느 수준까지 검증해야 완료로 인정할지를 정한다.

테스트 기준이 없으면 구현만 된 상태와 실제 사용 가능한 상태가 혼동될 수 있다.

자동 테스트 범위, 담당자 확인, 인수 조건과 Definition of Done을 함께 정해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 테스트 수준 | 핵심 기능만 자동 테스트 | 일정과 품질을 균형 있게 관리할 수 있다. |
| 단위 테스트 대상 | 비즈니스 로직만 | State Machine·위험 규칙·날짜 계산 등 핵심 로직에 집중한다. |
| 통합 테스트 | API·DB·AI/RAG까지 검증 | 실제 흐름과 가깝지만 외부 API 비용과 변동성이 있다. |
| E2E 테스트 | 정상·위험·근거 없음 시나리오 | 핵심 분기를 균형 있게 검증할 수 있다. |
| AI 테스트 | 자동 검사 + 사람 평가 | 가장 현실적인 혼합 방식이다. |
| 테스트 실패 시 병합 | 핵심 테스트 실패 시 병합 금지 | 안정적인 협업에 적합하다. |
| 완료 기준 | 구현+테스트+리뷰 완료 | 일반적인 팀 프로젝트 완료 기준이다. |
| 테스트 증빙 | 테스트 결과 파일·리포트 | 체계적이지만 관리 항목이 늘어난다. |

## 10. State Machine 규칙

### 무엇을 정하는 항목인가?

문의·상담·방문이 어떤 상태를 거치며, 누가 어떤 이벤트로 상태를 바꿀 수 있는지 정한다.

화면마다 임의로 상태를 변경하면 잘못된 순서, 중복 완료와 권한 오류가 발생할 수 있다.

상태, 이벤트, 전이 조건, 담당자, 허용 행동과 변경 이력을 백엔드 기준으로 통일해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 상태 관리 위치 | 백엔드 중심 | 모든 역할과 화면에서 동일한 업무 흐름을 보장할 수 있다. |
| 상태 모델 | 문의 상태·방문 상태 분리 | 업무 단계와 일정 단계를 명확히 관리할 수 있다. |
| 상태 변경 방식 | 이벤트 기반 전이 | 예: `REQUEST_CONSULTATION`, `START_VISIT`; 업무 의미와 검증이 명확하다. |
| 허용 행동 제공 | 백엔드가 `allowed_actions` 반환 | 규칙을 한 곳에서 관리할 수 있다. |
| 동시 수정 제어 | `state_version` 검사 | 동시에 수정된 요청을 감지할 수 있다. |
| 중복 요청 방지 | `idempotency_key` 사용 | 동일 요청을 한 번만 처리할 수 있다. |
| 변경 이력 | 모든 전이 이력 저장 | 이전·다음 상태, 변경자, 시각, 사유를 추적할 수 있다. |
| 완료 정책 | `COMPLETION_PENDING` 후 최종 완료 | 고객 피드백과 담당자 확인을 분리할 수 있다. |
| 잘못된 전이 | 업무 오류 반환 | 예: `INVALID_STATE_TRANSITION`; 원인 확인이 쉽다. |
| 외부 상태 변경 API | 행동별 Endpoint | `/request-consultation`, `/start-consultation`, `/finalize`처럼 사용자 행동별 API를 제공하며, 각 API는 내부의 공통 State Machine 이벤트를 호출한다. |

## 11. AI 출력 스키마와 프롬프트 관리

### 무엇을 정하는 항목인가?

LLM이 어떤 입력을 받고 어떤 JSON 형식으로 결과를 반환하며, 프롬프트를 어디서 관리할지를 정한다.

자유 형식 문장만 사용하면 에이전트 간 전달과 백엔드 검증이 어려워진다.

필수 필드, Enum, 재시도, 버전과 금지 표현을 공통 기준으로 관리해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| AI 출력 | JSON + 사용자용 문장 | 시스템 처리와 화면 표현을 함께 지원한다. |
| 스키마 검증 | JSON Schema·Pydantic 등으로 전체 검사 | 가장 안정적이지만 스키마 관리가 필요하다. |
| 잘못된 출력 | AI 내부에서 최대 1회 재생성 후 실패 시 상담 전환 | Backend는 동일 요청을 자동 재시도하지 않는다. |
| 프롬프트 위치 | 별도 텍스트·YAML 파일 | 코드와 분리되어 관리하기 쉽다. |
| 프롬프트 버전 | 버전 번호와 변경 이력 저장 | 평가 결과와 생성 결과를 재현하기 쉽다. |
| 공통 프롬프트 | 고객·상담사·기사 역할별 분리 | 역할에 맞는 표현을 만들기 쉽다. |
| AI 역할 | 구조화·문장 생성만 담당 | 위험 규칙과 상태 전환은 코드가 담당하여 통제하기 쉽다. |
| 모델 설정 | 작업별 모델 구분 | 비용·성능 최적화가 가능하지만 비교와 관리가 복잡하다. |
| 출력 저장 | 입력·모델·스키마 결과·프롬프트 버전 저장 | 재현성과 분석에 유리하다. |
| 사용 안내 상태 | `NORMAL`, `PARTIAL_STOP`, `TOTAL_STOP`, `PENDING_CONSULTATION` | Backend·AI·Web·Mobile에서 동일한 문자열을 사용한다. |
| Timeout·재시도 | Backend 전체 Timeout 30초, AI 내부 최대 재시도 1회, Backend 자동 재시도 0회 | 양쪽에서 동시에 재시도하여 LLM 호출이 중복되는 것을 방지한다. |

## 12. RAG 근거·문서 관리

### 무엇을 정하는 항목인가?

어떤 문서를 RAG에 넣고, 검색 결과를 어떤 기준으로 검증하여 화면에 제공할지를 정한다.

제품·세대·문서 버전이 다른 근거가 섞이면 잘못된 자가조치나 안전 안내가 생성될 수 있다.

원문, 청크, 메타데이터, 근거 카드와 제외 정책을 구분하여 관리해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| RAG 대상 문서 | 검증 문서 우선 + 조건부 보조 | 공식 매뉴얼을 우선하고 FAQ를 조건부로 사용할 수 있다. |
| 원문 저장 | 원문은 내부 저장, 메타데이터만 Git 관리 | 현재 공식 문서 관리에 적합하다. |
| 청크 기준 | 제목·문단·증상 단위 | 의미 보존이 좋지만 전처리 설계가 필요하다. |
| 검색 방식 | MVP에서는 pgvector Exact Search 사용 | 초기 데이터 규모가 작으므로 HNSW·IVFFlat은 적용하지 않는다. |
| 모델 필터 | 검색 전 필터 + 검색 후 재검증 | 가장 안전하지만 처리 단계가 늘어난다. |
| 근거 없음 처리 | 답변 보류·상담 전환 | 안전성과 신뢰성을 우선한다. |
| 화면 전달 | 구조화 근거 요약 전달 | 문서명·버전·페이지·요약만 제공한다. |
| 출처 링크 | 공식 랜딩 페이지 기본 제공 | 안정적이며 공식 출처 확인에 적합하다. |
| 근거 DTO | 공통 `EvidenceCardDTO` 사용 | 고객·상담사·기사 화면에서 같은 핵심 근거를 유지한다. |
| 데이터 분리 | MVP·확장 데이터를 물리적으로 분리 | 범위 통제가 쉽고 시연 안정성이 높다. |
| 문서 변경 감지 | 해시값·버전 비교 | 원문 변경 여부를 명확히 확인할 수 있다. |
| Embedding 차원 | `BAAI/bge-m3`의 원본 출력 차원 사용 | AI 임베딩 설정과 pgvector 칼럼 차원을 일치시킨다. |
| 검색 결과 수 | Top-5 | 대표 P0 질의의 정답 문서·페이지가 Top-5에 포함되는지 평가한다. |
| 검색 합격 기준 | 대표 P0 질의 전부 통과 | 전체 Recall@5는 참고 지표로만 기록한다. |
| 근거 오염 | 모델·세대 불일치 근거 허용 0건 | 다른 세대·후속 모델·제거 대상·미검증 FAQ의 혼입을 허용하지 않는다. |

## 13. 배포 및 버전 관리

### 무엇을 정하는 항목인가?

완성된 코드를 어디에 어떻게 배포하고, 어떤 버전을 공식 결과물로 볼지를 정한다.

팀원별 환경에서는 동작하지만 통합 서버에서는 실패하는 문제를 줄이기 위한 항목이다.

빌드, 배포 승인, 태그, 롤백, DB 반영과 배포 후 점검 방법을 함께 정해야 한다.

### 선택지

| 결정 항목 | 선택지 | 특징 |
| --- | --- | --- |
| 배포 방식 | Kubernetes | 확장성은 높지만 단기 프로젝트에는 과도할 수 있다. |
| 배포 자동화 | GitHub Actions CI/CD | 테스트·빌드·배포를 자동화할 수 있다. |
| 배포 환경 | 개발 서버 하나만 사용 | 단순하지만 테스트 중 장애가 시연 환경에 영향을 준다. |
| 버전 형식 | Semantic Versioning | 예: `v1.2.0`; 기능·수정·호환성 변경을 구분할 수 있다. |
| Git 태그 | 중간·최종 배포에 태그 생성 | 예: `v0.5.0`, `v1.0.0`; 결과 재현에 유리하다. |
| 배포 승인 | 테스트 통과 후 PM·DevOps 승인 | 안정적이지만 일정 조율이 필요하다. |
| DB Migration | 애플리케이션 시작 시 자동 실행 | 편리하지만 잘못된 변경이 자동 적용될 수 있다. |
| 백업 | Semantic Versioning | 예: `v1.2.0`; 기능·수정·호환성 변경을 구분할 수 있다. |
| 롤백 | 이전 Docker 이미지·Git 태그로 복귀 | 빠르게 이전 버전으로 되돌릴 수 있다. |
| 배포 후 확인 | 대표 E2E 시나리오 실행 | 실제 시연 흐름을 가장 확실하게 검증하지만 시간이 더 필요하다. |
| 산출물 보존 | 코드 태그·환경 설정·DB Seed·배포 문서 보존 | 최종 결과를 다시 실행하기 쉽다. |
