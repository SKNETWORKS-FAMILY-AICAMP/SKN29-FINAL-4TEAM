# M3 — 직접 학습은 성공했는데, 왜 답변 품질은 나빠졌을까?

> **S10 완료(2026-10-31) · S11 v2 데이터 구축 완료(2026-11-01) · S12 실제 GPU 학습 완료 · S13 DEV 16건 오류 분석 완료:** A40에서 LoRA 10단계 학습·재로드 완료. 이후 S07 Train 26건의 검색 근거·행동 다양성·학습 이용 상태를 로컬에서 점검함. **WaterBridge 성능 개선은 미평가, 학습 이용 승인은 미확정.**  
> **먼저 기억할 결론:** **S10·S12 모두 LoRA 가중치 학습은 정상 완료했지만 구조화 응답 품질은 개선되지 않았다. S13에서는 형식 오류와 행동별 계약 오류를 분리해 실제 퇴행 원인을 밝혔다.** S11에서는 데이터를 무작정 늘리기보다 *정답이 근거로 뒷받침되는가·행동 종류가 고르게 있는가*를 먼저 본다.

**읽는 순서**

- **PART 1 — 실험 이야기:** 먼저 여기만 읽어도 S10의 이유와 성공 조건을 알 수 있어.
- **PART 2 — 기술 공부:** LoRA·QLoRA·Loss·정답 마스킹이 실제로 어떻게 동작하는지 배워.
- **PART 3 — 실험 증거와 실행:** 코드·데이터·명령어·판정 기준을 확인해. GPU 비용은 이 단계에서만 발생할 수 있어.

## PART 1. 먼저 읽는 실험 이야기

### S10. 프롬프트를 넘어, 모델 자체를 조금 바꿔보자

#### M2에서는 무엇이 아쉬웠지?

M2의 S08에서는 같은 Qwen3-1.7B 모델에 고객 질문 6개를 주고, 시스템 프롬프트만 강화했어.

```text
                  기본 프롬프트(B0)     강한 프롬프트(B1)
JSON 파싱 성공           3/6                 6/6
정답 행동 선택           1/6                 1/6
```

프롬프트를 자세히 쓰니 **형식을 지키는 능력은 개선됐지만, 올바른 행동을 선택하는 능력은 여전히 부족**했어. 그렇다고 바로 “모델을 학습시키면 해결된다”고 결론을 내릴 순 없어. 당시 검색 근거 자체가 부족한 사례도 있었거든.

그럼에도 이제 한 번 해볼 만한 새로운 실험이 생겼어.

**“프롬프트에 규칙을 적는 것과, 정답 예시로 모델 가중치를 직접 업데이트하는 것은 무엇이 다를까?”**

이 차이를 배우는 것이 S10의 목적이야.

#### 하지만 WaterBridge 26건을 곧바로 학습시키면 안 돼

S07에 만든 26문장은 실제로 **6개 의미 그룹**에서 나온 작은 초안이야. S09에서 검색 근거를 연결했지만, 일부 답변 지시가 검색 결과에 완전히 뒷받침되지 않았고 공식 매뉴얼 자료의 학습 사용 범위도 확정되지 않았어.

학습 코드를 시험해 보겠다고 **그 26건을 몰래 사용하면** M2에서 지켜온 데이터 검수 원칙과 충돌해.

그래서 S10에서는 **실제 정수기 설명서와 전혀 무관한 가상 제품 `SIM-P100`, `SIM-P200`** 을 만들었어. 고객 질문과 규칙, 올바른 답변을 모두 새로 작성한 작은 연습장이야.

#### 예를 하나 보자

> 고객: “SIM-P100의 전원 표시등이 보라색으로 켜져 있어요.”

가상 설명서에는 이렇게 적혀 있다고 하자.

> “SIM-P100의 보라색 표시등은 절전 대기 상태다. 측면 버튼을 한 번 누르면 대기 모드를 해제할 수 있다.”

이 질문에 모델이 만들어야 할 답변은 다음과 같아.

```json
{
  "action": "ANSWER",
  "customer_message": "보라색 표시등은 절전 대기 상태를 뜻합니다. 측면 버튼을 한 번 눌러 대기 모드를 해제해 보세요.",
  "cited_evidence_ids": ["SIM-EVD-T01"],
  "missing_fields": []
}
```

학습할 때는 모델에 **고객 질문과 가상 규칙**을 먼저 보여주고, 위 JSON을 **정답 예시**로 제공해. 모델이 정답과 다른 토큰을 예측하면 오차가 발생하고, 그 오차를 줄이는 방향으로 일부 학습 가능한 가중치를 업데이트하지.

여기서 중요한 건 **문서 자체를 암기하는 성능보다, 입력과 정답을 연결하는 학습 과정이 제대로 작동하는지** 확인하는 일이야.

#### 모델 전체를 다시 학습하는 걸까?

아니. 이번에는 **LoRA**를 사용해. 이미 학습된 Qwen3-1.7B 원본 가중치는 그대로 두고, 그 옆에 붙인 **작은 어댑터의 가중치만** 업데이트하는 방식이야.

```text
[기존 Qwen3-1.7B]  ─── 원래 가중치는 고정
           +
[작은 LoRA 어댑터] ── 이 부분만 학습
           ↓
[가상 고객 문의 → JSON 응답]
```

학습이 끝나면 작은 어댑터 파일을 저장해. 그리고 **다시 불러와서** 같은 입력에 대해 원본 모델과 어댑터 모델이 어떻게 답하는지 비교해 볼 거야.

#### S10의 성공 조건은 무엇일까?

성공했다고 말하려면 **다음 네 가지를 실제 로그로 확인**해야 해.

1. 원본 모델 대부분은 고정되고 **LoRA 파라미터만 학습 대상**이 됐다.
2. 실제 GPU에서 학습 단계가 진행되어 **유한한 Loss 기록**이 남았다.
3. 어댑터 파일을 디스크에 저장하고 **별도 코드에서 재로드**할 수 있다.
4. 원본 모델과 학습 모델에 **동일한 가상 점검 질문**을 넣어 각각 응답을 생성했다.

**Loss가 작아졌거나 가상 문제 8건을 잘 맞혔다고 WaterBridge 응대 능력이 좋아졌다고 주장해서는 안 돼.** 그건 나중에 실제로 승인된 학습 자료와 동일 조건의 독립 평가가 필요해.

### 그리고 실제로 실행해 보니 어떻게 됐을까?

RunPod **NVIDIA A40**에서 `Qwen3-1.7B`를 사용했어. 가상의 고객지원 학습 문장 **40개**를 1 epoch, **10단계** 학습했고, 전체 파라미터 중 **0.186%**만 업데이트했어. 저장한 LoRA 어댑터도 다시 불러오는 데 성공했지.

그런데 학습 전후를 **서로 다른 원본 상황 8건의 가상 질문**으로 비교했더니 예상 밖의 결과가 나왔어.

| 가상 점검 결과 | 원본 모델 | LoRA 모델 |
|---|---:|---:|
| 정상 JSON 1개 출력 | **8/8** | 6/8 |
| 기대 행동 선택 | 5/8 | **6/8** |
| 필수 4개 필드까지 완전히 출력 | **8/8** | 1/8 |

겉으로는 행동을 한 건 더 잘 맞혔지만, **답변 JSON을 제대로 작성하는 능력은 크게 떨어졌어.** 구체적으로 학습 후 응답 5건은 필수 항목 `missing_fields`가 없었고, 2건은 JSON 객체를 여러 개 이어 써서 파싱 자체에 실패했어.

이 현상은 "**Loss가 내려갔다 = 좋은 모델이 됐다**"가 아니라는 것을 보여주는 실습 반례야. **실제 정수기 고객응대 성능은 이번에 측정하지 않았어.** 이 작은 결과만으로 LoRA 전체의 효과를 일반화할 수도 없어.

**PART 1의 핵심 한 문장:** S10은 *SFT 효과를 입증하는 최종 실험*이 아니라 **LoRA 학습의 전체 사이클을 본인 손으로 완성하는 첫 파일럿**이야.


### S11. 이제 학습 데이터를 늘리기만 하면 될까?

아니. S10에서 **40개 가상 데이터로 LoRA를 학습하는 데는 성공**했지만, 정작 JSON을 완전하게 출력한 건 **8건에서 1건으로 줄었어**. 모델을 학습시켰다는 사실만으로 답변 품질은 보장되지 않는다는 걸 알았지.

그럼 다음에는 '정수기 상담 데이터 26개를 학습하자'고 말하기 쉬워. 하지만 S07의 **26개는 원본 문제 13개를 각각 두 번 표현한 것**이야. 26개의 새로운 상황을 만든 게 아니라 실제로는 **6개 의미 그룹**에 머물러 있어.

그보다 더 큰 문제가 하나 있어. *정답 답변과 모델이 실제로 볼 근거가 서로 맞지 않을 수 있다는 것*이야.

#### 예를 하나 보자 — 냉수 잠금 문의

고객이 “냉수 버튼을 누르면 잠금 표시가 깜빡여요”라고 물었어. 우리가 검수한 정답에는 **[설정] 버튼 3초 → 냉수 잠금 해제 → 저장**이라는 구체적인 절차가 들어 있어.

그런데 실제 검색 결과는 “냉수 잠금을 해제하세요. 방법은 설명서 27쪽 참고” 정도의 **요약 청크**만 제공했어. 검색 결과에 정답 문서 ID가 있다고 해도, 모델에게는 세부 조작법이 전달되지 않은 거야.

이 상태로 학습시키면 **모델이 보지 못한 내용을 답변에 넣는 패턴**을 정답처럼 학습시킬 수 있지. SFT로 검색기에서 빠진 설명서 페이지를 대신 만들면 안 돼.

#### S11에서 실제로 확인한 현황

기존 S07 Train·S09 검색 미리보기·M2 사람 검수 기록을 합쳐서 다시 분류했어.

| 발견 | 실제 값 | 그래서 무엇을 해야 할까? |
|---|---:|---|
| 학습 후보 문장 | 26건 | 원본은 **13건·6개 의미 그룹**이므로 단순 증강만으로 충분하지 않음 |
| `EXPLAIN_UNSUPPORTED` 정답 | **0건** | 미지원 기능을 *근거가 있을 때만* 설명하는 독립 사례 필요 |
| Top-5에서 Gold 하나 이상 검색 | 26/26 | 이것만으로 고객 안내의 모든 조치가 뒷받침된다고 주장하지 않기 |
| 선언된 Gold 전부 검색 | 25/26 | 소음 사례 1건의 추가 Gold 누락과 정답 근거 부족을 구분해 수정 |
| 원본 13개 중 우선 근거 보강 대상 | **4개** | 잠금 해제 2개·누수 1개·소음 1개부터 점검 |

나머지 원본 시나리오 9개 중 4개는 **검색 순위·조건 검토**, 5개는 **기본 재확인**으로 분류했어. 이 분류는 **기존 사람 검수 결과를 정리한 것**이지, 사용설명서를 다시 자동 판독해서 새로운 정답을 확정한 실험은 아니야.

여기에 **자료 사용 범위** 문제도 남아 있어. Qwen 모델의 Apache-2.0 라이선스가 제조사 PDF를 SFT에 이용할 권한까지 보장하지 않아. 공개된 매뉴얼이라도 학습용 복제·가공·배포의 근거를 따로 확인해야 해.

**S11의 핵심 한 문장:** 모델 학습을 반복하기 전에 **학습할 정답·실제 검색 근거·데이터 사용 범위·새로운 상황의 다양성**부터 맞춘다. 지금은 **학습 승인 0건**, GPU 실행 없음.

#### S11 후속 — 근거 ID는 같은데 왜 설명이 달라질까?

P1 검수에서 이상한 사례를 발견했어. **IAC425 누수 문의**의 원본 질문(BASE)과 재표현 질문(PAR1)은 같은 누수 근거 ID를 인용했는데, 모델이 읽은 내용은 달랐어.

- BASE에는 **45쪽의 누수·알림음 안내**만 들어왔어.
- PAR1에는 같은 ID에 **45쪽 + 5쪽의 물받이 확인·감전 위험 안내**가 함께 있었어.

이유는 검색기가 **작은 청크(child)**를 찾아낸 뒤, 결과를 만들면서 여러 청크를 **큰 근거 그룹 ID(EVD)** 하나로 합쳤기 때문이야. 그래서 **그룹 ID가 같아도 실제로 포함된 문장이 달라질 수 있어.** 이 상태에서 “이 ID를 인용했으니 맞다”고 판단하는 건 위험해.

해결 방향은 의외로 단순해.

1. **실제로 검색된 작은 청크에 각각 `child_id`를 남긴다.** 어떤 문장을 봤는지 정확히 추적할 수 있어.
2. 비교 실험으로, **검색된 그룹 안의 다른 검증 청크도 함께 보여주면** 필요한 근거가 보완되는지 확인한다. 단, 이건 검색 모델이 찾은 Top-5가 아니라 **그룹 확장**이라는 별도 방법이야.
3. 남은 문제는 정직하게 남긴다. **IAC425의 냉수 잠금 상세 절차(27쪽), IAC606의 잠금 해제 절차(24쪽)는 기존 53개 검색 후보에 없다.** ID 형식만 바꾼다고 없는 근거가 생기진 않아. IAC606 복합 소음도 별도 그룹의 근거를 찾아야 해.

**사전 검산:** 저장소의 53개 원본 청크와 S09의 26건 검색 스냅샷을 대조하니, **130개의 검색 child를 26건 모두에서 식별 가능**했어. 그룹을 확장하는 대안은 **7개 질문에 총 25개 청크를 추가**할 수 있어. 하지만 그 25개가 유용하다는 보장은 없고, **Gold 전체 발견률 25/26도 그대로**야.

**결론:** 이번 작업은 **검색 결과를 정확히 인용할 수 있게 만드는 구조 수정안과 비교용 미리보기**야. 실제 WaterBridge 서비스 검색 코드, PDF 인덱스, 학습 데이터는 아직 수정하지 않았어.

#### S11 다음 실험 — 요약 문단은 있는데, 정확한 잠금 해제 방법이 없다면?

우리가 검색한 기존 53개 문서 조각에는 냉수 버튼이 잠겼을 때의 **증상 설명**은 있었어. 하지만 정작 고객에게 필요한 **해제 절차**는 빠져 있었지. 예를 들어 “설명서 27쪽을 보세요”라는 근거만 준 상태에서 AI가 구체적인 조작 방법까지 답하면, 그 조작법은 **제공받지 않은 자료를 이용한 응답**이 돼.

그래서 원본 PDF를 다시 확인했어. 두 제품의 공통 흐름은 **[설정] 버튼 3초 → 점멸 중인 [냉수] 버튼 선택 → 저장 또는 잠시 대기**야. 그런데 마지막 단계에 제품별 차이가 있어.

- **IAC425, 27쪽:** **[물] 버튼**을 누르거나 7초 동안 아무 버튼도 누르지 않으면 완료.
- **IAC606, 24쪽:** **출수/출빙 버튼**을 누르거나 약 7초 동안 아무 버튼도 누르지 않으면 완료.

기존 IAC606 문제 해결 안내가 29쪽을 참조하고 있지만, 실제 절차는 **24쪽**에 있어. 숫자만 믿고 해당 페이지를 새 문서로 만들었다면 다시 틀렸을 거야.

이번에는 **53개 원본을 그대로 두고, PDF에서 확인한 절차 2개를 별도 인덱스에 추가해 55개로 비교**하도록 만들었어. 새로운 절차에는 서로 다른 `child_id`를 붙이고, 기존 냉수 잠금의 `evidence_group_id`는 유지했지.

**여기서 새 문서가 생겼다는 사실과 검색기가 그 문서를 찾는 것은 달라.** 실제 BGE-M3가 새 절차를 Top-5에 넣는지, 새 검색 결과에 쓸데없는 문서가 더 많아지지는 않는지는 **같은 질문으로 53개와 55개를 다시 검색한 뒤** 확인해야 해.

**S11 이번 단계의 핵심:** *PDF 원문 확인 → 인덱스에 빠진 절차 추가 → 같은 검색 조건으로 전후 비교*. 아직 고객 답변 품질이나 학습 성능을 평가한 건 아니야.

#### S11 실제 결과 — 필요한 문서는 찾았지만, 엉뚱한 질문에도 나타났다

53개 문서에서 빠졌던 **두 냉수 잠금 해제 절차**를 추가한 55개 검색 결과를 확인했어. 냉수 잠금 문의 4행(BASE/PAR1)은 **4/4 모두 새 절차를 Top-5에서 찾았어**. 순위는 2·3·2·3위야. 이것은 문서가 색인에 있을 때 비로소 검색될 수 있다는 의미야.

그런데 다른 질문 **6건에도 새 해제 절차가 나타났어.** '냉수 잠금을 이미 해제했고 2시간이 지나도 미지근하다'거나 '잠금 표시가 없다'는 고객에게 그 절차를 다시 보여주면, AI가 **이미 한 조치를 반복하거나 증상을 혼동할 위험**이 있어. 검색 결과에 들어왔다고 무조건 안내해야 하는 것은 아니야.

또한 기존 Gold 그룹의 Hit@5는 **26/26→26/26**, 모든 Gold 발견은 **25/26→25/26**으로 그대로였어. 새 절차가 **기존 Gold 그룹과 같은 그룹 ID**를 쓰기 때문에, 그룹 단위 점수만 보면 이번 진전을 놓치게 돼. 그래서 **'해제 절차 child ID가 실제 검색됐는가?'**를 별도 지표로 측정한 거야.

**중요한 제한:** 이전 S09의 53개 스냅샷과 이번에 다시 실행한 53개 결과는 6행이 달랐어. 이번 53↔55 비교는 같은 실행 안에서 해석하지만, 서로 다른 날의 검색 결과를 동일하다고 취급하면 안 돼.

**핵심 한 문장:** 빠진 정보를 추가하면 찾을 가능성은 생기지만, **관련 없는 질문에까지 그 근거가 섞이지 않도록 선택하는 과정**도 필요해. 아직 모델 응답·학습 성능을 검증한 것은 아니야.

### S11 후속 — 잠금 해제 문서를 찾았는데, 고객에게 정말 보여줘야 할까?

이번에 추가한 냉수 잠금 해제 문서는 **필요한 네 질문 모두에서 검색됐어.** 하지만 다음 두 질문을 비교해 보자.

> **A (해제 절차가 필요함):** “냉수 버튼을 누르니 잠금 표시가 깜빡여요. 정수는 나옵니다.”  
> **B (해제 절차가 불필요함):** “냉수 잠금은 이미 해제했어요. 그런데 2시간 넘게 냉수가 계속 미지근해요.”

A에게는 해당 제품의 해제 절차를 제공할 근거가 있어. 반면 B에게 같은 절차를 다시 안내하면, **이미 끝낸 조치를 반복**하고 지속적인 냉각 이상을 놓칠 수 있지.

그래서 이번에는 BGE-M3 검색을 다시 하지 않았어. **55개 인덱스로 이미 검색한 Top-5 결과 뒤에 보수적인 조건 검사**를 한 겹 붙였어. 고객 원문에 냉수 선택·잠금 표시 점멸이 분명하고 해제 완료나 누수 등 충돌 신호가 없을 때만 *새로운 상세 해제 절차 청크*를 남기는 거야.

같은 Train 질문 26개에 적용해 보니:

- **잠금 문의 4건:** 새 상세 해제 근거 **4/4 유지**.
- **혼동된 냉수 온도 문의 6건:** 새 상세 해제 근거 **6/6 제거**.
- 그 외 16건: 새 상세 절차가 원래 검색되지 않았으므로 별도 변화 없음.

**하지만 이 결과는 훈련용 사례를 보고 만든 규칙을 같은 사례에 다시 적용한 것**이야. 실제 고객 질문에서도 100% 정확하다는 뜻은 아니야. 그뿐 아니라 새 청크를 제거한 후 다른 검색 결과로 빈자리를 채우지도 않았어. 일부 질문은 후보 4개만 남아.

**이번에 배운 점:** 검색기가 관련 문서를 찾았다는 사실과, *이 고객에게 그 조치를 안내해도 된다는 판단*은 서로 달라. **원문 조건을 반영한 후처리로 위험한 근거를 줄이는 시도**는 가능하지만, 확정된 서비스 정책으로 채택하려면 별도의 질문·안전 회귀 평가가 필요해.

### S11 다음 이야기 — 소음은 PDF에 있는데, 왜 검색 결과에서는 빠졌을까?

IAC606 사용자 한 명이 **물 흐르는 소리·얼음 떨어지는 소리·공기 빠지는 소리**를 함께 물었다고 하자. 사용설명서에는 이 소리들을 구분하는 문단이 있지만, BGE-M3가 원본 질문(BASE)에 대해 반환한 **상위 5개 청크에는 두 번째 필수 근거(냉매 순환 소음)가 없었다.** 같은 상황을 다르게 표현한 질문(PAR1)은 두 근거를 모두 찾았다.

여기서 문서를 더 만들거나 SFT부터 하는 건 잘못된 순서야. **PDF에도 있고 검색 후보 53개에도 있는데 못 찾았으니, 먼저 원인이 '6위 이하 순위'인지 '유사도 임계값 미달'인지 확인**해야 해.

이번 작은 실험은 검색 순위를 **Top-5·Top-8·Top-10**으로 비교해. 질문·제품·임베딩 모델·원본 53개 청크·유사도 최소 0.4는 동일하게 유지하고 **후보를 몇 개까지 보느냐만** 달리할 거야.

이때 늘어난 후보에 정답 근거가 포함됐더라도 **LLM 답변 정확도가 올랐다는 뜻은 아니야.** 무관한 온수 등 다른 청크도 더 많이 들어올 수 있고, 모델에 전달할 토큰도 늘어날 수 있거든. 이 실험도 기존 26개 Train 질문 내부 진단이므로 독립 검증이 아니다.

**이번에 확인할 단 한 가지:** *누락된 냉매 소음 근거는 BGE-M3의 몇 위에 있고, Top-K 확대만으로 복구되는가?*

### S11 마무리 — 이제는 검색기가 아니라 ‘가르칠 상황’을 늘릴 차례

앞에서 확인한 소음 근거는 원본 질문에서 **BGE-M3 6위**였어. 유사도 **0.581343**으로 임계값 0.4는 통과했지만 Top-5에서 잘렸던 것이지. Top-8에서는 두 소음 근거가 모두 포함되어 **전체 26건에서 지정 Gold를 모두 찾는 26/26**이 되었어. 대신 후보 수가 **130→208개**로 늘어나므로, 답변 품질이 좋아졌다고 단정할 수 없어. **검색 실험은 여기서 일단 종료**하고 실제 학습 데이터의 부족한 부분을 채우자.

#### 학습 질문 26개가 있는데 왜 아직 부족할까?

S07의 26문장은 실제로 **13개 원본·6개 의미 그룹**에서 나왔어. `ANSWER` 12건, `ASK` 4건, `ESCALATE` 10건이지만 `EXPLAIN_UNSUPPORTED`는 **0건**이야. 그리고 공식 PDF에서 나온 내용을 SFT에 사용해도 되는지도 아직 확정되지 않았어.

그래서 이번에는 기존 사례를 재표현해 불리지 않았어. 대신 **기능과 정책이 완전히 가상인 SIM 제품 16종**의 고객지원 상황을 직접 새로 작성했어. 한 제품군마다 다음 네 가지를 따로 설계했지.

- **ANSWER:** 조건이 분명하고 근거가 있어 바로 안내할 수 있음
- **ASK:** 핵심 설정이 빠져 있어 무엇을 먼저 물어야 함
- **ESCALATE:** 안전 신호 때문에 일반 조작보다 사용 중단·상담 안내가 우선임
- **EXPLAIN_UNSUPPORTED:** 이 제품에서 지원하지 않는 기능이라고 **근거에 명시**되어 있음

예를 들어 가상 조명 `SIM-L01`에서 파란 점 두 번 점멸은 *연결 대기*라는 규칙이 있어. 그런데 같은 제품의 *밝기 모드* 규칙도 동시에 보여줄 수 있어. 모델은 단순히 `SIM-L01`이란 이름이 같다는 이유로 밝기 설정을 안내하면 안 되고, **고객이 물은 조건에 맞는 규칙만 인용**해야 해. 이것이 이번 데이터에 일부러 넣은 *헷갈리는 근거(hard distractor)*야.

**이번 실제 산출물:** 16개 제품·주제 그룹에서 **64개 서로 다른 질문**을 작성했고, 그룹 12개에서 **Train 48건**, 다른 그룹 4개에서 **Probe 16건**을 분리했어. 행동은 각각 Train 12/12/12/12, Probe 4/4/4/4로 배치했어. 이전 WaterBridge Dev/Holdout은 사용하지 않았어.

여기서 `Probe`는 작은 가상 점검 세트라는 뜻이고, **WaterBridge의 공식 Holdout이나 블라인드 고객 평가가 아니야.** 직접 작성한 가상 규칙을 모델 입력에 넣는 방식이라, 지금 측정하는 능력은 *제공된 조건을 읽고 행동·JSON 형식에 맞추는 능력*이야. 실제 정수기 사용설명서 검색 성능을 측정하는 건 아니야.

**추가로 차단한 함정:** 첫 초안에서는 근거 ID 끝의 A/Q/E/U가 행동 라벨을 드러낼 수 있었어. 이건 모델이 근거를 읽지 않고도 답을 추측하게 만드는 **정답 누출**이므로, 최종 초안에서는 사례와 근거의 식별자 모두 행동을 드러내지 않는 해시 기반 ID로 바꾸고 회귀 테스트에 포함했어.

**초기 초안의 한계:** 처음에는 모든 질문의 `known_conditions`가 비어 있었어. 사용자 PC에서 Train 최대 **610토큰/768 제한**, 정답 마스킹과 구조 테스트 **16/16**은 통과했지만, 나중에 질문·근거·정답을 대조해 **3개 Train 사례의 조건·안전 문구 문제**를 발견했어. 아래 S11 v2에서 수정했지.

### S11 v2. 고객이 이미 한 일을 다시 시키면 어떻게 될까?

고객이 "바람 버튼을 이미 눌렀는데 흰 바람개비 표시가 그대로예요"라고 답했다고 해보자. 그래도 AI가 **"바람 버튼을 한 번 눌러 보세요"**만 반복하면 고객이 제공한 정보를 활용하지 않은 거야. 이제 모델 입력의 `known_conditions`에 *이미 버튼을 눌렀다는 사실*을 넣고, 정답 답변에서는 **같은 조작을 반복하지 않고 현재 표시를 확인**하게 만들었어.

비슷한 식으로 **가상 Train 48건 중 8건**에 이전 확인 사항을 추가했어. 예를 들어 **스피커 충전은 이미 중단했다**, **키패드는 다시 연결했다**, **화분 흙이 젖어 전선에 손대지 않았다** 같은 조건이야. 정답은 이 조건들을 무시하지 않아야 해.

함께 수정한 내용은 세 가지야.

- **스피커 음향:** 고객은 "음악이 아예 안 나온다"고 했지만 근거는 "소리가 작다"는 상황이어서, 고객 질문을 근거가 설명하는 저음량 상황으로 맞췄어.
- **스피커 배터리 팽창:** 답변에 *장치를 만지거나 분해하지 말 것*을 명시했어. 이미 충전을 중단했다는 고객의 진술도 인정해.
- **화분 센서 노출 전선:** 젖은 상태에서 *직접 분리하라*는 위험한 해석을 막도록 가상 정책과 답변을 함께 고쳤어.

**확인한 범위:** **Train 48 / 개발용 Probe 16**, 각 행동 Train **12건씩**, 그룹 **12/4 분리**, 기존 Probe 원본은 **바이트 단위로 그대로 보존**했어. 기존 Train 48건을 수정한 것이므로 **독립적인 새 사례 8건을 늘렸다는 뜻은 아니야.**

**남은 한계:** v2는 **AI가 사전 검토한 가상 데이터**이며 사람의 최종 승인이나 실제 고객지원 성능을 입증한 자료가 아니야. 특히 Probe 16건에는 이전 확인 사항을 포함한 새 질문을 추가하지 않았으므로, *이미 한 조치를 반복하지 않는 능력*은 아직 독립 검증하지 못했어. S12에서는 가상 모델 학습 기술 실험만 수행하고, 성능을 일반화해서 주장하지 말자.

### S12. 이번에는 무엇을 성공이라고 할까? — 가상 LoRA 학습 파일럿

#### 왜 S10을 다시 한 번 따라 할까?

S10은 **훈련이 실제로 돌아간다**는 사실을 확인했지만, 결과는 뜻밖이었지. 가상 점검 8건에서 `missing_fields`가 사라지거나 JSON이 반복 출력되면서 **스키마 준수 8/8 → 1/8**로 나빠졌어. 이 사례를 고치지 않고 그냥 모델을 오래 학습하면, Loss만 더 내려갈 수 있지.

그래서 S12에서는 먼저 **동일한 가상 DEV 질문 16건으로 학습 전 Qwen3 기준선을 저장**한 뒤 학습을 시작할 거야. 학습에 사용하는 것은 S11에서 직접 작성한 **Train 48건(F01~F12)**이고, 점검하는 것은 **서로 다른 제품·주제 그룹 16건(F13~F16)**이야.

핵심 질문은 단순해.

> **"동일 입력·동일 모델 버전·동일 출력 설정에서 LoRA를 학습한 후, 정답 행동과 JSON 계약이 함께 좋아지는가?"**

여기서 모델을 두 번 테스트하는 순서가 중요해.

```text
[동일 Qwen3-1.7B 기본 가중치 + 가상 DEV 질문 16건]
         ↓ (GPU 추론, 학습 전)
[BASE 출력 JSONL 저장]  ← 이후에 수정/덮어쓰기 금지
         ↓
[가상 Train 48건만 LoRA 학습]  ← DEV 정답 파일 금지
         ↓ (어댑터 저장 및 실제 재로드)
[LoRA 모델 + 같은 DEV 질문 16건]
         ↓
[LoRA 출력 JSONL 저장]
         ↓
[별도 EVAL_ONLY 정답 파일을 처음 사용하여 두 출력을 채점]
```

#### 이번에 일부러 제한한 것

- **학습:** A40 같은 CUDA GPU에서 **12 optimizer step**, `batch=1 × gradient accumulation=4`, 약 **48개 Train 입력을 한 차례씩 사용하는 파일럿**. 검증되지 않은 반복 학습은 하지 않아.
- **LoRA:** 원본 모델을 동결하고 `q_proj`·`v_proj`에만 rank 16 / alpha 32의 어댑터를 학습해. 학습 Loss는 기록하되 *품질 점수*로 해석하지 않아.
- **출력:** 원본·학습 모델 모두 **thinking 비활성화**, greedy decoding, 동일한 최대 256 생성 토큰, 동일한 시스템 프롬프트를 사용해.
- **모델 입력:** `customer_message`, 제품 코드, `known_conditions`, 가상 근거 2개만 포함돼. **정답 행동과 EVAL_ONLY 근거 ID는 추론 프롬프트에 없음.**
- **평가:** JSON 파싱, 필수 4필드, 필드 타입, `ASK`의 `missing_fields`, *실제로 제공한 근거만* 인용했는지, 기대 행동 일치와 근거 ID 정확 일치를 별도 지표로 기록해.

#### 정답 행동을 맞혀도 실패할 수 있을까?

그렇지. 예를 들어 모델이 `"action":"ASK"`를 맞혔어도 `"missing_fields"`를 아예 생략했다면 **행동만 맞힌 불완전한 응답**이야. 또는 고객에게 설명은 그럴듯하지만 프롬프트에 없는 인용 ID를 써도 **근거를 지어낸 응답**이지.

그래서 S12 결과에서는 `raw_action_match`와 `strict_action_match`를 따로 보여주고, **JSON 스키마 통과 + 행동 일치 + 근거 ID 정확 일치 + 누락 필드 정확 일치**가 동시에 만족된 사례를 `structured_target_match`로 표시해. 단, 이 지표는 **고객 안내 문구의 의미적 정확성 자체는 자동 판정하지 않아.**

#### 현재 완료된 것과 아직 하지 않은 것

**S11 v2 `--write` 완료와 실제 토크나이저 검사 PASS**를 확인했어. Train 48건의 최대 시퀀스는 **695/768토큰**, Dev 입력 최대 **497토큰**, 프롬프트 Loss 마스킹도 정상. S12용 **CPU 데이터 사전검사·평가기 회귀 테스트**를 준비했어.

**아직 RunPod GPU에서 S12 모델을 학습하거나 DEV 점수를 측정한 일은 없어.** 따라서 이 단계를 완수했다거나 JSON 품질을 회복했다고 주장하지 않아.

**중요한 연구 한계:** 16개 DEV 정답은 데이터 구축 과정에서 이미 AI가 검토한 자료야. 학습 그룹과 제품은 다르지만 **최종 블라인드 시험이 아니며**, 근거도 실제 RAG 검색이 아니라 우리가 고른 가상 규칙이야. 게다가 실제 매뉴얼 데이터의 SFT 권한은 여전히 미확보 상태야.

### S12~S13. 두 번째 LoRA 학습은 성공했는데 왜 점수가 더 떨어졌을까?

S11에서 실제 정수기 매뉴얼을 학습시키지 않으려고, **완전히 별개인 가상 SIM 제품 16그룹·64건**을 작성했지. 그중 12그룹 48건으로 모델을 학습하고, 학습에 들어가지 않은 다른 4그룹 16건으로 점검했어. 이 16건은 이미 AI 사전 검토에 사용한 **개발용 Dev**이지 최종 블라인드가 아니야.

이번 RunPod는 **RTX PRO 4000 Blackwell**이었어. Qwen3-1.7B의 약 **0.186%** 파라미터를 LoRA로 12단계 학습했고, 어댑터 재로드 뒤 동일 16건에 대해 전후 비교했어. GPU 학습은 성공했지만 `schema_valid`는 **11/16 → 4/16**으로 떨어졌지.

**그런데 JSON 자체를 못 만든 게 주된 문제는 아니었어.** 학습 모델의 16개 출력 중 15개는 완전한 4개 필드를 가진 JSON이었어. 실패 대부분은 **`action`과 `missing_fields`의 조건 불일치**였지. 예를 들어 `ESCALATE`는 누락 필드가 비어야 하는데 `product_code`가 들어갔어.

더 문제인 건 **위험 상황에서 `ESCALATE` 행동은 4/4 맞히면서도, 고객 안내문인 `customer_message`에 고객 질문을 그대로 복사**했다는 거야. 누액·연기·전원선 손상에 대해 "사용을 중단하고 만지지 마세요"라는 안내가 전달되지 않았지. 그래서 **안전 행동 라벨 정확도와 실제 고객 안내 품질을 다르게 봐야 해.**

반대로 정답 인용 ID를 **JSON 계약과 독립적으로** 계산하면 BASE 8/16, LoRA 11/16이야. 이전의 5→2라는 수치는 계약 유효성을 통과한 경우에만 정답 인용을 인정하는 **복합 지표**였어. 숫자를 어떤 순서로 계산하는지 이해하는 게 중요해.

**S13의 결론:** 이번엔 추가 GPU 학습이 아니라 **답변 필드 의미(`customer_message`)·표준 누락 슬롯(`missing_fields`)·안전 안내문 품질**을 먼저 고쳐야 해. 보고서는 `experiments/s13_fictional_error_analysis/s13_failure_analysis.md`를 참고하면 돼.

## PART 2. 원리가 궁금할 때 읽는 기술 공부

### 1. SFT는 프롬프트를 바꾸는 것과 무엇이 다를까?

**프롬프트 개선**은 모델 가중치를 바꾸지 않고 *이렇게 답하라*는 지시를 입력에 추가하는 일이야. 반면 **SFT(Supervised Fine-Tuning)** 는 *이 입력에는 이 출력이 정답이다*라는 쌍을 보여주고, 예측 오차에 따라 **학습 가능한 파라미터의 값을 업데이트**해.

한 번 학습했다고 모델이 원문을 정확히 이해하게 되거나 모든 위험 답변이 사라지는 것은 아니야. 올바른 학습 데이터와 평가가 따로 필요해.

### 2. LoRA는 왜 더 적은 GPU 메모리를 사용할까?

보통의 전체 파인튜닝은 원래 모델의 큰 가중치 행렬까지 업데이트하지만, LoRA는 그 행렬 `W`를 고정하고 작은 두 행렬 `A`, `B`를 학습해 보정값을 더해.

\[
W_{\mathrm{effective}} = W + \frac{\alpha}{r}BA
\]

- `W`: 동결한 기존 모델 가중치.
- `A`, `B`: 새로 학습하는 작은 행렬.
- `r=16`: 보정 행렬을 얼마나 낮은 차원으로 표현할지 정하는 값. **큰 값이 언제나 좋은 것은 아니야.**
- `alpha=32`: LoRA 보정 크기에 작용하는 설정값.

이번에는 Qwen3의 `q_proj`, `v_proj`에만 LoRA를 붙여 먼저 구조를 확인할 거야. 왜 전체 선형층을 대상으로 하지 않았냐면, **처음에는 학습 가능한 부분·메모리·동작을 단순하게 추적하려는 목적**이기 때문이야. 이 설정이 최적의 성능을 낸다는 주장은 아니야.

**QLoRA**는 원래 모델 가중치를 4비트 등으로 압축해 메모리를 더 절약하면서 LoRA를 학습하는 접근이야. **이번 S10에서는 QLoRA를 실행하지 않아.** LoRA로 먼저 전체 흐름을 확인하고 메모리 문제가 있으면 다음에 비교하자.

### 3. Loss는 무엇을 의미할까?

모델이 다음 정답 토큰을 얼마나 잘 예측하는지에 대한 **학습 오차**야. 예를 들어 정답이 `"action": "ANSWER"`인데 모델이 `"action": "ASK"` 쪽에 더 높은 확률을 줬다면 오차가 커질 수 있어.

훈련 과정에서는 역전파(backpropagation)로 그 오차의 기울기를 구하고 LoRA 어댑터를 업데이트해.

**주의:** Train Loss 감소는 모델이 학습 예시에 더 잘 맞춰졌다는 신호일 뿐, 새로운 상담 질문에서 올바른 조치를 더 잘 결정한다는 증거는 아니야. 데이터가 작으면 **암기·과적합**도 쉽게 생겨.

**S10 실제 예:** 첫 번째 단계 Loss는 **1.701**, 마지막 단계는 **0.734**, 전체 학습의 평균 Loss는 **1.147**이었어. 그럼에도 가상 점검 질문의 JSON 스키마 통과는 **8/8→1/8**로 떨어졌지. 이 두 수치는 서로 모순이 아니야. **학습 대상 데이터의 다음 토큰 예측 오차**와 **학습하지 않은 문항의 응답 형식·행동 품질**은 서로 다른 지표거든.


### 4. 질문까지 외우게 해야 할까? 정답 부분만 학습시키자

이번 데이터는 다음처럼 두 덩어리로 나뉘어.

```text
[Prompt — 학습 때 참고할 입력]
  시스템 지시 + 가상 제품 코드 + 고객 질문 + 가상 근거

[Completion — 모델이 생성해야 할 정답]
  {"action": "ANSWER", "customer_message": ..., ...}
```

모델은 입력을 읽어야 하지만, **입력 문장 자체를 그대로 출력하는 연습**을 할 필요는 없어. 그래서 정답 부분에만 Loss가 계산되도록 설정했어.

```text
입력 Prompt 토큰:        label = -100  ← Loss 계산에서 제외
정답 Completion 토큰:  label = 실제 토큰 ID  ← Loss 계산에 포함
```

`SFTTrainer`에 전달하는 학습 데이터에는 이미 `input_ids`, `attention_mask`, `labels`를 만들어 넣어. **`-100`으로 마스킹한 입력 부분이 실제 미니배치에서도 유지되는지** 학습 전 검사하도록 했어.

Qwen3의 모델 입력은 `enable_thinking=False`로 고정해, M2의 구조화 JSON 실험과 같은 *비추론(thinking 비활성화) 출력 형식*을 사용해. 다만 이번 가상 데이터 실습과 M2의 실제 Dev 기준선을 직접 점수 비교하지는 않아.

### 5. 학습 데이터는 왜 40건이고 점검은 왜 8건인가?

이번에는 완전히 가상으로 작성한 **원본 상황 20개**를 각각 다른 표현으로 바꿔 총 **학습 문장 40개**를 만들었어. 행동 네 가지(`ANSWER`, `ASK`, `ESCALATE`, `EXPLAIN_UNSUPPORTED`)에 대해 원본 상황을 5개씩 배치했지.

별도의 **가상 점검 질문 8개**는 학습에 들어가지 않아. 원본 상황 ID도 겹치지 않아. 단, 동일한 가상 제품·비슷한 규칙을 사용하므로 이 8개를 **독립적인 일반화 평가나 WaterBridge Holdout**이라고 부르지 않아.

특히 기존 WaterBridge의 S07 26건, S08 Dev 6건, Holdout 6건은 **코드에서 아예 읽지 않도록** 분리했어.

### 6. 학습 전후 비교에서는 무엇을 똑같이 해야 할까?

원본(Base)과 LoRA를 적용한 모델을 같은 **Qwen3-1.7B 리비전**에서 불러오고, **고객 질문·근거·시스템 프롬프트·생성 설정**을 동일하게 할 거야. 오직 LoRA 어댑터 적용 여부만 바뀌도록 비교 코드를 구성했어.

이렇게 해야 모델 출력의 차이를 비교할 수 있지만, 이번 8개의 가상 사례만으로 어댑터의 일반적인 성능 우위를 입증할 수는 없어. S13의 실제 Dev 비교는 **실제 학습 자료와 근거 문제가 해결된 후의 별도 실험**이야.


### 7. S11의 중요한 판단 네 가지

**첫째, `Hit@5`와 근거 충분성은 다르다.** Gold ID가 Top-5에 존재해도 정답 답변에 필요한 구체적인 조치·조건이 검색 본문에 없을 수 있어. 잠금 해제 절차와 물받이 넘침 여부 확인이 실제 사례야.

**둘째, 비슷한 오답 근거가 '하드 디스트랙터'가 된다.** 저출수와 완전 무출수, 정상적인 냉수 온도 상승과 지속적인 냉각 이상은 표현이 비슷해도 적절한 안내가 달라. 정답 문서를 2위로 밀어내는 다른 근거까지 함께 점검해야 해.

**셋째, 데이터 개수가 아니라 독립 상황과 행동 분포를 확인한다.** S07의 `ANSWER` 12, `ASK` 4, `ESCALATE` 10, `EXPLAIN_UNSUPPORTED` 0건은 재표현까지 포함한 행 수야. 같은 원본의 말투만 바꾸면 새 문제 해결 능력이 생겼다고 입증할 수 없어. 특히 **미지원 기능은 근거가 없다는 사실만으로 단정하지 말고, 기능 목록처럼 명시적인 근거를 확인한 뒤 행동을 결정**해야 해.

**넷째, S10 JSON 퇴행의 원인을 데이터 부족 하나로 단정하지 않는다.** S10 정답 예시에는 4개 필드가 있었지만 LoRA 출력에서 `missing_fields`가 빠지고 JSON이 중복 생성됐어. 모델·학습량·디코딩·종료 토큰·데이터 표현 등을 후속 실험에서 분리해 봐야 해.

### 8. child ID와 group ID는 역할이 다르다

비유하자면 `evidence_group_id`는 **설명서의 한 주제(서랍 이름)**이고, `child_id`는 그 안에 들어 있는 **특정 문단(서랍 속 문서 한 장)**이야. 같은 서랍을 찾았다고 해서 그 안의 모든 문단을 실제로 읽었다고 말할 수는 없어.

- **정확한 child 미리보기:** 기존 S09 결과에서 **실제로 검색된 다섯 청크만** 원래 child ID로 다시 표시한다. 어떤 문장을 봤는지 식별할 수 있지만, 과거 그룹형 결과가 잃어버린 **전역 child 순위와 코사인 점수는 복원할 수 없다.**
- **같은 그룹의 청크 추가(비교용):** 실제 검색된 그룹에 속한 **다른 검증 청크도 추가 제공**한다. 특정 Gold ID를 보고 추가하는 방식이 아니라 같은 그룹의 전체 후보를 추가한다. 그래서 **불필요한 문서가 늘어날 위험**과 입력 토큰 증가도 함께 고려해야 해.
- **원문에 있지만 인덱스에 없는 절차:** 정확한 PDF 페이지를 확인해 별도 추출·검증·인덱싱해야 한다. 모델이 모르는 절차를 SFT로 외우게 하는 것은 근거 문제의 해결책이 아니다.

**가장 중요한 제한:** 청크 ID가 정확해진 것만으로 고객 답변이 올바르다는 보장은 없다. **본문에 실제로 해당 주장을 뒷받침하는 문장이 있는지** 검토하고, 문서 이용 권한을 확인해야 해. 따라서 현재 생성하는 두 미리보기에는 **정답 assistant 출력 자체를 넣지 않아**, 실수로 학습 데이터로 쓰는 것을 막았어.

**학습 이용 권한:** 2026년 한국저작권위원회가 발간한 AI 학습 관련 공정이용 안내서는 개별 검토를 위한 참고자료야. 모든 학습이 자동 허용되거나 금지된다는 의미가 아니고, **SK매직 원문 학습 허락을 증명하는 문서도 아니야.** 현재 별도 이용 근거가 확인되지 않아 SFT 승인을 보류한다. 상세 체크리스트는 `portfolio_upgrade/docs/s11_source_use_review.md`를 참고해.

### 9. 새 청크를 추가하면 검색 성능이 자동으로 좋아질까?

**인덱스에 있음(index coverage)**과 **검색 Top-5에 들어옴(retrieval recall)**은 서로 다른 지표야. 이번에는 ‘잠금 해제 방법이 아예 없는 53개’와 ‘그 방법을 추가한 55개’를 동일한 임베딩 모델·질문·제품 필터·Top-5·임계값으로 비교하도록 만들었어.

- 비교 전: 원본 53청크를 수정하지 않고 SHA-256으로 동일 판본인지 확인한다.
- 비교할 것: 새 해제 절차의 **개별 `child_id`**가 잠금 질문 4행(BASE/PAR1)의 Top-5에 들어왔는가? 들어왔다면 몇 위인가?
- 주의할 것: 두 새 청크는 기존 **Gold 그룹 ID를 재사용**하기 때문에, 그룹 단위 Hit@5는 원래부터 높을 수 있다. **새로운 조작법을 실제로 찾았는지** 별도로 점검해야 한다.
- 금지할 것: 평가용 Gold를 검색 전에 넣거나, 새로운 문서를 무조건 삽입해 놓고 ‘검색 성공’으로 계산하는 방식.

**왜 기존 PDF를 학습시키지 않고 RAG 청크만 만드는가?** 제조사 매뉴얼의 학습 사용 조건은 아직 확인되지 않았어. 이번 후보의 `allowed_use=RAG_HANDOFF_ONLY`는 **오프라인 검색 근거 검수**에만 쓰고, SFT 데이터로 변환하거나 사용을 승인하는 플래그를 켜면 안 돼.

### 10. 검색 후 조건 검사(Post-retrieval gate)는 무엇을 하고, 무엇을 못 할까?

이번 필터는 **새로 색인한 두 개의 `COLD-LOCK-UNLOCK` child ID만** 대상으로 해. 기존 Top-5 중 다른 문서를 손대지 않고, 다른 제품의 해제 절차를 새로 끼워 넣지도 않아.

1. **입력:** 검색 결과의 `child_id`, 제품 코드, 고객의 **원문 발화**. 사람이 만든 `selected_symptoms`, 정답 행동, Gold ID는 필터의 판단에 사용하지 않아.
2. **유지:** 냉수 버튼 선택과 **잠금 표시 점멸**이 명확하고, 누수/전기 위험·잠금 해제 완료·잠금 표시 없음 등의 반대 정보가 없을 때.
3. **제외:** 해당 신호가 없거나 조건이 충돌하면 상세 해제 절차를 제외. **이것은 고장 진단·상담 자동 배정이 아니라 검색 근거 전달을 제한하는 결정**이야.
4. **검증:** 사람이 이전에 분류해 둔 4건/6건을 **필터가 작동한 뒤에만** 대조해. 평가 라벨은 오직 채점에만 사용해.

이 선택에는 대가가 있어. 보수적인 규칙은 표현이 다른 진짜 잠금 문의에서도 필요한 근거를 빼버릴 수 있고, 기존 요약 청크(`COLD-LOCK-001`)는 그대로 남아 있어. 또 이번 실험은 한국어 정규식 기반의 작은 조건 검사일 뿐 기존 WaterBridge의 전체 `Safety Stage`가 아니야.

**기술적 판단:** 개발용 10건에서 성공했다고 무조건 운영에 적용하지 않아. 앞으로는 고객 표현의 변형, 부정·동시 증상, 제품 혼동, 누수 같은 위험 사례를 독립적으로 만들어 재평가하고, 필요하다면 더 강한 분류기 또는 근거 재정렬과 비교할 수 있어. 다만 이번 S11에서 그 성능을 측정했다고 말하지 않아.

### 11. Top-K를 늘리면 Recall이 올라가는 대신 무엇이 위험해질까?

- **Top-K:** 검색 결과 중 모델에 제공할 최대 후보 수. 이번에는 5, 8, 10을 비교한다.
- **Recall 관찰:** 필요하다고 지정된 두 근거가 후보 안에 *모두* 들어왔는지 확인한다. Gold 하나만 발견한 Hit@K와 다르다.
- **유사도 임계값:** 후보가 전체 제품 검색 순위 6위여도 유사도 **0.4 미만**이면 이번 정책에서는 여전히 제외된다. 순위와 임계값을 분리해 기록한다.
- **반대 효과:** 추가 청크는 잘못된 제품 지침을 주거나 조건을 섞을 위험, 입력 토큰과 지연 비용을 높일 수 있다. 특정 Train 문의 하나를 맞혔다고 Top-10을 전역 채택하지 않는다.

이번 스크립트에서는 검색 점수를 **Gold를 보지 않고 먼저 전부 계산**한 뒤, 나중에만 정답 그룹 ID와 대조한다. S09와 지난 S11의 동일 53개 인덱스 재검색 기록이 다를 가능성도 `drift`로 따로 보고한다.

### 12. 새로운 학습 데이터의 ‘정답 누출’은 어떻게 막을까?

S11에서는 **질문·제품 코드·근거 문장 2개**만 사용자 입력으로 만들고, 올바른 행동과 응답은 `assistant` 정답에만 넣었어. 학습에서는 정답 응답을 Loss 대상으로 사용해도 되지만, **추론·평가할 때 사용자 메시지에 그 정답을 미리 넣으면 안 돼.**

또한 `SIM-L01` 같은 가상 제품 한 종류에서 네 행동을 모두 만들었기 때문에, 단순히 질문을 48/16으로 무작위 나누면 같은 제품 규칙이 Train과 Probe에 섞일 수 있어. 그래서 **제품·주제 그룹(F01~F16) 전체를 분할**했어. Train은 F01~F12, Probe는 F13~F16이야. 이렇게 하면 정확히 같은 제품 규칙을 학습하고 평가하는 누출은 방지할 수 있지만, *모든 의미상 유사성을 제거했다는 증거*는 아니야.

`EXPLAIN_UNSUPPORTED`를 만들 때는 검색 문서가 없다는 이유만으로 ‘없는 기능’이라고 정답을 지정하지 않았어. **모델별 미지원이 적힌 가상 정책 근거를 반드시 제공**했어. `ASK`에서는 `missing_fields`를 비워두지 않았고, 다른 행동의 JSON에도 필드 자체는 항상 들어가도록 했어. 이는 S10에서 발생한 `missing_fields` 누락 실패를 다시 검증하려는 설계야.

**주의:** 이번 데이터의 근거 2개는 직접 작성해 제공한 것이지 BGE-M3에서 실제 검색된 결과가 아니야. 따라서 S12에서 개선이 나타나도 이를 WaterBridge의 RAG 검색 품질 개선이라고 주장하지 않아.

### 13. 같은 데이터를 수정할 때 왜 원본을 남겨야 할까?

자동 검수에서 문제를 찾고 학습 파일을 그대로 덮어쓰면 **어떤 질문을 고쳐 성능이 바뀌었는지** 나중에 설명하기 어려워져. 그래서 이번에는 **v1 파일의 SHA-256을 검증하고, 수정본은 `data/s11_grounded/v2/`에 별도로 기록**했어.

- **질문 수정:** "소리 없음"과 "소리가 작음"처럼 조건이 다를 때는 근거와 질문을 일치시켜야 해.
- **근거 수정:** 하나의 근거 ID는 **모든 질문에서 같은 본문**을 가리켜야 해. 가상 정책을 고친다면 해당 ID를 사용하는 다른 질문에도 동시에 반영해야지.
- **이미 확인한 조건:** `known_conditions`는 모델이 추가로 알아야 할 고객 진술이지, `action`이나 Gold를 넣는 곳이 아니야.
- **학습·평가 분리:** Train 48건의 정답은 `assistant`에 있지만 Probe 16건의 모델 입력에는 **정답 메시지가 없어**. Probe의 기대 출력은 별도 `EVAL_ONLY` 파일에서만 확인해.

가장 중요한 제한은 **Probe가 이미 사전 내용 검수에서 공개된 개발용 점검 데이터**라는 점이야. 이 점수를 최종 블라인드 일반화 결과로 발표하면 안 되고, S12 학습·프롬프트 선택이 끝나면 별도 평가가 필요해.

### 14. 왜 JSON 스키마와 행동 정답을 별도로 계산할까?

모델의 답변 평가는 하나의 `정확도`로 축약하기 쉬워. 하지만 **의도 분류와 구조 출력은 서로 다른 실패 요인**이야.

- **`json_object`**: 출력 전체가 단 하나의 JSON 객체인지 확인. ```json 코드블록이나 연속된 두 객체는 탈락.
- **`fields_exact`**: `action`, `customer_message`, `cited_evidence_ids`, `missing_fields` 네 이름만 정확히 갖는지 확인.
- **`field_types_valid`**: 행동은 네 가지 enum 중 하나, 메시지는 비어 있지 않은 문자열, 두 필드는 문자열 배열.
- **`schema_valid`**: 앞의 구조 조건에 더해 인용 ID가 **제공된 근거의 부분집합(중복·빈 인용 금지)**이고, `ASK`에는 최소 하나의 `missing_fields`, 그 외 행동에는 빈 배열이 있어야 함.
- **`raw_action_match`**: 구조가 부서져도 `action` 문자열이 맞으면 기록. `strict_action_match`는 스키마 정상이라는 추가 조건을 요구.
- **`structured_target_match`**: 엄격한 행동 일치 + 근거 ID 집합 일치 + `missing_fields` 집합 일치. **답변 문장의 의미 적합도나 실서비스 만족도 측정은 별도.**

이렇게 나누면 **행동 선택만 나아지고 JSON 스키마가 무너지는 S10의 오류**를 점수에 숨기지 않을 수 있어. `customer_message`를 정답과 정확히 같은 문장으로 쓰도록 강요하지는 않아. 문장이 달라도 의미가 맞을 수 있고, 반대로 유사해도 위험한 표현이 있을 수 있으니까.

### 15. Train 48건의 정답은 어디까지 모델에 보여줄까?

학습용 메시지에는 `system`·`user`·`assistant`가 모두 있지만, **Loss를 계산하는 토큰은 `assistant` 정답 부분뿐**이야. 프롬프트 토큰의 `labels`에는 `-100`을 넣어 무시하고, 응답 JSON 토큰에는 실제 토큰 ID를 넣어 오차를 계산하지.

```text
input_ids: [시스템·고객·근거 ... ][정답 JSON ... ][<|im_end|>]
labels:    [ -100 -100 -100 ... ][정답 토큰 ... ][종료 토큰]
```

S12에서는 generic collator가 `labels`를 다시 만들지 않도록 **직접 만든 collator로 라벨을 보존**하고, 실제 Trainer 배치에서도 마스킹이 남아 있는지 확인한 뒤에 학습해. Dev 정답 파일은 훈련 데이터 생성과 Trainer에 **절대 전달하지 않아.**


### S13에서 배운 기술: JSON 파싱·구조 스키마·행동 정책을 분리하기

```text
JSON 파싱 가능?  →  정확한 네 필드/타입?  →  인용 ID가 실제 제공된 것?  →  action별 missing_fields 규칙?
        │                    │                        │                               │
     syntax                shape                grounding                       policy
```

S12의 `schema_valid`는 **네 단계 중 앞의 둘만 의미하지 않아.** citation ID 검증과 `missing_fields` 정책을 모두 통과해야 해. `citation_exact`도 `schema_valid`를 전제하므로 **문서 ID를 정확히 골랐어도 출력 정책을 위반하면 0점**을 받는다.

따라서 정확한 원인 분석을 위해서는 **① 엄격 JSON, ② 필드·타입, ③ 인용 ID 존재, ④ 행동별 누락 슬롯 조건, ⑤ 인용 ID 정답 일치, ⑥ 고객에게 실제로 전달되는 안내문**을 나눠서 보아야 해. 이것이 S13에서 S12 응답 원문을 다시 채점한 이유야.

특히 입력의 `customer_message`는 고객의 질문인데 출력에서도 같은 이름의 필드가 정답 고객 안내문을 뜻하는 건 **명명 충돌**이야. 데이터와 프롬프트가 이를 명시하지 않으면 모델이 질문을 그대로 복사할 수 있어. 다음 S14 실험에서는 이 의미를 명확하게 전달하는 별도 계약을 만들어야 해. 또 `missing_fields`의 자유 문자열 대신 **허용된 정규 슬롯 키**를 정의해야 해.

### 3. RunPod 재현 방법 — **이미 실행 완료, 다시 돌릴 필요 없음**

**S10에서는 앞서 쓰던 A40급 CUDA GPU 한 대로 시작**하되, 현재 Pod 상태·스토리지와 시간당 요금은 실행 전 직접 확인해. 스크립트는 GPU를 자동으로 생성하거나 대여하지 않아.

아래 명령어는 **이미 실행한 S10을 재현해야 할 때만** 참고하는 기록이야. 현재 LoRA 학습은 완료됐으므로 GPU 요금을 다시 지불하며 실행할 필요 없어.

```bash
cd /workspace
# 기존에 CUDA torch가 있는지 먼저 확인
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
# CUDA torch가 정상인 기존 가상환경에서만 의존성을 설치
python -m pip install -r portfolio_upgrade/configs/s10_requirements.txt

# 데이터 및 토큰 마스크 확인 (학습 전)
python portfolio_upgrade/scripts/s10_prepare_demo.py --check
python portfolio_upgrade/scripts/s10_train_lora.py --token-check

# 여기서부터 Qwen3 모델 가중치 로드와 실제 GPU 학습
python portfolio_upgrade/scripts/s10_train_lora.py --run --ack-cost

# **같은 GPU 세션에서**, 저장된 어댑터 재로드와 원본 비교까지 완료
python portfolio_upgrade/scripts/s10_probe_adapter.py --run --ack-cost
```

**중요:** `--ack-cost`를 명시해야 학습/추론을 시작하도록 했어. 코드는 실행 후 `adapter/`, `training_report.json`, `toy_probe_predictions.jsonl`, `toy_probe_summary.json`를 남기고, 완료한 실험을 다시 덮어쓰지 않도록 해. 오류가 나면 원인을 확인하기 전에 명령을 반복 실행하지 마.

특히 **RunPod를 Stop/Terminate하기 전에**, `portfolio_upgrade/experiments/s10_sft/pilot/` 폴더 전체를 **사용자 로컬 PC나 확실히 유지되는 저장 공간으로 복사**해야 해. 이전처럼 GPU를 다시 대여해서 결과 확인을 반복하지 않기 위한 절차야.

#### 학습 실행 기록 (실측)

| 항목 | 결과 |
|---|---|

| Loss | 첫 스텝 **1.701**, 마지막 스텝 **0.734**, 전체 평균 **1.147** |

학습 Loss의 단계별 값은 `training_report.json`의 `logs[].loss`에서 확인할 수 있어. 로그를 비교할 때 **첫 단계와 마지막 단계 수치**를 **전체 평균**과 혼동하지 마.

#### 가상 점검 8건 비교 (실측)

| 지표 | 원본 | LoRA | 결론 |
|---|---:|---:|---|
| JSON 문법 정상 | 8/8 | 6/8 | 퇴행 |
| 기대 행동 일치 | 5/8 | 6/8 | 1건 증가. 파싱 실패도 실패로 포함 |
| 스키마 준수 | 8/8 | 1/8 | **중대한 형식 퇴행** |
| 스키마와 행동 모두 충족 | 5/8 | 1/8 | 형식까지 고려하면 퇴행 |

**8건에서 무엇이 달라졌나?**

| 사례 | 기대 행동 | 원본 → LoRA | 관찰 |
|---|---|---|---|
| P01 화면 밝기 | ANSWER | ANSWER → ANSWER | 둘 다 완전한 JSON |
| P02 배터리 잔량 | ANSWER | ANSWER → 파싱 실패 | LoRA가 여러 JSON 객체를 연속 생성. 첫 객체가 맞더라도 엄격한 출력 계약에서는 실패 |
| P03 계정 잠금 | ASK | EXPLAIN_UNSUPPORTED → ASK | 행동은 개선, LoRA에 `missing_fields` 누락 |
| P04 업데이트 정체 | ASK | EXPLAIN_UNSUPPORTED → 파싱 실패 | 여러 객체를 출력. 첫 객체의 행동도 `ANSWER`로 기대와 다름 |
| P05 충전 중 누액 | ESCALATE | ESCALATE → ESCALATE | 행동은 유지, LoRA에서 필수 필드 누락 |
| P06 충전 단자 과열 | ESCALATE | EXPLAIN_UNSUPPORTED → ESCALATE | 행동은 개선, LoRA에서 필수 필드 누락 |
| P07 동영상 기능 미지원 | EXPLAIN_UNSUPPORTED | 동일 → 동일 | 행동은 유지, LoRA에서 필수 필드 누락 |
| P08 모바일 데이터 미지원 | EXPLAIN_UNSUPPORTED | 동일 → 동일 | 행동은 유지, LoRA에서 필수 필드 누락 |

**실패 원인 단정 금지:** 학습용 40건의 정답은 **모두 필수 JSON 4필드를 포함**했어. 따라서 `missing_fields` 누락을 학습 정답에 필드가 없었다는 이유로 설명할 수는 없어. 작은 학습 데이터·한 번의 학습·생성 조건 등이 영향을 줬을 가능성은 있지만, 이번 실행에서 원인을 분리해 검증하지는 않았어.

**점수 범위 주의:** `schema_valid`는 필드 존재와 형식에 대한 검사야. 해당 안내가 공식 문서에 맞는지, 인용 ID가 조치를 뒷받침하는지까지 자동 판정한 점수가 아니야. 가상 질문 8건은 WaterBridge Dev/Holdout도 아니고 독립적인 서비스 성능 평가도 아니야.

행동별로는 LoRA의 `ESCALATE`가 2→4건으로 증가했으나 `ANSWER`와 `EXPLAIN_UNSUPPORTED`는 **0→0**이었다. 학습의 정성·인과 분석은 별도이며, **고객 안내 문장 품질은 S12의 공식 지표에 포함되지 않았다**. S13 보고서는 16건을 모두 조사했고 안전 응답을 문장 단위로 확인했어.

**판정:** S12 파일럿은 **GPU 학습과 재로드 성공**, 학습된 모델의 DEV 계약 품질 개선 실패. 이제 S14에서 **출력 계약과 데이터 명세 개선을 먼저 실행**하고, 별도 독립 테스트를 준비해야 해. 실제 WaterBridge 매뉴얼로 SFT하거나 서비스에 적용한 것이 아님.
