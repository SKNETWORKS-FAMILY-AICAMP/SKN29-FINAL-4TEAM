## PART 1. 먼저 읽는 실험 이야기

### S03. 검색기가 맞는 문단을 찾기 전에, 이미 질문을 잘못 이해할 수 있다

#### M0의 Q008을 다시 보자

> **Q008:** “필터를 이미 갈았는데도 물이 조금씩만 나와요.”

M0에서는 **저출수**와 **완전 무출수** 문단을 검색기가 혼동하는 문제를 발견했지. 그런데 실제 고객 응대 시스템에서는 그보다 앞에 한 단계가 있어.

**“고객이 지금 무엇 때문에 문의했는지 파악하는 과정”**이야.

고객이 필터라는 단어를 썼다고 해서 '필터 교체 방법을 알려 달라'는 뜻은 아니야. 현재 문제는 **물줄기가 약한 것**, 이미 한 조치는 **필터 교체**야.

#### 실제 코드에서는 어떤 일이 생겼을까?

기존 WaterBridge의 **규칙 기반 증상 분류 함수**에 Q008을 넣었더니 `필터/관리 문의`로 분류됐어. 반면 “출수량이 적어요”라는 표현은 저출수 규칙에 맞았지.

분류 결과를 바꿔 같은 **샘플 근거 7개**를 필터 함수에 넣어 봤어.

- `필터/관리 문의`로 처리하면 **7개가 모두** 남았어.
- `출수량 저하`로 처리하면 **저출수 관련 1개**만 남았어. 이 경우에는 어떤 물 종류인지 묻는 정보도 중요하게 취급됐고.

**핵심 발견:** 질문을 어떻게 이해했는지에 따라 **뒤에서 검색 근거를 고르고 고객에게 추가 질문하는 방식까지 달라질 수 있다**는 거야.

하지만 여기서 오해하면 안 돼. 이 실험은 실제 DB에서 검색하고 LLM이 최종 답변까지 생성한 것이 아니야. **일부 함수만 따로 실행**한 결과이므로, 운영 서비스가 실제로 Q008에 오답을 냈다고 말할 수는 없어.

그럼 이제 다른 의문이 생기지.

**“검색과 답변이 맞는지 평가하려면, 무엇을 정답으로 정해야 할까?”**

### S04. 시험을 보기 전에 정답지부터 검수해야 한다

#### 설명서의 조건이 빠진 정답지는 위험하다

예를 들어 고객이 이렇게 질문했어.

> “가족들이 냉수를 연달아 많이 받은 직후부터 물이 덜 차가워졌어요.”

해당 설명서의 안내는 **잠시 기다린 다음 다시 냉수를 받는 것**이야. 그런데 평가 데이터의 정답에 이 조치가 빠져 있다면 어떨까?

AI가 올바르게 답해도 오답으로 채점하거나, 중요한 조치를 누락한 답을 정답으로 판단할 수 있어. 그래서 모델을 평가하기 전에 **공식 사용설명서와 정답 데이터를 직접 대조**했어.

이번에는 세 종류의 공식 PDF, 총 **144쪽**을 기반으로 한 합성 문의 **30건**을 살펴봤어. 이 중 **16건은 기존 라벨·조치·출처에 대한 보완 의견**을 남겼지. 실제 팀 원본 데이터를 모두 고쳐 반영한 것은 아니야.

#### 왜 30개를 무작위로 나누지 않았을까?

모델을 학습시키고 평가하려면 질문을 나눠야 해.

- **Train:** 모델에 가르칠 문제
- **Dev:** 개발하면서 규칙이나 프롬프트를 비교할 문제
- **Holdout:** 선택을 끝낸 뒤 마지막에 확인할 문제

그런데 “물을 연속으로 많이 받아 미지근해졌다”는 같은 문제를 말만 바꿔 Train과 Holdout에 넣으면, 시험을 처음 보는 것처럼 보이더라도 사실은 **이미 배운 문제를 다시 풀게 하는 셈**일 수 있어.

그래서 질문 **30건을 의미상 16개 그룹**으로 묶고, 같은 그룹이 서로 다른 분할에 들어가지 않도록 했어.

```text
합성 고객 문의 30건
      ↓ 비슷한 원인·근거·조치를 공유하는지 검토
의미 그룹 16개
      ↓ 그룹이 서로 다른 분할로 갈라지지 않도록 배치
Train 18건 / Dev 6건 / Holdout 6건
```

**중요한 점:** 같은 그룹이라고 반드시 정답 행동까지 같지는 않아. 예를 들어 *냉수를 많이 사용한 직후 잠시 덜 차가운 경우*는 기다렸다 재출수하라고 안내할 수 있지만, *2시간이 지나도 계속 미지근한 경우*는 상담이 필요할 수 있지. 비슷한 증상을 공유하기 때문에 같은 그룹에 둘 수 있어도 **적용 조건과 행동은 구별**해야 해.

이제 비교에 사용할 문제와 정답이 준비됐어. 그다음 질문은 이거야.

**“정답 문서를 찾으면 LLM은 제대로 답할까?”**

### S05. 정답 문서를 직접 줬는데도 AI가 잘못 안내했다

#### 검색 문제와 답변 문제를 나눠 보자

이번에는 S04의 **Dev 6건**을 사용했어. 한 가지 조건만 사용하면 오류가 어디서 생겼는지 모르니, 세 방식으로 나눠 비교했지.

**A. Oracle:** 평가자가 확인한 정답 근거를 **검색하지 않고 직접** LLM에게 줘. 검색이 성공했다고 가정한 조건이야.

**B. 일반 RAG:** BGE-M3로 실제 후보 문서를 검색한 결과를 LLM에게 줘.

**C. 안전 라우팅 RAG:** 위험·부정·무출수 등 조건을 먼저 살펴보고, 명확한 전체 무출수라면 해당 문서 후보를 우선하도록 제한한 뒤 검색해.

검색 결과는 달라졌어. 검색용 **Gold(평가상 정답 근거)**가 정의된 **5건**에서 상위 5개 안에 정답 근거를 넣은 수가 **일반 RAG 3/5 → 안전 라우팅 5/5**가 됐거든.

그런데 더 흥미로운 결과가 나왔어.

#### 행동은 맞혔는데, 안내 내용이 틀렸다

세 조건 모두 LLM의 **행동 라벨(ANSWER·ASK·ESCALATE 등)은 6/6** 일치했어. 이것만 보면 완벽해 보이지?

하지만 `JAC104-030`은 달랐어.

> **고객:** “7일 동안 집을 비운 뒤 냉수와 정수에서 평소와 다른 냄새가 납니다. 아직 마시지 않았어요.”

공식 설명서에서 이 조건에 맞는 핵심 조치는 **냉수·정수·온수를 각각 1L 이상 출수해 버린 뒤 사용하는 것**이야.

LLM은 이 안내를 했지만, **확인되지 않은 필터 전체 교체까지 추가**했어. 심지어 정답 문서를 처음부터 직접 제공한 **Oracle 조건에서도** 같은 종류의 문제가 나타났지.

즉, *검색만 개선하면 해결되는 오류가 아니라* **찾은 문서의 조건을 잘못 적용한 답변 오류**도 있었던 거야.

다른 사례인 `JAC104-033`에서는 **제빙 기능이 없는 제품**에 관한 질문에 무관한 **온수 안전 문서**를 인용했어. 존재하는 근거 ID를 골랐더라도 **그 문서가 실제 주장을 뒷받침하는지는 별도 문제**라는 걸 보여줬지.

#### 그래서 M1에서 결정한 것

**검색기를 더 좋게 만드는 일만으로는 충분하지 않아.** 검색 전에 질문을 제대로 이해해야 하고, 검색 후에는 제품·조건에 맞는 조치인지 확인해야 해.

또 안전 라우팅의 5/5는 **Dev의 실패를 보고 규칙을 만든 후 같은 Dev에서 다시 확인한 수치**야. 새로운 고객에게도 100% 통한다는 증거는 아니지.

이제 M2로 넘어갈 이유가 생겼어. **정답 근거가 있어도 조건을 어기는 오류**를 줄이고 싶다면, 무엇이 좋은 답이고 무엇이 금지되는 조치인지 학습 데이터로 정의해볼 수 있겠지. 다만 **SFT가 실제 해결책인지는 따로 시험**해야 해.

#### PART 1을 읽고 기억할 세 문장

1. **S03:** 질문을 잘못 분류하면 검색 근거와 추가 질문까지 달라질 수 있어. 다만 이번에는 함수 일부만 실행했어.
2. **S04:** 잘못된 정답으로 평가하지 않도록 공식 PDF를 검수하고, 비슷한 문제는 같은 의미 그룹으로 묶어 분할했어.
3. **S05:** 검색 Hit@5는 **3/5 → 5/5**가 됐지만, Oracle에서도 **조건에 맞지 않는 추가 조치**가 나타났어. 검색과 답변 품질은 다른 문제야.

여기까지 이해하면 **M1의 핵심을 잡은 거야.** 아래는 왜 그런 현상이 생겼는지 기술적으로 복기할 때 읽어봐.

## PART 2. 원리가 궁금할 때 읽는 기술 공부

### 1. 실제 RAG는 '검색기 하나'가 아니다 — S03

M0에서 검색기를 비교할 때는 **질문 → 문단 검색 → 정답 순위 측정**만 했어. 하지만 실제 WaterBridge는 여러 단계를 통과해.

```text
[고객 질문 + 제품 판매코드]
       ↓
[structuring] 현재 증상 / 이미 한 조치 등 구조화
       ↓
[safety] 누수·전기 위험 등 확인
       ├─ 위험 → 안전 우선 답변 경로
       └─ 일반
             ↓
[missing_fields] 답하기 전에 추가로 물어볼 정보가 있나?
       ├─ 필요 → 질문 후 대기
       └─ 충분
             ↓
[retrieval] 관련 공식 근거 검색 + 제품·토픽 검증
       ↓
[generation] 고객 안내 생성
       ↓
[validation] 결과 검증
```

이것은 기존 `single_rag_pipeline.py`에서 확인한 **코드상 흐름을 단순화한 그림**이지, S03에서 전부 실시간 E2E 실행했다는 뜻이 아니야.

여기서 각 기술의 역할을 구분해보자.

- **RAG:** 관련 문서를 찾아 답변 생성 시 참고하게 하는 **방식**.
- **LangGraph:** 각 단계의 상태와 *위험이면 다른 경로로 간다* 같은 **분기**를 관리하는 도구.
- **BGE-M3:** 질문·문서를 **임베딩 벡터**로 변환하는 모델.
- **PostgreSQL + pgvector:** 벡터를 저장·비교해 문서 후보를 검색하는 기반.
- **Policy Gate:** 검색에 들어가기 전, 제품 지원 범위·기능·자료 허용 여부를 판정하는 규칙.

**기술적 판단 — 왜 LangGraph?** 조건별로 경로가 달라지는 응대 과정을 노드와 상태로 표현하면 **어디서 분기했고 무엇 때문에 멈췄는지** 추적하기 쉬워. 하지만 LangGraph를 썼다고 안전성이나 정답률이 자동으로 좋아지는 건 아니야.

### 2. Q008에서 무엇이 먼저 잘못될 수 있나?

기존 규칙 분류 함수 `SymptomNormalizer.normalize_symptom_type()`은 표현을 키워드로 탐색해 표준 증상을 정해. Q008의 `조금씩만 나와요`는 당시 저출수 규칙에 매칭되지 않았고 `필터`라는 표현은 필터 관리 규칙에 매칭됐어.

문제는 **같은 단어가 다른 역할**로 쓰인다는 거야.

```text
"필터는 언제 교체하나요?"
       → 현재 질문: 필터 관리

"필터를 교체했는데도 물이 조금씩 나와요."
       → 현재 질문: 저출수
       → 이미 수행한 조치: 필터 교체
```

`필터`라는 단어 자체를 삭제하면 첫 번째 정상 문의를 처리하기 어려워져. 그래서 **현재 증상 / 이미 한 조치 / 부정 표현 / 위험 신호를 구별하는 것**이 더 적절한 개선 방향이야.

분류 결과는 두 곳에도 영향을 줬어.

- **근거 필터:** 샘플 청크 7개를 넣었을 때 `필터/관리 문의`는 7개, `출수량 저하`는 1개가 남았어.
- **필수 문진:** `출수량 저하`에는 `target_water_type`(어떤 물 종류인지)의 중요도가 `high`로 설정됐어.

**중요한 제한:** 이것은 규칙 함수와 후처리 함수의 **부분 실행**이야. 실제 LLM 기반 구조화가 개입할 경우 결과가 달라질 수 있어. 실서비스 최종 답변이 틀렸다고 여기서 단정하지 않아.

### 3. '검색 허용'과 '검색 성공'은 완전히 다르다

기존 정책 코드에서 반환하는 `PGVECTOR_QUERY`는 **검색을 진행해도 된다는 결정**이야. 정답 문서를 찾았다는 뜻은 아니야.

예를 들어 다음과 같은 판단이 있었어.

| 질문/조건 | 정책상의 예시 반환 | 의미 |
|---|---|---|
| 지원되는 제품의 정상 질문 | `PGVECTOR_QUERY` | 검색 허용 |
| 미등록 판매코드 | `POLICY_BLOCK_UNREGISTERED_EXACT_SALES_CODE` | 해당 코드로 검색 진행하지 않음 |
| 제품에 없는 기능 | `POLICY_BLOCK_UNSUPPORTED_CAPABILITY` | 기능 정책상 차단 |
| 필터 가격 등 정적 매뉴얼 밖의 질문 | `POLICY_BLOCK_OUT_OF_MANUAL_SCOPE` | 다른 데이터/업무 경로 필요 |

검색을 허용한 뒤에도 정답을 놓칠 수 있고, 검색 결과가 나온 뒤 제품·토픽 필터에서 다시 제외될 수도 있어. 실제 코드의 메타데이터 정책은 **정확한 판매코드, 문서 검증 상태, 이용 가능 범위(`allowed_use`)** 등도 구분해. 관련성이 높은 문서라도 다른 제품·승인 범위의 자료라면 그대로 사용하면 안 되니까. 그래서 오류를 진단할 때는 **정책 → 검색 후보 → 후처리 → 생성**을 구분해야 해.

### 4. 정답지를 어떻게 만들고 왜 '의미 그룹'으로 나누나? — S04

S04는 합성 고객 문의 **30건**, 공식 사용설명서 **3종(총 144쪽)**, 후보 청크 **53개**, 근거 그룹 **43개**를 바탕으로 했어. 공식 PDF와 대조해 **16건의 보완 제안**을 남겼고, 해당 제안을 팀 원본에 반영했다는 뜻은 아니야.

**Gold**는 평가할 때 정답으로 인정할 정보야. 이번 프로젝트에서는 단순한 문단 ID 외에 **기대 행동·필수 조치·적용 조건·출처**도 중요해.

예를 들어 **냉수가 미지근하다**는 두 질문을 비교해보자.

| 고객 상황 | 기대 행동 | 왜 다른가? |
|---|---|---|
| 냉수를 여러 번 연속 출수한 **직후** 덜 차가워짐 | `ANSWER` | 잠시 기다렸다 다시 출수하는 조치가 있음 |
| 전원과 잠금을 확인했고 **2시간 후에도** 계속 미지근함 | `ESCALATE` | 지속 이상으로 상담센터 문의 조건에 해당 |

이 사례들이 같은 **의미 그룹**에 들어갈 수도 있어. **같은 라벨**이라서가 아니라, 냉수 온도 문제에 관한 **공통 근거·원인 구조를 공유**하기 때문이야. 그래서 그룹이 Train과 Dev 또는 Holdout으로 갈라지지 않도록 관리했어.

**무작위로 행 단위 분할하면 왜 위험할까?** 서로 아주 비슷한 질문을 학습 데이터에서 보고, 평가 데이터에서 다시 풀 수 있기 때문이야. 이를 **데이터 누출(data leakage)**이라고 불러.

**단순 텍스트 해시 검사만으로는 부족해.** “냉수를 많이 썼더니 안 차가워요”와 “손님들이 연달아 냉수를 받고 나니 미지근해요”는 문장 해시가 달라도 의미가 겹칠 수 있어.

#### 실제 분할 파일이 어려워 보였던 이유

`semantic_group_id`의 `sg-ef6b56fea3f1` 같은 값은 **그룹의 설명이 아니라 식별자**야. 이것만 보고 내용을 유추할 수 없어.

읽을 때는 다음 순서로 보자.

1. `scenario_id`로 원본 합성 질문의 `request.raw_symptom`을 찾는다.
2. `family`로 증상 종류를 확인한다.
3. `semantic_group_id`로 어떤 질문끼리 묶였는지 확인한다.
4. `split`으로 Train/Dev/Holdout 배정을 확인한다.
5. `intended_oracle_action`과 `required_actions_from_pdf`를 확인한다.

이미 만든 **[S04 분할표 읽기 가이드](../data/splits/S04_분할표_읽기_가이드.md)**와 `S04_분할표_쉽게읽기.xlsx`에는 고객 질문과 16개 그룹의 의미가 연결돼 있어. 원본 CSV만 읽는 것보다 이 자료부터 보는 편이 이해하기 쉬워.

**실제 검수 결과:** Train **18건(9그룹)** / Dev **6건(4그룹)** / Holdout **6건(3그룹)**. 선언된 그룹의 분할 간 교차는 **0건**으로 검사됐어. 다만 사람이 놓친 **모든 잠재적 의미 중복이 없다는 보장은 아니야.**

### 5. S05의 세 조건을 비교하면 무엇을 분리할 수 있나?

**Oracle**은 검색을 생략하고 검수한 Gold 근거를 직접 주는 방식이야. 검색기는 정답을 놓칠 수 있지만 Oracle은 **정답 근거를 받았다는 가정**을 만드는 거지. 그렇다고 LLM의 최종 답변까지 정답인 건 아니야.

**일반 오프라인 RAG**는 BGE-M3가 후보 **53개 청크**에서 질문과 가장 가까운 청크를 찾았어. 정확한 제품 판매코드로 후보를 제한한 뒤, **1024차원 정규화 임베딩의 코사인 유사도**로 정렬하고, **0.4 이상에서 Top-5**를 골랐지.

이때 NumPy로 임베딩 벡터의 내적을 계산했어. 실제 WaterBridge의 **PostgreSQL/pgvector 쿼리와 전체 LangGraph**를 실행한 것은 아니야.

**안전 라우팅 RAG**는 검색 후보를 무조건 좁히지 않았어. 누수·스파크·연기 같은 위험, 전체 무출수의 부정, 온수만 안 나오는 경우, 저출수 표현을 먼저 분리하고, **명확한 전체 무출수**에 한해서 그 제품의 무출수 관련 후보를 우선하도록 했어.

```text
위험·부정·특정 물 종류·저출수인가?
      ├─ 예 → 전체 후보에서 일반 검색(안전 근거 제거 방지)
      └─ 아니오, 명확한 전체 무출수인가?
                  ├─ 예 → 해당 제품의 무출수 후보 우선
                  └─ 아니오 → 일반 검색
```

해당 무출수 후보가 없으면 전체 후보 검색으로 돌아가는 **fallback**도 뒀어. 그래도 **운영 서비스의 위험 판정 전체를 구현한 것은 아니야.**

**기술적 판단:** 후보를 좁히면 무관한 문서를 줄일 수 있지만, 분류가 틀리면 정답 문서까지 제거할 수 있어. 특히 누수·전기 위험의 근거를 잘못 제거하는 건 검색 점수 몇 점보다 큰 문제야.

### 6. 검색이 좋아져도 답변이 틀리는 이유 — 두 사례

**① `JAC104-030`: 정확한 근거를 줘도 조건을 넘는 안내**

7일 부재 후 냄새가 난 고객에게는 PDF 기준 **냉수·정수·온수 각각 1L 이상 출수해 버리기**가 필요한 조치야. 그런데 모델은 확인되지 않은 **필터 전체 교체**까지 추가했어. Oracle에서도 발생했으니 검색 누락만 탓할 수 없어.

**② `JAC104-033`: 존재하는 인용 ID라도 엉뚱한 인용**

해당 JAC104 계열 제품에는 제빙 기능이 없는데, 오프라인 검색은 관련 없는 **온수 안전 문서**를 반환했어. 모델은 존재하지 않는 ID를 만든 게 아니지만, **제빙 관련 주장에 온수 근거를 연결**했어.

따라서 서로 다른 지표가 필요해.

- **검색 Hit@K:** 정답 근거 중 하나라도 검색했나?
- **행동 일치:** `ASK`, `ANSWER`, `ESCALATE` 등 큰 행동을 맞혔나?
- **필수 조치 충족:** 상황에서 꼭 안내해야 할 내용을 포함했나?
- **조건 위반:** 적용하지 않아야 할 조치를 추가했나?
- **인용 관련성:** 인용한 문서가 실제 안내를 지지하나?

`invalid_cited_ids = 0`은 **제공되지 않은 ID를 만들지 않았다**는 뜻일 뿐, 모든 인용이 적절했다는 뜻이 아니야.

### 7. 다음 기술 선택은 무엇을 기준으로 해야 하나?

| 원인 | 먼저 점검할 방법 | SFT가 첫 선택인가? |
|---|---|---|
| 무출수 정답 후보를 놓침 | 검색 후보·증상 라우팅·Top-K·필터 | **아니오** |
| 고객에게 꼭 물어야 할 항목 누락 | 추가 질문 규칙·대화 상태 | 아직 아님 |
| 정답 근거가 있어도 조건을 넘는 답변 | 조건 구조화·프롬프트·검증 규칙 | 비교해 본 뒤 판단 |
| 없는 기능에 관한 설명·무관한 인용 | 제품 기능 정책 Gate·근거 검증 | **아니오** |

M1은 'SFT를 하자'를 증명한 실험이 아니야. **어떤 오류는 검색에서, 어떤 오류는 답변 판단에서 고쳐야 한다**는 구분을 만든 단계야.
