## S03 — 실제 WaterBridge의 증상 분류·검색·검증 흐름 추적

### 0. 실험 한눈에 보기

**질문:** 검색기가 정답을 찾는 것 외에, 실제 WaterBridge에서는 어떤 단계가 고객 답변에 영향을 미치는가?

| 항목 | 기존 기록에서 확인된 내용 |
|---|---|
| **입력 예시** | Q008 “필터를 이미 갈았는데도 물이 조금씩만 나와요.” + 제품 `WPUJAC104DWH` |
| **살펴본 코드** | LangGraph 처리 흐름, 증상 정규화, 필수 문진, 검색 정책 Gate, 근거 필터 |
| **직접 실행한 부분** | 규칙 분류 **3입력**, 7개 샘플 청크 후처리, 필수 필드 비교, 정책 Gate **6입력** |
| **핵심 관찰** | Q008 규칙 분류가 **`필터/관리 문의`**로 나옴. 분류에 따라 샘플 근거 **7개 vs 1개**, 필수 문진 차이 발생 |

| **핵심 파일** | `ai/app/structuring/symptom_normalizer.py`, `ai/app/retrieval/filters/evidence_topic_filter.py` |

### 1. 실험 정의 — 정확히 어디까지 확인했나?

기존 WaterBridge의 **질문 입력부터 최종 답변까지의 코드 경로를 읽고**, 그중 **규칙 함수·근거 필터·정책 Gate만 별도로 실행**해 입력에 따라 무엇이 달라지는지 확인하는 실험이다.

고정 질문은 다음과 같다.

> “필터를 이미 갈았는데도 물이 조금씩만 나와요. 어떻게 하죠?”
>
> 판매코드: `WPUJAC104DWH`

사람이 이해하는 문의는 **현재 증상: 출수량 저하 / 이미 한 조치: 필터 교체**다. **‘필터’라는 단어가 나왔다고 필터 관리 방법을 묻는 질문은 아니다.**

**실험 대상과 실제 실행 범위를 구분한다.** 아래 그래프 전체는 코드에서 확인한 구조이고, 이 실험에서 끝까지 실시간 실행한 경로가 아니다.

### 2. 실험 목적 — 왜 검색기 실험 다음에 했나?

M0에서는 어떤 청크가 Top-3에 있는지를 측정했다. 그런데 실제 서비스는 검색 *이전*에 증상을 분류하고, *이후*에 제품·토픽·적용 조건을 확인한다. 예를 들어 검색 모델이 정답을 찾더라도:

- 질문을 **필터 관리**로 해석하면 엉뚱한 근거가 후단으로 남을 수 있다.
- **필수 출수 종류**를 묻지 않으면 조건에 맞는 조치를 결정하지 못할 수 있다.
- 제품에 없는 기능을 질문했는데도 **무조건 문서 검색**하면 관련 없는 근거를 이용한 설명이 나올 수 있다.

따라서 **‘검색 모델 정확도’와 ‘질문 이해·안전·업무 정책의 정확도’가 서로 다른 문제인지** 확인하려고 실제 저장소 코드를 추적했다.

### 3. 실험 과정 — 처리 흐름과 기술적 판단

#### 3-1. 먼저 전체 흐름을 이해한다: RAG ≠ LangGraph ≠ DB

RAG는 공식 설명서를 검색해 LLM 답변의 근거로 제공하는 **접근 방식**이다. LangGraph는 단계 사이의 **상태와 분기**를 관리한다. 임베딩 모델은 질문·문서를 **숫자 벡터**로 바꾸고, pgvector는 PostgreSQL에서 **벡터 유사도**를 계산해 검색한다.

기존 `single_rag_pipeline.py`에 선언된 실행 경로는 요약하면 다음과 같다.

```text
START
  ↓
structuring : 질문을 제품·증상·이미 한 조치 등으로 구조화
  ↓
safety : 위험 신호가 있나?
  ├─ 위험 → generation → validation → END
  └─ 일반 → missing_fields : 추가로 확인할 정보가 있나?
                     ├─ 대기 필요 → questionnaire_pending → validation → END
                     └─ 진행 가능 → retrieval → generation → validation → END
```

- **`structuring`**: 자연어를 표준 증상·조건으로 바꾼다. 일부는 규칙, 일부는 LLM 기반 구조화 의존성을 가진다.
- **`safety`**: 누수 등 위험 신호를 별도 판단한다. 위험일 때 무조건 일반 검색을 먼저 하면 안 된다.
- **`missing_fields`**: 답변 전 필요한 물 종류 등 고객 정보를 확인한다.
- **`retrieval`**: 적합한 공식 근거를 검색하고 제품·증상·메타데이터 조건으로 거른다.
- **`generation` / `validation`**: 근거를 바탕으로 응답하고 결과를 검토한다.

**[기술적 판단] 왜 순차적인 함수 호출만으로 끝내지 않고 LangGraph인가?**

위 흐름에는 **‘위험이면 일반 경로 생략’, ‘정보 부족이면 대기’, ‘검색 가능하면 답변’** 같은 조건부 분기가 있다. 그래프로 노드와 상태 전이를 명시하면 **어느 단계에서 멈췄는지·어떤 상태가 전달됐는지·어떤 회귀 테스트가 필요한지** 구분하기 쉽다. 반면 **LangGraph를 썼다는 사실이 위험 분류 정확성, 검색 품질, 중단·재개 안정성을 자동으로 증명하지 않는다.** 그 성능은 별도 검증 대상이다.

**코드 확인:** `ai/app/orchestration/pipeline_router.py`, `ai/app/orchestration/pipelines/single_rag_pipeline.py`의 분기 함수.

#### 3-2. 실제 검색은 M0의 미니 검색과 다르다

M0는 **8개 청크에 Overlap/BM25/E5**를 적용한 독립 실습이다. 기존 WaterBridge의 기본 검색 코드에는 **`BAAI/bge-m3` 1024차원 임베딩**, **pgvector 코사인 exact search**, **Top-5**, **유사도 임계값 0.4**가 설정돼 있다.

```text
검색 전 Policy Gate
   ├─ 차단 → 지원 범위·안전·정책에 맞는 별도 경로
   └─ PGVECTOR_QUERY(검색 허용)
              ↓
       질문 임베딩 + DB 검색
              ↓
       후보 청크 + 제품·세대·공식 검증 상태/근거 역할 조건
              ↓
       증상 토픽·적용 조건을 포함한 Python 후처리
              ↓
       답변 생성·검증
```

**기술적 판단:** 벡터 유사도는 문장 의미의 관련성을 알려 주지만 **해당 고객 제품에 적용해도 되는지를 보장하지 않는다.** 따라서 제품 정확 판매코드, 세대, `official_verified`, `allowed_use`, 문서 판본·출처 해시 등 **메타데이터 정책을 검색 전 SQL과 검색 후 검사에서 적용**한다. 이런 검증은 임베딩 검색 점수만으로 대체할 수 없다.

**중요한 구분:** `VectorSearchService.execution_path()`에서 반환되는 `PGVECTOR_QUERY`는 **DB 검색을 진행해도 되는 경로라는 판정**일 뿐, 실제로 DB를 호출하거나 정답을 찾았다는 뜻이 아니다.

**코드 위치:** `ai/configs/retrieval_policy.yaml`, `ai/app/retrieval/search/vector_search.py`, `ai/app/integrations/embedding/embedding_client.py`, `ai/app/integrations/vector_store/vector_store.py`, `ai/app/orchestration/stages/retrieval_stage.py`.

#### 3-3. Q008을 이용해 **분류 오류의 전파 가능성**을 확인한다

**1) 규칙 분류기의 판단**

`SymptomNormalizer.normalize_symptom_type(raw_text, selected_symptoms)`는 원문 키워드를 우선 탐색해 표준 증상을 반환한다. 기존 코드에서 `조금씩만 나와요`라는 표현은 저출수 규칙에 매칭되지 않았지만 **`필터`는 ‘필터/관리 문의’ 규칙에 매칭**됐다. 이때 원문 키워드를 찾으면 먼저 반환하므로, 선택한 증상 `LOW_FLOW`를 줘도 최종 규칙 분류가 바뀌지 않았다.

반면 **“출수량이 적어요”**처럼 등록된 표현을 쓰면 저출수 규칙에 매칭된다.

**관찰**은 *규칙 함수의 분류 결과*다. 실제 서비스에 LLM 기반 구조화가 활성화되어 있다면 그 결과를 별도로 검증·교정할 수 있으므로, **‘실제 고객 최종 답변까지 틀렸다’고 주장하지 않는다.**

**2) 동일한 샘플 청크를 후처리에 직접 입력**

공식 검증 샘플 청크 **7개**를 검색 DB가 아닌 **근거 필터 함수에 강제로 입력**하고, 분류 결과만 바꿔 비교했다.

| 분류 | 필터 통과 | 필수 정보 규칙 | 무엇을 알 수 있나? |
|---|---:|---|---|
| **`필터/관리 문의`** | **7개 전부** | 출수 종류 `high` 없음 | 주제 필터가 제대로 좁혀지지 않을 가능성 |
| **`출수량 저하`** | **1개**(저출수 근거) | **`target_water_type` 중요도 `high`** | 관련 근거 제한·필수 문진이 연결됨 |

**[기술적 판단] 왜 단순히 ‘필터’라는 단어를 삭제하지 않나?** 진짜 필터 교체 주기 문의에는 그 표현이 필요하다. 고쳐야 할 대상은 단어 하나가 아니라 **현재 증상과 이미 수행한 조치의 분리, 부정 표현 처리, 위험 우선순위**다. 그리고 잘못된 증상 필터는 정답 근거를 제거할 수도 있으므로 **필터를 더 강하게 만드는 것이 항상 개선은 아니다.**

**주의:** 백엔드의 `NO_WATER`와 `LOW_FLOW`가 상위 표준 분류 `출수량 저하`에 매핑되는 부분이 있고, 이후 세부 검색 토픽에서 **완전 미출수 vs 부분 저출수**를 구별한다. **상위 증상 라벨과 세부 검색 토픽은 같은 개념이 아니다.**

**코드:** `ai/app/structuring/symptom_normalizer.py`, `ai/app/retrieval/filters/evidence_topic_filter.py`, `ai/app/structuring/missing_field_checker.py`.

#### 3-4. ‘검색 허용’과 ‘검색 성공’을 혼동하지 않도록 정책 Gate를 확인한다

**[기존 함수 실행 기록]** 검색 전 판정 6개를 실행했다.

| 테스트 문의 | 반환값 | 의미 |
|---|---|---|
| 정상 제품의 Q008 | `PGVECTOR_QUERY` | 검색 **허용** |
| 미지원 모델 `WPU-IAC506` | `POLICY_BLOCK_UNSUPPORTED_MODEL` | 현재 지원 범위 밖 |
| 미등록 제품 `UNKNOWNMODEL` | `POLICY_BLOCK_UNREGISTERED_EXACT_SALES_CODE` | 판매코드 미등록 |
| 필터 **가격** 문의 | `POLICY_BLOCK_OUT_OF_MANUAL_SCOPE` | 정적 매뉴얼 범위 밖 |
| 해당 제품에 **없는 얼음 기능** 문의 | `POLICY_BLOCK_UNSUPPORTED_CAPABILITY` | 기능 자체가 지원되지 않음 |
| 미검증 FAQ만을 요구 | `POLICY_BLOCK_UNVERIFIED_SOURCE` | 검증되지 않은 정보 요구 차단 |

**실패 원인 분리:**

| 상황 | 우선 살펴볼 곳 |
|---|---|
| Gate에서 의도적으로 차단 | 제품/기능/자료 허용 정책 — 정상 차단은 검색 실패가 아님 |
| 위험 상태이므로 검색 생략 | `safety` 판정과 LangGraph 분기 |
| 필수 항목 미기입으로 대기 | `missing_fields`와 질문 기록 |
| 검색 실행했지만 후보가 없음 | 임베딩·청크 인덱스·Top-K·임계값·SQL 조건 |
| 검색 후보는 있지만 후처리에서 0개 | 증상/제품/적용 조건 필터 |
| DB·모델 예외 | 예외 로그·연결 상태·timeout |
| 정답 근거는 전달됐으나 응답이 오답 | 생성 프롬프트·적용 조건·응답 검증 |

#### 3-5. 기술적 판단을 실제 개선안으로 연결하려면?

**[후속 제안 — 이번 S03에서 실행하지 않음]** 다음 회귀 테스트를 우선 정의한다.

| 입력 | 바람직한 판정 | 검증 이유 |
|---|---|---|
| 필터를 갈았는데 조금씩만 나옴 | **저출수** + `actions_taken=필터 교체` | 핵심 Q008 오류 |
| 필터는 언제 교체하나요? | 필터 관리 문의 | 기존 정상 의도 보존 |
| 물이 조금씩 나오고 바닥에 물이 샘 | **누수 위험 우선** | 일반 증상보다 안전 대응 중요 |
| 물이 아예 안 나옴 | 완전 미출수 토픽 | 저출수와 혼동 방지 |
| 안 나오는 건 아니고 물줄기가 약함 | **완전 무출수로 분류 금지** | 부정 표현 |
| 온수만 안 나옴 | 전체 무출수로 단정 금지 | 특정 기능/물 종류 문제 |

변경 전후에 **분류 정확도뿐 아니라 필요한 필수 문진·근거 적용·안전 우선순위**까지 함께 검사해야 한다. 규칙 하나를 바꿔 다른 고객 발화를 망가뜨리는 회귀를 피하기 위해서다.

### 5. 결과 해석 및 결론 — 어디에 문제가 있고 무엇은 미확인인가?

**관찰:** Q008에서는 현재 증상보다 **‘필터’ 키워드**가 규칙 분류에 먼저 영향을 줬다. 이 분류를 바꾸면 **근거 후처리와 필수 문진 규칙**이 달라진다는 것을 부분 실험으로 확인했다.

**해석:** 검색이 틀린 것처럼 보이는 현상도 실제로는 **앞단 증상 분류**나 **뒷단 근거 필터**의 문제일 수 있다. 따라서 실제 RAG를 고도화할 때 **검색기만 바꾸는 접근은 충분하지 않다.**

**기술적 결론:** Q008 같은 경우 **원문에 있는 단어와 고객이 겪는 현재 증상을 분리해 구조화하고**, 안전 신호·부정 표현을 우선 처리하는 설계를 검증할 가치가 있다. 단, 이것은 **개선 제안이지 실제 팀 서비스에 반영한 성과가 아니다.**

**주장할 수 없는 것:** 이 실험만으로 *실제 pgvector가 일곱 청크를 검색했다*, *BGE-M3 성능이 나빴다*, *최종 고객에게 위험한 답변이 나갔다*, *LangGraph E2E가 성공했다*고 말할 수 없다.

### 1. 실험 정의 — 무엇을 검수하고 나누었는가?

기존 정수기 설명서·청크·합성 고객 상담 시나리오를 **공식 PDF 원문과 대조**해 평가상의 정답(Gold)과 적용 조건을 확인한 다음, **유사 질문이 Train·Dev·Holdout에 걸쳐 섞이지 않도록** 데이터 분할을 검증하는 실험이다.

이것은 **합성 시나리오 30건의 파일럿 준비 과정**이며, 30명에게 상담 서비스를 제공하거나 모델을 SFT 학습한 실험이 아니다.

### 2. 실험 목적 — 왜 데이터부터 검증했나?

M0의 10문항은 **한 제품의 비슷한 세 증상**에서 만든 학습용 질문이다. 이를 학습에 쓰고 비슷한 질문을 평가에 다시 쓰면, 새로운 문제에 일반화한 것처럼 수치가 높아질 수 있다.

더 근본적인 문제도 있다. **평가 정답 자체가 원본 PDF의 조건을 빼먹었다면**, 실제로 맞는 답변을 오답 처리하거나 조건에 맞지 않는 답변을 정답 처리할 수 있다.

따라서 다음 두 문제부터 검증했다.

1. **Gold 품질:** 설명서의 *제품·조건·조치·금지 사항*과 라벨이 일치하는가?
2. **데이터 누출:** 내용이 같은 문제를 말만 바꿔 서로 다른 분할에 넣지 않았는가?

### 3. 실험 과정 — 원문 감사·의미 그룹·분할 설계

#### 3-1. 공식 문서를 기준으로 가공 데이터에 오류가 없는지 본다

| PDF 종류 | 페이지 | 확인해야 하는 차이 |

| IAC425 REV.02 | 52쪽 | 오프라인 평가 대상으로만 사용, 기본 공개 Runtime 승인과 구별 |

기존 기록에는 공식 PDF 3종의 SHA-256을 팀 출처 목록과 대조했다고 되어 있다. **이 문서 개편에서 원본 PDF를 다시 내려받아 해싱한 것은 아니다.**

가공 후보는 팀의 **53개 청크**, **43개 근거 그룹**, **30건 합성 상담 시나리오**다. 원본과 대조하면서 **30건 중 16건의 라벨·조치·출처 보완 의견**을 작성했다.

**주의:** **16건은 팀 원본에 반영한 수정 실적이 아니라 개인 평가 자료에 남긴 ‘보완 제안’**이다.

#### 3-2. 데이터 누출이 무엇인지 이해한다

**Train**은 모델 학습에 쓰는 자료, **Dev**는 검색 규칙·프롬프트·학습 설정을 조정하는 자료, **Holdout**은 설정을 정한 뒤 마지막에 평가할 자료다.

가령 Train에 “장기간 물을 안 썼더니 냄새가 나요”가, Holdout에 “며칠 집을 비운 뒤 물맛이 이상해요”가 들어 있다면, **문자열 해시가 달라도 같은 원인·조치**를 요구할 수 있다. 이때 단순 중복 0건이라고 해서 독립 평가를 보장하지 못한다.

**[기술적 판단] 왜 해시만으로 분할하지 않았나?**

- **정확한 텍스트 해시:** 같은 텍스트를 찾아내는 데 좋지만 **동일 의미의 다른 표현**을 잡지 못한다.
- **제품 코드별 무작정 분할:** 서로 다른 제품이 **같은 원인과 조치**를 공유하면 의미가 겹칠 수 있다.
- **채택한 방법:** 제품·질문 상황·원문 근거·요구 조치를 함께 검토해 **의미 그룹 `semantic_group_id`를 선언**하고, 그룹 단위로 분할한다. 해시 검사는 별도로 병행한다.
- **여전히 남는 위험:** 사람이 놓친 의미상 중복은 검증기가 알아서 증명해 주지 않는다.

기존 파일럿에서는 **30건을 16개 의미 그룹**으로 묶었다. 특정 의미 그룹을 Train과 Dev 양쪽에 넣지 않도록 확인했다.

#### 3-3. Train/Dev/Holdout이 서로 다른 역할을 맡도록 나눈다

| 분할 | 건수 | 용도 | 하면 안 되는 일 |
|---|---:|---|---|
| **Train** | **18** | 학습 데이터 준비 및 후속 SFT | Train 성능을 일반화 성능으로 주장 |
| **Dev** | **6** | 프롬프트·검색 규칙 등 **개발 중 비교** | 같은 Dev에서 만든 규칙의 수치를 독립 평가라 부르기 |
| **Holdout** | **6** | 설정을 확정한 뒤 최종 확인용 | 보고 나온 오류로 반복 튜닝하면서 ‘처음 본 데이터’라 주장하기 |

Dev 6건은 **실질적으로 4개 의미 그룹**이다. 세 제품의 ‘물이 전혀 안 나옴’은 서로 다른 문장·모델 코드지만 같은 의미 그룹에 묶일 수 있다. **독립 사례 6개에서 100%를 얻었다고 해석하면 안 된다.**

**미학습 제품을 평가한다**는 말도 두 가지를 구분한다.

1. **학습하지 않은 제품의 상담 질문을 평가:** 해당 제품의 질문·정답 예제를 Train에서 제외하되, **RAG에는 공식 매뉴얼을 제공**해 새 문서를 읽고 활용하는지 측정한다.
2. **문서 자체가 없는 제품을 평가:** 공식 매뉴얼도 검색에서 제외해 **추측을 멈추고 미지원·근거 부족을 처리하는지** 본다.

S04가 세 제품의 공식 PDF를 봤다는 것과 **세 제품이 공개 서비스에 승인됐다**는 것은 다르다.

#### 3-4. 근거가 ‘없다’는 말을 네 가지로 분리한다

| 실제 상황 | 먼저 확인할 곳 | 왜 다르게 다뤄야 하나? |
|---|---|---|
| PDF에는 답이 있지만 **인덱스 청크가 없음** | PDF 추출·청크 생성·인덱싱 | `NO_INDEX_EVIDENCE`는 ‘원문에도 없다’가 아님 |
| 인덱스에는 있지만 검색 **Top-K 밖** | 검색·필터·유사도 | 후보 생성·순위 문제 |
| 제품이 해당 기능을 지원하지 않음 | 공식 기능 목록·제품 Policy Gate | 검색 점수보다 **기능 지원 정책** 우선 |
| 실시간 가격·방문 일정 문의 | 동적 데이터/API 및 상담 경로 | 정적 설명서만으로 확정할 수 없음 |

**[기술적 판단] Gold를 어떻게 써야 하나?**

Gold는 단순한 ‘정답 문서 ID 하나’보다 **기대 행동(`ASK/ESCALATE/ANSWER/EXPLAIN_UNSUPPORTED`), 적용 조건, 필수 조치, 금지 조치, 출처**를 포함해야 한다. 기존 CSV의 `required_actions_from_pdf`, `intended_oracle_action` 등을 이용하고, 더 정교한 자동 채점 필드 설계는 **후속 제안**으로 구분한다. 특히 **해당 조건에서만 적용되는 필터 교체**를 일반적 필수 조치로 적으면 오히려 잘못된 학습을 유도한다.

**관찰:** 합성 상담 30건을 공식 PDF 원문 기준으로 검토했고, 16건에 **보완 의견**을 남겼다. 선언된 16그룹을 Train/Dev/Holdout **18/6/6**으로 나누고 규칙 검사를 통과했다.

**해석:** **평가 정답이 어떤 원문 조건에서 나왔는지 추적할 수 있는 파일럿 토대**를 만들었다. 그러나 잘못 만든 Gold·의미상 누출을 *완전히* 제거했다는 보증도, 이미 모델이 학습·일반화했다는 뜻도 아니다.

**기술적 결정:** **Holdout 6건은 개발 중 튜닝에 사용하지 않는다.** S05는 Dev 6건을 사용해 실험하고, 독립 질문을 확대하기 전에는 모델 성능의 일반화를 주장하지 않는다.

**미완료:** 팀 원본의 16건 수정 반영, 전체 공식 인덱스 품질 보증, 별도 대규모 블라인드 평가, 실제 SFT 학습은 **S04에서 하지 않았다.**

### 1. 실험 정의 — 무엇을 같게 하고 무엇을 바꿨나?

**공식 설명서 기반 합성 Dev 6건**에 대해 **생성 모델·고객 질문·기대 행동**을 같은 기준으로 유지하고, LLM에 전달할 **근거의 선택 방법**을 세 가지로 바꿔 비교했다.

| 실험군 | LLM에 전달한 근거 | 무엇을 확인하는가? |
|---|---|---|
| **A. Oracle** | PDF와 연결해 검수한 **Gold 근거를 검색 없이 직접 제공** | 검색이 성공했다고 가정해도 **LLM 답변 오류**가 남는가? |
| **B. 일반 RAG** | 오프라인 **BGE-M3가 제품별 후보에서 검색한 Top-5** | 실제 검색에서 놓친 근거가 답변에 영향을 미치는가? |
| **C. 안전 라우팅 RAG** | 위험·부정·특정 물 종류/증상 표현을 먼저 구분하고, **명확한 전체 무출수에 한해 후보를 제한**한 후 BGE-M3 Top-5 | 증상에 맞는 후보 제한이 검색 및 응답을 개선하는가? |

**공통 생성 설정(기존 기록):** `gpt-4.1-mini-2025-04-14`, 동일한 기본 안내 프롬프트 코드·출력 스키마, `temperature=0`을 사용했다. 다만 **세 실험군에 실제 제공한 근거 내용·개수·토큰 수는 다르기 때문에** 입력이 완전히 동일하거나 엄밀한 인과 실험이라는 뜻은 아니다. `temperature=0`도 **완전한 결정적 재현**을 보장하지 않는다.

**원시 Gold는 검색 순위를 정하는 데 사용하지 않았다.** 검색 결과가 생성된 후 Hit@K 채점에만 사용했다. Oracle은 의도적으로 Gold를 입력하는 **서로 다른 실험 조건**이다.

### 2. 실험 목적 — 왜 Oracle까지 필요한가?

RAG가 틀린 답을 한다면 다음 두 실패는 원인이 다르다.

```text
고객 질문 → 잘못된 근거 검색 → LLM이 좋은 문장을 써도 잘못된 답변 가능
고객 질문 → 올바른 근거 검색 → LLM이 조건을 오해하면 여전히 잘못된 답변 가능
```

검색만 평가하면 **‘정답 근거를 찾았는지’**는 알지만 **‘고객에게 적절한 안내를 했는지’**는 알 수 없다. 반대로 최종 답변만 보면 검색이 나빴는지 생성이 나빴는지 구분하기 어렵다.

따라서 Oracle로 **검색 실패의 영향을 줄여 놓은 조건**을 만들어 비교하고, 일반 RAG와 검색 후보 개선 조건에서 어떤 오류가 남는지 분석했다. **Oracle이 정답 문서를 제공한다고 해서 최종 답변이 무조건 정답인 것은 아니다.**

### 3. 실험 과정 — 오프라인 검색, 후보 제한, LLM 평가

#### 3-1. 오프라인 BGE-M3 검색기를 만든다

S04의 팀 후보 청크 **53개**를 사용한다. **정확한 판매코드**로 대상 제품을 제한하고, `BAAI/bge-m3`의 **1024차원 정규화 임베딩**을 생성한 뒤 **NumPy 벡터 내적(코사인 유사도)**으로 청크를 정렬한다. **Top-5**, 임계값 **0.4**를 적용했다.

```text
질문 + 정확한 판매코드
  ↓
해당 제품의 공식 검증 후보 청크 선택
  ↓
BGE-M3로 질문·청크 임베딩 → 정규화 코사인 순위
  ↓
유사도 0.4 이상에서 Top-5 반환
  ↓
Gold ID는 이때 사용하지 않고, 출력 뒤에만 평가
```

**[기술적 판단] 왜 실제 pgvector 대신 NumPy인가?** 이번 단계의 목적은 **근거 후보와 LLM 답변의 차이를 작은 개발셋에서 분리**하는 것이다. 동일한 계열의 임베딩·제품 범위·Top-K 설정으로 검색 오류를 관찰하는 **오프라인 파일럿**이 가능하다. 반면 DB SQL, 인덱스 적재, 전체 LangGraph 상태, Safety Stage, 공개 API 지연은 검증할 수 없다. **오프라인 BGE-M3 수치를 실제 WaterBridge 운영 pgvector 수치로 바꿔 말하면 안 된다.**

**코드:** `portfolio_upgrade/scripts/s05_offline_bge_rag.py`. 팀 후보 데이터: `data/processed/structured/rag/expansion/rag_child_chunks_3model_v1.jsonl`.

#### 3-2. 먼저 일반 검색에서 무엇이 누락되는지 본다

Dev 6건 중 검색 정답 Gold가 정의된 사례는 **5건**이다. `JAC104-033`은 제빙 기능이 없는 제품에 관한 문의로, 이번 검색 후보에는 미지원 사실을 직접 뒷받침하는 **검색용 Gold 그룹이 없으므로** Hit@K 분모에서 제외한다. 이 사례는 **정책·출처 적절성**으로 별도 평가한다.

| 사례 | 무엇을 묻는가? | 일반 BGE-M3에서 첫 Gold |
|---|---|---:|
| `IAC425-105` | 물이 전혀 안 나옴 | **2위** |
| `IAC606-105` | 물이 전혀 안 나옴 | **Top-5 밖** |
| `JAC104-025` | 물이 전혀 안 나옴 | **Top-5 밖** |
| `JAC104-029` | 누수·감전 위험 | **2위** |
| `JAC104-030` | 7일 부재 뒤 물맛·냄새 이상 | **1위** |
| `JAC104-033` | 제빙 기능 미지원 | **검색 Gold 없음 — 별도 정책 사례** |

이때 눈에 띈 것은 **전체 무출수 질문 세 건의 검색 순위**다. 단순 의미 유사도보다 **해당 제품의 무출수 토픽을 제한**하는 편이 좋을지 시험할 이유가 생겼다.

#### 3-3. 1차 무출수 규칙을 그대로 도입하면 왜 위험한가?

‘물이 안 나와요’라는 단어만 보고 후보를 **무조건 전체 무출수 설명서로 제한**하면 위험하다.

| 질문 예시 | 왜 필터를 적용하면 안 되나? | 올바른 검토 방향 |
|---|---|---|
| “물이 안 나오는데 제품 아래에서 물이 새요” | **누수 안전 근거를 검색에서 제거**할 수 있음 | 위험 우선 |
| “안 나오는 건 아니고 물줄기가 약해요” | 고객이 전체 무출수를 **부정**함 | 부분 저출수로 분리 |
| “온수만 안 나와요” | 제품 전체가 아니라 특정 물 종류 문제 | 기능·출수 종류 먼저 확인 |
| “물이 안 나오고 플러그에서 스파크가 튀어요” | 전기 위험을 일반 무출수로 덮을 수 있음 | 안전 분기 우선 |

**[기술적 판단] 왜 ‘위험 신호 우선’ 규칙을 추가했나?** 검색 후보를 좁히면 관련 없는 청크를 줄일 수 있지만 **정답과 안전 조치까지 제거하는 실패**가 더 위험하기 때문이다. 따라서 단어 하나로 단정하기보다 아래 순서를 사용했다.

```text
1. 누수·스파크·연기 등 위험 신호?       → 후보 제한 적용 안 함
2. 전체 무출수를 부정하는 표현?        → 후보 제한 적용 안 함
3. 온수만/냉수만 등 특정 기능 문제?     → 후보 제한 적용 안 함
4. 조금씩/졸졸 등 저출수 표현?         → 후보 제한 적용 안 함
5. 명시적인 '전체 무출수'?             → 그 제품의 무출수 토픽 후보 우선
6. 위에 모두 해당하지 않음?           → 일반 검색
```

관련 무출수 토픽 청크가 아예 없다면 **해당 제품의 전체 후보로 돌아가는 fallback**도 둔다. 이는 *검색 후보 제한을 생략하는 로직*이지 **운영 Safety Stage를 수행하거나 안전한 최종 답변을 보장하는 기능은 아니다.**

개인적으로 만든 합성 반례 **20건 규칙 테스트 20/20 통과**는 위 조건문의 예시 처리가 맞았다는 사실만 확인한다. **실제 고객의 모든 부정·위험 표현을 탐지했다고 증명하지 않는다.**

**코드:** `portfolio_upgrade/scripts/s05_safe_routing_guard.py`의 `decide_route`, `choose_model_candidates`.

#### 3-4. 왜 세 조건에서 똑같은 행동 라벨을 따로 평가하나?

최종 LLM 출력에는 우선 어떤 행동을 할지 나타내는 `action`이 있다.

- **`ASK`**: 필요한 정보를 고객에게 추가로 묻기.
- **`ESCALATE`**: 위험·상담 이관 등 지정된 경로로 안내.
- **`ANSWER`**: 근거를 바탕으로 답변.
- **`EXPLAIN_UNSUPPORTED`**: 지원하지 않는 기능/범위를 설명.

**행동 라벨이 맞다 = 답변 내용이 모두 올바르다**는 뜻이 아니다. 예를 들어 `ASK`라는 행동은 맞더라도 **무엇을 물었는지**, `ANSWER`가 맞더라도 **조건부 조치를 멋대로 추가하지 않았는지**, 인용 ID가 존재하더라도 **그 인용이 해당 주장을 뒷받침하는지** 별도로 봐야 한다.

**기술적 판단:** 추후 평가지표는 행동 일치율뿐 아니라 **필수 조치 충족률·금지 조치 위반률·조건 일치 여부·출처 관련성·문진 완전성**을 포함해야 한다. 이 가운데 일부는 **이번 실험에서 자동 채점한 지표가 아니라 후속 평가 설계**다.

### 4. 실험 결과 — 검색·LLM·사례별 오류와 증거

#### 4-1. 검색 평가 **[기존 오프라인 실행 기록]**

| 사례 | 일반 BGE-M3 | 안전 라우팅 |
|---|---:|---:|
| `IAC425-105` | 2위 | **1위** |
| `IAC606-105` | Top-5 실패 | **1위** |
| `JAC104-025` | Top-5 실패 | **1위** |
| `JAC104-029` | 2위 | 2위 |
| `JAC104-030` | 1위 | 1위 |
| `JAC104-033` | 검색 Gold 없음 | 검색 Gold 없음 |
| **Hit@1** | **1/5** | **4/5** |
| **Hit@5** | **3/5** | **5/5** |
| **MRR@5** | **0.40** | **0.90** |

MRR 계산을 실제로 따라가면 다음과 같다.

$$
MRR@5_{\text{일반}}=\frac{1/2+0+0+1/2+1}{5}=0.40
$$

$$
MRR@5_{\text{안전 라우팅}}=\frac{1+1+1+1/2+1}{5}=0.90
$$

**왜 5/5가 됐는가?** 전체 무출수 질문에서 해당 제품의 무출수 후보 청크가 **한 개뿐이었기 때문**이다. 라우팅이 해당 주제를 선택하면 이 청크가 자동으로 1위가 된다. **임베딩 모델을 학습·개선했기 때문이 아니다.** 이 규칙도 **Dev 실패를 보고 만든 것**이므로 같은 Dev의 5/5를 독립 일반화 정확도 100%라고 주장하지 않는다.

#### 4-2. LLM의 행동 선택과 호출 기록 **[기존 실행 기록]**

| 측정 항목 | Oracle | 일반 RAG | 안전 라우팅 RAG |
|---|---:|---:|---:|
| **기대 행동 일치** | **6/6** | **6/6** | **6/6** |
| **제공하지 않은 근거 ID를 인용** | **0건** | **0건** | **0건** |
| LLM 호출 구간 평균(초) | **2.08** | **1.91** | **2.30** |
| 총 입력+출력 토큰 | **5,094** | **7,835** | **6,191** |

**실험 의미를 제한해야 한다.** 여기의 응답 시간은 **LLM 호출 구간**이며 실제 서비스 E2E(임베딩 로딩·DB·API·LangGraph 포함)가 아니다. 입력 근거 길이도 달라 **3조건의 비용·속도 우위를 공정하게 확정할 수 없다.** `invalid_cited_ids=0`은 **인용한 문자열 ID가 제공 목록 안에 있었다**는 뜻이지 **해당 인용이 문맥상 적절했다**는 뜻이 아니다.

#### 4-3. 반드시 읽어야 할 실패 사례

| 사례 | **관찰된 결과** | 원인 해석·한계 |
|---|---|---|
| **`IAC425-105`** | Gold가 **2위→1위**, 개선 답변은 밸브·직수관케어·호스를 더 구체적으로 질문 | 문진 내용 개선. 다만 첫 질문에 모든 항목을 나열해야 하는지는 후속 대화 기준으로 평가 필요 |

**JAC104-030을 특히 기억한다.** 정답 근거를 직접 준 **Oracle에서도 부적절한 추가 조치**가 나왔다는 것은 **‘검색 문서가 없어서 틀렸다’**는 설명만으로 부족하다는 뜻이다. 우선 공식 PDF의 **적용 조건을 구조화**하고 필요 조치와 금지 조치가 답변에 반영되는지 봐야 한다. 그다음 프롬프트·검증 규칙의 효과와 SFT를 별도로 비교해야 한다.

**JAC104-033도 중요하다.** `invalid_cited_ids=0`이더라도 답변이 온수 관련 문서를 제빙 기능 설명의 근거로 쓰면 **그 인용은 부적절**하다. 실제 WaterBridge에는 미지원 기능을 검색 전에 차단하는 Gate가 있지만, **이번 오프라인 스크립트는 그 정책 경로를 실행하지 않았다.** 따라서 이를 운영 서비스 결함으로 적으면 안 된다.

### 5. 결과 해석 및 결론 — 무엇을 고칠지, SFT를 언제 할지

#### 5-1. 검색·생성·정책 문제를 구분한 최종 판단

| 문제 유형 | 이번 실험에서 본 사례 | 우선 검증할 개선 방향 | SFT가 첫 선택인가? |
|---|---|---|---|
| **검색 후보 누락** | IAC606-105, JAC104-025 | 증상 라우팅·메타데이터·검색 후보·Top-K | **아니오** |

**관찰:** 이번 Dev에서는 안전 라우팅이 검색 Gold 5건을 모두 Top-5에 넣었다. 동시에 세 조건의 **행동 라벨이 모두 6/6으로 맞아도**, 답변 내용의 조건 위반·무관한 인용·문진 부족은 남았다.

**해석:** 하나의 ‘LLM 정확도’라는 말로 묶지 말고, **검색 후보 → 정보 적용 조건 → 정책 → 최종 답변** 중 어디에서 오류가 발생했는지 구분해야 한다. 정확한 근거가 있는 **Oracle에서도 오류가 나타나는 문제**는 생성·근거 해석 쪽을 더 조사할 가치가 있다.

**기술적 결정:** **안전 라우팅은 오프라인 개발 후보로만 유지한다.** 개발 데이터에서 그 실패를 보고 규칙을 만든 뒤 같은 Dev를 다시 평가했기 때문에 **새 고객 질문에서도 같은 성능이라고 보장할 수 없다.** 기존 운영 경로를 교체하지 않으며, 이 결과만으로 SFT가 필요하다거나 이미 효과적이라고 주장하지 않는다.

#### 5-2. 어떤 후속 비교가 필요한가? **[후속 제안]**

이 단계들은 아직 실행 결과가 아니다.

1. **강한 기존 프롬프트를 기준선으로 고정**한다.
2. 같은 고객 질문·같은 공식 PDF 근거에서 **조건/필수 조치/금지 조치가 구조화된 프롬프트**를 비교한다.
3. **필수 조치 충족률·조건 위반률·인용 관련성·ASK 질문 충족률·안전 위반율**을 동일 Gold로 채점한다.
4. 개선되지 않는 **생성 단계** 문제가 남는다면 **Train 데이터만으로 소형 LLM SFT/LoRA·QLoRA** 대안을 시험한다.
5. 실제 pgvector·LangGraph·API E2E에서 성능과 지연·비용·안전성을 검증한다.
6. 개발 선택을 고정한 뒤 **독립 Holdout**에서 최종 비교한다. Holdout 결과를 보고 다시 수정한다면 더 이상 엄밀한 최초 Holdout 평가라고 주장하지 않는다.
