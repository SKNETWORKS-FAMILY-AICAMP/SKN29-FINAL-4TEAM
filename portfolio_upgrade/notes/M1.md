# M1 — 실제 WaterBridge RAG 이해와 평가 기준선 구축 (S03~S05)

> **진행:** S03(코드 경로·부분 실행·핵심 이해 확인 완료) / **S04·S05 미착수**
> 이 문서는 **[실측] 실제 확인한 결과**, **[코드 확인] 저장소의 동작 구조**, **[예정] 앞으로 할 실험**을 분리한다.
> 처음 읽는다면 [개요](overview.md)의 네 단계 그림부터 확인한다. [M0](M0.md)의 미니 검색기와 실제 WaterBridge는 다르다.

## M1에 들어가기 전: 왜 검색만 잘해도 충분하지 않을까?

고객이 “필터를 갈았는데도 물이 조금씩 나와요”라고 말했을 때, 검색 모델이 가장 비슷한 문서를 찾더라도 **고객 증상이 ‘출수량 저하’라는 사실을 잘못 이해**하면 잘못된 안내로 이어질 위험이 있다. 또 어떤 고객은 **다른 제품을 사용**하거나 **안전상 즉시 상담이 필요한 상황**일 수 있다.

그래서 실제 AI 서비스는 보통 ‘검색’ 하나가 아니라 다음 과정을 연결한다.

```text
고객 문의
  → ① 증상 분류 (무슨 문제인가?)
  → ② 안전·제품·정보 확인 (지금 검색하는 게 맞나?)
  → ③ 공식 설명서 검색 + 적용 조건 확인 (근거가 맞나?)
  → ④ 안내 생성 + 검증 (근거 밖 내용을 말하지 않았나?)
```

**LangGraph**는 이 과정에서 '안전 문제면 검색 생략', '필수 정보가 없으면 되묻기'처럼 **다음 단계를 조건에 따라 고르는 흐름**을 관리한다. **규칙 기반 검증과 제품·안전 정책은 LLM의 추측과 분리**한다.

### 지금 필요한 용어만 먼저

| 용어 | 쉽게 설명하면 |
|---|---|
| **증상 구조화(Structuring)** | 고객의 자유로운 문장을 `출수량 저하` 같은 정해진 항목으로 바꾸기 |
| **Policy / Gate** | 모델·제품·질문 범위가 허용되는지 검색 전 검사하기 |
| **Metadata Filter** | 제품 코드·세대·공식 검증 상태에 맞는 문서만 통과시키기 |
| **증상 주제 필터(Topic Filter)** | 누수 질문에는 누수 근거처럼 관련 주제의 청크만 남기기 |
| **추가 질문(Clarification)** | 출수 종류 등 필수 정보가 부족하면 고객에게 먼저 확인하기 |
| **Oracle Evidence** | 검색기의 성능과 무관하게 올바른 정답 근거를 직접 넣어 답변을 테스트하기(S05 예정) |

**기억할 비유:** `PGVECTOR_QUERY`는 *서류 합격(검색 허용)*에 해당한다. 실제 DB에서 검색하는 것은 *면접 응시*, 정답 근거를 확보한 것은 *면접 합격*, 올바른 안내까지 마친 것은 *입사 후 업무 성과*와 비슷하다.

## S03

### 1. 왜 실제 WaterBridge 코드를 살펴봤나?

S01과 S02는 **검색 결과를 잘 고르는 방법**에 집중했다. 그런데 실제 고객 응대에서는 검색이 잘되어도 **질문을 잘못 이해하거나, 다른 모델의 설명서를 사용하거나, 필요한 추가 질문을 빼먹으면** 잘못 안내할 위험이 있다.

그래서 S03에서는 S01·S02의 미니 검색기가 아니라, **기존 WaterBridge 서비스 코드가 질문 하나를 어떤 순서로 처리하는지** 추적했다.

살펴본 질문은 S01에서 문제가 드러났던 **Q008**이다.

> “필터를 이미 갈았는데도 물이 조금씩만 나와요. 어떻게 하죠?”
> 제품 코드: `WPUJAC104DWH`

**사람이 이해한 고객 증상:** ‘필터를 교체했다’는 *이미 한 조치*이고, 현재 문제는 **물이 적게 나오는 것(출수량 저하)**이다.

### 2. WaterBridge의 처리 흐름은 네 단계로 기억한다

| 단계 | 쉽게 말하면 | 실제 WaterBridge 코드에서 하는 일 |
|---|---|---|
| **① 질문 이해** | 고객이 무엇을 겪고 있나? | 제품 코드와 자연어 증상을 확인하고 표준 증상 유형으로 정리한다. |
| **② 검색 여부 결정** | 추가 정보가 필요한가? 설명서로 답할 수 있나? | 위험 상황은 안전 안내로, 필수 정보가 부족하면 추가 질문으로 분기한다. 검색 전 제품·기능·문서 범위도 검사한다. |
| **③ 공식 근거 찾기** | 해당 모델의 공식 설명서에 답이 있나? | BGE-M3로 임베딩해 pgvector에서 검색하고, 제품·주제·적용 조건이 맞는 근거만 남긴다. |
| **④ 답변 생성·검증** | 찾은 내용으로 안전하게 안내했나? | 근거가 있으면 안내를 생성하고, 근거가 없거나 위험한 경우 지정된 안내를 사용하며 최종 결과를 검증한다. |

이 단계들의 **실행 순서와 조건부 분기**를 관리하는 데 **LangGraph**가 사용된다. 정상 경로는 대략 ‘증상 구조화 → 안전 검사 → 추가 질문 검사 → 검색 → 안내 생성 → 검증’이다. 단, 위험하거나 필수 정보가 누락되면 검색으로 곧장 가지 않을 수 있다.

함수 이름 전체를 외울 필요는 없다. **어떤 판단이 왜 검색 전에 필요한가**를 이해하는 것이 중요하다.

### 3. 실제 서비스의 검색은 미니 검색기와 무엇이 다른가?

| 항목 | S01·S02 연습 | 실제 WaterBridge 기본 검색 경로 |
|---|---|---|
| 임베딩 모델 | E5-small | **BGE-M3** |
| 검색 방식 | 로컬 Overlap/BM25/E5/RRF 실험 | **pgvector의 코사인 exact search** |
| 임베딩 크기 | 실습 모델 설정에 따름 | **1024차원** |
| 검색 결과 개수 | Top-3 | **Top-5** |
| 검색 전·후 조건 | 학습용 작은 검색기 | 제품 코드·세대·공식 검증 상태·증상 주제·적용 조건 확인 |
| 결과 활용 | 검색 순위와 지표 계산 | 이후 고객 안내 생성 및 검증 |

실제 검색 코드의 유사도 임계값 기본값은 **0.4**이고, 제품의 정확한 판매 코드와 세대, 공식 검증 상태 등으로 검색 후보를 제한한다. S02의 **E5+RRF는 실제 서비스 검색 경로에 연결되지 않았다.**

### 4. Q008에서 발견한 분류 문제

규칙 기반 증상 분류기만 직접 실행하니 아래 결과가 나왔다.

| 입력 | 실제 분류 결과 |
|---|---|
| Q008 원문 | **필터/관리 문의** |
| Q008 + 사용자가 선택한 `LOW_FLOW` | **필터/관리 문의** |
| ‘필터를 교체했는데도 **출수량이 적어요**’ | **출수량 저하** |

**왜 이런 일이 생겼나?** 규칙 기반 분류기에 `필터`라는 단어는 등록되어 있지만, Q008의 `조금씩만 나와요`는 출수량 저하를 탐지하는 표현에 포함되어 있지 않았다. 이 코드에서는 원문 키워드 규칙을 먼저 검사하고 **선택된 `LOW_FLOW`는 그다음에 검사**하기 때문에 결과가 바뀌지 않았다.

다만 **이것은 규칙 기반 분류기의 결과**이다. 실제 서비스에서 LLM 기반 구조화가 활성화돼 있으면 LLM의 검증된 결과가 이를 교정할 수도 있다. 최종 고객 답변이 실제로 틀렸다고 주장할 수는 없다.

### 5. 잘못된 분류가 왜 문제가 될 수 있나?

WaterBridge는 분류된 증상에 따라 **어떤 근거를 사용할지**와 **무엇을 추가로 확인할지**를 다르게 결정한다.

검증된 설명서 청크 7개를 **검색 DB가 아니라 근거 필터 함수에 직접** 넣어 비교했다.

| 검사 | ‘필터/관리 문의’로 분류 | ‘출수량 저하’로 분류 |
|---|---|---|
| 통과한 청크 | **7개 모두 통과** | **저출수 근거 1개만 통과** |
| 필수(`high`) 확인 항목 | 없음 | **`target_water_type`** (냉수·온수·정수 등) |
| 의미 | 다양한 주제의 근거가 후단에 남을 수 있다 | 맞는 주제의 근거만 남기고 필요한 정보도 추가 확인할 수 있다 |

이 결과로 **‘증상 분류 → 근거 필터 → 추가 질문 조건’이 연결되어 있다**는 사실을 확인했다.

**중요:** 이는 같은 샘플 청크 7개를 *강제로 입력한 후처리 실험*이다. 실제 DB에서 7개가 검색됐다는 뜻도, 고객에게 잘못된 해결책을 제공했다고 확인됐다는 뜻도 아니다.

### 6. 검색을 허용하는 것과 검색에 성공하는 것은 다르다

실제 검색을 실행하기 전에 WaterBridge는 **해당 질문을 공식 매뉴얼에서 검색해도 되는지** 검사한다.

예를 들어 고객 질문이 **필터 가격**을 묻는다면 정적 사용설명서에 실시간 가격 정보가 없으므로 검색 전 차단할 수 있다. 반면 Q008과 같은 정상 제품 문의는 검색을 진행할 수 있다.

직접 실행한 정책 검사 결과는 다음과 같다.

| 입력 | 실제 판정 | 쉬운 해석 |
|---|---|---|
| Q008, 지원 제품 | `PGVECTOR_QUERY` | 검색 허용 |
| 미지원 제품 `WPU-IAC506` | `POLICY_BLOCK_UNSUPPORTED_MODEL` | 현재 지원 대상 아님 |
| 미등록 `UNKNOWNMODEL` | `POLICY_BLOCK_UNREGISTERED_EXACT_SALES_CODE` | 등록되지 않은 제품 |
| 필터 가격 문의 | `POLICY_BLOCK_OUT_OF_MANUAL_SCOPE` | 설명서 범위를 벗어남 |
| 없는 얼음 기능 문의 | `POLICY_BLOCK_UNSUPPORTED_CAPABILITY` | 해당 제품의 지원 기능 아님 |
| 미검증 FAQ만 요구 | `POLICY_BLOCK_UNVERIFIED_SOURCE` | 미검증 근거만 사용하라는 요청 차단 |

여기서 **`PGVECTOR_QUERY`는 ‘검색을 해도 된다’는 판정**일 뿐이다. 실제 DB에 접속해 검색한 것도 아니고 정답 근거를 찾았다는 뜻도 아니다.

취업 과정으로 비유하면 이해하기 쉽다.

1. **서류 합격:** 검색해도 된다는 판정.
2. **면접 응시:** 실제 DB에서 관련 문서를 검색.
3. **면접 합격:** 적합한 근거를 확보.
4. **입사 후 업무 성과:** 그 근거로 올바른 답변을 생성하고 검증.

따라서 **검색 허용 ≠ 검색 실행 ≠ 정답 근거 확보 ≠ 올바른 최종 답변**이다.

### 7. 검색에 문제가 생겨도 원인을 구분해야 한다

| 상황 | 뜻 | 확인해야 할 대상 |
|---|---|---|
| **정책 차단** | 검색 전에 제품·기능·질문 범위를 허용하지 않음 | 검색 전 정책 판정 |
| **검색 미실행** | 위험 상황이거나 추가 질문을 기다려 DB 검색을 건너뜀 | LangGraph 분기·상태 |
| **검색은 했지만 적합한 근거 없음** | 검색 또는 후처리 후 사용할 근거가 남지 않음 | 검색 결과 및 증상·조건 필터 |
| **검색 실행 오류** | DB/모델 실행 자체가 실패함 | 예외·재시도·지연 로그 |

이것들을 모두 ‘검색이 안 됐다’라고 합치면 개선해야 할 위치를 알기 어렵다. 특히 정책 차단과 정답 미검색을 **같은 검색 성능 실패로 해석하지 않는 것**이 중요하다.

### 8. 실제 코드 위치와 검증 범위

코드 위치는 **나중에 다시 찾기 위한 참고용**이다. 핵심 흐름을 먼저 이해하고 필요한 함수만 열어본다.

| 확인할 주제 | 파일 |
|---|---|
| 제품 확인과 실행 경로 선택 | `ai/app/orchestration/pipeline_router.py` |
| LangGraph의 분기 | `ai/app/orchestration/pipelines/single_rag_pipeline.py` |
| 규칙 기반 증상 분류 | `ai/app/structuring/symptom_normalizer.py` |
| 검색 질문 구성·근거 필터 | `ai/app/orchestration/stages/retrieval_stage.py` |
| 검색 전 정책과 임베딩 | `ai/app/retrieval/search/vector_search.py` |
| 실제 pgvector SQL | `ai/app/integrations/vector_store/vector_store.py` |
| 증상별 공식 근거 선별 | `ai/app/retrieval/filters/evidence_topic_filter.py` |
| 필수 추가 질문 판단 | `ai/app/structuring/missing_field_checker.py` |

**이번에 실제 실행한 것:** 규칙 기반 분류 결과 3건, 샘플 근거 필터 비교(7개 대 1개), 필수 필드 비교, 검색 전 정책 판정 6건. 사용자 PC의 출력과 코드 흐름을 함께 확인했다.

**실행하지 않은 것:** 실제 PostgreSQL 질의, BGE-M3 모델 재추론, LLM 구조화/생성, 고객 응대 API의 E2E. 따라서 **실제 고객 응대 장애를 확인·수정했다고 주장하지 않는다.**

**S03 결론:** 검색 모델 자체보다 앞뒤의 **질문 이해·증상 분류·필수 문진·근거 적용**도 중요하다는 것을 배웠다. S04에서는 독립 제품군·평가 데이터의 범위를 만들고, S05에서는 실제 응답의 오류가 어디에서 생기는지 구분할 계획이다.

**이번 주 마무리:** S01~S03의 코드·부분 실험은 완료했다. 다음 개발에서도 **‘실제 실행으로 확인한 사실’과 ‘코드로 추정한 영향’을 구분**한다.

## S04 — 공식 설명서 확장과 평가 데이터 초기 분할 **[미착수 · 실행 계획]**

### 1. 왜 S04가 필요한가?

M0에서는 공식 매뉴얼 **한 종류의 37~38쪽**에서 만든 10문항으로 검색을 비교했다. Q003과 Q010처럼 같은 누수 상황을 다른 말로 반복한 질문도 있다. 이런 데이터에서 높은 점수를 얻어도 **처음 보는 제품이나 다른 증상**에 잘 대응한다는 결론은 낼 수 없다.

**S04의 목표는 모델 성능을 높이는 것이 아니라, 앞으로 성능을 제대로 비교할 수 있는 자료와 평가 기준을 마련하는 것**이다.

### 2. 데이터는 이미 어디에 있고, 어떤 제약이 있나? **[코드·목록 확인]**

팀 저장소 `data/catalog/datasets.yaml` 및 `data/processed/metadata/source_inventory.csv`에는 다음 **세 개의 공식 설명서 원천**이 기록돼 있다.

| 판매 모델 코드 | 매뉴얼 / 버전 | 페이지 | 현재 역할 |
|---|---|---:|---|
| `WPUJAC104DWH` | WPU-JAC104(D)·JCC104(D) 공용 REV.00 | 44 | **현재 MVP 검색 원천** |
| `WPUIAC425SNW` | WPU-IAC425 REV.02 | 52 | **확장/참고 검증용**, 공개 Runtime 아님 |
| `WPUIAC606SNW` | WPU-IAC606 REV.00 | 48 | **확장/참고 검증용**, 공개 Runtime 아님 |

합계 **144페이지**가 *목록에 등록*돼 있지만, 이것이 곧 144개 독립 사례 또는 3개 제품이 실제 운영 서비스에서 모두 활성화됐다는 뜻은 아니다. JAC104와 JCC104는 **같은 공용 설명서**이므로 별도 독립 원천 두 개로 세지 않는다. 다른 두 제품은 **공개 Runtime 승인 대상이 아니므로**, 오프라인 실험에서 활용하더라도 실제 고객용 검색 허용 상태를 임의로 바꾸지 않는다.

찾아볼 코드·데이터:
- `data/catalog/datasets.yaml`: 처리된 설명서 목록과 용도
- `data/processed/metadata/source_inventory.csv`: 원본 출처, 모델, 버전 및 팀 기록 해시
- `data/processed/documents/manuals/`: 페이지별 텍스트 원천
- `data/processed/structured/rag/`: 검색 후보 청크(사용 범위가 서로 다름)

### 3. Gold 평가 데이터는 무엇을 기록해야 하나?

질문 하나에 단순히 '정답 문장'만 쓰면 **어느 제품에 해당하는지, 언제 적용 가능한지** 놓치기 쉽다. 최소한 다음을 한 사례로 묶어 관리하자.

| 필드 | 뜻 | 적어야 하는 이유 |
|---|---|---|
| `case_id` | 질문 식별자 | 테스트 결과와 대조 |
| `question` | 고객 표현(합성이라면 명시) | 검색·생성 입력 |
| `model_code` | 정확한 판매 모델 코드 | 다른 제품 근거 혼입 방지 |
| `scenario_group` | 출수량 저하, 누수 등 증상·원인 묶음 | 비슷한 질문을 독립 표본으로 중복 계산하지 않기 |
| `source_document_id`, `source_page` | 원본 문서와 쪽 | 사람이 원문을 재검증할 수 있게 |
| `gold_evidence_ids` | 정답으로 인정할 실제 근거 청크 ID | 검색 성능 채점 |
| `expected_behavior` | `ANSWER` / `ASK` / `ESCALATE` 등 | 반드시 답해야 하는지, 추가 질문이 필요한지 구분 |
| `provenance` | 공식 원문/합성 질문/가상 정책 | 원본과 가상 데이터를 혼동하지 않기 |

**중요:** M0 연습 청크의 `WB-S02-006`과 실제 WaterBridge 샘플 청크의 `RAG-WPUJAC104DWH-LOW-FLOW-001`은 **다른 데이터셋의 ID**다. 서로 치환해 Gold를 만들면 안 된다.

### 4. train / dev / holdout은 왜 나누나?

- **train(학습용):** 나중에 SFT에서 모델을 학습시키는 사례.
- **dev(개발·조정용):** 프롬프트와 설정을 바꾸며 비교하는 사례.
- **holdout(최종 보류):** 모델·프롬프트·검색기 선택을 끝낸 뒤 한 번 최종 평가하는 사례.

**같은 증상·매뉴얼 문장을 조금 바꾼 질문을 train과 holdout에 나누면 일반화 평가가 과장될 수 있다.** 제품·공용 매뉴얼·증상 시나리오 묶음으로 중복을 찾아 분리한다. 서로 다른 제품의 매뉴얼에 동일한 조치 문장이 반복되는 경우도 확인해야 한다.

또 ‘미학습 제품 평가’는 **그 제품의 질문·정답 라벨을 학습에서 숨긴다**는 뜻이지, RAG가 접근할 공식 매뉴얼까지 제거해야 한다는 뜻은 아니다. 검색에 쓰일 근거는 있어야 한다. 단, 실제 서비스의 제품 사용 정책과 오프라인 평가는 분리한다.

### 5. 실제 작업 순서 **[예정]**

1. 세 문서의 원본 출처·REV·모델 코드·공용 여부를 확인하고 원본 파일을 대조한다. 기존 팀 기록의 SHA-256은 현재 파일의 재해시 결과와 구분한다.
2. **제품×증상×상황** 기준으로 서로 다른 평가 시나리오부터 모은다. 같은 문장 바꾸기만으로 개수를 늘리지 않는다.
3. 샘플 **10건 이상**을 공식 원문과 직접 대조하고, 정답 근거·적용 조건·답변 가능 여부를 검수한다.
4. 공용 매뉴얼·유사 증상·같은 절에서 파생한 사례를 `scenario_group`으로 묶고 **train/dev/holdout 분리 원칙**을 기록한다.
5. 실제 확보한 문서·독립 시나리오 수를 명시하고, 자료가 부족하면 일반화 주장 범위를 축소한다.

**산출물 방향:** 새 독립 설명 보고서가 아니라, **원시 데이터·출처 명세와 이 M1 문서의 S04 결과 절**만 남긴다. 실제 파일 경로는 작성 시 확인한다.

**S04를 완료했다고 말하려면:** 출처를 확인한 공식 원천, 실제 검수 사례, 중복/누수 방지 분리 기준, 부족한 데이터의 한계를 제시할 수 있어야 한다. **현재는 완료되지 않았다.**

## S05 — 실제 RAG 응답 기준선과 실패 원인 분석 **[미착수 · 실행 계획]**

### 1. 왜 검색 성능과 최종 응답을 따로 볼까?

문서를 올바르게 찾았어도 LLM이 잘못 해석하면 틀린 안내가 나온다. 반대로 정답 근거가 애초에 검색되지 않았다면, LLM이 추측으로 답변하도록 기대해서는 안 된다. **검색 오류인지, 근거 해석·응답 생성 오류인지 먼저 분리해야** 이후 SFT로 어떤 능력을 학습할지 결정할 수 있다.

예를 들어 Q008에서 ‘필터를 이미 교체했다’는 고객이 **수행한 조치**다. 모델이 정답 근거를 보았는데도 ‘필터부터 교체하세요’라고만 답하거나, 완전 미출수 조치를 저출수에 단정적으로 적용하면 **적용 조건을 잘못 해석한 사례**가 된다. 다만 이 예시는 **앞으로 검증할 실패 유형이지 실제 WaterBridge가 이미 그런 답변을 했다는 기록이 아니다.**

### 2. Oracle 근거 실험이란?

같은 질문·같은 생성 모델·같은 출력 규칙을 두고 **LLM에게 제공하는 근거만 바꿔** 원인을 추적하는 실험이다.

| 조건 | LLM에게 제공하는 문서 | 무엇을 알아보나? |
|---|---|---|
| **실제 RAG** | 검색기가 실제로 반환하고 후처리한 근거 | 검색부터 답변까지 이어진 현재 기준선 |
| **Oracle 근거** | 사람이 원문 확인한 정답 근거를 **직접** 제공 | 검색이 완벽하다고 가정해도 생성·해석 오류가 남는가? |

**결과 해석 예시:** 실제 RAG는 틀리고 Oracle은 맞으면 검색·후처리 쪽을 먼저 의심한다. 두 조건 모두 틀리면 **프롬프트·생성 모델·정답 스키마·문서 적용 조건**을 점검한다. 물론 질문 자체가 모호하거나 ‘추가 질문’이 정답인 경우도 있으므로, 무조건 문장을 생성해야 성공이라고 평가하지 않는다.

이때 비교 기준인 **강한 프롬프트(Strong Prompt)**는 제품 코드·근거 표시·적용 조건·안전 제한·근거 부족 시 보류·추가 질문 원칙을 명확히 작성한 프롬프트다. 이후 SFT와 비교할 때 **프롬프트가 지나치게 허술한 상태를 일부러 기준선으로 두지 않는다.**

### 3. 어떤 오류를 기록할까?

| 오류 유형 | 쉬운 설명 | 기록할 내용 |
|---|---|---|
| **검색 후보 누락** | 필요한 문서가 검색 상위권에 없음 | Gold ID와 실제 검색 ID·순위 |
| **근거 후처리 누락** | 검색됐지만 필터에서 제거됨 | 제거된 청크와 이유 |
| **증상·조건 혼동** | 저출수를 완전 미출수로 보거나 반대로 처리 | 고객 증상과 적용 문단 조건 |
| **추가 질문 누락** | 제품·상황을 확인해야 하는데 바로 답변 | 누락된 필수 정보 |
| **근거 없는 주장** | 문서에 없는 원인·수리 방법을 단정 | 원문과 답변 불일치 부분 |
| **형식·안전 오류** | 출처 표시 누락, 위험 조치, 허용되지 않는 표현 | 출력 검증 결과 |
| **정상 보류·상담 처리** | 답할 근거가 없을 때 억지 답 대신 보류/인계 | 기대 행동과 실제 경로 |

검색이 차단된 경우, 검색은 했으나 정답이 없는 경우, LLM 실행에 실패한 경우를 **같은 오답 원인으로 합치지 않는다.**

### 4. 실제 작업 순서 **[예정]**

1. S04에서 검수한 **개발용 20~30개 안팎의 질문**을 정하고 모델·출처·정답 행동을 확인한다. 숫자는 목표이며 확보 완료된 데이터 수가 아니다.
2. 기존 WaterBridge 정상 경로가 실행 가능한지 점검한다. DB·모델·API 설정이 준비되지 않았다면 **오프라인 실험과 실제 E2E를 구분**하고, 어디까지 실행했는지 기록한다.
3. **강한 프롬프트 + 실제 검색 근거**, **동일 프롬프트 + Oracle 근거**를 같은 생성 모델·디코딩 설정으로 비교한다.
4. 답변이 맞는지 실제 원문·조건·안전 조치와 대조한다. LLM-as-a-Judge가 있더라도 사람의 원문 검수를 최종 기준으로 둔다.
5. 검색 실패 / 근거 해석 오류 / 추가 질문 누락 / 생성 형식 오류를 **건수와 실제 예시**로 분류한다.
6. SFT가 필요한 구체적인 오류를 2~3개 확보하거나, 없다면 **학습 목표를 응대 정책·구조화 출력 등으로 재정의**한다.

**실험 고정 원칙:** 동일 질문·원문 문서·모델·프롬프트·온도·출력 길이와 동일한 판정 규칙으로 비교한다. Holdout은 최종 검증 전까지 조정에 사용하지 않는다.

**S05를 완료했다고 말하려면:** 실제 RAG 기준선과 Oracle 근거 실험의 입력·출력·판정 로그, 오류 분류 및 **SFT 학습 대상으로 삼을 이유**가 남아야 한다. **현재는 완료되지 않았다.**
