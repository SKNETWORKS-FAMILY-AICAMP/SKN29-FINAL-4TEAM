## M1에 들어가기 전: 왜 검색만 잘해도 충분하지 않을까?

고객이 “필터를 갈았는데도 물이 조금씩 나와요”라고 말했을 때, 검색 모델이 가장 비슷한 문서를 찾더라도 **고객 증상이 ‘출수량 저하’라는 사실을 잘못 이해**하면 잘못된 안내로 이어질 위험이 있다. 또 어떤 고객은 **다른 제품을 사용**하거나 **안전상 즉시 상담이 필요한 상황**일 수 있다.

그래서 실제 AI 서비스는 보통 ‘검색’ 하나가 아니라 다음 과정을 연결한다.

```text
고객 문의
  → ① 증상 분류 (무슨 문제인가?)
  → ② 안전·제품·정보 확인 (지금 검색하는 게 맞나?)
  → ③ 공식 설명서 검색 + 적용 조건 확인 (근거가 맞나?)
  → ④ 안내 생성 + 검증 (근거 밖 내용을 말하지 않았나?)
```

**LangGraph**는 이 과정에서 '안전 문제면 검색 생략', '필수 정보가 없으면 되묻기'처럼 **다음 단계를 조건에 따라 고르는 흐름**을 관리한다. **규칙 기반 검증과 제품·안전 정책은 LLM의 추측과 분리**한다.

### 지금 필요한 용어만 먼저

| 용어 | 쉽게 설명하면 |
|---|---|
| **증상 구조화(Structuring)** | 고객의 자유로운 문장을 `출수량 저하` 같은 정해진 항목으로 바꾸기 |
| **Policy / Gate** | 모델·제품·질문 범위가 허용되는지 검색 전 검사하기 |
| **Metadata Filter** | 제품 코드·세대·공식 검증 상태에 맞는 문서만 통과시키기 |
| **증상 주제 필터(Topic Filter)** | 누수 질문에는 누수 근거처럼 관련 주제의 청크만 남기기 |
| **추가 질문(Clarification)** | 출수 종류 등 필수 정보가 부족하면 고객에게 먼저 확인하기 |
| **Oracle Evidence** | 검색기의 성능과 무관하게 올바른 정답 근거를 직접 넣어 답변을 테스트하기(S05 예정) |

**기억할 비유:** `PGVECTOR_QUERY`는 *서류 합격(검색 허용)*에 해당한다. 실제 DB에서 검색하는 것은 *면접 응시*, 정답 근거를 확보한 것은 *면접 합격*, 올바른 안내까지 마친 것은 *입사 후 업무 성과*와 비슷하다.

## S03

### 1. 왜 실제 WaterBridge 코드를 살펴봤나?

S01과 S02는 **검색 결과를 잘 고르는 방법**에 집중했다. 그런데 실제 고객 응대에서는 검색이 잘되어도 **질문을 잘못 이해하거나, 다른 모델의 설명서를 사용하거나, 필요한 추가 질문을 빼먹으면** 잘못 안내할 위험이 있다.

그래서 S03에서는 S01·S02의 미니 검색기가 아니라, **기존 WaterBridge 서비스 코드가 질문 하나를 어떤 순서로 처리하는지** 추적했다.

살펴본 질문은 S01에서 문제가 드러났던 **Q008**이다.

> “필터를 이미 갈았는데도 물이 조금씩만 나와요. 어떻게 하죠?”
> 제품 코드: `WPUJAC104DWH`

**사람이 이해한 고객 증상:** ‘필터를 교체했다’는 *이미 한 조치*이고, 현재 문제는 **물이 적게 나오는 것(출수량 저하)**이다.

### 2. WaterBridge의 처리 흐름은 네 단계로 기억한다

| 단계 | 쉽게 말하면 | 실제 WaterBridge 코드에서 하는 일 |
|---|---|---|
| **① 질문 이해** | 고객이 무엇을 겪고 있나? | 제품 코드와 자연어 증상을 확인하고 표준 증상 유형으로 정리한다. |
| **② 검색 여부 결정** | 추가 정보가 필요한가? 설명서로 답할 수 있나? | 위험 상황은 안전 안내로, 필수 정보가 부족하면 추가 질문으로 분기한다. 검색 전 제품·기능·문서 범위도 검사한다. |
| **③ 공식 근거 찾기** | 해당 모델의 공식 설명서에 답이 있나? | BGE-M3로 임베딩해 pgvector에서 검색하고, 제품·주제·적용 조건이 맞는 근거만 남긴다. |
| **④ 답변 생성·검증** | 찾은 내용으로 안전하게 안내했나? | 근거가 있으면 안내를 생성하고, 근거가 없거나 위험한 경우 지정된 안내를 사용하며 최종 결과를 검증한다. |

이 단계들의 **실행 순서와 조건부 분기**를 관리하는 데 **LangGraph**가 사용된다. 정상 경로는 대략 ‘증상 구조화 → 안전 검사 → 추가 질문 검사 → 검색 → 안내 생성 → 검증’이다. 단, 위험하거나 필수 정보가 누락되면 검색으로 곧장 가지 않을 수 있다.

함수 이름 전체를 외울 필요는 없다. **어떤 판단이 왜 검색 전에 필요한가**를 이해하는 것이 중요하다.

### 3. 실제 서비스의 검색은 미니 검색기와 무엇이 다른가?

| 항목 | S01·S02 연습 | 실제 WaterBridge 기본 검색 경로 |
|---|---|---|
| 임베딩 모델 | E5-small | **BGE-M3** |
| 검색 방식 | 로컬 Overlap/BM25/E5/RRF 실험 | **pgvector의 코사인 exact search** |
| 임베딩 크기 | 실습 모델 설정에 따름 | **1024차원** |
| 검색 결과 개수 | Top-3 | **Top-5** |
| 검색 전·후 조건 | 학습용 작은 검색기 | 제품 코드·세대·공식 검증 상태·증상 주제·적용 조건 확인 |
| 결과 활용 | 검색 순위와 지표 계산 | 이후 고객 안내 생성 및 검증 |

실제 검색 코드의 유사도 임계값 기본값은 **0.4**이고, 제품의 정확한 판매 코드와 세대, 공식 검증 상태 등으로 검색 후보를 제한한다. S02의 **E5+RRF는 실제 서비스 검색 경로에 연결되지 않았다.**

### 4. Q008에서 발견한 분류 문제

규칙 기반 증상 분류기만 직접 실행하니 아래 결과가 나왔다.

| 입력 | 실제 분류 결과 |
|---|---|
| Q008 원문 | **필터/관리 문의** |
| Q008 + 사용자가 선택한 `LOW_FLOW` | **필터/관리 문의** |
| ‘필터를 교체했는데도 **출수량이 적어요**’ | **출수량 저하** |

**왜 이런 일이 생겼나?** 규칙 기반 분류기에 `필터`라는 단어는 등록되어 있지만, Q008의 `조금씩만 나와요`는 출수량 저하를 탐지하는 표현에 포함되어 있지 않았다. 이 코드에서는 원문 키워드 규칙을 먼저 검사하고 **선택된 `LOW_FLOW`는 그다음에 검사**하기 때문에 결과가 바뀌지 않았다.

다만 **이것은 규칙 기반 분류기의 결과**이다. 실제 서비스에서 LLM 기반 구조화가 활성화돼 있으면 LLM의 검증된 결과가 이를 교정할 수도 있다. 최종 고객 답변이 실제로 틀렸다고 주장할 수는 없다.

### 5. 잘못된 분류가 왜 문제가 될 수 있나?

WaterBridge는 분류된 증상에 따라 **어떤 근거를 사용할지**와 **무엇을 추가로 확인할지**를 다르게 결정한다.

검증된 설명서 청크 7개를 **검색 DB가 아니라 근거 필터 함수에 직접** 넣어 비교했다.

| 검사 | ‘필터/관리 문의’로 분류 | ‘출수량 저하’로 분류 |
|---|---|---|
| 통과한 청크 | **7개 모두 통과** | **저출수 근거 1개만 통과** |
| 필수(`high`) 확인 항목 | 없음 | **`target_water_type`** (냉수·온수·정수 등) |
| 의미 | 다양한 주제의 근거가 후단에 남을 수 있다 | 맞는 주제의 근거만 남기고 필요한 정보도 추가 확인할 수 있다 |

이 결과로 **‘증상 분류 → 근거 필터 → 추가 질문 조건’이 연결되어 있다**는 사실을 확인했다.

**중요:** 이는 같은 샘플 청크 7개를 *강제로 입력한 후처리 실험*이다. 실제 DB에서 7개가 검색됐다는 뜻도, 고객에게 잘못된 해결책을 제공했다고 확인됐다는 뜻도 아니다.

### 6. 검색을 허용하는 것과 검색에 성공하는 것은 다르다

실제 검색을 실행하기 전에 WaterBridge는 **해당 질문을 공식 매뉴얼에서 검색해도 되는지** 검사한다.

예를 들어 고객 질문이 **필터 가격**을 묻는다면 정적 사용설명서에 실시간 가격 정보가 없으므로 검색 전 차단할 수 있다. 반면 Q008과 같은 정상 제품 문의는 검색을 진행할 수 있다.

직접 실행한 정책 검사 결과는 다음과 같다.

| 입력 | 실제 판정 | 쉬운 해석 |
|---|---|---|
| Q008, 지원 제품 | `PGVECTOR_QUERY` | 검색 허용 |
| 미지원 제품 `WPU-IAC506` | `POLICY_BLOCK_UNSUPPORTED_MODEL` | 현재 지원 대상 아님 |
| 미등록 `UNKNOWNMODEL` | `POLICY_BLOCK_UNREGISTERED_EXACT_SALES_CODE` | 등록되지 않은 제품 |
| 필터 가격 문의 | `POLICY_BLOCK_OUT_OF_MANUAL_SCOPE` | 설명서 범위를 벗어남 |
| 없는 얼음 기능 문의 | `POLICY_BLOCK_UNSUPPORTED_CAPABILITY` | 해당 제품의 지원 기능 아님 |
| 미검증 FAQ만 요구 | `POLICY_BLOCK_UNVERIFIED_SOURCE` | 미검증 근거만 사용하라는 요청 차단 |

여기서 **`PGVECTOR_QUERY`는 ‘검색을 해도 된다’는 판정**일 뿐이다. 실제 DB에 접속해 검색한 것도 아니고 정답 근거를 찾았다는 뜻도 아니다.

취업 과정으로 비유하면 이해하기 쉽다.

1. **서류 합격:** 검색해도 된다는 판정.
2. **면접 응시:** 실제 DB에서 관련 문서를 검색.
3. **면접 합격:** 적합한 근거를 확보.
4. **입사 후 업무 성과:** 그 근거로 올바른 답변을 생성하고 검증.

따라서 **검색 허용 ≠ 검색 실행 ≠ 정답 근거 확보 ≠ 올바른 최종 답변**이다.

### 7. 검색에 문제가 생겨도 원인을 구분해야 한다

| 상황 | 뜻 | 확인해야 할 대상 |
|---|---|---|
| **정책 차단** | 검색 전에 제품·기능·질문 범위를 허용하지 않음 | 검색 전 정책 판정 |
| **검색 미실행** | 위험 상황이거나 추가 질문을 기다려 DB 검색을 건너뜀 | LangGraph 분기·상태 |
| **검색은 했지만 적합한 근거 없음** | 검색 또는 후처리 후 사용할 근거가 남지 않음 | 검색 결과 및 증상·조건 필터 |
| **검색 실행 오류** | DB/모델 실행 자체가 실패함 | 예외·재시도·지연 로그 |

이것들을 모두 ‘검색이 안 됐다’라고 합치면 개선해야 할 위치를 알기 어렵다. 특히 정책 차단과 정답 미검색을 **같은 검색 성능 실패로 해석하지 않는 것**이 중요하다.

### 8. 실제 코드 위치와 검증 범위

코드 위치는 **나중에 다시 찾기 위한 참고용**이다. 핵심 흐름을 먼저 이해하고 필요한 함수만 열어본다.

| 확인할 주제 | 파일 |
|---|---|
| 제품 확인과 실행 경로 선택 | `ai/app/orchestration/pipeline_router.py` |
| LangGraph의 분기 | `ai/app/orchestration/pipelines/single_rag_pipeline.py` |
| 규칙 기반 증상 분류 | `ai/app/structuring/symptom_normalizer.py` |
| 검색 질문 구성·근거 필터 | `ai/app/orchestration/stages/retrieval_stage.py` |
| 검색 전 정책과 임베딩 | `ai/app/retrieval/search/vector_search.py` |
| 실제 pgvector SQL | `ai/app/integrations/vector_store/vector_store.py` |
| 증상별 공식 근거 선별 | `ai/app/retrieval/filters/evidence_topic_filter.py` |
| 필수 추가 질문 판단 | `ai/app/structuring/missing_field_checker.py` |

**이번에 실제 실행한 것:** 규칙 기반 분류 결과 3건, 샘플 근거 필터 비교(7개 대 1개), 필수 필드 비교, 검색 전 정책 판정 6건. 사용자 PC의 출력과 코드 흐름을 함께 확인했다.

**실행하지 않은 것:** 실제 PostgreSQL 질의, BGE-M3 모델 재추론, LLM 구조화/생성, 고객 응대 API의 E2E. 따라서 **실제 고객 응대 장애를 확인·수정했다고 주장하지 않는다.**

**S03 결론:** 검색 모델 자체보다 앞뒤의 **질문 이해·증상 분류·필수 문진·근거 적용**도 중요하다는 것을 배웠다. S04에서는 독립 제품군·평가 데이터의 범위를 만들고, S05에서는 실제 응답의 오류가 어디에서 생기는지 구분할 계획이다.

**이번 주 마무리:** S01~S03의 코드·부분 실험은 완료했다. 다음 개발에서도 **‘실제 실행으로 확인한 사실’과 ‘코드로 추정한 영향’을 구분**한다.

### 1. 왜 S04를 했나?

M0의 8개 청크·10개 질문은 검색 개념을 배우기 위한 **작은 연습 데이터**였다. 이 결과만으로 새로운 모델이나 다른 제품의 고객 문의를 잘 처리한다고 주장할 수 없다. S04에서는 제품과 질문 범위를 넓히고, **학습 데이터와 평가 데이터를 섞지 않는 기반**을 만들었다.

- **Train:** 모델에게 학습시킬 예제. 취업 준비에 비유하면 공부한 기출문제다.
- **Dev:** 프롬프트나 설정을 조정하며 반복 평가하는 문제. 모의면접에 해당한다.
- **Holdout:** 앞의 선택이 모두 끝난 뒤 최종 점검용으로 남겨둔 문제. 실제 면접에 해당한다.

같은 내용을 표현만 바꾼 질문을 Train과 Holdout 양쪽에 놓으면, 배웠던 답을 반복한 것인데도 새로운 문제를 잘 푼 것처럼 보일 수 있다. 이를 **평가 데이터 누출 위험**이라고 한다. 반면 RAG가 공식 설명서에서 근거를 찾아 읽는 행위 자체는 정상적인 검색이므로 구분한다.

### 2. 무엇을 확보하고 실제로 검토했나? **[원문 PDF 검토·데이터 감사]**

| 공식 원문 | 설명서 | 실험상 역할 |
|---|---:|---|
| JAC104(D)/JCC104(D) 공용 REV.00 | 44쪽 | 현재 MVP 모델 `WPUJAC104DWH`; JCC104는 별도 기능 범위 점검 |
| IAC425 REV.02 | 52쪽 | **오프라인 평가**용(현재 공개 Runtime 미승인) |
| IAC606 REV.00 | 48쪽 | **오프라인 평가**용(현재 공개 Runtime 미승인) |

**총 144쪽의 원본 PDF 3종**을 확보했고, 해당 파일의 SHA-256을 팀 출처 목록과 대조했다. 기존 가공 자료는 검색 후보 청크 53개, 근거 그룹 43개, 합성 상담 시나리오 30건이었다. 원본 설명서의 관련 페이지를 기준으로 **30건 모두 증상·조치·위험/상담 조건·제품 적용 범위**를 검토했다. 이는 실제 고객 상담 기록이 아닌 **합성 시나리오**다.

### 3. 어떤 오류 위험을 찾았나? **[PDF 검수 결과]**

검수한 30건 중 **16건은 보완·구분 의견을 제안**했다. 이것은 *팀 원본 코드·라벨 16건을 이미 수정했다*거나 *확정된 서비스 장애 16건*이라는 뜻이 아니다. 교정안은 별도의 개인 평가 자료에 두고 팀 원본은 보존했다.

| 예시 | 왜 중요한가? |
|---|---|
| 연속 다량 출수 후 냉수가 미지근함 | ‘잠시 기다린 뒤 다시 출수’라는 핵심 조치가 일부 `safe_actions` 요약에 빠져 있음 |
| IAC425의 조리수 동시 사용으로 저출수 발생 | 조리수를 멈추는 직접적인 조치가 정답 요약에 빠져 있음 |
| JAC104/IAC425/IAC606 온수 모듈 또는 히터 경고 | 조건에 맞는 **출수 물 음용 금지**가 최우선 안내여야 함 |
| IAC606에서 10일 이상 미사용 후 맛·냄새 이상 | 10일 이내 조치와 10일 이상 조치가 달라 세척 절차를 구분해야 함 |
| JCC104 온수 문의·미지원 버튼 사례 | ‘설명서에 답이 없다’와 ‘현재 인덱스/공개 서비스에서 지원하지 않는다’는 서로 다른 문제 |

특히 원본 설명서에는 답이 있어도 기존 검색 인덱스에 해당 근거가 없는 사례가 있다. 따라서 **`no index evidence`를 곧바로 ‘원문에도 정답 없음’이라고 해석하지 않는다.**

### 4. 데이터 누출을 어떻게 예방했나? **[실행 확인]**

문자열이 똑같은 검색 청크는 SHA-256으로 찾을 수 있다. 그러나 ‘냉수를 많이 뽑아 미지근해졌다’와 ‘연속 출수 후 냉수가 덜 차갑다’처럼 **표현은 다르지만 같은 조건·조치**를 요구하는 문장은 해시만으로 잡을 수 없다.

그래서 제품·근거 내용·질문 상황을 함께 검토하여 **30건을 의미상 16개 그룹**으로 묶고, 같은 그룹은 한 분할에만 배치했다.

| 데이터 분할 | 질문 수 | 근거가 연결된 사례 | 현재 인덱스 근거가 없는 사례 | 안전 관련 사례 |
|---|---:|---:|---:|---:|
| **Train** | 18 | 15 | 3 | 2 |
| **Dev** | 6 | 5 | 1 | 1 |
| **Holdout** | 6 | 5 | 1 | 3 |

**사용자 Windows 환경에서 실행한 검증기 결과:**

```text

Cases: 30 semantic groups: 16
No exact-evidence/text or declared semantic group crossing split: PASS

```

따라서 **등록된 의미 그룹 및 정확히 같은 근거·청크 텍스트의 분할 간 중복은 0건**이었다. 모든 가능한 의미상 중복이 없음을 통계적으로 증명한 것은 아니다. 검증 스크립트는 PDF 파일을 새로 열지 않고 기록된 SHA 및 평가 자료 간 일관성을 검사한다.

### 5. 남은 한계와 다음 단계

- 파일럿 Holdout은 **6건**이며, 서로 관련된 사례가 있어 통계적으로 신뢰할 수 있는 ‘눈가림 최종 성능’ 자료가 아니다. 모델·프롬프트 선택에 **사용하지 않는다**.

- 본격 SFT 일반화 평가를 위해서는 **추가 독립 시나리오 및 별도 블라인드 테스트**가 필요하다.

## S05 — Oracle·일반 RAG·안전 라우팅 RAG 비교 **[오프라인 파일럿 종료]**

<!-- M1_S05_OFFLINE_PILOT_CLOSE_20261030 -->

> **실행 근거:** 사용자 PC에서 저장한 실제 검색 JSONL·LLM 응답 JSONL (2026-10-30 한국 시간 무렵).
> **정확한 범위:** Dev **6건(4개 의미 그룹)**, 생성 모델 `gpt-4.1-mini-2025-04-14`, 공식 설명서 기반 **오프라인** 실험.
> **하지 않은 것:** 세 제품의 공개 API E2E, 실제 pgvector 질의, 전체 LangGraph/Safety Stage, 모델 SFT, 독립 블라인드 일반화 성능 평가. **Holdout 6건은 사용하지 않았다.**

### 1. 왜 S05가 필요한가? — '근거 찾기'와 '답변하기'는 별개다

M0에서는 검색된 청크의 **순위**를 계산했다. S03에서는 실제 WaterBridge가 **증상 → 정책 검사 → 근거 선택 → 안내**를 연결한다는 점을 확인했다. S04에서는 서로 유사한 질문의 데이터 누출을 막기 위해 파일럿 데이터를 나눴다.

이제 질문은 **'정답 문서를 찾은 LLM이 정말 적절한 안내를 할까?'**다. 고객에게 제공하는 답변은 단순히 `ANSWER`/`ASK`라는 행동만 맞아서는 충분하지 않다. 반드시 필요한 안전 조치를 포함하고, **다른 상황에만 적용되는 조치**를 잘못 덧붙이지 않아야 한다.

비유하면, **검색은 시험에서 참고할 교과서 부분을 찾는 과정**, **LLM 생성은 그 부분을 읽고 답안을 쓰는 과정**이다. 책을 잘못 펴서 틀릴 수도 있고, 정확한 책을 펴고도 해석을 잘못해 틀릴 수 있다.

### 2. 세 실험에서 무엇을 같게 하고 무엇을 바꿨나?

| 조건 | LLM이 받은 근거 | 실험 목적 |
|---|---|---|
| **Oracle** | PDF 근거와 연결된 **정답 근거를 직접 제공** | 검색에 실패하지 않아도 생성 오류가 남는지 확인 |
| **일반 RAG** | BGE-M3가 제품별 후보 청크에서 찾은 Top-5 | 근거 검색 실패가 답변에 미치는 영향 확인 |
| **안전 라우팅 RAG** | 위험·부정·물 종류 표현을 먼저 판단한 뒤 BGE-M3가 찾은 Top-5 | 잘못된 검색 후보를 줄였을 때 답변이 달라지는지 확인 |

세 조건의 고객 질문과 기대 행동은 **동일한 Dev 6건**이다. 같은 OpenAI 생성 모델·출력 스키마·기본 안내 프롬프트 코드를 재사용했다. 그러나 **제공한 근거의 내용·개수와 실제 입력 토큰은 다르므로**, 완전히 동일한 입력이나 엄밀한 인과 검증이라고 부를 수는 없다.

**검색 측면의 구현:** 공식 검증된 팀의 후보 청크 53개에서 `BAAI/bge-m3`(1024차원)로 정규화 임베딩을 만들고, **NumPy의 코사인 내적**으로 제품 코드에 맞는 청크를 Top-5로 정렬했다(유사도 임계값 0.4). 실제 **pgvector DB를 구동하지는 않았다.** 2개 얼음정수기는 공개 런타임 미승인 제품이므로 *오프라인 개발 실험*으로만 취급한다.

**정답(Gold)은 검색 결과가 정해진 뒤 평가할 때만 사용했다.** 정답 청크 ID를 사용하여 검색 범위를 줄이거나 검색 순서를 조작하지 않았다.

### 3. 우선 검색에서 정답을 찾았는가?

원래 Dev 6건 중 **5건은 검색할 정답 근거가 존재**한다. 남은 `JAC104-033`은 미지원 제빙 기능에 관한 **정책/지원 범위 사례**이므로 Hit@K 분모에서 제외한다.

| 사례 | 문제 | 일반 BGE-M3 정답 순위 | 안전 라우팅 정답 순위 |
|---|---|---:|---:|
| `IAC425-105` | 물이 전혀 안 나옴 | 2위 | **1위** |
| `IAC606-105` | 물이 전혀 안 나옴 | Top-5 밖 | **1위** |
| `JAC104-025` | 물이 전혀 안 나옴 | Top-5 밖 | **1위** |
| `JAC104-029` | 누수·감전 위험 | 2위 | 2위 |
| `JAC104-030` | 7일 부재 뒤 물맛·냄새 이상 | 1위 | 1위 |
| `JAC104-033` | 제빙 기능 미지원 | 평가용 정답 근거 없음 | 평가용 정답 근거 없음 |

| 지표 | 일반 BGE-M3 | 안전 라우팅 |
|---|---:|---:|
| **Hit@1** | 1/5 | **4/5** |
| **Hit@5** | 3/5 | **5/5** |
| **MRR@5** | 0.40 | **0.90** |

**왜 무출수 세 건이 1위가 됐나?** 질문에서 전체 무출수를 명확히 판별한 경우, 먼저 **해당 제품의 무출수 주제 청크**로 후보를 좁혔다. 이 데이터에서는 모델별 무출수 청크가 한 개였으므로 그 청크가 1위가 됐다. **임베딩 모델을 재학습하거나 더 똑똑하게 만든 것은 아니다.**

> **주의:** 이 규칙은 Dev 실패 사례를 본 뒤 설계한 것이므로 **Dev 5/5 = 실제 일반화 정확도 100%가 아니다.** 파일럿 Holdout은 여전히 튜닝에 사용하지 않는다.

### 4. '검색 범위를 좁히면 무조건 좋다'는 가설은 왜 위험했나?

첫 무출수 규칙만 적용하면 '물이 안 나오면서 누수', '스파크 발생', '안 나오는 건 아니고 물줄기가 약함', '온수만 나오지 않음' 같은 질문까지 전체 무출수로 잘못 분류할 수 있었다. 이럴 경우 **안전 근거 또는 조건에 맞는 근거가 후보에서 빠질 위험**이 있다.

그래서 오프라인 라우팅 규칙을 다음과 같이 보완했다.

1. **누수·전기·연기 등 위험 신호 가능성:** 무출수 전용 필터를 적용하지 않는다.
2. **'안 나오는 건 아니고' 같은 부정 표현:** 완전 무출수로 단정하지 않는다.
3. **졸졸/조금씩/출수량 저하:** 완전 무출수와 구분한다.
4. **온수만·냉수만·얼음 등 특정 기능 문제:** 전체 무출수로 단정하지 않는다.
5. **전체 무출수가 명확한 경우에만:** 무출수 주제 후보를 우선 제한한다.

작성한 **합성 반례 20건 규칙 테스트는 20/20 통과**했다. 하지만 이 테스트는 우리가 만든 반례에서 동작을 확인한 것일 뿐 **실제 고객 안전성이나 독립 평가에서의 정확도를 입증하지 않는다.** 또한 위험 신호면 필터를 건너뛰는 것이지, 이 스크립트가 **WaterBridge의 실제 Safety Stage를 실행하는 것은 아니다.**

### 5. LLM의 행동 선택과 답변 내용은 각각 어땠나?

| 측정 | Oracle | 일반 RAG | 안전 라우팅 RAG |
|---|---:|---:|---:|
| **기대 행동 선택 일치** | **6/6** | **6/6** | **6/6** |
| **인용한 ID가 제공 목록에 없는 경우** | 0건 | 0건 | 0건 |
| LLM 응답 시간 평균(초) | 2.08 | 1.91 | 2.30 |
| 총 입력+출력 토큰 | 5,094 | 7,835 | 6,191 |

응답 시간은 **LLM 호출 구간**이며, 검색 모델 로딩·임베딩·실제 DB를 포함하는 서비스 종단 간 지연이나 공정한 속도 우위가 아니다. 토큰도 근거 길이가 서로 달라 직접적인 비용 효율 비교로 단정하지 않는다.

**모두 6/6인데도 왜 개선할 점이 있을까?** `ASK`를 선택하는 것과 **필요한 내용을 묻는 것**, `ANSWER`를 선택하는 것과 **근거의 적용 조건을 지키는 것**은 서로 다르기 때문이다.

| 사례 | Oracle/일반/개선 RAG를 비교하며 확인한 것 | 현재 판단 |
|---|---|---|
| `IAC425-105` | 정답 근거가 2위→1위. 개선 답변은 밸브·직수관케어·호스 질문을 더 구체적으로 물음 | 문진 구체성 개선 |
| `IAC606-105` | Top-5에서 못 찾던 무출수 근거를 1위로 검색. 개선 답변 문구가 이번 Oracle 실행과 동일 | **검색 실패의 영향이 유력한 사례** |
| `JAC104-025` | Top-5 실패→1위. 필터·호스 질문을 하게 됐지만 원수 밸브 확인은 빠짐 | 일부 개선, **필수 문진 완전성은 별도 평가 필요** |
| `JAC104-029` | 세 조건 모두 원수 밸브 잠금·플러그 분리·상담 연결 안내 | 이 사례의 안전 조치는 충족 |
| `JAC104-030` | 세 조건 모두 1L씩 버리는 핵심 조치는 맞았으나 **조건을 확인하지 않은 필터 전체 교체**를 추가 | **근거 적용 조건 확대 문제** |
| `JAC104-033` | 가상의 제빙 방법을 만들지는 않았으나, 개선 RAG는 **무관한 온수 안전 근거 ID를 인용** | **출처 관련성 실패**. 실제 서비스라면 별도 기능 Gate가 우선돼야 함 |

**출처 검증의 함정:** `invalid_cited_ids=0`은 인용 ID가 **모델에게 제공된 근거 목록 안에 있었다**는 뜻이다. **인용한 근거가 고객 질문이나 해당 주장에 적절했는지**까지 검사한 수치는 아니다. `JAC104-033`의 인용은 실제로 온수 관련이라 질문과 맞지 않았다.

**무출수 ASK 평가의 함정:** 첫 답변에서 가능한 점검 항목을 *전부* 나열하지 않았다고 즉시 오답 처리할 수는 없다. 후속 문진에서 중요한 누락 항목을 순서대로 확인하는지도 평가해야 한다.

### 6. 검색 문제와 생성 문제를 어떻게 구분했나?

| 발견된 실패 | 우선 원인 후보 | 바로 SFT를 해야 하나? |
|---|---|---|
| IAC606/JAC104 무출수 근거 Top-5 실패 | **검색 후보 선택**·증상 라우팅 | 아니요. 검색/후처리를 먼저 검증 |
| 7일 부재 후 냄새에 필터 전체 교체를 덧붙임 | **근거 적용 조건 해석**(Oracle에도 재현) | 바로 확정하지 않음. 프롬프트·근거 구조화·금지 조건 검사와 비교 |
| 제빙 미지원 질문에 온수 근거를 인용 | **검색 전 지원 기능 정책·인용 근거 검증** | 아니요. 정책 Gate·출처 관련성 검사부터 |
| ASK 행동은 맞지만 필수 확인 항목 일부 누락 | **문진 정책·질문 구성** | 먼저 후속 대화 평가, 필수 필드 스키마 검토 |

**핵심 교훈:** 오류는 모두 하나의 'LLM 정확도 문제'가 아니다. 정확한 근거가 없으면 검색·주제 필터를, 근거를 줘도 잘못 해석하면 답변 생성 조건을, 미지원 제품 기능이면 정책 검사를 먼저 살펴야 한다.
