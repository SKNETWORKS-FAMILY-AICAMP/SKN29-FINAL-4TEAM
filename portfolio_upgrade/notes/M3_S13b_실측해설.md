# M3 추가 교재 — S13b 2×2 실측과 출력 포맷의 함정

> 기존 `M3.md`는 보존하고, 이 부록을 S13b 실측 완료 기록으로 붙인다. 최초 실행계획 v4에서 S13은 Strong Prompt vs SFT 비교였고, S14는 오류 분석과 모델 종료 판단 단계다.

## PART 1 — 실험 이야기

S12에서 LoRA가 문제를 해결하지 못했으니 **프롬프트만 더 명확하게 써도 나아지는가?**가 다음 질문이 됐다. 같은 16개 가상 Dev에 P0/P1×BASE/LoRA를 비교했다. 그런데 P1에서 두 모델 모두 JSON을 코드 블록으로 감싸 내놓으면서 **공식 점수가 전부 0**이 됐다. 이렇게 끝내면 '강화 프롬프트가 JSON을 망쳤다'는 성급한 결론이 된다.

원본 문자열 안쪽에는 실제 JSON 객체가 있었다. 그래서 원본 점수는 그대로 두고, 단일 fence만 제거하는 **사후 진단**을 별도로 수행했다. 그 결과 P1 BASE와 LoRA는 모두 행동 정답 10/16, 전체 구조화 정답 4/16이었다. **학습 모델만의 이득이 나타나지 않았다.** 동시에 순수 JSON 출력 약속은 모두 어겼으므로 P1을 그대로 쓸 수도 없다.

## PART 2 — 기술 원리

- `json.loads(raw)` 성공 여부는 API 응답이 요구하는 **문자열 형태**의 문제다. ` ```json {...} ``` `은 내부 JSON이 맞아도 JSON 문서 한 개가 아니다.
- fence 제거는 모델 성능이 아니라 **시스템 후처리**다. 원래 출력 점수와 후처리 이후 점수를 하나의 그래프로 섞으면 안 된다.
- `action` 분류 정확도는 JSON 생성 성공, `missing_fields` 계약, 근거 인용 정확성, **위험 상황에서 사용자에게 조치를 전달했는지**와 각각 구별한다.
- `EXPLAIN_UNSUPPORTED` 미성공 0/4는 같은 문장을 읽었는데도 행동 라벨이 일치하지 않는 문제를 보여준다. `ASK`는 어떤 정보를 물을지를 추측하는 문제까지 포함한다.
- Dev 데이터는 이미 관찰했으므로 P1 사후진단 10/16을 실서비스 성능으로 주장할 수 없다.

**결과의 채택 의미:** SFT 구현 경험은 증명됐으나 LoRA 채택 이유는 없다. 현재 후보 네 가지 중 어느 것도 사용자에게 그대로 제공할 만큼 안전·계약 품질을 입증하지 못했다. S14에서는 추가 GPU 실험보다 `출력 검증 → 위험 우선 처리 → 사람 인계` 원칙을 기록하고 SFT 실험을 동결하는 쪽이 합리적이다.
