# M3 — S13b 보완: 학습이 필요한가, 프롬프트를 고치면 되는가?

> **단계:** 실험 설계 및 코드 검증 완료. **새 GPU 추론 결과는 아직 없음.** 기존 M3.md의 S10~S13 내용을 덮어쓰지 않는 별도 부록이다. 새 결과가 나오면 이 부록을 통합한다.

## PART 1 — 실험 이야기

### S13의 실패 분석만으로는 원래 질문에 답할 수 없다

S12에서 가상 Dev 16건을 Qwen3-1.7B 원본과 LoRA로 평가했다. JSON 객체는 BASE 16/16, LoRA 15/16이었지만, **행동별 출력 계약까지 포함한 `schema_valid`는 11/16에서 4/16으로 줄었다.** `raw_action_match`는 6/16에서 8/16으로 늘어도 엄격한 행동 정답은 4/16으로 같았다.

S13 분석은 왜 실패했는지 세 가지를 분리했다.

- `customer_message` 출력에 고객 질문을 그대로 복사한 사례가 많다. BASE는 16/16, LoRA는 8/16.
- `ASK`인데 `missing_fields`가 비거나, `ASK`가 아닌데 필드가 채워지는 문제가 있다.
- 인용 ID만 독립 비교하면 BASE 8/16, LoRA 11/16이다. `citation_exact` 5/16→2/16은 **JSON 계약 통과를 조건으로 하는 다른 지표**다.

따라서 **'LoRA 때문에 나빠졌다'는 비교만으로는 '프롬프트를 잘 쓰면 해결할 수 있었을까?'에 답할 수 없다.** 최초 v4 계획의 S13은 `Strong Prompt RAG vs SFT+RAG`였다. 그 빠진 실험을 S13b로 보완한다.

### 네 조건을 비교하는 이유

| | P0: 기존 S12 프롬프트 | P1: 계약을 더 명확히 쓴 프롬프트 |
|---|---|---|
| BASE: Qwen3-1.7B | **이미 실측됨.** 바꾸지 않음 | **새 추론.** 16건 |
| LoRA: S12 저장 어댑터 | **이미 실측됨.** 바꾸지 않음 | **새 추론.** 16건 |

- **P1 내의 BASE ↔ LoRA 비교:** 강화 프롬프트를 똑같이 준 상태에서 LoRA의 추가 효과.
- **BASE 내의 P0 ↔ P1 비교:** 학습을 하지 않고 프롬프트만 바꾼 효과.
- **LoRA 내의 P0 ↔ P1 비교:** 학습 후에도 프롬프트 계약 강화가 도움이 되는지.
- **P0 내 BASE ↔ LoRA:** S12 원본 실험을 그대로 보존.

**중요한 제한:** 이것은 `provided_evidence`가 미리 제공되는 **가상 근거 기반 추론**이다. 실제 BGE-M3에서 검색한 문서가 아니다. 따라서 원래 이름의 `RAG`를 엄밀하게 충족하지 못하며, WaterBridge 실사용 개선이나 최종 일반화 성능을 입증하지 않는다.

## PART 2 — 기술 원리

### 왜 모델과 프롬프트를 나란히 바꿔야 할까?

P0의 BASE와 P1의 LoRA만 비교하면 프롬프트·가중치가 **동시에** 달라져 어떤 변화가 결과를 만들었는지 모른다. 2×2 설계는 둘 중 하나만 바꾼 비교를 가능하게 해준다. 다만 16개로 구성된 동일 개발셋이고 모델이 이미 그 실패를 분석했기 때문에, 이 실험에 맞춘 P1은 **튜닝된 개발 비교**일 뿐 새 독립 검증이 아니다.

### 출력 계약과 단순 문법은 무엇이 다를까?

`json.loads()`가 성공하고 네 필드가 모두 있다고 해서 고객에게 올바른 응답이 되는 것은 아니다. `action`이 `ASK`이면 `missing_fields`가 비어선 안 되고, `ESCALATE`이면 고객에게 안전 조치를 말해야 한다. 강한 프롬프트 P1은 **출력의 `customer_message`는 '고객의 발화'가 아니라 '고객에게 보낼 AI 안내문'**임을 명시한다.

### `missing_fields` 정확 일치 0/16을 어떻게 봐야 할까?

가상 Train의 각 제품에 필요한 확인 필드는 대부분 **서로 다른 새 이름**이다. Dev 4개 제품에는 Train에 없던 필드 이름이 나타난다. `tracking_mode`처럼 특정 영문 키가 근거에 직접 명시되지 않은 경우가 있어서, 의미상 맞는 질문을 하더라도 **문자열 exact-match는 0점**이 될 수 있다. 그래서 exact-match 수치는 계속 보존하되, 사람이 *어떤 상태를 질문하는지* 별도 판정한다. 새로운 P1에 Dev 정답 키를 직접 넣는 것은 정답 누출이므로 금지한다.

### 인용과 내용 일치는 별개다

`citation_id_exact_not_schema_gated`는 참조한 ID가 Gold와 일치하는지만 센다. 같은 ID를 인용하면서도 고객에게 틀린 조작법을 말할 수 있으므로, 16건의 개별 응답을 읽어 **근거 적용·안전 안내·행동 타당성**을 별도로 평가해야 한다.

## PART 3 — 실행과 증거

### 입력 고정

- Qwen3-1.7B: `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`.
- Train 48건: S12가 학습한 데이터 그대로, **S13b는 학습하지 않는다**.
- Dev 16건: 기존 `s11_fictional_probe_inputs_v2.jsonl` 그대로, P1에서는 **시스템 프롬프트만 교체**.
- `known_conditions`, `product_code`, `customer_message`, `provided_evidence`: 모두 동일.
- 설정: greedy decoding, `enable_thinking=False`, `max_new_tokens=256`.
- P1 프롬프트에 Dev 예시, 정답 action, `missing_fields` 정답 키를 넣지 않는다.

### 점수 및 채택 규칙

기존 `schema_valid`, `raw_action_match`, `strict_action_match`, `citation_exact`, `missing_fields_exact` 점수를 그대로 재현한다. 별도로 인용 ID 자체 일치, 고객 질문 복사, 행동별 정답 개수를 보고, **사람이 16건의 안내 의미·위험 조치·근거 일치를 판정하기 전에는 모델 채택을 결정하지 않는다**.

- 기존 P0 결과는 재사용한다. **재학습 절대 금지.**
- P1 BASE/LoRA 새 추론 32건만 실행한다.
- S13b에서 별도 데이터를 추가하지 않고 Dev 성능을 맞추는 방식의 지속적인 프롬프트 탐색은 하지 않는다.
- 최종 결정은 **S14에서 한 번** 한다. 개선 입증이 없으면 LoRA를 서비스 후보에서 기각하고 그 이유를 남기는 것이 정당하다.
