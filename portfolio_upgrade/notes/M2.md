# M2 — AI에게 무엇을 가르칠지 정하고, 학습 전 실력을 확인했다

> **대상:** S06(정답 행동 검수), S07(학습 질문 만들기), S08(Qwen3 학습 전 B0/B1 평가), S09(모델·검색 근거 점검)

- **PART 1 · 실험 이야기 (먼저 읽기):** 고객 질문이 학습 데이터로 바뀌고, 왜 아직 학습을 하지 않았는지 따라가는 부분.

**범위 주의:** M2는 **데이터 설계와 소규모 파일럿·GPU 추론**까지 수행했어. **SFT(정답 예시로 모델을 미세조정하는 방법), LoRA/QLoRA 같은 모델 가중치 학습은 아직 하지 않았어.**

## PART 1. 먼저 읽는 실험 이야기

### S06. AI를 학습시키려면, 먼저 무엇이 정답인지 알아야 한다

#### M1에서 어떤 문제가 남았지?

M1에서는 정답 문서를 제공해도 LLM이 **조건을 잘못 읽고 필요하지 않은 조치를 추가**하는 경우를 봤어.

그렇다면 질문 하나가 생겨.

**“AI에게 어떤 답변을 잘했다고 가르쳐야 할까?”**

실제 고객 문의 하나로 출발하자.

> **고객:** “WPU-IAC425에서 냉수 버튼을 누르면 소리가 나고 잠금 표시가 깜빡입니다. 정수는 나옵니다.”

공식 IAC425 사용설명서 **43쪽**은 부저음과 잠금 표시 점멸을 냉수 잠금과 연결하고, **27쪽**에는 해제 절차가 있어.

이 고객에게는 '고장입니다'라고 단정하는 것보다 **냉수 잠금 해제 방법을 안내하는 것**이 적절하겠지.

그래서 정답을 이렇게 정의할 수 있어.

```text
고객이 겪는 상황: 냉수 버튼 부저음 + 잠금 표시 점멸
            ↓ 공식 설명서 확인
해야 할 행동: ANSWER (직접 안내)
답변에 넣을 핵심: 냉수 잠금 해제
하면 안 되는 일: 근거 없이 고장·방문 접수를 확정
```

이처럼 **문의에 맞는 행동과 필수 조치·금지할 안내를 정하는 작업**이 S06이야.

S04의 Train **18건** 중 **15건**을 선정해서 PDF와 비교했어. **13건**은 기존 행동 라벨이 설명서와 부합했고, **2건**은 `ASK`로 추가 질문해야 하는지 아니면 `ANSWER`로 바로 설명할지 미결이어서 보류했지.

**핵심:** S06에서 AI를 학습한 게 아니야. **AI에게 가르칠 정답의 품질을 검수**한 거야.

### S07. 같은 문제를 다른 말로 물어도 정답은 같아야 한다

#### 실제 고객들은 똑같은 문장으로 질문하지 않아

앞의 냉수 잠금 문의를 그대로 사용해 볼게.

**원본 질문**

> “WPU-IAC425에서 냉수 버튼을 누르면 소리가 나고 잠금 표시가 깜빡입니다. 정수는 나옵니다.”

**S07에서 만든 재표현 질문**

> “WPU-IAC425 냉수를 선택할 때 알림음이 들리고 잠금 표시가 깜빡여요. 정수는 정상적으로 나옵니다.”

말투는 달라졌지만 **제품, 증상, 이미 확인한 조건**이 같으니 기대 행동도 `ANSWER`로 유지하는 거야.

이런 식으로 S06에서 라벨이 부합한 **원본 13건에 각각 재표현 1건씩** 추가했어.

```text
기존 고객 문의 13건
      +
같은 의미의 재표현 13건
      ↓
학습 데이터 검수용 초안 26건
```

그런데 재표현 13건 중 **3건은 문장이 미묘하게 달라져서 수정**했어. 이를테면 고객이 **2시간 기다렸다**는 조건이나 **버튼을 누를 때마다** 경고음이 난다는 조건을 바꾸면 원래와 다른 상황이 될 수 있거든.

여기서 반드시 기억해야 할 건 **26건이 26가지 독립 문제는 아니라는 점**이야. 실제 원본 문의는 **13개**, 의미상 그룹은 **6개**에 불과해.

**핵심:** S07은 *데이터를 크게 늘려 학습한 단계*가 아니라, **의미를 바꾸지 않고 질문을 다양화하는 방법을 작은 규모로 검증**한 단계야.

### S08. 모델을 학습시키기 전에, 프롬프트만 개선해보면 어떨까?

#### 왜 학습 전 성능을 측정했을까?

나중에 SFT를 하고 나서 “모델이 좋아졌습니다”라고 말하려면, **학습하기 전 같은 모델의 성능**이 있어야 하겠지.

그래서 학습하지 않은 **Qwen3-1.7B**에게 S04의 **Dev 질문 6건**을 풀게 했어. 앞서 만든 **Train 26건을 시험지로 쓴 게 아니라**, 따로 보관해 둔 Dev 6건을 사용했다는 점이 중요해.

이번에는 두 조건으로 나눴어.

- **B0:** 기본 시스템 프롬프트를 준 원본 모델.
- **B1:** **동일한 모델·Dev 질문·검색 근거**를 주고 시스템 프롬프트만 구체적으로 강화한 모델.

가령 B1에는 **위험하면 우선 상담으로 안내, 정보가 부족하면 질문, 관련 근거만 인용, JSON 객체 하나로 출력** 같은 규칙을 더 자세히 적었어.

#### 결과: 형식은 좋아졌는데 판단은 그대로였다

```text
                   B0 (기본)      B1 (강화)
유효한 JSON          3 / 6         6 / 6   ← 개선
정답 행동 일치*      1 / 6         1 / 6   ← 변화 없음
```

\* 정답 행동은 **원시 출력에서 행동을 판독한 기준**이야. JSON 형식까지 함께 통과한 경우는 **B0 0/6, B1 1/6**이었어.

**JSON을 잘 만든다는 것과 고객 상황을 올바르게 판단한다는 것은 다른 능력**이라는 걸 확인한 거지.

특히 `JAC104-033`에서는 제빙 기능이 없는 제품에 대해 **존재하지 않는 제빙 조작법**을 안내했어. `JAC104-030`에서는 7일 부재 후 냄새가 난 문의에 필수 조치를 일부 빠뜨리고 **근거 없는 필터 전체 교체**를 추가했지.

단, 이 실패를 모두 Qwen3의 판단 능력 탓으로 돌릴 수는 없어. **검색 근거를 놓친 사례도 있었고, 제품 기능을 뒷받침할 정보가 제공되지 않은 사례도** 포함됐어.

**핵심:** 강한 프롬프트로 형식 오류는 줄었지만, **근거를 제대로 제공하고 조건을 지키는 문제**는 남았어. 그렇다고 SFT가 해결책이라는 결론까지 나온 건 아니야.

### S09. 그러면 준비한 26건을 바로 학습시키면 될까?

#### 여기서 다시 문제가 발견됐어

우리가 AI에게 가르치려는 건 단순히 **정답 문장을 외워서 출력하는 일**이 아니야. 고객 질문과 함께 실제 설명서 검색 결과를 받았을 때, 그 **근거를 보고** 올바르게 판단하는 일이야.

그런데 S07에서 만든 초기 파일에는 **정답 문장은 있지만 모델에게 제공할 검색 근거가 비어 있었어.** 그대로 학습시키면 나중에 평가할 때의 RAG 조건과 달라지겠지.

그래서 S05에서 사용했던 **BGE-M3 검색 방식**을 Train 초안 **26건**에도 적용했어. 실제 검색된 설명서 청크를 학습 입력 미리보기에 연결한 거야.

검색은 겉으로 보기엔 잘 됐어.

- **26/26건:** 상위 5개 안에 정답 근거를 **하나 이상** 찾음.
- **25/26건:** 지정된 정답 근거를 **모두** 찾음.

하지만 내용을 직접 읽어보니 또 문제가 있었어.

**소음 문의 하나**는 두 종류의 근거가 모두 필요했는데 원본 질문에서는 하나가 빠졌어. **냉수 잠금 문의**는 검색된 문단에 '잠금을 해제하라'는 말은 있지만 구체적인 **버튼 조작 순서**가 없었고, **누수 문의**에는 PDF에 있는 안전 확인 절차 일부가 검색 입력에서 빠졌어.

결국 **정답 문서 ID를 하나 찾았다 ≠ 답변에 필요한 근거를 전부 확보했다**는 뜻이야.

#### 그래서 모델을 학습했을까?

**아직 하지 않았어.** 세 가지 이유가 남아 있어.

1. **근거 완전성:** 답변의 모든 필수 조치가 실제 검색 입력에 의해 뒷받침되는가?
2. **데이터 다양성:** 사실상 6개 의미 그룹뿐인 예시로 일반적인 상담 행동을 가르칠 수 있는가?
3. **이용 범위:** 제3자의 공식 사용설명서에서 유래한 내용을 **모델 학습에 사용하는 것이 허용되는지** 확인됐는가?

Qwen3-1.7B 자체는 선택했고 RunPod **A40에서 추론하는 것까지** 확인했지만, **LoRA/QLoRA로 가중치를 학습하지는 않았어.**

#### PART 1을 읽고 기억할 네 문장

1. **S06:** 좋은 답변의 행동·필수 조치·금지 안내를 PDF로 확인했다. 15건 중 2건의 라벨은 보류했다.
2. **S07:** 원본 13건에 재표현 13건을 더해 26건을 만들었지만, 독립 의미 그룹은 6개다.
3. **S08:** Qwen3의 JSON 성공은 **3/6 → 6/6**, 정답 행동은 **1/6 → 1/6**로 그대로였다.
4. **S09:** Train 26건 모두 Gold 하나 이상은 검색했지만 일부 필수 근거가 누락됐고 학습 이용 범위도 미확정이어서 **SFT를 보류**했다.

여기까지 이해했다면 **M2에서 무엇을 했고 왜 아직 학습하지 않았는지** 알게 된 거야. 이제 원리와 실제 파일을 연결해보자.

## PART 2. 원리가 궁금할 때 읽는 기술 공부

### 1. 우리가 만들려는 SFT 데이터는 어떤 모습인가?

**SFT(Supervised Fine-Tuning)**는 모델에게 **입력과 원하는 정답 출력**을 짝지어 주고, 정답 토큰을 예측하도록 모델의 학습 대상 가중치를 조정하는 방법이야.

우리 목적은 정수기 사실 자체를 암기시키는 것보다는 **근거에 따른 행동과 답변 형식**을 학습시키는 거야.

```text
[입력 = Prompt]
- 고객 질문과 정확한 제품 코드
- 고객이 이미 확인한 사실
- 해당 질문에서 실제 검색된 설명서 근거
- 기본 응대 규칙
          ↓
[정답 = Target]
- action: ANSWER / ASK / ESCALATE / EXPLAIN_UNSUPPORTED 중 하나
- customer_message: 고객에게 보여줄 답변 또는 확인 질문
- cited_evidence_ids: 실제 근거 ID
- missing_fields: 더 물어봐야 할 정보
```

**SFT는 정답 행동을 어떻게 배우는 걸까?** 이 설계에서는 행동 라벨을 별도의 분류기에서 예측하는 게 아니라, 모델이 **정답 JSON 문장 전체를 다음 토큰부터 차례로 예측**하도록 학습하려는 거야. 예를 들어 정답의 `"action": "ANSWER"` 부분이나 고객 안내 문장의 토큰을 맞히도록 **손실(loss)**을 계산하고, 손실을 줄이는 방향으로 학습 가능한 가중치를 업데이트해. 그래서 올바른 라벨을 정해놓는 S06이 먼저 필요한 거지.

**LoRA와 QLoRA는 왜 거론할까?** 일반적인 전체 파인튜닝은 기반 모델 가중치 전체를 바꾸지만, **LoRA는 작은 어댑터 파라미터만 학습**해 메모리 부담을 줄이는 방법이야. **QLoRA는 기반 모델의 가중치를 저비트로 양자화한 상태에서 LoRA 어댑터를 학습**해 추가로 메모리를 절약할 수 있어. **이번 M2에서는 둘 다 실행하지 않았고**, M3에서 학습 방식과 자원을 비교할 예정이야.

**중요한 기술적 구분:** SFT에서는 **정답을 가르칠 때** `assistant` 응답을 활용하지만, **모델 성능을 시험할 때**는 정답 응답을 입력에 섞으면 안 돼. 시험 문제에 답을 같이 보여주는 셈이기 때문이야.

S09 미리보기 파일에는 `messages`가 `system`·`user`·`assistant`로 구성돼 있어. `user`에는 실제 검색 근거가, `assistant`에는 정답 예시가 들어가는 구조야. 별도의 `audit_only` 필드는 검수용 메타데이터이지 **모델에게 줄 질문 내용이 아니야.**

**현재 상태:** 이 형식으로 **검수용 미리보기만 만들었어.** 실제 SFT 학습에 사용할 최종 데이터셋은 승인하지 않았어.

### 2. S06 — 행동 라벨은 어떻게 정의했나?

S04 CSV에는 이미 `intended_oracle_action`이 있었어. S06에서 **분류 알고리즘을 새로 학습한 게 아니라**, 그 라벨을 가져와 공식 PDF와 대조했어.

| 행동 | 의미 | 사례 |
|---|---|---|
| `ANSWER` | 조건과 근거가 충분해 직접 안내 | 냉수 잠금 해제, 다량 출수 뒤 잠시 대기 |
| `ASK` | 꼭 필요한 정보가 없어서 추가 확인 | 정상 소음인지 판단하려면 소음 크기·지속 상황 확인 |
| `ESCALATE` | 위험·지속 이상으로 상담 연결 안내 | 누수, 2시간 후에도 냉수 미지근함 |
| `EXPLAIN_UNSUPPORTED` | 제품이 지원하지 않는 기능임을 근거로 설명 | 제빙 기능이 없는 제품에 제빙 방법 문의 |

추가로 `TOOL_REQUEST`라는 향후 도구 실행 제안도 스키마에서 고려했지만, **이번 S06 Train 사례에는 없었어.** `EXPLAIN_UNSUPPORTED` 역시 초기 15건의 안정 라벨 학습 초안에서는 포함되지 않았어. 나중에 다양한 행동을 가르치려면 이런 빈 범주도 보완해야 해.

정답 라벨 하나만 있으면 충분할까? 아니야. `ESCALATE`라고 맞혔더라도 **제품별 필수 안전 조치**를 빠뜨릴 수 있으니까.

그래서 정답을 네 부분으로 구분했어.

- **`input`:** 고객 질문·모델 코드·이미 확인한 조건.
- **`target`:** 기대 행동·정답 답변·반드시 포함할 조치·금지 주장.
- **`provenance`:** PDF 페이지·해시·원본 시나리오 ID·분할·Gold 근거 정보.
- **`review`:** 사람이 공식 PDF를 검수했는지, 보류 사유가 무엇인지.

`forbidden_claims`는 **공식 PDF 문구를 그대로 복사한 문장 목록이 아니라, 검수자가 잘못된 답변을 막기 위해 정리한 금지 주장**이야.

**보류한 2건:** IAC425·IAC606의 버튼 명칭을 혼동한 문의는 기존 `ASK`로 기록돼 있었지만, 정확한 모델을 알고 있다면 버튼 차이를 **바로 안내(ANSWER)**할 가능성도 있어. 임의로 라벨을 바꾸지 않고 재검토 대상으로 분리했어.

### 3. S07 — 왜 데이터 증강을 하면서 '조건'을 고정했나?

**데이터 증강(data augmentation)**은 같은 학습 신호를 다양한 표현으로 제시하는 방법이야. 여기서는 고객 문장만 재표현하고 **제품·적용 시간·부정 표현·이미 수행한 행동·정답 라벨**은 바꾸지 않았어.

예를 들어 다음 두 문장은 얼핏 비슷해도 다른 정답을 요구할 수 있어.

- “냉수를 많이 받은 **직후** 덜 차가워졌어요.” → 잠시 기다렸다 다시 출수할 조건.
- “전원은 정상이고 **2시간이 지나도** 냉수가 미지근해요.” → 상담센터에 문의할 조건.

시간 조건을 삭제하면 같은 라벨을 붙이기 어려워져.

실제로 수정한 재표현 세 건은 다음과 같아.

- `IAC606-103`: 상담 후 **해결 여부 확인 중**이라는 맥락 복원.
- `IAC606-107`: 경고음이 버튼을 누를 **때마다** 발생한다는 조건 복원.
- `JAC104-027`: 원문에 없는 **재출수 행동**을 추가하지 않고 냉수·2시간 조건 유지.

**기술적 판단:** 원본·재표현은 **같은 `semantic_group_id`**를 유지해야 해. 단순히 행이 두 배가 됐다고 독립적 학습 사례가 두 배가 된 건 아니지.

**검수 상태도 구분:** 최초 파일의 `review.pdf_reviewed=true`는 S06 원본의 검수 상태가 복사된 것일 수 있어. 새 재표현의 의미 검수 여부는 `s07.paraphrase_pdf_rechecked` 등 **별도 필드**로 확인했어.

### 4. S08 — SFT 성능을 공정하게 비교하려면 무엇을 같게 할까?

M1의 GPT-4.1-mini 결과를 **Qwen3의 학습 전 점수**로 사용할 수는 없어. 모델이 다르기 때문이야. 그래서 Qwen3-1.7B의 **학습 전 원본 모델**을 먼저 측정했어.

비교를 위해 고정할 조건은 다음과 같아.

- **같은 기반 모델과 모델 리비전:** `Qwen/Qwen3-1.7B`, revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`.
- **같은 Dev 질문:** 6건(4개 의미 그룹).
- **같은 검색 근거:** S05에서 저장한 오프라인 BGE-M3 검색 스냅샷.
- **같은 생성 설정:** `do_sample=False`, `max_new_tokens=512`, thinking 모드 끔.
- **같은 출력 형식과 채점 기준:** JSON의 행동·답변·인용·추가 확인 정보.

B0/B1에서는 **시스템 프롬프트만 변경하는 비교**를 의도했어. 두 실험의 모델 리비전과 입력 SHA는 확인됐지만, 라이브러리/환경 차이와 `attention_mask` 관련 경고도 있었어. **모든 실행 조건이 완벽히 같았다고 과장하지 않아.**

**검증 지표도 네 가지로 나눠야 해.**

| 무엇을 평가하나? | B0 | B1 | 뜻 |
|---|---:|---:|---|
| JSON 파싱 성공 | **3/6** | **6/6** | JSON 문법을 지켰는가? |
| 필수 필드까지 정상 | **2/6** | **6/6** | 지정한 네 필드를 갖췄는가? |
| 원시 출력 행동 일치 | **1/6** | **1/6** | JSON 오류가 있어도 행동을 읽어 맞혔는가? |
| JSON·행동 모두 충족 | **0/6** | **1/6** | 형식과 행동이 동시에 맞았는가? |

JSON 형식이 좋아졌다고 최종 답변 안전성이 좋아졌다고 말하면 안 돼. `JAC104-029` 누수에서 B1은 안전 조치를 일부 안내했지만 **행동을 `ESCALATE` 대신 `ASK`**로 냈어. `JAC104-030`은 필수 조치와 조건 해석이 어긋났고, `JAC104-033`은 없는 제빙 조작법을 만들어냈지.

게다가 일부 Dev 질문은 **정답 검색 근거가 빠져 있었어.** 따라서 행동 일치 1/6은 **검색과 생성이 섞인 파일럿 결과**이고, Qwen3 자체의 보편적 성능을 증명하는 점수가 아니야.

### 5. S09 — 모델과 토크나이저를 먼저 확인한 이유

Qwen3-1.7B를 처음 후보로 선택한 이유는 소형 모델로 **학습·추론·오류 분석의 비용을 제한**하면서 SFT 실험 흐름을 검증하기 위해서야. 더 큰 7~8B 모델을 처음부터 학습하면 VRAM과 실험 비용 부담이 커질 수 있거든.

**토크나이저(tokenizer)**는 텍스트를 모델이 처리하는 **토큰 ID의 연속**으로 바꿔. 데이터가 너무 길면 모델의 입력 한도나 GPU 메모리에 영향을 줄 수 있으니 학습 전에 길이를 확인했어.

사용자 PC에서 Qwen3 토크나이저로 **20개 미리보기 예시**를 점검했을 때 길이는 **277~393토큰(중앙 352)**이었어. 하지만 이 미리보기는 **실제 검색 결과 전체를 붙이기 전의 텍스트**야. 따라서 실제 학습 입력이 잠정 한도 **1,536토큰** 이내인지는 아직 검증되지 않았어.

RunPod **NVIDIA A40**에서 Qwen3의 **추론**이 작동하는 것도 확인했지만, 이것이 LoRA/QLoRA의 **학습 VRAM 요구량**을 확인했다는 뜻은 아니야.

`train_pilot.yaml`의 LoRA rank 16, micro-batch 1, gradient accumulation 4, 최대 길이 1,536은 **초기 실험용 설정 초안**이야. 실제 학습 결과가 아니야.

### 6. 검색 Gold를 26/26 찾았는데 왜 학습을 보류했나?

모델이 실제로 보게 될 근거를 만들기 위해 BGE-M3로 **53개 검증 청크**에서 Train 26건의 문서를 검색했어. 제품 코드 필터·코사인 검색·Top-5·임계값 0.4는 S05와 같은 방식이야.

이때 정답 Gold를 검색 순위를 정하는 데 사용하지 않았어. 검색이 끝난 뒤 **평가에만** 사용했지.

```text
고객 질문 → BGE-M3 검색 → 상위 5개 근거
                              ↓ 검색이 끝난 뒤
                    Gold가 포함됐는지 평가
```

**Hit@5 = 26/26**은 *정답 근거 중 적어도 하나가 상위 5개에 등장*했다는 뜻이야. 모든 필수 근거를 찾은 것은 **25/26**이었어.

내용 검수에서도 다음 문제가 발견됐어.

- **소음:** `SYN-IAC606-104-BASE`는 답변에 필요한 **제빙 소리와 냉매 순환 소리 관련 근거가 모두 필요**했지만 그중 한 종류를 놓쳤어. 재표현 `PAR1`에서 찾았어도 원본 `BASE` 문제가 해결된 건 아니야.
- **냉수 잠금:** IAC425·IAC606 원본/재표현 **4행**은 '해제하라'는 요약을 검색했지만 **구체적인 해제 버튼 순서**가 빠졌어. PDF 원문에는 있음.
- **누수:** IAC425 누수 원본/재표현 **2행**은 PDF에 있는 **물받이 넘침 여부 확인**이 검색 근거에는 없었어.
- **관련 없는 근거 선순위:** 일부 질문에서 온수 관련 문서가 정답 소음·냉수 문서보다 먼저 나타나거나, 일시적 온도 변화 문서가 지속 이상 문서보다 먼저 나왔어.

따라서 **근거 ID가 존재함 → 답변이 정확함**으로 넘어갈 수는 없어. 인용 ID와 실제 답변의 **주장 하나하나**가 연결되는지 살펴봐야 해.

**학습 자료 이용도 별도 판단:** Qwen3 모델 카드의 Apache-2.0 라이선스는 **공식 사용설명서에서 유래한 데이터까지 자유롭게 SFT에 사용할 수 있다는 허가가 아니야.** 원문 사용 범위를 확인하기 전까지 파일의 `training_ready=false`를 유지했어.

### 7. M3로 넘어가기 위한 최소 준비는 무엇인가?

M2에서 얻은 결론은 'SFT가 좋다'가 아니라 **'무엇이 부족한지 확인했다'**야. M3 전에 다음 문제를 해결해야 해.

1. **학습 자료의 사용 허용 범위 확인:** 원문·가공 데이터·합성 답변의 이용 범위 점검.
2. **근거와 정답의 대응 보강:** 검색된 입력으로 정답 조치·인용을 실제 설명할 수 있도록 보완.
3. **입력 길이 재측정:** 실제 검색 근거가 포함된 시퀀스로 토큰 길이와 VRAM 확인.
4. **독립 학습 시나리오 확대:** 6개 그룹에 과도하게 의존하지 않도록 서로 다른 상황 보충.
5. **학습 전후 비교 규칙 고정:** 원본 모델과 SFT 모델에 같은 질문·근거를 주고, 행동뿐 아니라 필수 조치·안전·인용을 채점.

이 조건들을 해결하기 전에는 **26건을 무작정 GPU 학습에 넣지 않는 편이 타당해.**

아래는 기존 실험의 사전 점검용 명령이야. **이미 실행한 검사를 다시 해야만 학습이 되는 건 아니야.**

`--run`은 모델 가중치 다운로드·GPU 과금을 수반할 수 있어. **이미 B0/B1 원시 결과를 저장했으므로, 문서 복습을 위해 다시 실행할 필요는 없어.** GPU 추론과 SFT 학습은 다른 작업이야.
