## 0. v3에서 무엇을 바꿨나

**v3의 약점:** 작은 검색기와 평가기를 이해하는 데는 효과적이지만, 마지막까지 **모델 학습 없이 검색 조정 하나로 끝날 가능성**이 있었다. 그렇게 되면 '직접 학습·추론·서비스 실행' 역량의 깊이를 보여주기 어렵다.

**v4의 결론:** 기초 학습을 버리는 것이 아니라 **실제 학습·Agent·서빙으로 이어지는 진입 단계**로 이용한다.

| 항목 | v3 | v4 |
|---|---|---|
| 최종 기술 목표 | 실험 후 개선 기술 1개 선택 | **SFT 실험·Tool Agent·모델 서빙** 세 축을 수행. 단, **학습 모델의 실제 채택은 실험 결과에 따름** |
| 검색 | 중심 기술 후보 | **근거 공급 기반**, RRF 등은 빠르게 비교하고 필요할 때만 추가 개발 |
| 학습 | 선택 사항 | **소형 LLM의 LoRA/QLoRA SFT를 최소 1회 직접 수행하고 검증** (필수 실험) |
| 서비스 | 기존 응대에 개선 코드 연결 | **실제 도구 호출 → 고객 확인 → 개발용 DB 반영 → 상담 인계**의 시연 가능한 변화 |
| 운영 | 지연 측정 | **vLLM 등 추론 서버를 직접 올리고 병목·품질·비용 측정** |
| 일정 | 47일을 날짜로 배치 | **25개 작업 세션 + 단계별 통과 기준**. 더 빨리 끝나면 즉시 다음 단계 |
| 이해 | 학습을 매일 기록 | 기술마다 **선택 이유·핵심 로직·실패 반례를 말로 설명한 뒤 통합** |

**하지 않을 것:** SFT·Reranker 학습·GraphRAG·MCP·멀티모달·멀티에이전트를 전부 억지로 탑재. 모델 학습 효과가 없는데도 좋았다고 주장. 처음부터 팀 프로젝트의 1,049개 테스트를 분석·재작성. 기존 `main` 또는 팀의 안전 검증·업무 계약을 파괴.

## 1. 최종 완성품을 먼저 정의한다

**프로젝트 한 문장**

> 제품 모델과 상태가 다른 고객 문의에서 **공식 매뉴얼 근거를 정확하게 활용하고**, 정보가 부족하면 추가 질문하며, 자동 안내로 해결되지 않으면 **승인받은 도구 호출로 상담을 접수**하는 고객지원 Agent를 구현한다. 이를 위해 소형 LLM을 **데이터를 설계해 직접 학습**하고, 실제 서빙 환경에서 **품질·응답 지연·비용**을 대안과 비교한다.

### 고객에게 보이는 대표 시연 (최종 목표, 아직 구현 완료가 아님)

1. 고객이 모델명과 증상 입력: “필터를 바꿨는데도 물이 조금씩 나와요.”
2. `lookup_product`로 제품·지원 범위를 확인, `search_manual`로 **적용 가능한** 매뉴얼 근거 확보.
3. 필요한 상태가 빠져 있으면 추가 질문(수압·다른 수전 동시 사용 등 **원문이 뒷받침하는 범위만**).
4. LLM이 근거·조건을 표시해 안내. 확신이 없으면 임의 조치를 생성하지 않음.
5. 고객이 상담을 원할 때 **접수 내용 미리보기 및 고객 확인 후** `create_consultation` 실행.
6. 개발용 상담 DB에 **실제로 한 조치 / AI가 제안했지만 미실행인 조치 / 참조 근거**를 구분해 기록.
7. 운영자 관점에서 trace: 검색 문서 ID, 모델·프롬프트 버전, 도구 호출, 상태, 오류·지연 확인.

**구조적 책임 분리:** LLM은 내용을 추출하고 다음 행동을 **제안**한다. 제품 지원 여부·고객 동의·위험 조치·권한·중복 요청·영속 상태의 **최종 집행은 Python/Backend 규칙**이 담당한다. 기존 WaterBridge의 팀 정책을 새 모델로 임의로 대체하지 않는다.

### 기술 스택: 선택과 조건

- **검색 기반:** 기존 BGE-M3/pgvector 검토 + BM25/E5/RRF 실습 비교. 후속 검색 개선은 문제의 원인이 검색일 때만 진행.
- **모델 학습 주력:** 한국어 대응이 가능한 **라이선스 확인된 1~3B급 Instruct 모델 1개** → LoRA/QLoRA + TRL `SFTTrainer` + PEFT. 처음부터 7~8B는 선택하지 않음.
- **학습 내용:** 사실 암기보다 **근거 적용 조건 구분 / 확인 질문 / 답변 보류 / 명세된 구조화 출력**. 도구 호출 학습은 별도 확장 실험으로 관리.
- **Agent:** 기존 LangGraph를 **필요한 경우 재사용**. 도구는 최소 3개(`lookup_product`, `search_manual`, `create_consultation`), 진짜 개발용 API/DB와 연결.
- **서빙:** Linux + CUDA 환경의 **vLLM OpenAI-compatible API**로 자체 모델을 실행. 먼저 모델·토크나이저·채팅 템플릿 호환성 점검.
- **평가/관측:** 정답 원문 판정, 도구 최종 DB 상태, 응답 품질/안전, p50/p95·토큰·GPU/호출 비용. 기존 Langfuse/OTel은 연결 필요성이 확인되면 사용.
- **MCP·다중 Agent:** 독립적인 외부 도구 연동이 실제 요구되거나 단일 워크플로가 해결 못 하는 문제가 있을 때만 추가(아래 보너스 후보에서 판정).

### 최종 결과물이 반드시 남길 핵심 증거

| 증거 | 최소 표현 |
|---|---|
| **학습 데이터 직접 설계** | 정답 근거/조건/오답 근거/정답 행동, 검수 방법, 누수 방지 분리 |
| **모델 학습** | 학습 모델·방법·GPU·loss·실험 설정·체크포인트, 학습 전후 같은 입력 출력 |
| **공정한 비교** | 강한 프롬프트 RAG vs SFT+같은 RAG, 공통 평가 질문, 개선·퇴행, 비용과 한계 |
| **동작하는 업무 Agent** | 도구 요청·응답·고객 승인·실제 DB 접수 상태 및 실패/중복 방어 |
| **서빙·운영** | 내 모델 API, concurrency별 p95·처리량·실행 비용, 채택·기각 이유 |
| **개인 기여** | 팀 원본과 개인 고도화 작업의 구분, Git SHA·재현 커맨드 |

## 3. 개발 운영 원칙 — 이해를 버리지 않고 속도를 높인다

1. **작업 진입:** “이번 작업으로 어떤 오류를 줄이려는가?”를 2문장으로 작성.
2. **개념:** 20~45분 집중 이해. 필요한 로직의 입력→출력→판정 조건을 그린다.
3. **구현:** 예제 하나를 먼저 실행. 반복되는 코드 작성·JSON 변환·실험 스크립트는 AI 도움 활용 가능.
4. **검증:** 실패할 반례부터 정의하고 수치·DB 상태·로그 등으로 확인.
5. **설명:** 본인이 1~3분간 **왜 이 방법/왜 다른 방법은 아닌지** 설명하고 핵심 코드(직접 선택한 부분)를 찾을 수 있어야 통과.
6. **주간 회고:** 완료한 작업 세션이 5~7개 쌓일 때마다(달력 날짜와 무관) `notes/weekNN.md` 작성. **실제 한 것 / 실패 / 수치 / 배우고도 모르는 것 / 다음 선택**을 구분. 1주차 실험·회고는 `notes/week01.md`에 통합해 관리한다.
7. **취업 우선:** 채용 지원·면접과 충돌하면 실습 시간을 줄인다. 포트폴리오 완성까지 지원을 보류하는 규칙은 없다.

## 4. 평가 설계 — 큰 기술을 쓰기 전에 비교를 고정한다

### 데이터 출처와 구분

- **제품 지식의 출처:** 공식 사용설명서. 원문과 다른 조작 지침을 모델에게 정답으로 학습시키지 않음.
- **대화·사용자 표현:** 매뉴얼을 바탕으로 합성할 수 있으나, **합성 질문·합성 답변**이라고 표시하며 원문 대조 검수.
- **도구·업무 기록:** 가상 제품·상담 정보·가상 정책으로 개발용 DB를 구성. 실제 제조사 예약·상담 정책이라고 주장하지 않음.
- **분리 단위:** 제품군 / 공유 매뉴얼 / 원본 시나리오. 같은 제품 같은 증상을 조금만 바꾼 문장이 train과 holdout에 동시에 들어가면 일반화 평가로 주장하지 않음.
- **미학습 제품 검증:** 독립 제품군이 충분할 때에만 적용. 해당 제품 매뉴얼은 **검색 대상에 포함**하되, 학습 질문/라벨을 학습과 설정 선택에서 제외.
- **검수 규모(잠정 작업 목표):** 학습 200~500개, 개발 40~80개, 독립 보류 60~120개 정도를 지향. 실제 자료량에 따라 축소 가능. **현재 확보·검수 완료된 개수를 의미하지 않음.** 안전/누수 포함 고위험 사례는 우선 전수 검수. 소규모 표본이면 큰 개선을 입증하기 어렵다는 점 기록.

### 판정 라벨

| 필드/라벨 | 뜻 |
|---|---|
| `ANSWER` | 근거·조건이 충분해 공식 범위 내 안내 가능 |
| `ASK` | 조건이 부족해 추가 질문 필요 |
| `ESCALATE` | 공식 근거 부족·지원 범위 밖·상담 필요 |
| `TOOL_REQUEST` | 도구 호출 필요(제품 조회/상담 접수 등); **실제 실행 허가와 별개** |
| `gold_evidence_ids` | 올바른 원문/절/페이지 식별자 |
| `required_actions` | 명시된 안전·확인 행동(원문이 뒷받침하는 것만) |
| `forbidden_claims` | 원인 확정·임의 수리·미실행 조치 완료 주장 등 |
| `provenance` | 공식 원문/합성 시나리오/가상 도구 정책을 분리 기록 |

### 반드시 같은 조건으로 비교할 집합

| 실험 | 통제 조건 | 확인할 성과 |
|---|---|---|
| 검색 | 동일 문서/청크/질문, 각 방식 Top-K; `BM25`, `Embedding`, `RRF` | Hit@1/3/5, MRR@3/5, **필수 근거 확보율**, 오류 유형 |
| **모델 학습(핵심)** | 같은 기반 모델·같은 검색 근거·같은 출력 형식·같은 디코딩 설정 | **Strong Prompt + RAG** vs **SFT + 동일 RAG**; 가능하면 일반 SFT vs 조건 중심 SFT도 분리 |
| 응대 정책 | 동일 질문, 필요 정보/정답 행동, 원문 대조 | **올바른 안내 비율**, 조건 혼동률, 근거 없는 주장 비율, ASK/ESCALATE F1 또는 정확도 |
| Agent | 같은 도구·DB 초기 상태·업무 시나리오 | 도구 선택/인자 정확도, 승인 전 쓰기 0건, **최종 DB 기준 접수 성공률**, 중복/취소 처리 |
| 서빙 | 같은 모델·출력 예산·GPU·동시성·warm/cold 설정 | 응답 p50/p95, TTFT, tokens/s, 실패율, 성공 응대 1건당 실행 비용 |

**지표 함정:** `Hit@K`는 정답이 하나라도 포함되면 성공으로 판정하며, 모든 필수 근거 확보/정확한 최종 안내를 뜻하지 않음. 오류·빈 결과를 정답 평균에서 조용히 제외하지 않음. 모델이 전부 상담으로 넘기는 경우를 성공으로 평가하지 않음. **최종 holdout 결과를 보고 프롬프트/학습을 고치면 그 결과는 개발셋으로 재분류**하고, 새 보류셋을 마련한다.

### 채택 기준(최종 평가 전에 확정할 잠정 기준)

- **SFT:** 강한 프롬프트 RAG 대비 핵심 KPI가 개선되고(초기 의사결정 목표 예: **+5%p**), 중요한 안전 오류가 증가하지 않아야 서비스 채택. 표본이 작으면 건수·불확실성으로 해석. **모델 학습 실험 자체는 개선 유무와 관계없이 수행한 역량의 증거**.
- **Agent:** 정상 흐름의 실제 DB 작업 완료, 취소/반복 요청/도구 실패 테스트에서 잘못된 쓰기 **0건**. 이 기준은 테스트 범위 내 결과이지 운영 무결성을 보장하지 않음.
- **서빙:** SFT 또는 채택 모델을 서버에서 직접 호출, 소규모 부하 실험의 지연·비용을 측정하고 실제 배포 구성의 선택 이유를 설명.
- **RRF:** 같은 질문에서 BM25/Embedding과 동등하거나 더 낫고, 실패 유형의 개선이 있으면 채택. 그렇지 않으면 원래 강한 기준선 유지.

### 진행 방식의 전제

- `seunghyuk`에서 작업하고 기존 `main`은 건드리지 않음. 기존 1,049개 테스트 전체 분석은 선행조건 아님.
- MVP의 표준적인 구조를 먼저 구현하고, 새 기능이 필요한 경우에만 LangGraph/MCP 등 사용. **기술 이름이 아니라 대안 대비 증거**로 판단.
- 시간이 급하면 **UI 꾸미기 → 모델 크기 추가 비교 → Reranker 추가 학습 → MCP 도입** 순으로 축소. **SFT 실험 + 작동하는 Agent + 모델 서빙 + 최종 평가**는 보호.
- GPU는 학습·서빙 작업 중에만 비용 지출. 비용·가용성은 실행일 RunPod 가격과 설정을 확인하고, 작업 종료 시 Pod·볼륨 비용 확인.

## 7. 단계 사이의 의사결정 Gate

| Gate | 시점 | GO(진행) 조건 | NO-GO/대안 |
|---|---|---|---|
| **G0** | S02 후 | RRF 실습 결과·원본 문서 대조 이슈·1주차 회고를 정리 | RRF가 안 좋으면 결과를 남기고 검색의 강한 단일 기준선 유지 |
| **G1** | S05 후 | **학습할 응대 오류를 최소 두 종류** 발견(원문·질문·오답 출력 확보) | 검색이 문제라면 검색/청크부터 수정; 생성 오류가 없으면 ASK/ESCALATE·형식·도구 행동을 학습 과제로 전환 |
| **G2** | S09 후 | 정답 출처 검수·데이터 분리·모델/라이선스/GPU 확인 | 데이터 부족 시 작은 학습은 진행하되 '일반화 증명'을 주장하지 않음 |
| **G3** | S14 후 | SFT 실험 수행, 같은 RAG 조건의 개선/퇴행·비용·오류 파악 | 개선이 없으면 **기존 강한 프롬프트 모델을 제품 채택**, SFT는 학습·실패 분석 경험으로 정직하게 기록 |
| **G4** | S18 후 | 실제 개발용 DB를 쓰는 Agent, 동의/취소/중복/타임아웃 시나리오 검증 | 안전/상태 문제를 해결하기 전 실제 상태 변경 도구 노출 중지 |
| **G5** | S21 후 | vLLM endpoint E2E, 동시 요청 지표, GPU 시간·비용 확인 | VRAM/성능 부족 시 작은 모델·정밀도/컨텍스트 축소, 서빙 시스템 비교 기록 |
| **G6** | S25 후 | 독립 보류 평가 + 6페이지·데모·기여·README 수치 일치 | 완성 지연 시 보너스 기능 전부 중단하고 제출할 수 있는 검증된 범위로 축소 |

### 세 갈래의 실패가 있을 때 우선 해결 방식

1. **근거를 못 찾음:** BM25/Embedding/RRF/청크·메타데이터 검토. 이 문제를 SFT로 가리지 않음.
2. **근거를 줘도 판단을 틀림:** 강한 프롬프트·출력 형식·추가 질문 정책 기준선 → SFT 실험으로 개선 가능성 판단.
3. **판단은 맞지만 업무 실패:** 도구 스키마·승인·DB 트랜잭션·중복 방지·재시도 확인. 이 문제에 '멀티에이전트'를 장식으로 추가하지 않음.

## 8. 기술적 임팩트를 더 키울 수 있는 보너스 후보 (자동 추가 금지)

다음 기술들은 **관찰된 오류·채용 목표·남은 자원**을 만족할 때만 도입한다.

| 후보 기술 | 도입할 이유가 되는 구체적 현상 | 비교·성과 증거 | 우선도 |
|---|---|---|---|
| **Domain reranker SFT** | RRF로도 같은 제품의 다른 조건 문서가 먼저 나옴 | 공개 reranker vs hard-negative SFT, 미학습 제품 결과 | 중 (데이터·GPU 여유 시) |
| **Tool-call SFT** | 도구 선택·인자 생성에 모델 오류가 지속됨 | 프롬프트 기반 도구 호출 vs SFT 도구 호출, DB 최종 성공 | 중 (Agent 오류가 실제로 있으면) |
| **MCP 서버** | 여러 소비자/외부 애플리케이션에서 동일 도구를 표준 방식으로 재사용해야 함 | 기존 직접 API vs MCP의 통합·권한·운영 측면 차이 | 낮음 |
| **Durable LangGraph** | 승인 대기 중 프로세스 재시작에 상태·요청이 유실됨 | 재시작·재실행·중복 방지 E2E | 중 (실제 실패를 재현하면) |
| **Multi-Agent** | 단일 상태 워크플로에서 역할 분리로 확인 가능한 품질·비용 이점 | 동일 도구·업무에서 단일 vs 다중 Agent | 낮음 |
| **Multi-modal manual RAG** | 그림·표·배치가 핵심 정보인데 텍스트 추출에서 누락 | OCR/텍스트만 vs 페이지 이미지 포함 검색, 근거 정확도 | 낮음~중 |
| **Model routing / distillation** | 소형 모델이 쉬운 문의는 잘하지만 어려운 문의에 실패하고 상용 API 비용이 높음 | 로컬/상용/라우팅 성능과 비용, 처리량별 손익 | 중 (서빙 지표 후) |

**차별화 후보 추천:** SFT 후에도 헷갈리는 조건이 남는다면 **조건 중심 데이터 보강/Tool-call 학습**이 가장 자연스럽다. 새로운 모델 이름보다 **실패→데이터→수치**로 이어지는 이야기를 우선한다.

## 9. RunPod 계획 (GPU 비용을 실험과 분리)

| 작업 | 권장 | 판단 근거 |
|---|---|---|
| RRF, BM25, 평가기, 문서 정리 | **로컬** | GPU 이점 거의 없음 |
| API 기반 RAG 응대 기준선 | **로컬/상용 API** | 모델이 외부에서 실행되면 GPU 임대 불필요 |
| 1~3B LoRA/QLoRA 파일럿/본학습 | **RunPod 권장** | CUDA·VRAM·학습 시간 부담을 줄임 |
| Tool Agent API·DB·테스트 | **로컬 우선** | 모델 호출만 GPU 필요 여부 판단 |
| 학습 모델 vLLM 서버·부하 실험 | **RunPod 권장** | CUDA 서버 환경·동시 요청 측정에 적합 |
| 6페이지 구성·회고·그래프 | **로컬** | GPU 필요 없음 |

- **첫 후보:** 24GB GPU(예: RTX 3090/4090) + 소형 모델과 짧은 문맥. **7~8B, 긴 문맥, 도구 호출 긴 대화, 큰 배치에서 OOM**이 나면 48GB GPU(A40/L40S 등) 또는 배치·모델 크기 축소. 이는 메모리 용량에 따른 **권장 시작점**이지 무조건 동작한다는 보장이 아니다.
- RunPod 공식 가격표는 **2026-10-08 갱신**된 GPU별·지역/공급 방식별 요금으로 표시된다. 작업 직전에 실제 선택 옵션·스토리지·중단 정책 재확인. 가격은 자주 바뀌므로 **이 문서에 예상 총비용을 성과처럼 고정하지 않음**.
- 시작 전 `budget_limit`, `GPU_type`, `VRAM`, `dataset_size`, `tokens_per_example`, `max_steps` 기록. 실험 끝나면 모델·로그 다운로드하고 Pod 종료/볼륨 보존 비용 확인.
- CPU 로컬 실행이 지나치게 오래 걸리면 사전에 '이 단계는 RunPod 권장'이라고 명시하고, GPU를 이용해도 기술 이해·재현성 검증은 생략하지 않는다.

| 페이지 | 페이지의 한 문장 주장(계획) | 반드시 보여줄 증거 |

**레이아웃 원칙:** 페이지마다 **문제 하나 → 이유 있는 선택 하나 → 증거 하나 → 수치 결과 하나**. 학습이 개선되지 않았다면 P3의 주장을 ‘데이터와 대조실험으로 SFT의 효과와 한계를 검증했다’로 바꾼다. **말하기 어려운 기술은 채용 PDF에서 과장하지 않음.**

## 11. 최소 포기 불가 / 축소 가능 범위

**최소 포기 불가**
- 학습용 mini 결과와 실제 평가 결과의 구분, 자료 출처 검수.
- SFT 최소 1회 학습·재실행 및 강한 기준선과 비교.
- 사용자 승인·중복 방지를 포함한 최소 Tool Agent와 개발용 DB E2E.
- 학습 모델 또는 비교 모델의 자체 API 서버와 p95/비용 측정.
- 독립 보류 평가와 직접 설명 가능한 6페이지 + 코드 링크.

**시간·예산이 부족하면 먼저 줄일 것**
1. 화려한 UI/다수 페이지/모바일 재구현.
2. 여러 기반 모델·여러 seed·거대 하이퍼파라미터 탐색(불확실성이 남았음을 표시).
3. 별도 Reranker 파인튜닝과 DPO/RAFT 전면 구현, 멀티모달.
4. MCP·Multi-Agent·추가 자동화의 부가 기능.

**주의:** 마감이 없다고 개발을 무한 연장하지 않는다. 첫 완성 조건이 충족되면 **그때 바로 포트폴리오 작성과 채용 지원**으로 넘어간다.

## 12. 주간 회고 및 기술 면접 학습 기록

`notes/weekNN.md` 양식:

```markdown
# N회차 진행 회고 (실제 완료 세션 SXX~SYY)
- 이번 묶음의 목표 / 실제 완료 / 미완료
- 처음에 발견한 문제와 오류 사례 (원문 근거/코드/실행 로그 링크)
- 선택한 방법의 작동 원리 (내 말 3~5문장)
- 반대 대안과 제외한 이유 (비교 조건)
- 실험 지표 (성공 건수/전체 수, p95, 비용, 퇴행 사례)
- 내가 직접 수정·설계한 부분 / AI가 생성한 부분 / 재사용한 팀 코드
- 1분 설명이 막혔던 질문 / 다음 실험
- 결과를 보고 수정한 계획 및 그 이유
```

학습 복기를 위해 각 세션이 끝나면 **이해 확인 질문에 답한 문장을 3~5줄만** 남긴다. 모르는 경우 다음 단계 작업량을 최소화해 작은 반례부터 다시 실험한다. 하루 계획량을 넘어선 경우 회고 묶음이 빨리 끝나도 좋다.
